# client — 案件管理・財務管理・カレンダー・設定（v4 対象）

ONAiR で一番大きいアプリ。**1つの Vite バンドルに4つ（v4 では5つ）の「入口」が入っている**。
ベースパス `/`・ポート 5173。44画面・約36,000行。

## 入口とルート接頭辞

| 入口（利用者から見た名前） | ルート | 権限モジュール | contexts |
| --- | --- | --- | --- |
| 案件管理 | `/sales/*` | `sales` | `contexts/sales`, `contexts/tasks` |
| 財務管理 | `/budget/*` | `budget` | `contexts/finance` |
| カレンダー | `/studio/*` | `studio` / `partner_schedule` | `contexts/production` |
| 設定 | `/settings/*`（**v4 で `/admin/*` から改名**・旧 URL は転送） | `admin` | `contexts/platform` |
| **プロジェクト管理（v4 で新規）** | `/gpm/*` | `gpm` | `contexts/gpm`（新設） |

- ルート定義は `src/App.tsx` の1ファイル。**旧URLからの転送表もここ**（`<Navigate>` 約12本）
- **入口の URL（`/sales` など）はその入口のダッシュボードへ送る。** アプリ切替と
  トップページのタイルがここに来るので、案件一覧に送っていると
  「トップを押してもダッシュボードにならない」ことになる（v4 で直した）
- 左メニューの定義は `src/components/layout/nav.ts` の `CLIENT_NAV`（入口ごとの塊）。
  **案件管理だけ v4 の情報設計に差し替え済み**（下記）
- ページは `contexts/<領域>/pages/` に置く。`contexts/shared/components/` は領域をまたぐ部品

## 案件のライフサイクル（旧「統合プロジェクトライフサイクル」）

- 旧 `opportunities` テーブルは廃止し、**単一 `projects` テーブル**に統合済み
- `stage`: `neta` → `d_hold` → `c_proposal` → `b_verbal` → `a_won` → `s_completed` / `e_lost`
- **`gls_number IS NULL` = ヨミ段階、`IS NOT NULL` = GLS発番済み**
- GLS発番は別エンドポイント: `POST /projects/:id/issue-gls`
- 案件分類は `gls_category`（`A`=スタジオ / `B`=ビジネス）。発番後の A↔B 切替は
  `PATCH /projects/:id/gls-category`（採番し直し＋エピソードコード＋BOX フォルダを追随）
- 費用按分は `project_groups` テーブル

**ダッシュボード（①）で決めたこと**
- **お金の画面をやめて、案件の画面にした。** 旧実装は売上・仕入・粗利・販管費・営業利益の
  KPI と月次推移のグラフで、**中身は財務管理ダッシュボード（`/budget/dashboard`）と同じもの**
  だった。案件を見に来た人が決算の数字を1画面ぶんスクロールしていたので外した。
  案件管理から見たいお金は**「見積の返事待ち」と「今月の売上」の2つだけ**に絞り、
  どちらも押すと元の画面へ行ける
- **「今月の受注」ではなく「今月の売上（確定）」を出す。** モックは受注額だが、
  **DB がステージの変更日を記録していない**ので「今月 受注になった案件」を数えられない
  （`projects.updated_at` は名前を直しただけでも動く）。数えられないものをそれらしく
  出さない。履歴を残すようにしたら差し替える
- **数字は `GET /dashboard/sales-overview` の1本でまとめて取る**
  （`contexts/platform/services/salesOverview.service.ts`）。5本に分けると遅い1本のせいで
  数字が後から差し替わり、読み間違える。ステージ別・今週の現場・動いている案件は
  **既にある物を使う** — 同じ数字を2か所で数えると必ず食い違う
- **「動いている案件」は案件一覧と同じ `GET /projects`** を `sort_by=last_move` で並べ替えただけ。
  そのために `SORT_COLUMN_MAP` に `last_move` を足した（SELECT の別名をそのまま使う。
  式を書き写すと片方だけ直したとき並び順と表示が食い違う）
- **「自分の案件」にしない。** v4 は案件担当者という概念を持たないので、
  誰がやるかは**次のアクションの担当**として1行ごとに出す
- **「止まっている」理由はステージから導く。** モックは「見積を送ったまま連絡がありません」と
  具体的に書くが、それを言うにはステージ変更の履歴が要る。**作り話をしない**
- **受付カードは動く入口だけ出す。** モックは3タイル（メール取込・録音・手で登録）だが、
  **録音はまだ無い**。押しても何も起きないボタンを置くと「壊れている」と受け取られ、
  以後この枠全体が信用されなくなる。無いものは無いと書く
- `salesDashboard/Panel.tsx` は**この画面だけの部品**。`dashboard/SectionCard` は v4 より前の段
  （`rounded-lg` = 8px・見出しの下に区切り線）で、まだ作り直していない画面が使っている

**トップページ（共通）で決めたこと**
- **上＝アプリの入口 ／ 下＝自分の今日**に絞った（`pages/HomePage.tsx` ＋ `pages/home/`）。
  1,273行 → 177行。旧トップは KPI・営業ダッシュボード・AI活動フィード・直近の案件・
  クイックアクセスまで載っていて、**同じ数字を各アプリのダッシュボードでも見ていた**
  （トップの KPI は財務ダッシュボードと同じ中身）。行き先は `HomePage.tsx` の冒頭に列挙
- **アプリは2段。** 日々の業務（3列の大きいタイル）と**イベントで使うもの**
  （本番の日にだけ開く・4列）。毎日の入口と本番だけの入口を混ぜると探しにくい
- **タイルの数字は「押せば片づくもの」の件数。** そのアプリにある物の総数ではない
  （総数は押す理由にならない）。**数えられないアプリには数字を出さない**
- **同じものを2か所で数えない。** 案件管理・日常業務は受信箱（`/dashboard/inbox`）が
  数えているものを振り分けて使い、財務・カレンダー・機材だけを
  `/dashboard/app-badges`（新設）で数える
- **`/dashboard/app-badges` は `sales` の権限ゲートの外に置く。** `/dashboard` の
  ルーターは全ルートに `sales` を要求するが、**トップは全員が最初に開く画面**で
  経理だけ・機材だけの人も来る。中に置くとその人たちのトップで 403 になる
  （実際に 403 を確認してから外に出した）
- **数えられないときは書かない。** `sales` も `dailyops` も無い人に「0件です」と書くと、
  見えていないだけなのに「無い」と言い切ることになる。その1行ごと出さない
- **プロジェクト管理のタイルは出さない。** モックには載っているが画面がまだ無い
- **中身が1枚も無いなら「今日」の節ごと出さない**（見出しだけ残ると壊れて見える）
- **「AI に任せる」は既存の `TaskIntakeBox` をそのまま置いた。** LLM 解析 ＋ 規則ベースの
  フォールバックを持つ動いている部品なので、枠の作り直しと同時に中身を触らない
- **お待たせ中は受付（②）と同じ `inbox/kinds.ts` を使う。** 見出しの作り方を書き写すと、
  片方だけ直したときトップと受付で表記が食い違う
- **スマホでは AI の入口を1行に畳む**（M7・`home/MobileIntake.tsx`）。
  `TaskIntakeBox` は 390px で**約 500px**（切替タブ＋複数行の入力欄＋説明＋送るボタン）。
  トップを開く人の大半は自分のタスクと予定を見に来るのに、その前に箱を通り過ぎていた。
  **場所は最上部のまま、大きさだけ 1 行**にする（下に送ると「あとでいいか」になる）。
  **開いたら閉じない** — 書いている途中で畳むと入力が消えたように見える
- **スマホでは挨拶に名前を出さない**（M7）。自分の端末なので誰かは分かっており、
  「おはようございます、○○ さん」は 390px で2行になって 140px 使っていた
- **「自分のタスクを全部ひらく」はスマホで出さない**（M7）。`MyTasksCard` の
  「全部ひらく」と**同じ行き先で二重**だった
- 実測: 「自分のやること」に着くまで **2,273px → 411px**、全体 3,552 → 3,102px
- **スマホでは「今日」を先に出す**（M3）。PC は横3列なのでタイルが2〜3段に
  収まるが、375px では1列に落ちて**「今日」に着くまで 1,676px（2.5 画面ぶん）
  こする**ことになっていた（実測。全体は 3,552px = 5.4 画面ぶん）。
  **並べ替えるだけで、消していない**（`isMobile` で `appsSection` の位置を変える）
- **制作資料・技術資料を「イベントで使うもの」の段へ移した**（M3）。
  どちらも凍結アプリで、案件の本番の日に開くもの。大きいタイルが 9 → 7 枚になる。
  ⚠️ **消してはいけない** — `visibleApps()` は凍結4アプリを既定で外すので、
  **上辺バーのアプリ切替にも左メニューにも凍結アプリは出ていない**。
  つまり**押して開ける場所はトップのタイルだけ**で、消すと Qシート・技術資料・
  計時LIVE・リアルタイムCG が URL 直打ちでしか開けなくなる（放送が止まる）。
  `DAILY_KEYS`（`HomePage.tsx`）と `EVENT_KEYS`（`home/AppTiles.tsx`）は**対**なので、
  片方だけ直すとタイルが二重に出るかどこにも出なくなる
- **凍結4アプリをトップから消していない**（ご判断）。プラン承認時の決定は
  「トップページのアプリ一覧・アプリ切替からは外す」だったが、モックは
  制作資料・技術資料を並びに残し、計時LIVE・リアルタイムCG を
  **「イベントで使うもの」**という別の列に置いている。4つとも今日使える画面で、
  消すと **URL を覚えている人しか開けなくなる**ため、モックに従って残した。
  → **「検証環境なので消さなくてよい」**とご判断いただいた。
  **本番に出す前（Phase 7）にもう一度だけ確認する**（`docs/v4-plan.md` の項目2）。
  戻すなら `home/AppTiles.tsx` の `EVENT_KEYS` と `HomePage.tsx` の `DAILY_KEYS` の2行

**左メニュー（案件管理）で決めたこと**
- **v4 の情報設計に差し替えた**（モックの `navMenus`）。旧メニューは7つの塊に 20 項目あり、
  **ダッシュボードが「ふりかえり」の中**にあった。さらに「カンバン」と「タスクリスト」は
  **押すと同じ画面**（v4 でカンバンを畳んだのにメニューだけ残っていた）
- **業務**（ダッシュボード・受付・案件一覧）／**全案件**（タスク一覧・見積・請求）／
  **設定**（料金表・標準工程テンプレート）の3つ
- **受付をメニューに出す**（ご判断）。モックの PC サイドバーには無いが、
  毎日開く画面なのでダッシュボードのカード経由だけだと遠回りになる
- **v4 で作り直していない 11 画面は「そのほか（作り直し前）」に畳む**（ご判断）。
  消すと動いている画面に辿り着けず、全部並べると v4 の並びが読めない。
  作り直したものから上の塊へ移す
- **タスク一覧は `/sales/tasks/list` を指す。** `/sales/tasks` は `kanban` へ転送されるが、
  `kanban` と `list` は同じ画面

**受付（②）で決めたこと**
- **4種類のまま。** モックの受付は引き合い（メール・電話）だけだが、この受信箱は
  「お客様を待たせているもの」を集める別の目的で既に使われており、片方を消すと
  **期限超過のアクションを見る場所が無くなる**。3ステップ（入れる→確かめる→案件にする）を
  通せるのは**ネタ案件だけ**なので、そこだけ作業台（中央＋右）を出す
- **確信度（高/中/低）は出さない。** MCP の `create_project` は確信度を渡さないので、
  その値が無い。無い数字をそれらしく出すより**「必須なのに空」を赤で名指し**する
- **「聞き方の下書き」は AI ではない。** 入っていない項目から機械的に組み立てる
  （`pages/inbox/ask.ts`）。同じ入力なら必ず同じ結果になるので、変なときに原因が追える。
  **AI を1つ足すたびに5条件を満たす経路が要る**ので、文面を自然にするためだけには増やさない
- **`primaryAction` を使わない。** スマホでは画面下端に固定されるので、
  「ダッシュボードに戻る」を置くと**主役でないものが主役の位置**に出る
- **AI に返る経路をこの画面で閉じた**（会社方針「AI を使い捨てにしない」）:
  - `create_project`（MCP）が起票内容の**全文**を `ai_outputs`(kind=`project_draft`) に残す。
    `mcp_audit_log` は `args` を 1000 文字で切り詰める監査用で、教師データにならない
  - `projectService.update` が保存時に**サーバー側で自動比較**し、
    「どの項目を・何から何に」を `ai_corrections` に入れる（`project-ai-feedback.service.ts`）。
    **人には何も入力させない**
  - **起票から7日以内の更新だけ**を見る。窓を切らないと数ヶ月後の通常の業務更新まで
    「AI の誤り」に数えられ、修正率が意味のない数字になる
  - **直さなかった項目も `none` で残す**（無修正採用率の分母）。ただし**直した回だけ**。
    開くたびに積むと、よく開かれる案件ほど精度が高く見える
  - 見送り（`e_lost`）は `reject` として残す＝**拾いすぎの指標**
  - 成果（受注/失注）は `projects.stage` から導出する。**`ai_outcomes` に行を足さない** —
    既存データで表現できるものに新しいテーブルを作ると、書き忘れた日から数字が嘘になる
  - 還流は `get_ai_feedback_digest`（MCP）が `kind=project_draft` を読めるようにした

**見積・請求（⑤）で決めたこと**
- **検収と入金を ONAiR で持つ**（ご判断）。`revenues` には請求日・支払期日・
  請求書の発行済フラグはあったが、**「検収したか」と「いつ入金されたか」が無かった**
  （仕入 `purchases` には `inspection_date` があるのに売上側には無い、という非対称）。
  migration 140 で `inspection_date` / `paid_date` を追加
- **フラグではなく日付**。済んだかを別のフラグでも持つと片方だけ更新されて必ず食い違う
  （日付が入っていれば済み）。`invoice_issued` と `billing_date` が同じ形になりかけている
- **取り消しは訊く。** 黙って戻せると、経理の訂正が誰にも気づかれない
- **旧版（`superseded`）は出さない。** サーバー側で外している。差し替え済みの版が並ぶと
  「返事待ちが何件か」が読めない
- **どちらのタブも常に引く。** 開いている側だけにすると、閉じている側のタブに出る件数が
  0 のままで**数字が嘘になる**（実ブラウザで「見積 0 / 請求 2」と出て気づいた）
- **「見積を作成」ボタンは置かない。** 見積は案件にぶら下がるもので、ここで押しても
  「どの案件の？」を先に訊くことになる。行を押すとその案件の見積タブへ飛ぶ
- 請求は `status='confirmed'` かつ `group_id IS NULL`（按分の親行を二重に数えない）

**標準工程テンプレート（⑦）で決めたこと**（`pages/flow/` ＋ migration 178）
- **モックの 6 段 26 工程をそのまま初期値に入れた。** 担当の職種・実施日からの逆算日数・
  外せるかどうかまで書かれているので、文書で整理し直すより**画面で目にしながら直すほうが早い**
- **種類ごとに工程を削らない。** モックは種類ごとに工程数が違う（リアルイベント 18 /
  ハイブリッド 26 / 生放送 24 / 公開収録 22 / 収録ありイベント 20 / スタジオ収録 14）が、
  **どれを外すのかは書かれていない**。推測で 8 本消すと「この種類には要らない工程」を
  勝手に決めることになり、しかも消えたことに誰も気づけない。
  → **26 本の型を1つ入れ、複製して削ってもらう**（画面にもそう書いてある）
- **案件をつくったときに黙って入れない**（ご判断）。小さい案件でも 26 行並び、
  使わないタスクの山でタスクタブが読めなくなる。タスクタブの帯 → `ApplyFlowDialog` で
  **一覧を見せ、チェックを外してから**入れる。外せない工程だけチェックを固定する
- **二度は入れられない**（`projects.flow_applied_at`）。押し直しで**同じタスクが 2 組**
  できると、どちらを消すか分からなくなる。**守りを外すと 26 → 52 件になることを確かめてある**
- **担当は入れない。** 型が持つのは**職種**で、誰がやるかは案件ごとに決まる
  （v4 は案件担当者という概念を持たない）。適当な人を入れると
  「自分のタスク」に他人の仕事が並ぶ
- **期限が出せない工程も落とさずに入れる。** 実施日が未定の案件では逆算の工程の期限が
  出せないが、落とすと**「入るはずの工程が入っていない」ことに誰も気づけない**。
  期限なしで入れ、**何件が期限なしになるかを押す前に出す**
- **日付はサーバーが案件から読む**（`POST /flow-templates/:id/preview` に `project_id`）。
  画面から日付を送らせると、**下見に出た期限と実際に入る期限が食い違う**
- **受付日は SQL で文字列にする**（`to_char(created_at AT TIME ZONE 'Asia/Tokyo', …)`）。
  `created_at` は TIMESTAMPTZ で pg は `Date` を返すので、`String(...).slice(0,10)` は
  `Wed Aug 08` になり、**受付から数える工程の期限が全部 null になっていた**
  （型チェックには出ない。実 DB に当てて見つけた）。時間帯を書かないと、
  夕方以降に登録した案件の受付日が前日になる
- **入れたあとは 4 つの鍵を落とす。** かんばん `task-columns` / リストとガント
  `project-tasks` / 全案件 `task-dashboard` / 帯を消すための `project`。
  1つ落とし忘れると、その見え方だけ古いまま = 「入れたのに出てこない」
- **型を直せるのは `sales` の manager 以上。** 型を変えると**以後すべての案件**に効くので、
  案件を1件直すのと同じ権限（editor）では緩すぎる。入れるのは editor、読むのは reader
- **職種は選ぶ形にする**（`ROLES` の4つ）。自由入力だと「テクニカル」「技術」「Tech」と
  揺れて、あとで職種で絞り込めない。**外す（決めない）こともできる**
- **日数は符号つきの1つの数。** 「前／後」の選択と数の2つで持つと、
  前を選んだまま -60 と入れて 60 日後になる取り違えが起きる
- **プロジェクト管理（`/gpm/templates`）とは別系統。** 工事・構築の工程
  （発注確定 → 設計 → 調達 → 施工 → 検収）と放送案件の工程は1つも重ならない

**料金表（⑧）で決めたこと**
- **場所ごとの表にした**（大③・migration 172）。`pricing_categories.location_id`。
  分類ごと場所に属する（品目に持たせると1つの分類に用賀と渋谷が混ざる）。
  **既存 78 品目はすべて用賀の料金**なので `loc-yoga` に寄せた。NOT NULL —
  場所の決まっていない分類は、どのタブにも出ないか全部のタブに二重で出るかになる
- **空の場所は「料金は未定」と言い切る。** ふつうの空表示だと「消えた」と読まれる。
  始め方は ①ほかの場所の表を丸ごと写す ②空から作る の2つ。
  **写せるのは空の場所だけ**（2回押すと同じ品目が2つ並び、どちらを選んだかで金額が変わる）
- **分類を別の場所へ移せない。** 移すと、その分類を使った過去の見積が
  「別の場所の表から選んだ」ことになる。要るなら写して消す（何が起きるか目に見える）
- **見積を組むときは場所を出す**（`pages/pricing/LocationPicker.tsx`）。
  案件のスタジオ予約が1つの場所に揃っていればそれを既定にし、**なぜその場所かを1行書く**。
  複数の拠点にまたがる案件では**推測しない**（どちらの料金でも間違いになりうる）。
  `projects` に場所の列は無いので、`studio_bookings` → `studio_booking_rooms` →
  `studio_rooms.location_id` からたどる（`studio_bookings.room_id` は存在しない）
- **`created_by` / `updated_by` を足した（migration 139）。** `pricing.routes.ts` の
  **6つの書き込みすべてが 500 で落ちていた** — ルートはこの2列に書いているのに、
  どちらのテーブルにも列が無かった（001b の定義に入っていない）。つまり料金表は
  **読むことしかできない状態**で、画面に `onError` が無かったため
  「ダイアログが閉じない」以外に何も出ていなかった。SQL から列を消しても直るが、
  **誰が値段を変えたかは残したい**ので列を足すほうを選んだ
- **並び順の数字を入力させない。** 「10 と 20 の間だから 15」は内部の都合の押し付けで、
  同じ数字を2つ入れると並びが不定になる。**↑↓ で2つの `sort_order` を入れ替える**
  （全件に振り直すと、同時に別の人が触っていたとき見ていない分類まで動く）
- **「設定なし」(NULL) と「¥0」を見分けられるようにした。** NULL は「その相手には
  出さない品目」で 0 円とは別。両方 NULL のときは「見積のどこにも出てきません」と警告する
- **消す前に何がいっしょに消えるかを出す。** 分類のゴミ箱は押した瞬間に消えていた
- **権限が無い人には操作ボタンを出さない**（分類 `owner` / 品目 `editor`・消すのは `manager`）。
  出しても押せば 403 になるだけ
- **モックの「変更の記録」パネルは載せていない。** 履歴テーブルが無く、出せる中身がない

**案件一覧（③）で決めたこと**

- **バッジの文字は和文だけ**（`STAGE_BADGE_LABEL`）。「A 受注済」のまま入れると

- **「ネタ」の見え方は未実装。** モックのネタ表は入口（メール/電話）と確信（高/中/低）を

**タスク一覧（④）で決めたこと**
- **タスクの状態は4つ**（未着手／進行中／相手待ち／完了）。ただし**DB は2列に分けている**：
  `is_completed`（完了したか・**ここが正**）と `work_state`（完了していないときの止まり方）。

- **「相手待ち」を足したのがこの版の中身。** これが無いと未完了タスクが全部同じ重さに見え、
  自分が止めているものが埋もれる。導出できない（`progress` からは出せない）ので列を足した
- **カンバンを畳んだ。** 旧「カンバン」は案件ごとの小さな板を縦に積み**各列5件まで**で、
  案件をまたいで見えていなかった。同じことは案件詳細の板のほうがよくできる
- **ガントは残した**（全案件の山を1枚で見る場所がここしかない）。
  ただし**中身は旧実装のまま**（`DashboardGantt/DashboardGanttView.tsx` 522行）。
  時間軸の描画は別の仕事なので、一覧の作り直しと混ぜていない
- **`invalidateTasks` は `task-dashboard` も落とす。** 案件の中のタスクと全案件の一覧は
  同じタスクを別の鍵で持っており、案件側だけ落としていたので**一覧から直しても一覧が古いまま**
  だった（反証試験で再現を確認済み）
- **チェックボックスは列にしていない。** 7段のいちばん狭い枠が 56px で 18px の四角には広すぎ、
  段を増やすと「その画面だけの幅」ができる。`RowMain` の中に入れてある

**案件詳細（⑥）で決めたこと**
- **「読む画面」と「直す画面」を分けた。** `/sales/projects/:id` は v4 のタブ付き詳細（読む）、
  `/sales/projects/:id/edit` が**いままでの `ProjectFormPage` そのまま**（直す・新規も）。
  **フォームは中身を1行も変えていない** — 枠の入れ替えと中身の作り直しを同じ回でやると
  どちらが原因で壊れたか切り分けられない（前回の刷新が捨てられたのがこれ）
- **タブの URL の鍵は `episode` / `task` のように単数**。`episodes` / `tasks` にすると
  既存の `/sales/projects/:projectId/episodes` と衝突し、押した瞬間に枠ごと消える
  （React Router は静的な区切りを優先する）。⑥-B・⑥-C で古い画面を畳んだら綴りを揃える
- **8タブとも中身がある。** ふりかえりはモック自身が「これから作ります」と書いていた分で、
  絵が無いので**いま持っている数字だけ**で組んだ（下記）
- **回タブと見積・請求タブは `BusinessProjectView`（2,042行）を呼ぶだけ。**
  旧 `EpisodeListPage` / `EstimatePage` は**同じものを別 URL で開いていた32行のラッパー**
  だったので削除し、旧 URL は転送にした（違いは `isEstimateMode` の有無だけだった）
- **タスクタブは既存のかんばん／リスト／ガントをそのまま呼んでいる。** 落としたのは
  見出しだけ（枠が出すので二重になる）。旧 `/sales/projects/:id/tasks` は転送にして
  `ProjectTasksPage` は削除した
- **ふりかえりタブを作った**（`projectDetail/ReviewTab.tsx`）。**モックに絵が無い**分
  （モック自身が「これから作ります」と書いている）なので、**いま持っている数字だけ**で
  組んだ — 新しい欄を作って「入力してください」と言うと、入れない欄が増えるだけになる。
  ①お金（想定 → 出した見積 → 確定売上 → 仕入 → 粗利を**引き算の順に**並べる）
  ②進み方（タスクの終わり具合・期限を過ぎたまま）
  ③実施の記録（`event_reports`。**隔週キープと同じ表・同じ口**）。
  - **差の読み方を書かない。** 「見積より N% 高く売れた」は、値引きなのか追加受注なのか
    数字からは分からない。**数字を並べるだけ**にして、読むのは人に任せる
  - **`GET /keep/event-reports/:id` は書いていなくてもお金の実績を返す**ようにした。
    売上・仕入は書いたかどうかと関係なく存在するのに、`found=false` で落としていたので
    **ふりかえりが「売上 —」で始まっていた**（実ブラウザで見つけた）
  - **空欄（null）と 0 を分ける。** 「数えていない」と「0 人だった」は別
- **議事録の持ち帰りを1件ずつタスクにできる**（`POST …/minutes/:id/open-items/:index/task`）。
  - **二度作らない。** 作ると `open_items` のその要素に `task_id` を書き戻す。
    画面のボタンを隠すだけだと、**同時に開いた別の画面が古いままボタンを出す**
  - **担当は入れない。** `owner` は AI が文字起こしから拾った**名前の文字列**で、
    利用者の id ではない。名前で突き合わせると同姓の人や取引先の名前を社内の誰かに割り当てる。
    **説明に書くだけ**にする（どの打合せから来たかも一緒に残す）
  - 期限は `YYYY-MM-DD` の形のときだけ写す（**推測の日付を作らない**）
- **書類タブから BOX にファイルを置ける**（`POST /projects/:id/box-files?scope=`）。
  - **社内と社外は別のカードで、置き場所を選ばせない。** 1つの枠で「どちらに入れますか」と
    訊く形にすると、急いでいるときに取り違えて**原価が外に出る**
  - **読み取りと違って失敗を隠さない。** 中身を出すほうは BOX が落ちていても 200 で返すが
    （案件を止めないため）、**置くほうは理由を付けて失敗を返す** — 上がっていないのに
    上がったように見えるのが一番困る
  - **同じ名前は新しい版として上げる**（BOX の 409 を拾って `uploadFileVersion`）。
    諦めると「上げ直したのに入らない」が起き、しかも理由が出ないと押し直され続ける
  - **1つずつ上げて、上がった分だけ返す**。まとめて失敗にすると「3つ中2つは入っている」ことに
    気づけず、同じものをもう一度上げることになる
  - multer は multipart のファイル名を latin1 で読む。**日本語の名前が化けたまま BOX に載ると
    探せないうえ直せない**ので、`Buffer.from(name, 'latin1').toString('utf8')` に通す
  - 置き場所が無い（フォルダ未作成・BOX 未接続）ときは**枠ごと出さない**
- **書類タブは BOX の中身を1階層ぶん出す**（`GET /projects/:id/box-files?scope=`）。
  **再帰しない** — 深いフォルダを全部たどると呼び出し回数が読めず画面が固まる。
  **失敗しても 200 で返し `reason` を渡す**（`NO_FOLDER` / `NOT_CONFIGURED` /
  `UNAVAILABLE`）。500 にすると BOX が落ちた日に案件詳細が全部開けなくなる
  （`shared/services/box.ts` の「BOX 障害が業務をブロックしない」方針）。
  **ファイルを置く（アップロード）はまだ無い**ので画面に明記している
- **当日タブは凍結アプリへの導線。** `GET /qsheet/documents?project_id=` /
  `GET /techsheet/documents?project_id=` でこの案件の資料を引き、**あるものだけ**並べて
  `/qsheet/editor/:id` を直接開く（凍結＝URL は生きているので今日から使える）。
  資料ごとの進み具合は凍結アプリ側の作りに依存するので出さず、その旨を画面に書いた
- **見積は `estimates` / `estimate_items` の別テーブル**（migration 138）。
  **`revenues` に相乗りさせてはいけない** — `revenues` を読む **41 か所が `status` を
  見ておらず**（トップの当月売上を含む）、見積の行を入れると売上に足される。
  実測してから別テーブルに切り替えた
- **版は1行ずつ**。v1 と v2 は別の行で、`group_id` で束ねる。列に版番号を持たせて
  上書きすると v1 の中身が残らない（「送った見積を見返せる」が要件そのもの）
- **出した版（`sent`）と旧版（`superseded`）は直せない。** 直すなら次の版を作る
  （前の版を丸ごと写して version を +1、前の版は中身を触らず印だけ付ける）
- **合計はサーバーが出す。** 画面が送ってきた合計は保存しない（計算が2つになると必ず食い違う）
- 「売上・請求」の切り替えで開くのは**既存の `BusinessProjectView`**。1行も変えていない
- **「エピソード」→ タブ名は「回」。** モックは「エピソード」だが、v4 の用語の決めごと
  （`docs/wording.md`・`check-ui-tokens` の `forbidden-wording`）で画面に出さない語。
  **用語の決めごとを優先した**
- **「請求」タブは作らず、見積タブを「見積・請求」にする**（ご判断）。モックには請求タブが
  無いが、案件を開いている人が請求額を探しに行かずに済むほうを取った
- **「打合せを録音」を入れた**（やり取りタブ）。録音 or 音声ファイル → **Whisper** で文字起こし
  → LLM が決定事項・持ち帰りを下書き → 人が直して確定。
  - **音声は保存しない。** 文字にしたら捨てる（容量と、取引先の声が入るため）。
    残すのは `transcript`（全文・切り詰めない）と議事録だけ
  - **裏で走らせる。** 1時間の録音で数分かかるので、行を先に作って `status` を持たせる
    （リクエストの中で待つと **nginx の 60 秒で切れる**）。ジョブの表は作らない
  - **決定事項には引用を必須にする。** 引用が出せないものは決定にせず持ち帰りへ落とす
    （`normalizeMinutes`）。議事録は取引先との合意の記録なので、AI が話を補うのが最悪
  - **日付は推測させない。** 壊れた形は空にする
  - **差分の before は「AI が出したもの」**（`ai_outputs.payload_snapshot`）。
    直前の行の状態と比べると、**書きかけを保存してから確定した人の修正が全部
    「無修正」になる**（実測して直した）
  - `met_on` は差分に数えない — 人が投げるときに入れる値で、AI の出力ではない
  - 録音は 32kbps で録る。**既定の 128kbps だと 25 分で Whisper の 25MB 上限に当たる**

**プロジェクト管理（GPM）の見積で決めたこと（大⑤・migration 173）**
- **`estimates` を案件と共用する。** 別表にすると版・明細・合計の作りが2つになり、
  片方だけ直る形が生まれる。`project_id`（案件）と `gpm_project_id`（プロジェクト）は
  **CHECK で排他**（両方入ると案件管理とプロジェクト管理の両方に出て合計が二重になる）
- **先に「案件がある前提の読み手」を数えた。** `estimates` を読むのは **3か所**で、
  `revenues` の 41/53 のような広がりは無かった。ただし
  **`salesOverview` の「見積の返事待ち」だけが案件の結合を持たず**、
  GPM の見積が案件管理のダッシュボードに足される穴だった（`project_id IS NOT NULL` で塞いだ）。
  `billing.routes` は内部結合で自然に落ちるが、**偶然そうなっている**状態に頼らず
  `gpm_project_id IS NULL` を明示した
- **提出先（自社／依頼元／PM会社）は作るときに必須。** 同じ工事でも社内見積と
  PM 会社への見積は中身も金額も別物なので、空だと「どちらの見積か」が分からなくなる
- **版を作ると行き先と提出先を写す。** 片方だけ写すと CHECK に弾かれるか、
  案件とプロジェクトの両方に出る行ができる
- **「検収待ち」は「受注にしたが検収が済んでいないもの」。** 検収日は売上が持つが、
  **プロジェクトの見積は売上に変換できない**（`revenues.project_id` が NOT NULL）。
  請求前のものも数に入るので、**その但し書きをカードに出している**
- **明細は案件の見積と同じ部品**（`projectDetail/EstimateItems.tsx`）。
  写しを作ると合計と粗利の計算が2か所になり、片方だけ直した日から
  **同じ見積が画面によって違う金額**を出す。保存する口だけ GPM 側
  （`PUT /gpm/estimates/:id/items`）に向けていて、**サーバーはプロジェクトの見積しか
  受け付けない**（`gpm_project_id IS NULL` を 403 で弾く。案件の金額を
  `gpm` だけの人に書かせない）。読むのは `GET /gpm/estimates/:id`（明細つき・
  一覧には明細を積まない）

**カレンダー（①〜④）で決めたこと**
- **カレンダーを1本にした。** 旧メニューは「統合／スタジオ／パートナー／マイ」の
  4本が並び、**どれを開けばよいか分からなかった**（中身はほぼ同じで見えるレイヤーが
  違うだけ）。v4 は **① 予定 = 統合カレンダー1本 + レイヤー**。`/studio/all` は転送
- **パートナーとマイは残す**（「そのほか（作り直し前）」に畳む）。
  **予定を作る導線がそこにしかない** — 消すと作れなくなる
- **① 予定は FullCalendar をやめて自分で描いた**（`pages/calendar/`）。
  モックの月マスは **17px の帯に「3px の色棒 + 時刻 + 題名」**、週・日は
  **重なりを横に割った角丸の札**で、FullCalendar の DOM とは組み立てが違う。
  CSS で寄せると `.fc-*` に依存した規則が何十行も積み上がり、
  **版が上がるたびに黙って崩れる**。**旧スタジオ・パートナー・マイの3画面は
  FullCalendar のまま**（作り直し前の画面なので同じ回で触らない）
- **置き方の計算は `calendar/calendarLayout.ts`。** 間違えると**予定が消える**
  （描画の外に飛ぶ・幅 0 になる）のに、画面を見ても「無い」としか分からない。
  `shared/tests/calendarLayout.test.ts` で 26 項目を固定してある
- **週表と日表は同じ部品**（`TimeGrid`）。違うのは列の数だけ。2つ書くと、
  どちらかだけ直した日から**同じ予定が別の位置に出る**
- **重なりは「同時にいくつあるか」で割る。** 「1件めは左半分・2件めは右半分」に
  すると**3件重なった日に3件めが消える**。塊ごとに列を数えてその数で割る
- **表示（8:00〜22:00）の外から続く予定を捨てない。** 端で切って **↑↓** を
  付けて出す（② 部屋の空きと同じ決め方。捨てると朝から使っている部屋が空きに見える）
- **「いま」の線は時間帯の外なら出さない。** 上端・下端に貼り付くと、
  そこに何かあると読まれる
- **「予定を入れる」を足した。** 着手前の統合カレンダーには**新規作成が1つも無く**、
  「入れるときは各カレンダーへ」と書いてあるだけだった。v4 は ① 予定が1本なので、
  ここから入れられないと**入れる場所が消える**。3つ（部屋・自分・パートナー）は
  持ち物が違うので、まず何を入れるか選んでもらう（1つのフォームにまとめない）
- **祝日は設定 ⑥ の表から読む**（`GET /business-hours/holidays`）。着手前は画面に
  **2025〜2027 が直書き**で、**2028 年になると祝日が1つも出なくなる**状態だった。
  この口だけ**権限を掛けていない** — 祝日は国が決めた公開情報で、`studio` を
  要求するとパートナーの予定しか見ない人のカレンダーで日付が黒いままになる
- **期間に時刻が付いていても通す。** この製品の期間指定は `to=…T23:59` の形が多く、
  日付だけを要求すると呼ぶ側が2通りになる（日表に切り替えたとき 400 を踏んだ）
- **絞り込みは「何が消えるか」を先に書く。** 部屋で絞ると部屋を持たない自分・
  パートナーの予定が、人で絞ると人を持たないスタジオ予約が出なくなる（モックの注記）
- **② 部屋の空きを別画面にした。** ① は「日付ごとに何があるか」の画面で、
  「8/2 の 14 時に WORLD が空いているか」は読めない（全部読んで頭で並べ替えることになる）。
  **部屋 × 時間の1枚**にすると空いている幅がそのまま見える
- **終日の予定は帯にしない**（部屋名の下に出す）。時間の幅を持たないので、
  横一杯の帯にすると**丸1日埋まって見える**
- **表示の外（8:00 より前）から始まる予定を捨てない。** 端で切って必ず出す —
  捨てると朝から使っている部屋が空きに見える。短い予定には最低幅を持たせる
  （線になると空きと見分けが付かない）
- **③ 仮押さえは残り日数順**（日付順ではない）。**過ぎてしまった仮押さえが先頭に来る** —
  押さえたまま忘れられた枠がそれ。7日/14日で色を変える
- **`PUT /studios/bookings/:id` を部分更新に直した。** 元は全置換で、
  `{ status: 'confirmed' }` だけ送ると**件名・日時・部屋が消えていた**
  （`start_time` は NOT NULL なので運が良ければ 500）。仮押さえの一覧から
  状態だけ変えたいので直した。全部送っている既存の呼び出しは今までどおり動く
- **④ 設定はダイアログの中に隠れていたものを出しただけ**（部屋 / 外部カレンダー /
  サイネージ の3タブ）。足す・直すは今までのダイアログをそのまま開く
- **サイネージの URL はログインなしで開ける**（表示機にログインさせられないため）。
  **URL を知っている人はその部屋の予定を全部見られる**ので、画面にそう書いた。
  トークンの作り直しは配ってある URL を全部無効にするので system_admin だけ
- **ICS は黙って止まる**（URL 変更・期限切れ）。予定が増えないだけなので
  見ている人は気づけない。**最後に取れた時刻とエラーを必ず出す**

**設定（①② ＋ システムの情報）で決めたこと**
- **設定トップは「案内板」にした**（`SettingsHubPage`）。旧 `/settings` はアプリの版と
  Excel バックアップが置いてあるだけで、**設定を探しに来た人が欲しいもの
  （拠点・料金表・権限）へは行けなかった**。それらは左メニューの別々の場所にあり、
  **どこにあるか知っている人しか辿り着けなかった**
- **7枚とも押せるようになった。** 着手時は3枚（お金のルール / 休日・営業時間 /
  通知とテンプレート）が画面を持たず、`to: null` ＋ `todo` で「これから作ります」と
  出していた。**`to: null` の仕組みは残してある** — 今後また「並べるが押せない」枚が
  出たときに、押しても何も起きないカードを置かずに済むようにするため
- **「直せるのは誰か」をカードに書く。** 設定は権限の分かれ方が細かく、
  **押してから 403 で気づく**ことが多い場所。権限が無いカードは**カードごと出さない**
- **設定トップとシステムの情報には権限を掛けていない。** 掛けると
  料金表（`sales`）や取引先（`budget`）だけを直す人が来られない。
  旧 `/settings` は `admin` 必須だったので、**パスワードを変えたい人が
  管理者しか来られなかった**。全データバックアップだけ画面の中で `system_admin` に絞る
- **拠点・部屋を設定に置いた理由。** 拠点はカレンダーだけのものではない —
  migration 172 で**料金表が拠点ごと**になったので、拠点を1つ足すと
  「予約できる部屋」と「見積に出る金額」の両方が変わる。
  **部屋の一覧はカレンダーの設定と同じ部品**（`calendarSettings/RoomsTab`）を使う。
  この画面が足しているのは**拠点の段**（部屋数と料金表の品目数）だけ
- **拠点・部屋を直せるのは `system_admin` だけ。** サーバーが
  `requireRole('system_admin')` を掛けている（`studio.routes.ts` の `adminOnly`）。
  **`studio` の manager にボタンを出していたのは間違いで、押すと 403 だった**
  （カレンダーの設定も同じ間違いをしていたので直した）
- **⑤ お金のルール（`pages/money/`）— 並べるだけにしない。**
  14 項目を表示するだけの画面にすると「設定した気になる」だけで何も変わらない。
  **3つは実際の計算に効かせてある**:
  1. **支払期日** … 締め日＋サイトから逆算（`server/src/shared/services/dueDate.ts`）。
     **取引先ごとの例外が優先**（`customers.closing_day / payment_months / payment_day`。
     **NULL = 決めていない**。0 を既定値に入れないこと — 「0か月後と決めた」と区別できなくなる）
  2. **消費税の端数** … `tax-category.service` の `roundByRule` 1 か所。
     **既定を四捨五入から切り捨てに変えた**（モックの指定）。今後つくる書類の税額が最大 1 円下がる。
     `xpoint-parse.service` が 1.1 / 1.08 を直書きしていたのもここに寄せた
     （放っておくと**取込だけ四捨五入のまま**で、同じ請求が入口によって 1 円ずれる）
  3. **値引きの上限** … 役割ごと（`role_discount_limits`）。超えた見積は
     **保存はできるが `approval_state='pending'` になり、送付済みにできない**。
     承認できるのは**その見積を作った人の役割に決めた承認者だけ**（誰でも承認できたら上限が無意味）
- **期日の計算を画面に写さないこと。** この製品は **server が `shared/` を import しない構成**
  （`rootDir` が `server/src`）。画面にも同じ式を書くと写しが2つになるので、
  **画面は `POST /money-rules/preview` に訊く**（保存前の値も渡せる）。
  計算そのものは `shared/tests/dueDate.test.ts` が server のファイルを直接読んで固定している
- **「上限なし」と 0 は別物。** 空欄を 0 として保存すると**1 円も値引けなくなる**。
  上限を決めていない役割は画面に「決めていません」と出す（「上限なし」と決めたのとは別の見た目）
- **請求書の自動下書きは作らない**（ご判断）。締め処理という新しい業務フローを1つ作ることになり、
  誤って請求書が量産される余地が生まれる。画面には「自動では作りません」と書いてある
- **⑥ 休日・営業時間（`pages/hours/`）— 予約を止めない。**
  着手前は**時間の検査が1行も無く、何時でも予約が作れた**。ここで初めて制限が入るので
  一番ゆるい段から始める（ご判断）:
  - **注意を出して通す。** 保存は止めず、`studio_bookings.out_of_hours` に印を残し、
    `GET /business-hours/out-of-hours/list` であとから拾う
  - **既存の予約は1行も書き換えない**（モックの指定）。列の既定は false のまま。
    遡って印を付けると「昔から時間外だった予約」が大量に出て、見るべきものが埋もれる
  - 休業日を足すときは**保存する前に「重なる予約が N 件あります」を出す**。
    消さない仕様なので、出さないと「休業日にしたのに予約が残っている」に気づけない
  - **割増（＋30％・＋50％）の列は作らない**（ご判断）。何に掛けるかが決まっておらず、
    列にすると入っている数字が正しいと読まれる
- **祝日は計算して表に書き出す**（`server/src/shared/services/holidays.ts` → migration 176 に 89 件）。
  手で入れると毎年 16 件、外の API を見に行くと通信できないときに予約画面が止まる。
  - **初期値は `open`（営業する）。** 放送・制作は祝日こそ稼働するので、
    いきなり「相談のうえ」にすると祝日の予約すべてに注意が出るだけになる。
    **当てても予約の見え方は 1 つも変わらない**
  - **春分・秋分は「予測」。** 政府が前年 2 月に公示するまで確定しない。
    近似式（1980〜2099）で出し、`estimated` の印を画面に出す
- **`closed_days.location_id IS NULL` = 全拠点。** 拠点ごとの行があればそちらが優先。
  こうしないと祝日 16 日 × 拠点 4 = 64 行を毎年作ることになる
- **⑦ 通知とテンプレート（`pages/notify/`）— 社外メールは送らない**（ご判断）。
  モックの 11 本のうち 6 本はお客様に届くメール。差し込みのずれ・きっかけの誤爆・
  古い宛先のどれも**届いてしまうと取り返しがつかない**。文面を貯めて
  **件名と本文を別々にコピーできる**ところまでにした。
  - **「まだ作っていない」ではなく「作らないと決めた」と画面に書く。**
    送信ボタンが無いだけだと「未完成」と読まれる
  - 差し込み語は**埋めずにそのまま**コピーさせる。空にすると「・金額：」のような
    欠けた行になり、値が 0 なのか差し替え漏れなのか読み手に分からない
  - 社外の時刻型2本は送らず、「**送る時期が来ました**」を社内のベルに出す
- **社内通知は上辺バーのベル**（`shared/src/client-v4/NotificationBell.tsx`）。
  **`src/client/` に置かないこと** — 凍結4アプリの CSS が増える。
  シェル側は `notificationSlot` の受け口だけ（新しいクラス名を書かない）
  - 通知を押したときの移動は**素の遷移**（`window.location.href`）。行き先が
    アプリをまたぐ（案件管理のベルに機材の未返却が出る）ので、ルーターでは動けない。
    3アプリそれぞれに「自分の中か外か」を判定させると、間違えたアプリだけ
    押しても動かないという気づきにくい壊れ方をする
- **定時実行（`scheduler.service.ts`）は二重に送らないことが最優先。** 2段で守る:
  1. `scheduled_job_runs(job_key, run_date)` の主キー … その日2回目は行を作れない
  2. `notifications` の一意索引 … 同じ人・同じ対象・同じ日は1行だけ
  片方だけだと、記録を書く前に落ちた回や複数プロセスの回で二重になる。
  **索引を外すと実際に倍になることを確かめてある**
  - 15分ごとに起きて「過ぎていれば流す」形。**時刻ちょうどを狙わない** —
    起きられなかった回（再起動中など）がその日ぶんまるごと飛ぶ
  - 実績の件数は `created = created + ?` で**足し込む**。`= ?` にすると
    画面から流し直したとき「新しく出たのは0件」で上書きされ、その日の実績が消える
  - **SQL の列名は実 DB で確かめてから書くこと。** 型チェックは SQL の中身を見ない。
    `project_tasks.status`（存在しない・正しくは `is_completed`）と
    `due_date` が `date` 型（他は TEXT なので `substr` が落ちる）で実際に踏んだ
- **料金表の場所を URL に持たせた**（`/sales/pricing?location=`）。
  画面の中の状態だけだと、拠点・部屋から送られた側は毎回タブを押し直すことになる
- **メニューの `module` を書いていなかったのを直した。** データビューア・
  DBバックアップ・権限とメンバーは無指定で、**`admin` が無い人にも出ていた**。
  旧 `/settings` 自体が admin 必須だったので気づけなかったが、
  設定トップを開放した以上そのままにはできない
- **権限とメンバー（`pages/members/`）— 役割は「型」にした。**
  モックは **役割5種 × 権限8項目 × 3レベル**で権限は役割にだけ付くが、いまの ONAiR は
  **人ごとに 12 区画 × 5 段**を持ち、その判定が **311 か所**ある。判定を役割ベースに
  置き換えると、取りこぼした 1 か所が「開けない（仕事が止まる）」か
  「見えてはいけないものが見える」になる。そこで **役割は `user_permissions` へ押す型**にした
  （migration 174 ／ `permission-role.service.ts`）。画面は役割が主役、下は今までどおり。
  役割は自分たちで足せる。
  - **`ROLE_MODULES` に凍結4アプリを足さないこと。** 足すと役割を押すだけで
    Qシート・リアルタイムCG などの権限が消える（放送が止まる）。
    守りを外して実際に消えることを確かめてある
  - **表の行は 12 区画で、モックの 8 項目にしない。** モックの 8 のうち 4 つ
    （案件・見積・工程・料金表）は実装では**同じ `sales`**。8 行に分けると
    「見積だけ見るだけにした」つもりで案件も工程も料金表も変わる（`moduleLabels.ts`）
  - **旧「権限修復」ボタンは外した。** 全スタッフに 12 区画すべてを配る作りで、
    押すと経理しか見てはいけない数字が全員に見える。役割ができた今は
    「役割を押し直す」が正しい直し方（API は残してある）
  - 型を直したとき、押してある人への反映は **既定で「しない」**。
    保存時に「この役割の N 名にも反映しますか」を出す

**⑧ 取引先（財務）で決めたこと**
- **仕入先とパートナーを1画面のタブにまとめた**（`pages/CounterpartyPage.tsx`）。
  旧実装は2画面（208行＋224行）で、**中身はほぼ同じ**（名前・担当・電話・メール＋1項目）。
  別画面だと、探すときにどちらにいるか思い出す必要がある。旧 `/budget/partners` は転送
- **請求先（顧客）はここに入れない。** 案件管理の「取引先マスター」で編集する。
  **同じ相手を2か所から直せるようにすると、片方だけ直された相手ができる**。
  画面からはそちらへ送るだけにした
- **フックは1つ。** タブで `endpoint` を切り替えるだけにする（2つ持つと、
  片方だけ検索が残る・件数が古いままになる）
- **送る列は種類で変える。** 仕入先＝`invoice_registration_number`（文字列）、
  パートナー＝`specialties`（配列）。**サーバーが知らない列を送らない**
- **取引額は出していない。** モックは相手ごとの取引額を出すが、
  **期間の取り方（今年度／直近12か月／全期間）が決まっていない**。
  仕入先だけは既存の「仕入先集計」へ送るボタンを置いた

**① 財務ダッシュボードで決めたこと**
- **KPI を8枚並べるのをやめて、引き算の順に並べた**（`financeDashboard/ProfitFlow.tsx`）。
  売上 − 変動原価 = 限界利益 − 固定原価 = 売上総利益 − 販管費 = 営業利益。
  旧実装は同じ大きさのカードが8枚で、**どれとどれを引くとどれになるのかが
  読み取れなかった**（「限界利益」と「売上総利益」が隣にあるのに関係が書いていない）
- **利益（引き算の結果）だけ枠と色を変え、赤字は赤**にする。並べただけでは
  マイナスに気づかない
- **期間の計算と5本のクエリは1行も変えていない。** 金額の集計を、画面の作り直しと
  同じ回で触らない（月／四半期／年／期間指定・案件での絞り込みはそのまま）
- **合計を画面で足し算し直さない。** 内訳は上位だけを出すので、画面側で足すと
  内訳と合計が食い違う。合計は `GET /monthly-summary` が出したものをそのまま出し、
  「内訳は上位だけ・合計とは一致しない」と画面に書いた
- **案件で絞ると販管費が外れることを画面に書く。** 書かないと
  「販管費が 0 になった＝壊れた」と読まれる（販管費は案件に紐づかない）

**② 請求・入金（財務）で決めたこと**
- **月次の締めを一括でやる画面**にした（`pages/ClosingPage.tsx`）。締め月を決めて、
  その月ぶんを選んで「請求書を出す／入金を記録する／検収を記録する」
- **⑤ 見積・請求（案件管理）との住み分け。** あちらは案件をまたいで取りこぼさない
  ための一覧（1件ずつ・期日順）、こちらは締め月ぶんをまとめて処理する画面。
  **書き込む列も検査も同じ**なので、どちらから記録しても食い違わない
- **`sales` か `budget` のどちらかで通す**（`requireAnyPermission` を新設）。
  `billing.routes` は `sales` だけを要求していたので、**経理だけの人は
  月次の締めができなかった**（実際に 403 を確認した）
- **申込書が揃っていない案件は請求書を出せない。** 四角を消すのではなく
  **押せない四角と鍵のアイコン**を出す（消すと「なぜ選べないのか」が分からない）。
  サーバー側でも弾く — 画面で隠すだけだと直接叩けば通る
- **申込書を要求するのは請求書を出すときだけ。** 入金と検収の記録は止めない
- **一部だけ処理したときは飛ばした件数を返す**（`skipped_blocked`）。
  黙って一部だけ入るのがいちばん困る
- **請求書番号は付けていない。** `revenues` に列が無く、採番には
  ①連番の単位 ②取り消したときの扱い ③いま経理が使っている番号との突き合わせ
  を決める必要がある。**勝手に採番すると会計側の番号と二重になる**。画面に明記した
- **売上台帳からのリンク先を `/budget/billing` にした**（同じ財務の中で完結する）

**⑥ 受け取った書類（財務）で決めたこと**
- **日常業務から財務へ移した**（`/daily/finance` → `/budget/documents`）。旧実装は
  `dailyops` 権限だけを要求しており、**経理が開けなかった**（実測で 403）。中身は
  金額・締月・支払期日・GLS番号 で完全に経理の道具なので財務に置き、
  **`dailyops` か `budget` のどちらか**で通す（`requireAnyPermission`）。
  **いま見られる人は見られたまま、経理が見られるようになる**
- **`/daily/finance` は転送だけ残した**（`client-daily/src/App.tsx` の `RedirectToFinanceDocs`）。
  別のバンドルなので `navigate` では飛べず `window.location.replace` を使う
  （`replace` なので「戻る」で転送ページに戻り続けない）
- **日常業務の左メニューとホームのタイルは消していない。** `dailyops` だけの人は
  アプリ切替に財務管理が出ないので、消すと**辿り着く道が無くなる**
- **「処理完了」を本物にした。** 以前は状態が変わるだけで**台帳に何も作られず**、
  同じ請求書を2回入力して突き合わせは記憶頼みだった。いまは「台帳に入れる」で
  仕入か販管費の行を作り、**書類にどの行になったかを記録する**（migration 142 の
  `linked_kind` / `linked_id`）。行き先が2つのテーブルに分かれるので外部キーにはできない
- **承認済みだけ渡せる。** 確認前・却下を入れられると承認のステップが意味を持たない
- **二度渡せない**（409 `ALREADY_LINKED`）。渡し済みをもう一度渡すと台帳に二重に載る
- **金額を勝手に割り戻して保存しない。** 書類の金額は**税込**（`record_finance_doc` の
  説明が「金額 (税込・円)」）で台帳は税抜。書類に税区分が無いので、黙って 1.1 で割ると
  8% や 非課税 の書類で静かにずれる。**目安を初期値に入れ、そう入れたことを画面に書く**
- **取り消しても台帳の行は消さない。** 経理がそのあと直しているかもしれないので、
  勝手に消すほうが危険。書類側の結びつきだけ外して「承認」に戻し、**確認ダイアログで
  「行は残る・いるかどうかは台帳で確かめて手で消す」と明示**する
- **この画面より前に「処理完了」にした書類は `linked_id` が無い。** 黙って隠すと
  二重入力に気づけないので、**結びつきが無いことを行に書く**
- **書き込みは1つのトランザクション。** 分けると台帳に入ったのに書類が未処理のまま残り、
  もう一度渡される

**⑦ 取り込み（財務）で決めたこと**
- **3画面を1画面3タブに畳んだ。** 精算PDF（`/budget/xpoint-import` 980行）・
  総勘定元帳（`/budget/kessan-import`）・二重計上（`/budget/dedup-screening`）は
  やることが全部「外の数字を読む → 中身を確かめる → 台帳に入れる」で同じなのに、
  **手順の見せ方も結果の出し方も確認の訊き方もバラバラ**だった
  （`alert` と `window.confirm` が計4か所）。決算インポートと二重計上は
  **続けて使うもの**なのに別の URL でメニュー経由でしか行き来できなかった
- **旧3 URL は必ず生かす**（毎月使う業務画面でブックマークされている）。
  `?src=pdf` / `?src=gl` / `?src=dedup` へ転送する
- **権限はタブで出し分ける。** 精算PDF は `budget` の editor、総勘定元帳と
  二重計上は `system_admin`（サーバーが `requireRole` で止める）。
  **タブが1つしか無い人にはタブ自体を出さない**（選べないものを選ばせない）
- **ステップの現在地を作り話にしない。** 行の状態（`new`/`parsed`/`registered`）や
  `dryRun` から導く。常に1段目を光らせると飾りになり、2回目からは誰も見ない
- **AI の読み取り信頼度 % を出さない。** モックは行ごとに「読み取り 98%」を出すが、
  `xpoint-parse.service.ts` は正規表現のパーサで**スコアという概念が無い**。
  それらしい数字を置くと、他の画面で守っている決めをここだけ破ることになる
- **「BOX に置く必要はありません」とも書かない。** 解析は Box の extracted_text 一本道で、
  Box が使えない日は直接アップロードも動かない。書くとその日に「壊れた」と言われる
- **金額を組み立てるロジックは1行も変えていない。** 税抜換算（`税込 ÷ (1+税率)`）と
  `billing_key` の作り方はサーバーと噛み合っており、整理のついでに触ると
  **実際の仕入・販管費の金額がずれる**
- **総勘定元帳の「台帳に入れる」は物理削除を伴う。** 対象月のマーカー
  `[kessan:YYYY-MM]` が付いた行を `DELETE FROM` で消してから入れ直す（論理削除ではない）。
  4つのトグルの既定値は旧実装から変えていない
- **二重計上の確認ダイアログから2文を落とさない** —「手で入れた行は残ります」と
  「論理削除なのでバックアップから戻せます」。無いと押す人は何が起きるか分からない

**AI が取り込んだメールの出し方（⑥ と 日常業務⑤ で共通）**
- **`details`（意味の単位の配列）と `body_text`（原文）を持つ**（migration 160）。
  それまでは 差出人・要件・希望日・人数・予算・期限 を**1本の自由文に潰して**
  渡しており、画面は `📝 <そのままのテキスト>` と出すだけだった。
  しかも `finance_docs.content` は**一度も描かれていなかった**
- **AI に HTML を書かせない。** 取引先の文面がそのまま実行される（XSS）うえ、
  書体・色・余白が AI ごとに変わり、後から検索も集計もできない。
  **AI は「何の情報か」を言い、見せ方は `RichContent` が決める**
- 部品は **`shared/src/client-v4/richContent.tsx`**。`shared/src/client/` に置くと
  **凍結4アプリの CSS が増える**（実測4規則・231バイト）ので、
  v4 対象3アプリの Tailwind だけが読む場所に分けてある
- **行に出さず「中身を読む」で開く。** 行に出すと中身の量で行の高さがバラバラになり、
  金額の桁が縦にそろわない
- **古い行は自由文しか持たない**ので `fallback` で今までどおり出す（過去のぶんを消さない）

**財務の台帳3画面（③ 売上 ／ ④ 仕入 ／ ⑤ 販管費）で決めたこと**
- **行の描き方を1つにした**（`pages/ledger/LedgerRows.tsx`）。3画面は列の意味が同じ

  **売上8列・仕入9列・販管費10列**で金額の桁も揃っていなかった
- **列幅のドラッグを外した。** 3画面に3つの実装があり、他の一覧には無く、保存もされない
  （次に開くと戻る）。揃った幅を部品側で持つほうが桁を読み違えない
- **金額を扱うフォームは中身を変えていない。** ダイアログを別ファイルに出しただけ
  （`ledger/RevenueDialog.tsx` / `ledger/PurchaseDialog.tsx` / 既存の `SgaDialog`）。
  枠の入れ替えと中身の作り直しを同じ回でやらない
- **合計は絞り込み全体**を出す（`total_amount`）。ページごとの合計だと、めくるたびに
  数字が変わって読み間違える。絞り込みチップの件数（`state_counts`）も
  **その軸以外の絞り込みだけ**を掛けて数える（案件一覧の `stage_counts` と同じ考え方）
- **売上の請求・入金の状態はここでは変えられない。** 押すと ⑤ 見積・請求へ移る。
  同じ数字を2か所から書き換えられると、経理の記録が台帳から戻される事故が起きる
- **仕入は変動原価と固定原価をタブで分けた。** サーバーは `fixed_cost` で絞れるのに
  画面から渡しておらず、**案件の原価と月の固定費を足した「合計」**が出ていた
- **販管費は勘定科目で絞れない。** `sga_expenses` に勘定科目の列が無い（モックは
  通信費／地代家賃／旅費交通費で絞る形）。持っている軸（固定費／都度、社員／経理）
  だけを出し、無い理由を画面に書いた
- **直したこと3件（どれも実データで再現を確認済み）**:
  - **売上を案件名で検索できなかった。** `buildRevenueWhere` が請求KEYと備考しか
    見ておらず、画面には「請求KEY・案件名で検索」と書いてあった。仕入も案件名が抜けていた
  - **明細のある売上を直すと明細が消えた。** 編集で開くと `items` を空にしていたので、
    1行足して保存すると**元の明細が全部消える**（サーバーは `items` があると全置換）。
    開くときに `GET /revenues/:id` で明細を読むようにした
  - **`status=all` が「status という文字列が all の売上」を探していた**（＝0件）。
    「確定も見込みも出す」を表す値として扱うようにした。**空文字とは区別する** —
    既定を変えると `status` を渡していない集計（月次サマリ・MCP・Excel）に
    見込みが混ざって金額が変わる
