# 見張りの最中に踏んだ落とし穴（追記していく記録）

**この手順が言っていなかったことを踏んだら、ここに1行足してください。**

⚠️ **書かないと、同じ落とし方を何度でも繰り返します。** この製品は
「説明文の中に実物のクラス名を書く」を**4回**踏んでいて、4回目に気づけたのは
機械の検査（`check:frozen`）が拾ったからでした。**人の記憶は数えられません。**

## 書き方

1行につき **いつ / どの PR / 何が起きたか / 次はどうするか** の4つ。
**「気をつける」で終わらせないこと** — 次に同じ場面に来た人が**手を動かせる形**で書きます。
機械で止められるなら、**止める道具の名前も書きます**。

## 読み方（リリースのたびに）

- **同じことを2回以上踏んでいるものは [SKILL.md](../SKILL.md) 本体へ昇格**させます
  （ここは「まだ手順になっていないもの」の置き場です）
- **機械で止められるようになったものは、その検査名を書いて残します。** 消さないこと —
  消すと「なぜこの検査があるのか」が分からなくなり、次に誰かが外します

### 2026-08-17 ／ PR #175 ／ 共有している SQL の列を増やして、呼び出しを1か所だけ直した

**何が起きたか**: `seed.ts` の `projSql`（複数の呼び出しが共有する INSERT）の列を
16 → 18 に増やしたとき、**ヨミ段階と失注の呼び出しだけを直し、GLS 発番済みの呼び出しを
16 個のまま残しました**。新しい DB では**最初の GLS-A 案件で bind パラメータ不一致**で落ち、
insert が取引にまとまっていないので**途中まで入った状態で止まり**、
2回目以降は「ユーザーが居るのでスキップ」になるため
**壊れたシードのまま検証環境が立ち上がります**。Codex の P1 指摘で見つかりました。

**なぜ自分では気づけなかったか**: `typecheck` は通ります（`ins(sql, unknown[])` の
配列の長さは型で数えられない）。`lint` も `test` も通ります。
そして ⚠️ **CI はシードを1度も流しません**（`checks` / `build` のどちらにも無い）。
つまり**手元でシードを流す以外に気づく方法がありませんでした**。

**次はどうするか**:
- **SQL の定数を書き換えたら、その定数を使っている呼び出しを `grep` で全部数える**
  （`grep -n "projSql" …` で3か所出る。直したのは2か所だった）
- **`seed.ts` / `migrations/` を触った PR では、新しい DB でシードを1回流す**:
  ```bash
  bash scripts/dev-verify/up.sh --fresh          # 検証用 Postgres
  su postgres -c "createdb -h 127.0.0.1 -p 5433 -U postgres onair_seedtest"
  DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:5433/onair_seedtest \
    SKIP_SEED=false npm run db:seed -w server    # 「Seed data inserted successfully.」まで見る
  ```
  ⚠️ **`up.sh` が作った DB では確かめられません** — 検証用ユーザーを入れてあるので
  シードが「もう入っている」と判断して**黙ってスキップします**（それを緑と読まないこと）
- **未対応の宿題**: CI に「新しい DB でシードを流すだけ」の一手を足すかは、
  必須チェックを増やす話なのでユーザーに相談中（PR #175 のスレッドに書いてあります）

## マージ後の棚卸しを push しようとしたら `stale info` で弾かれた

**2026-08-22 / PR #300 のマージ後**

**何が起きたか**: #300 がマージされた直後、棚卸しの記録を同じブランチ名
（`claude/production-support-homepage-uiux-bs7zdu`）で push しようとしたところ、
`git push --force-with-lease` が **`! [rejected] … (stale info)`** で2回続けて失敗しました。

**原因**: **マージ時にリモートのブランチが削除されていました**（このリポジトリの設定）。
手元にはまだ `origin/<ブランチ>` の追跡参照が残っているため、`--force-with-lease` は
「リモートは自分が知っている SHA のはず」と照合しようとして、**参照そのものが消えている**
状態を「情報が古い」と判断して止まります。`git fetch origin` だけでは消えた参照は落ちません。

**なぜ自分では気づけなかったか**: エラーが `stale info`（＝誰かが先に push した、と読める文言）
なので、**競合と誤読して `git fetch` → 再試行を繰り返しがち**です。実際には
競合ではなく「押す先が無い」状態でした。

**次はどうするか**:
- マージ済みブランチに続きを積むときは、**まず消えた参照を落とす**:
  ```bash
  git fetch --prune origin
  git push -u origin <ブランチ>        # 新規ブランチとして作られる。--force は要らない
  ```
- そもそも**マージ済み PR のブランチは作り直してから使う**のが前提です
  （`git fetch origin main && git checkout -B <ブランチ> origin/main`）。
  作り直したあとは中身が完全に別物なので、**`--force-with-lease` を付ける理由がありません**

## 説明文の中に実物のクラス名を書いて `check-ui-tokens` を止めた（5回目）

**いつ**: 2026-09-01 / GPM の請求タブ（2,032行）を分割する PR

**何が起きたか**: 切り出したファイルの冒頭コメントに

> ⚠️ **生のパレット（`bg-orange-500` など）はそのまま。**

と**例としてクラス名を書いた**ところ、`check-ui-tokens` の `raw-palette` が
`client 94 → 95` に増えて `npm run lint` が落ちました。

この検査は**ソースを文字列で数えます**。コメントか JSX かを区別しないので、
**説明のために書いただけで1件に数えられます**。しかも増えるのは「分割で写した」
ように見えるため、**原因の見当がつきにくい**（実際、増えた1件を探すのに
`origin/main` との件数比較まで必要でした）。

⚠️ **これはリポジトリが「4回踏んだ」と記録している罠の5回目です。**
`CLAUDE.md` にも「同じ落とし方を3回繰り返しても、記録が無ければ誰も気づけない」
と書いてあるとおりで、**記録があっても書く側が読んでいなければ再発します**。

**次はどうするか**:
- **説明文にクラス名・トークン名・禁止パターンの実物を書かない。**
  「橙・琥珀系の生の色」「ブラウザの確認ダイアログ」のように**言葉で書く**
- 数が増えたら、まず `git show origin/main:<ファイル> | grep -oE '<パターン>' | sort | uniq -c`
  と現在を突き合わせて**どの記号が増えたか**を1つに絞る
- ⚠️ `--update` で逃げない。**増えたぶんは必ず理由がある**

## 2026-09-05 · PR #568 — 行番号を鍵にした ALLOW は、上に行を足すと黙って外れる

**用語統一（463 ファイル）で `checks` が落ちました。** 落ちたのは
`check-contrast-tokens.mjs` の1件だけで、指されたのは

```
client/src/contexts/platform/pages/home/MobileAiBar.tsx:91   text-primary-foreground
```

**その行の色は正しい**（ボタンの塗りが `linear-gradient(var(--primary) → var(--info))` で、
この検査はグラデーション記法を塗りと認識しないため、もともと `ALLOW` に登録済みだった）。

外れた理由は**登録が `ファイル名:行番号` を鍵にしている**ことです。同じファイルの
冒頭コメントに4行足したので、対象が **87 → 91 行目**へ動き、登録が効かなくなりました。

⚠️ **落とし穴は「検査が落ちたこと」ではなく「手元で気づけたのに見落としたこと」です。**
push 前に `npm run lint` は実行していましたが、**`✗` を grep して 0 件だったので通ったと判断**
しました。この検査は `✗` を出さず、`[contrast] 塗りの無いところに…` と書いて
**exit 1 で落ちます**。`tail -3` に出ていた「直し方」の助言を、無関係な出力だと読み違えました。

**次はどうするか**:
- ⚠️ **lint の合否は必ず終了コードで見る。** `npm run lint > log 2>&1; echo $?` の形にする。
  **出力の中の記号（`✗`・`error`）を grep して合否を決めない** — 検査ごとに書式が違う
- **行を足したら、行番号を鍵にしている一覧を確認する。** この製品では
  `scripts/check-contrast-tokens.mjs` の `ALLOW` がそれ（他にも増えたら、ここに足す）
- 落ちた検査は**単体で走らせて再現**してから直す（`node scripts/check-contrast-tokens.mjs`）。
  `npm run lint` は `&&` で繋がっているので、**最初に落ちた1つより後ろは走っていません**

## 2026-09-07 / PR #607 — 新しい依存を足した PR は、手元の gate に `npm audit` が入っていなかった

`checks` は型・lint・テストのあとに **`npm audit --omit=dev --audit-level=high`** を走らせる
（この文書の隣の [ci-jobs.md](ci-jobs.md) の表に載っていなかった）。pptxgenjs を足した PR が、

修正版が無い推移的依存で、**実行時に読まれていないことを dist で確かめられる**なら、
宣言を外した tarball を `vendor/` に同梱して `file:` で参照する
（`scripts/vendor-pptxgenjs.mjs`・[vendor/README.md](../../../../vendor/README.md)）。

## 2026-09-07 / PR #607→#610 — マージ後に同じ枝名で棚卸しの PR を出すとき、`--force-with-lease` は「stale info」で弾かれる

マージ済みの枝を `git checkout -B <同じ枝名> origin/main` で作り直して push したら、
`git push --force-with-lease` が `[rejected] (stale info)` で失敗した。GitHub がマージ後に
head の枝を自動で消しており、手元の追跡参照（前回 push の SHA）と実物（無い）が合わないため。
しかも `git push ... | tail` と繋いでいたので exit code が隠れ、「push ok」と読み違えた。

**次はこうする**: 先に `git ls-remote --heads origin <枝名>` で実物を見る。無ければ**素の
`git push -u origin <枝名>`**（force は要らない）。push の成否は `${PIPESTATUS[0]}` か
パイプ無しで読む。

## 2026-09-08 / PR #647 — 新しく足した検査は、**再現ファイルで両向きに**確かめてから出す

`check-ui-tokens.mjs` に検査を3本足したが、Codex に P2 を2件返された。どちらも
**「その検査が禁じたはずのものを、その検査が許していた」**という同じ形:

- `page-width-by-hand` — コメントには「モーダルは対象外」と書いたのに `only` は
  `client*/src` 配下すべてで、**コメントと実装が食い違っていた**。ダイアログを広げただけで
  記録（件数制）を超えて lint が見当違いの案内で止まる
- `page-h1-by-hand` — 大きさ（`text-xs`〜`3xl`）を並べて当てたので、**素直に
  `text-h1` と手書きした見出し**も、**`className` を次の行に書いた見出し**も素通りした
  （この検査は1行ずつ当てる）

さらに直す最中に2つ踏んだ:

- 直した正規表現 `/<h1[\s>/]/` は、**行末で終わる `<h1`** に当たらない（次の文字が無い）。
  再現ファイルを置いていなければ「直した」と誤認したまま出していた
- 検査が**自分の説明文**に当たった。行頭の `//` `*` を落とすだけでは
  **ブロックコメントの2行目以降**が素通りする（`/* … ＋ 14px の <h1> … */` が違反になった）。
  この製品が4回踏んだ「説明文の中に実物を書く」と同じ系統

さらに**その直しにも指摘が付いた**（3件目）。コメント判定を「直前3行の窓」で
実装したが、コメントが4行以上あって5行目で実物に触れると窓に `/*` が入らず、
**説明文が違反になる** — その判定が防ぎたかったものそのもの。窓をやめ、
ファイルを1度なめて**コメントを空白で塗り潰した写し**に当てる形へ直した。

**次はこうする**: 検査を1本足したら、**当たるべき例と当たってはいけない例を書いた
使い捨てのファイル**を置いて両向きに走らせ、確かめてから消す。
`only` を書いたら、その隣のコメントが言っていることと一致しているか読み直す。
コメントの中を除外するときは、**行頭記号でも固定幅の窓でもなく**、
ファイル全体を走査して塗り潰す（`blankComments()`）。
そのとき**文字列の中は塗らない**こと — `'/*'` という値でファイルの残りが
コメント扱いになると、false positive を潰した代わりに**違反を丸ごと見逃す**。
走査が読み違えた（ブロックが閉じない）ときは写しを捨てて元の行に当て、
静かに効かなくなるより多めに報告する側へ倒す。

**この3件はすべて「新しく足した検査そのものの欠陥」だった。** 画面のコードは
1件も指摘されていない。**門を足した回は、門そのものをいちばん疑うこと。**

## 2026-09-08 / PR #647 — 見出しの `sub` に説明文を入れると、スマホで後半が消える

`DashboardHeader.description`（折り返る）を `PageHeader.sub` に移したら、
