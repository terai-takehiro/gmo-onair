# PR を見張る（CI 失敗とレビュー指摘を片づけるまで）

## なぜこれがあるか（この製品で実際に起きたこと）

**PR を出したあとが、いちばん記録が消えるところです。**

| 起きたこと | 実測 |
| --- | --- |
| v4 の PR 68 本に、指摘が付いたままマージされて埋もれていた | **143 件** |
| その 143 件を潰す作業そのものにも指摘が付いた | **26 件**（**24 件は記録されず**） |
| そのうち、リリースが出せなくなる回帰（P1） | **1 件** |
| **レビューが1件も付かないままマージした PR** | **3 本**（#154 / #159 / #165） |

⚠️ **マージすると、レビューの指摘は GitHub の画面から消えます。** 直っていなくても消えます。
⚠️ **レビューが0件の PR は、画面上「指摘なし」と見分けが付きません。**
⚠️ **CI の緑は「検査が通った」と同義ではありません** — `check-changelog.mjs` は浅い clone のせいで
**どの PR でも一度も動いていませんでした**（版の3か所を書き換えても緑のまま）。

つまり **PR のあとを人の記憶に任せると、必ず抜けます。** そこを手順にしたのがこれです。

## 見張りの姿勢は2つある

どちらかを最初に決めてください。**やることが変わります。**

- **自分が出した PR** … **緑にするまで自分の仕事**です。CI 失敗の起床では、
  **①直しを push する ②直せない理由を PR に返信する** のどちらかを必ずやります。
  **3つ目の選択肢（何もせず起床を終える）はありません。** 1往復で終わりでもありません —
  新しい失敗が来るたびに再診断して押し直し、緑になったらそう言います
- **見張りを頼まれた他人の PR** … 1件ずつ判断します。**確信があって小さくて範囲内なら直す**／
  **曖昧か設計に関わるなら `AskUserQuestion` で訊く**／**重複か対応不要なら黙って飛ばす**

## 最初にやること

1. **購読する**（`subscribe_pr_activity`）。これでコメント・CI 失敗がこの会話に届きます。
   ⚠️ **`sleep` で待たないこと**。イベントで起きる仕組みなので、待つと待った分だけ無駄になります
2. **いまの状態を確かめる**（届いていないぶんがあるので、購読しただけで終わらせない）:
   - `pull_request_read` の `get_check_runs` … 走っている／落ちている検査
   - 同 `get_review_comments` … **未解決のスレッド**（`isResolved: false` が返信すべきもの）
   - 同 `get` … `mergeable` / `mergeable_state`（コンフリクトの有無）
3. **落ちているものと未解決の指摘があれば、その場で片づけます**

## CI が落ちたとき

**診断してから直す。押してから考えない。**

- ⚠️ **「flaky」は診断ではありません。** 再実行が正解なのは
  **テスト本体が1つも走る前に死んだとき**だけ（checkout・依存の取得・runner の消失）。
  それ以外は必ず原因まで降りて、**再実行したなら「なぜ再実行で足りるのか」を書きます**
- ⚠️ **テストを消す・飛ばす・隔離することで緑にしない。** それは緑ではなく検査の削除です
- **push する前に手元で再現し、この製品の速い検査を通します**（`npm run lint` /
  `npm run typecheck` / `npm run test`）。**確かめた1回の push が、当てずっぽうの3回に勝ちます**
- **base（`main`）でも落ちるなら、それは自分の変更ではありません。** その旨を**1度だけ**
  スレッドに書き（「`<検査>` が赤ですが `main` でも落ちています。復旧したら回し直します」）、
  復旧の知らせが来たら `main` を取り込んで push し直します。**これが唯一の「自分のではない」で、
  それでも黙りません**
- ⚠️ **承認が消えることを理由に直しを止めない。** push で approve が外れるのは
  緑にするための当然の費用です

**この製品の CI は2ジョブだけ**（`checks` / `build`）で、落ち方ごとの読み方と直し方は
[references/ci-jobs.md](references/ci-jobs.md) にあります。**赤いジョブ名を見たら先にそこを読んでください** —
「型チェックが落ちた」と「凍結アプリの CSS が変わった」は直し方が全く違います。

## レビュー指摘に対応するとき

- **Codex（`chatgpt-codex-connector`）の指摘は P1 / P2 の重みが付いています。**
  P1 は「壊れている・データが壊れる・権限が抜けている」、P2 は「使えない・読めない・数が合わない」
- **直したら、何をどう直したかを1〜2行で返信します。** 直さないと決めたなら
  **理由と、何が変われば直すか**を書きます（表からも消しません。下記）
- **返信は往復が片づいたとき・詰まったとき・訊きたいときだけ。** 1件ずつの実況はしません
  （差分が記録です）。ただし**状態のチェックリストは起床ごとに更新**して、
  スレッドが「いまどこまで」を示すようにします
- **自分が書いたコメントが起床として返ってきたら飛ばします**（自分の返信は依頼ではありません）。
  すでに片づけた重複も飛ばします
- ⚠️ **すべてのコメントの末尾に Claude 由来の印を付けます**（空行 → `---` → 斜体のリンク行）。
  サーバーが重複を落とすので、二重に付く心配はありません

### ⚠️ レビューが0件のときは「指摘なし」と読まない

**3本（#154 / #159 / #165）が、レビューが1件も付かないままマージされています。**
#165 は **1時間28分開いていて0件**でした。画面上、これは「読まれて問題なし」と**同じ見た目**です。

- **待てるなら待ちます**（Codex は数分で付きます）
- 待たずにマージするなら、**0件だったことを記録に残します**
  （[docs/reviews/codex-findings-v4.md](../../../docs/reviews/codex-findings-v4.md) に
  「#NNN — レビュー0件のままマージ」の行）。**書かないと、次に読む人には「指摘なし」に見えます**

## マージ後に必ずやること（棚卸し）

**マージすると指摘は画面から消えるので、書かなければ存在ごと消えます**（143 件がそうなりました）。

```bash
GITHUB_TOKEN=<token> npm run reviews:debt      # 直近 20 本のマージ済み PR
```

1. 返していない指摘が出たら、**[docs/reviews/codex-findings-v4.md](../../../docs/reviews/codex-findings-v4.md)
   の表に足す**。⚠️ **直すのが先ではありません — まず書く**（書いてあれば直すのは別の日でよい）
2. 直したら状態を ⭕️ にして、**直した PR 番号を書く**
3. ⚠️ **「直さない」と決めたものも消さない**（❌ のまま、理由と「何が変われば直すか」を残す）
4. ⚠️ **件数を文章に書かない。** 表を数えてください（文章と表が食い違ったことがあります）

正は [docs/branching.md](../../../docs/branching.md) の「マージしたら、その PR のレビューを棚卸しに移す（必須）」。

## 見張りは、マージかクローズまで終わらない

⚠️ **webhook は CI の成功・新しい push・コンフリクトの発生を確実には届けません。**
イベントだけを頼りにすると、**緑になったことに気づかないまま黙って終わります**。

- **起床を終える前に、1時間ほど先の自分への確認を予約します**（`send_later`）。
  火が付いたら CI・未解決の指摘・`mergeable`・open かどうかを見直し、
  **何も変わっていなければ何も言わずに次を予約**します（黙って再武装するのが正しい）
- **コンフリクトの知らせが来たら自分で解決します。** base を取り込み（この製品の慣習は merge）、
  **ロックファイルや生成物は手で混ぜずに作り直し**、手元の検査を通して push。
  返信するのは**本当に曖昧なとき**（両側が同じ処理を変えていて、どちらを採っても振る舞いが落ちる）だけ
- **「base が緑に戻った」の知らせは待ちではなく合図**です。取り込んで push し、CI を回し直します
- **やめてと言われたら即やめます**（`unsubscribe_pr_activity`）。以後その PR には push しません

## やってはいけないこと

- **CI 失敗の起床を、push も返信もせずに終える**（自分の PR のとき）
- **テストを消して緑にする／原因を見ずに再実行する**
- **レビュー0件を「指摘なし」として黙ってマージする**
- **マージした指摘を棚卸しに移さずに放置する**
- **`main` へ直接 push する／ユーザーの明示的な指示なくリリースを公開する**
- **`sleep` でイベントを待つ／ポーリングで回し続ける**

## 踏んだ落とし穴は書き足す（この手順を資産にする）

⚠️ **同じ落とし方を3回繰り返しても、記録が無ければ誰も気づけません**（この製品は
「説明文の中に実物のクラス名を書く」を4回踏みました）。

見張りの最中に**手順が言っていなかったこと**を踏んだら、
[references/pitfalls.md](references/pitfalls.md) に1行足してください
（**いつ・どの PR で・何が起きて・次はどうするか**）。
リリースのたびに読み直し、繰り返しているものは**この SKILL.md 本体へ昇格**させます。
それが「AI を使い捨てにしない」の③（改善に反映）の受け皿です。
