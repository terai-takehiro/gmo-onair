## 基盤: 共通3テーブル

機能ごとに個別実装すると絶対に収束しない（AI 接点は MCP ツール・スキル・メール取込・下書き生成と増え続ける）。
**全接点が登録する共通レイヤーを 1 つ**作り、各機能はそこに 1 行足すだけにする。

### `ai_outputs` — AIが出したもの 1件 = 1行

| カラム | 目的 |
|---|---|
| `id` | 以降の修正・成果がここに紐づく |
| `kind` | 案件下書き / 活動記録 / 見積下書き / 返信案 / ニュース / レポート要約 … |
| `target_table` + `target_id` | 生成された業務レコードへの参照。自動 diff の起点になる |
| `payload_snapshot` (JSONB) | **切り詰めなしの全文**。ここが教師データの本体 |
| `model` / `prompt_version` | 改善の前後比較に使う。無いと「効いたのか」が言えない |
| `actor_id` / `requested_by` | 誰の実行か / 誰の指示か |
| `source_channel` / `message_id` | 流入経路と由来。外部システムとの突合キー |
| `audit_id` | 既存の実行ログへのリンク（あれば） |

### `ai_corrections` — 人間の修正差分

`output_id` / `field_path`（`items[2].unit_price` まで指せる粒度）/ `before_value` / `after_value` /
`correction_type`（`fix` 誤り・`enrich` 追記・`reject` 不採用・`rephrase` 表現）/ `note`（理由・任意）/
`corrected_by` / `corrected_at`

`note` は任意にする。必須にすると入力されず、結果としてテーブルが空になる。

### `ai_outcomes` — 顧客反応と成果指標

`output_id` / `outcome_type`（受注・失注・返信あり・無反応・クレーム・KPI）/
`metric_key` + `metric_value`（`days_to_first_reply=2`, `amount_won=5000000`, `handled_minutes=12`）/
`observed_at` / `note`

## 条件2を人手ゼロで満たす: 自動 diff

人に「何を直したか」を入力させる設計は運用が続かない。**サーバー側で自動的に差分を取る。**

1. `ai_outputs.target_table` + `target_id` で「AI 由来のレコード」が特定できる状態にする
2. 既存の update service 層に共通ヘルパ `recordCorrections(before, after, outputId)` を差し込む
3. AI 由来レコードの UPDATE のときだけ before/after を比較して `ai_corrections` に書く
4. `correction_type` は値の変化から推定する（空→値あり = `enrich` / 値が変化 = `fix` / 削除 = `reject`）
5. UI には任意の「直した理由（任意）」欄だけを小さく置く

これでユーザーの操作は増えず、差分が自動で貯まる。

**下書き→確定フローがある場合の必須対応**: 確定時に全置換している実装は、
**置換の前に下書きを `payload_snapshot` として保存する**。この 1 行が無いと差分は永久に取れない。

## 条件3を新規テーブルなしで満たす: 成果の自動導出

`ai_outcomes` の大半は既存データから日次バッチで生成できる。新しい入力画面を作る必要はない。

| 導出したいもの | 既存データからの導出 |
|---|---|
| 受注/失注 | ステージ遷移・失注理由 |
| 金額インパクト | 確定売上・粗利 |
| 顧客が返信したか | AI 起票の後に人由来の活動記録が付いたか |
| 対応時間 | 受信時刻 → 対応完了時刻の差 |
| 案件化率 | 昇格先レコードの ID が入っているか |
| 採用率 | 採用フラグ・ピック番号・承認ステータス |

## 条件4の還流: 3段構え

貯めただけでは賢くならない。**読ませる経路**が要る。効果の大きい順:

### 1. AI 自身が読むダイジェスト（最も効く）

`get_ai_feedback_digest` のようなツールを用意し、AI が実行時に自分の直近の誤り傾向を読む。

> 例: 「`create_project` の `customer_name` が 28% 修正されている。うち 9 割が法人格の表記揺れ」

**プロンプト更新を待たずに次の実行から改善される**のがこの方式の強み。人間のリリース作業が
ボトルネックにならない。

### 2. ナレッジ化

反復する修正パターンをルール文に昇格させ、専用テーブルに保持して AI から読めるようにする。

> 例: 「"GMOインターネットグループ株式会社" と書かれたら顧客マスタの表記に寄せる」

**人間が承認したものだけ有効化**する。自動昇格させると誤ったルールが固定化する。

### 3. データセット export

期間と種別を指定して「AI出力 + 修正差分 + 成果」を JSONL で出力する。
これを AI に読ませてプロンプト/スキルの改善案を作らせる。`prompt_version` と突き合わせれば
**改善前後で修正率が下がったかを検証**できる。個人情報を含むので権限は管理者限定にする。

## 条件5のレビュー運用

新しい仕組みを作らず、既存の定例レポート基盤に相乗りするのが定着しやすい。

- **頻度**: 週1回。自動生成をスケジュール実行に載せる（修正率・修正の多いフィールド・KPI 推移・改善提案）
- **担当**: 領域オーナー（営業機能なら営業責任者、経理機能なら経理担当）。AI 担当者 1 人に集約しない
- **承認**: 下書き → 承認済みの遷移を持つ既存の仕組みを流用。**承認されたものだけ**がナレッジに反映される

## 経路が作りにくいケースと代替案

「できない」で止めないための定石。粒度を落とす・proxy を使う・登録タイミングを設計で縛る。

| ケース | 障害 | 代替案 |
|---|---|---|
| チャットに出す下書き（返信案・概算） | 人が別の場所で書き換えて送るので差分が残らない | 出力を登録し投稿に短い ID を付ける。**最小案: リアクション（👍採用 / ✏️修正 / ❌不採用）を回収するだけで採用率が測れる**。将来は送信済みメールを message_id で突合して自動 diff |
| 顧客満足度 | どこにも記録がない | 新規アンケート基盤は作らない。失注理由・クレーム種別を proxy にする。加えて案件終了時に**1問だけ**の設問を既存基盤で出す |
| 情報収集系の当たり外れ | 良し悪しの判定者がいない | 人間が付ける採用フラグ（1〜5 等）が既にあれば、それが正解ラベル。出力に紐づけるだけで完成 |
| AI が関与しない領域 | ループを作る対象がない | 無理に作らない。**AI を入れる時点で出力登録を必須にする規約**にすれば後付けコストは 0 |
| 外部 SaaS が生成する出力 | こちらで保存できない | Webhook/API で取得できる範囲（ID・タイムスタンプ・ステータス）だけ登録し、成果側だけ自前で紐づける |

## 計測を壊さないための注意

**時間窓を必ず設ける。** AI 出力から N 日以内（目安 7日）の変更だけを修正候補として扱う。
3 ヶ月後の金額変更は AI の誤りではなく正常な業務更新であり、これを混ぜると修正率が
無意味な数字になって改善判断ができなくなる。種別は人が上書きできるようにしておく。

**個人情報の扱い。** 全文スナップショットには顧客情報が入る。元の業務 DB に既にある情報なので
新たな露出は増えないが、**export と横断閲覧は管理者権限に限定**する。

**プロンプトのバージョニング。** 改善の効果測定は `prompt_version` の突き合わせに依存する。
最初から持たせておく。後から付けると、それ以前のデータが比較に使えない。
