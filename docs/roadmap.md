## コーディングが遅い原因と、直したこと (2026-07-26)

実測して 3 つに切り分けた。

| # | 原因 | 実測 | 直したこと | 効果 |
| --- | --- | --- | --- | --- |
| 1 | **CLAUDE.md が毎ターン全文読み込まれるのに、その 96.7% が過去の履歴だった** | 828,591 文字中 801,027 文字が履歴 | 最新5件だけ残し `docs/version-history.md` に切り出し | **828KB → 58KB (93%減)** |
| 2 | ルートの `npm run build` が 8 ワークスペースを**直列**で回していた | 1分50秒 | `shared` の後を `concurrently -m 4` で並列化 (旧挙動は `build:serial` に残置) | **1分50秒 → 47秒** |
| 3 | 「実 Postgres で N 項目」の**検証の土台を毎回ゼロから書き起こしていた** | 毎回 15〜30 分 + 同じ落とし穴の踏み直し | `scripts/dev-verify/` に up/down を用意し、落とし穴も README に固定 | **冷えた状態から 4 秒** |

### 1 が一番効く理由

CLAUDE.md はコーディング中、**ツールを 1 回叩くたびに全文が読み込まれる**。
履歴を全部ここに置くと、1 行直すだけの作業でも毎回 828KB を運ぶことになる。
さらに読み込み量が増えるほど会話の途中で要約が挟まり、**作業の途中経過が失われてやり直しになる**。
遅さの体感の多くはこれだった。

**今後のルール**: 新しい版を足したら、6件目に押し出された版を `docs/version-history.md` へ移す。
CLAUDE.md に残すのは常に最新5件 (このルールは CLAUDE.md 本文にも書いた)。

### 3 で固定した「毎回踏んでいた落とし穴」

`DATABASE_URL` の 1 本だけを読む / `user_permissions.access_level` (`level` ではない) /
`users.role` は 2 値のみ / `JWT_SECRET` は 32 文字以上 / 開発の認証は `x-user-id` ヘッダー /
Playwright の外部フォント失敗は JS エラーに数えない。

### 手をつけなかったもの (意図的)

- **検証の項目数そのものは減らさない**。v2.9.277 では実際に本番影響のバグを 2 件見つけている
  (経理が財務を開けない / ベルが出ない)。ここを削ると速くはなるが、壊れたまま出る。
- **1章 = 1PR の粒度も変えない**。まとめると差し戻しが効かなくなる。

### 決めたこと

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| 型 (Ver.2.5) | **変えない**。変えるのは「誰が埋めるか」だけ | 会社のフォーマットなので実装側で変えない |
| ページの構成 | **コードの定数**（`KEEP_PAGES` 16枚） | DB に置くと「型が変わったのか、その回だけ違うのか」が区別できない |
| DB に持つもの | 人が書いた分 と その回に足した議題 だけ | それ以外は既にある |

| 「そのほか（自由）」 | **名前を人が書くのを必須にした** | 候補の名前がそのまま議題名になると何の話か分からない |
| ③の6テーマ | テーマと担当は**固定**。人は1行だけ | 毎回作り直さない |
| ①の3行 | **空でも進める**（前の値を消さない） | 相談が無い回もある。書かないという判断も記録 |
| チェックリスト | 落ちている項目**だけ**出す | 全部出すと出したことの意味が消える |
| 確定 | 落ちている項目があっても**止めない** | 止めると会議が始められない |
| 出力 | **PDFだけ** | 依頼3で合意。投影は画面のまま |

**負の数で結果が違う**（`Math.round(-0.5) = -0` / `(-0.5).toFixed(0) = "-1"`）。
取り消しの請求書などマイナスが出る画面があるので、画面によって数字が変わり得た。

**見出しの書き方が3種類あった**: `text-xl lg:text-2xl font-bold` / `text-xl font-bold sm:text-2xl` /
`heading-page text-xl lg:text-2xl`。しかも **`/finance/import` は枠の見出しが `sm:`、
中身の見出しが `lg:`** だったので、**同じページの中で2つの段が混ざっていた**
（幅 640〜1024px では枠と中身で見出しの大きさが違って見える）。

### 決めたこと

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| 部品の置き場所 | `shared/src/client/ui/numbers.tsx` に集約 | 7アプリから同じものを使う |
| 数字のサイズ | **4段だけ**（lg / md / sm / inline）。`KpiCard` と同じ値 | 片方だけ変えると同じ数字が画面で違う大きさになる |
| 万円の丸め | `manYen()` 1本 | 負の数で結果が変わらないよう「絶対値で丸めて符号を戻す」形にそろえた |
| ページ見出し | `<PageTitle>` | 38か所・3種類の書き方を1つにする |
| 守り方 | **`npm run lint` の先頭で検査を走らせて止める** | 部品を用意しても手で書けるままだと必ず増える |
| 逃げ道 | 行に `ui-tokens-ok` と書けば見逃す | 例外を作れないと、例外が必要な場面で検査そのものを外される |

### 検査で止めること（理由も一緒に出す）

1. `¥` を数字と一緒に手で書く → 桁が揃わない・丸め方が揃わない
2. 万円に丸める式をその場に書く → 負の数で結果が変わる
3. 大きい数字に `text-*` を直書き → 同じ数字が画面で違う大きさになる
4. ページ見出しの指定を直書き → 見出しの大きさがばらつく

**対象から外したもの**: 部品の実装そのもの（`shared/src/client/ui/`）、各アプリの
再エクスポート層（`components/ui/`）、放送に出るCG（`/cg/`・出力ページ。画面設計の対象外）。
