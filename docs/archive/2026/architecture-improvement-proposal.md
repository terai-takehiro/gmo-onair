# 改善提案: GLS発番・売上仕入・案件グループ

## このドキュメントについて

シンプル化プランの補足として、以下3点について「今よりもっと良いやり方」を提案します。

1. GLS発番（イベントコード発行）の流れ
2. エピソード単位の売上・仕入れの管理方法
3. 案件グループの設計

---

## 1. GLS発番の改善

### 現状の問題

「口頭決定」ボタンを押すと、GLS発番と同時に案件・エピソード・売上まで一気に作られてしまう。

- ユーザーは「何が作られたか」を把握しづらい
- 途中でやめられない
- エラー時に中途半端なデータが残るリスク

### 提案: 2ステップ方式

GLS発番を「ヨミ側の操作」と「案件側の操作」に分ける。

**ステップ1: ヨミ画面でステージを変更する**
- 「口頭決定」ボタンを押す
- ヨミのステージだけが「B 口頭決定」に変わる
- この時点ではGLS番号は発行されない
- 画面に「次のステップ: 案件を作成してください」というガイドが出る

**ステップ2: 案件作成画面でGLS発番する**
- ヨミ画面のガイドから「案件を作成する」ボタンを押す
- 案件作成フォームが開く（番組名・種別・媒体を入力）
- 「作成」を押すとGLS番号が発行され、案件が作成される
- エピソードは案件管理画面から後で追加する（自動作成しない）

### なぜこの方が良いか

| 観点 | 現状（1ステップ） | 提案（2ステップ） |
|------|------------------|------------------|
| わかりやすさ | ボタン1つで裏側で色々起きる | 1つの操作で1つのことだけ起きる |
| 柔軟性 | エピソード数を発番時に決める必要がある | 案件作成後にいつでもエピソード追加可能 |
| エラー時 | 5テーブルのどこで止まったかわからない | 各ステップが独立しているので影響が限定的 |
| 売上の自動作成 | 自動で作られるが正確でないことが多い | ユーザーが案件画面で正確な金額を入力 |

## 2. 売上・仕入れの改善

### 現状の問題

売上と仕入の入力経路が多すぎて混乱する。

**現状の入力経路:**
- エピソード画面 → 売上追加
- エピソード画面 → 仕入追加
- 案件詳細画面 → 売上追加
- 案件詳細画面 → 仕入追加
- 案件グループ画面 → グループ仕入追加 → 按分
- エピソード一括作成時 → 売上自動作成

**関連テーブル:** revenues, purchases, purchase_allocations, purchase_episode_allocations（4テーブル）

### 提案: 案件を中心にしたシンプルな構造

**原則: 売上も仕入も「案件」に紐づける。エピソード紐付けは任意。**

#### 売上の流れ（変更後）

```
案件詳細画面の「売上」タブ
  → 売上追加ボタン
  → フォーム: 金額、顧客、税区分、エピソード（任意）、計上日
  → 保存

これだけ。入力経路は1つ。
```

#### 仕入の流れ（変更後）

```
案件詳細画面の「仕入」タブ
  → 仕入追加ボタン
  → フォーム: 金額、仕入先、税区分、エピソード（任意）、計上日
  → 保存

これだけ。入力経路は1つ。
```

#### 「エピソード紐付けは任意」の意味

- 1回の収録で使うカメラレンタル代 → エピソード#3に紐付け
- 年間のスタジオ使用料 → 案件に紐付け（エピソード指定なし）
- 複数話にまたがるセット費用 → 案件に紐付け（エピソード指定なし）

エピソード別の集計は、紐付けられたものだけで自動計算される。
紐付けなかったものは「案件共通費用」として表示される。

### 按分（配分）について

**現状の問題:** グループ仕入の按分と、エピソード仕入の按分が別々の仕組みで動いている。

**提案:** 按分機能は廃止し、以下のように整理する。

| ケース | 現状 | 提案 |
|--------|------|------|
| 3案件で共有する仕入 | グループ仕入として登録 → 按分操作 | 各案件に個別に仕入を登録（金額を手動で分ける） |
| 5話分まとめた仕入 | エピソード按分テーブルで管理 | 案件に1つの仕入として登録（エピソード指定なし） |

**なぜ按分を廃止するか:**
- 按分の計算ロジック（均等割り・端数処理）がバグの温床
- 実務では「均等に割る」ケースより「担当者が判断して配分する」ケースが多い
- 按分結果のテーブルが2つ（project用・episode用）あり、管理が複雑
- 配分したい場合は、最初から分けて登録した方が明確

**結果:** purchase_allocations と purchase_episode_allocations テーブルを廃止

## 3. 案件グループの改善

### 現状の問題

案件グループの機能が多すぎる。

- グループのCRUD（作成・編集・削除）
- グループへの案件追加・削除
- グループ仕入のCRUD
- グループ仕入の按分（均等按分・手動按分）
- 按分の表示・編集

→ これだけで **17個のAPIエンドポイント** がある。

### 提案: グループを「ラベル（タグ）」に変える

**やりたいこと（本質）:** 関連する複数の案件をまとめて見たい

**現状のアプローチ:** 「案件グループ」という別エンティティを作り、仕入管理まで持たせている

**提案のアプローチ:** 案件に「タグ」をつけるだけ

#### 具体的な変更

**変更前:**
- project_groups テーブル（名前、説明、期間）
- projects.group_id（1つのグループにしか所属できない）
- グループ仕入 + 按分テーブル

**変更後:**
- projects に `tags` カラムを追加（カンマ区切りテキスト、例: `"2026春,GMO案件"` ）
- 案件一覧画面でタグでフィルタリング
- グループ仕入・按分は廃止（仕入は各案件に直接登録）

#### 画面のイメージ

**案件一覧画面:**
```
[すべて] [2026春] [GMO案件] [定期配信]  ← タグでフィルタ

GLS番号   案件名          顧客        タグ
GLS-001   春のイベント    A社         2026春, GMO案件
GLS-002   夏のイベント    B社         2026夏
GLS-003   定期配信#12     C社         定期配信
```

**案件編集画面:**
```
タグ: [2026春 ×] [GMO案件 ×] [+ タグ追加]
```

#### なぜタグの方が良いか

| 観点 | グループ（現状） | タグ（提案） |
|------|----------------|-------------|
| 所属数 | 1つのグループにしか入れない | 複数のタグをつけられる |
| 管理画面 | グループ専用の管理画面が必要 | 案件一覧のフィルタだけで十分 |
| 仕入管理 | グループ仕入＋按分という複雑な仕組み | 各案件に直接登録（シンプル） |
| API数 | 17エンドポイント | 0（既存の案件更新APIにタグを含めるだけ） |
| 学習コスト | 「グループとは何か」を理解する必要 | 「タグをつけるだけ」で直感的 |

## 実施の優先順位

この提案は、先にお出しした「シンプル化プラン」のPhase A〜Dと統合して進めます。

```
Phase A: データ整理
  - ヨミの日程・失注理由をスリム化
  - 案件グループをタグ化
  - 按分テーブルの廃止

Phase B: ステージ変更の分離
  - GLS発番を2ステップ方式に変更
  - 売上の自動作成を廃止

Phase C: 売上・仕入の一本化
  - 入力経路を案件詳細画面に統一
  - エピソード紐付けを任意に

Phase D: 画面整理
  - ヨミ編集画面の分割
  - ラベル定義の統一
  - 料金シミュレーションの独立化
```
