# GMO ONAiR シンプル化プラン

## このドキュメントについて

現在のシステムが複雑になりすぎているため、**使いやすく・壊れにくく・理解しやすい**構造に整理するプランです。

---

## 現状の問題（なぜ複雑なのか）

### 問題1: ヨミに付属する機能が多すぎる

現在、1つのヨミ（営業案件）に対して、以下の情報がバラバラに管理されています。

| 情報 | 管理方法 | 問題点 |
|------|---------|--------|
| 基本情報（案件名・顧客・金額など） | ヨミ本体 | OK |
| 日程（複数の日付） | 別テーブルで管理 | 大半のヨミは「実施予定日」1つで足りる |
| 料金シミュレーション | 別テーブルで管理 | ヨミとセットにする必要がない |
| 失注理由 | マスタテーブル＋外部キー | 選択肢7個のためにテーブルは大げさ |

**例えるなら**: メモ帳に書けば済む買い物リストを、Excelの別シートで管理しているような状態です。

### 問題2: ボタン1つで裏側の処理が多すぎる

「B 口頭決定 → GLS発番」ボタンを押すと、裏で以下が**一気に**実行されます。

```
1. ヨミのステージを更新
2. 案件（プロジェクト）を新規作成
3. エピソード（話数）をまとめて作成
4. 発注記録を作成
5. 売上データを自動作成
```

**例えるなら**: 「契約します」と言っただけで、契約書の作成・納品スケジュールの確定・請求書の発行まで全部同時に行われるようなものです。便利に見えますが、途中で1つでもエラーが起きると全体がおかしくなります。

### 問題3: 1つの画面にダイアログ（ポップアップ）が多すぎる

ヨミ編集画面だけで、以下のダイアログがあります。

1. 料金シミュレーション
2. GLS発番の確認
3. GLS発番の完了通知

**例えるなら**: 1つの書類に付箋が3枚も4枚も貼ってある状態です。

## 変更プラン

### 変更A: ヨミ周りのデータをスリム化する

**やること**: ヨミに必要ない情報を切り離す

| 変更前 | 変更後 | 理由 |
|--------|--------|------|
| 日程を別テーブルで管理（複数日付対応） | ヨミ本体に「開始日」「終了日」の2項目を追加。複数日程が必要な場合はメモ欄に記載 | 実運用では1〜2日程で十分。シンプルになる |
| 料金シミュレーションがヨミに紐づく | 料金シミュレーションを独立した「見積電卓」機能に変更。ヨミに紐付けなくても使える | 見積もりは営業の道具。ヨミと1対1で紐付ける必要がない |
| 失注理由がマスタテーブル（7件） | 画面上の選択肢リストに変更（データベースのテーブルを廃止） | 7個の固定選択肢のためにテーブルは不要 |

**結果**: ヨミ関連のテーブルが **5つ → 2つ** に減ります。

```
変更前: opportunities + opportunity_dates + opportunity_simulations
        + lost_reasons + activity_logs

変更後: opportunities + activity_logs
        （料金シミュレーションは独立機能として別途残す）
```

### 変更B: ステージ変更を段階的にする

**やること**: 「ボタン1つで全部やる」→「1ステップずつ進める」に変更

#### 変更前の流れ

```
[口頭決定ボタン] → 一瞬で5つの処理が走る → 完了
```

ユーザーからは「何が起きたかわからない」「途中で止められない」

#### 変更後の流れ

```
ステップ1: [口頭決定ボタン] → ヨミのステージだけ変わる
                ↓
ステップ2: 画面に「案件を作成してください」というガイドが表示される
                ↓
ステップ3: [案件作成ボタン] → GLS番号が発行され、案件が作成される
                ↓
ステップ4: 案件管理画面で、必要に応じてエピソードや売上を追加
```

**メリット**:
- 各ステップで何が起きているか、ユーザーが理解できる
- 途中で間違いに気づいたら止められる
- エラーが起きても、どこで問題が起きたかすぐわかる

### 変更C: ヨミ編集画面を分割する

**やること**: 1つの大きな画面を、役割ごとに整理する

#### 変更前

```
ヨミ編集画面（567行の巨大な1画面）
├── 基本情報フォーム
├── 日程管理
├── ステージ変更ボタン群
├── 料金シミュレーションダイアログ
├── GLS発番ダイアログ
└── GLS発番完了ダイアログ
```

#### 変更後

```
ヨミ編集画面（メイン：基本情報の入力だけ）

ステージ変更エリア（別パーツ：ボタンと状態表示だけ）

GLS発番の流れ（別パーツ：案件作成の専用フロー）
```

**例えるなら**: 1枚の巨大な申込用紙を、「お客様情報」「プラン選択」「お支払い方法」の3枚に分けるイメージです。

### 変更D: ラベル定義の統一

**やること**: 同じものに違う名前がついている状態を解消する

現在、ステージの名前（「ネタ」「D:保留」など）が**2か所に別々に定義**されています。

```
変更前:
  ・ヨミ一覧画面 → 画面の中に直接書いてある
  ・ヨミ編集画面 → 共通定義ファイルから読み込んでいる

変更後:
  ・すべての画面 → 1つの共通定義ファイルから読み込む
```

**メリット**: ラベルを変えたくなったとき、1か所直せば全画面に反映されます。

## 変更の影響範囲

### ユーザーへの影響

| 項目 | 影響 |
|------|------|
| 見た目 | ほぼ変わらない（ボタンの配置が少し変わる程度） |
| 操作手順 | 口頭決定→案件作成の流れが2ステップになる |
| できること | 変わらない（機能の追加・削除はなし） |
| 料金シミュレーション | ヨミ画面からも引き続き使えるが、単独でも使えるようになる |

### データへの影響

| 項目 | 影響 |
|------|------|
| 既存のヨミデータ | そのまま残る |
| 既存の日程データ | ヨミ本体に移行（自動） |
| 既存のシミュレーション | そのまま残る（紐付けが任意になるだけ） |
| 既存の案件・売上データ | 影響なし |

---

## 実施順序

```
Phase A（データ整理）       ← まずここから
  ・日程テーブルの統合
  ・失注理由をフロント定数化
  ・マイグレーション作成

Phase B（ステージ変更の分離）
  ・changeStage APIの簡素化
  ・案件作成を別APIに分離
  ・UIにガイド表示を追加

Phase C（画面の分割）
  ・OpportunityFormPageを3パーツに分割
  ・ラベル定義の統一

Phase D（料金シミュレーション独立化）
  ・シミュレーション機能を独立ページ化
  ・ヨミからのリンクは維持
```

各Phaseは独立しているため、1つずつ確認しながら進められます。

## まとめ

| 指標 | 変更前 | 変更後（見込み） |
|------|--------|-----------------|
| ヨミ関連テーブル数 | 5 | 2 |
| 口頭決定時のDB書き込み | 5テーブル同時 | 1テーブルずつ |
| ヨミ編集画面のダイアログ数 | 3つ | 1つ（GLS発番のみ、別フローに移動） |
| ステージ変更API内の処理数 | 5処理 | 1処理 |

**一言でいうと**: 「1つのボタンで全部やる」から「1つずつ確認しながら進める」設計に変えます。
