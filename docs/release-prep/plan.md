## この計画を3分で（だれでも読める版）

**いまの状態**: v4 の部品は全部そろった。ただし本番のサイトは 8月18日の版（v4.1.7）のままで、
その後にできた **240 個以上の変更がまだ本番に出ていない**。この中には
「元に戻せない種類のデータベース変更」が約 30 個含まれている。

**いちばん大事な結論**: **大掃除より先に、たまった変更を本番に出す。**
掃除を続けるほど「一度に出す量」が増えて、何かあったときに原因を探せなくなる。
先に出してしまえば、掃除は小さく分けて安全に進められる。

**そのあとの掃除は6つ**（順番に意味がある）:

1. **検査の道具を先に足す** — 文書のリンク切れ検査・画面崩れ検査の穴埋め。掃除で壊したらすぐ分かるようにする
2. **ルールの見直し** — 古くなったルール・矛盾したルールを消す（例: もう存在しない「凍結アプリ」を守るルールが 20 か所以上残っている）
3. **文書の大整理** — 役目を終えた文書を書庫（archive）へ。README は今 393KB あって普通に読めないので 20KB 以下に
4. **だれでも読める説明書づくり** — 「ONAiR とは何か」「直しはどうやって本番に届くか」など6本を新しく書く
5. **画面の総点検** — 機械検査 → 全画面のスクリーンショット → 実機（iPhone/iPad）の3段階で崩れを拾って潰す
6. **技術的な借金の返済** — 既知のセキュリティ更新・使っていないコードの削除など

**進め方の約束**: いまも複数の作業が同時に走っているので、
**小さく分ける・数時間で終わらせる・混み合う場所（制作技術支援まわり等）は避ける**。

**あなたに決めてほしいことが 7 つ**、すぐ下にあります。

## 全体の段取り

```
R0 たまった変更を本番に出す（最優先・単独で完結）
└→ R1 検査道具 ──→ R2 ルール刷新 ──→ R3 文書大整理 ──→ R4 説明書（guide/）

   └→ R6 技術負債の返済（R0 の後ならいつでも。独立PR群）
```

- 各パッケージは **1セッション=1パッケージ=1ブランチ** で割り当てられる粒度にしてある
- どの PR も「着手直前に main を取り直す → 数時間以内にマージ」の短命運用（1日超えたら作り直す）

## 並行開発と衝突しないための決めごと

いまのマージ速度は **15〜30分に1件**（8/22 実測50件）。以下を全パッケージ共通の規約とする。

1. **短命PR**: 着手直前に main を取り直し、数時間以内にマージ。1日超えたら作り直す
2. **混み合う場所に入らない**: `client-techops/**`・`server/src/contexts/{qsheet,liveops}/**`・`shared/src/client/apps.ts`・server の wiring・生成基準ファイル（file-size-baseline 等）は準備作業の掃除対象から**除外**
3. **ホットスポットは原子的PR**: CLAUDE.md（R2-a の1本のみ）・codex-findings-v4.md（行追加のみ・再構成は静穏時）・リリースPR（切ったら即マージ、他セッションのマージ停止を依頼）
4. **文書移動は git mv のみの専用PR**とし、対象が直近2週間変更ゼロなことを確認してから切る
5. **成果物は新規ファイル**（この docs/release-prep/ 配下）。既存文書へはリンク1行だけ
6. **1セッション=1パッケージ=1ブランチ**。ユーザーがパッケージ ID（R1-a 等）で各セッションに割り当てる
