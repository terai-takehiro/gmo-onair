## 監査が見ていなかった穴（計画で補ったもの）

- 「UIUX再点検」のUX側（操作フロー・文言・空状態・エラー時挙動）を誰も見ていない。全監査がレイアウト/レスポンシブに限定。devでのアプリ単位ウォークスルー（release-readiness の受け入れ確認1巡と統合可）で補う
- 「不要ルール洗い出し」が古い/誤った記述の修正に偏り、現役の重いルール自体（全PRの reviews:debt 棚卸し必須・ai-feedback-loop 必須・pr-watch マスト等）の費用対効果を問う観点が無い。残す/軽くする/やめるをユーザーと決める場を計画に入れる

## 順序に関する批評

- 最初に決めるべき最大の分岐が未決: 滞留分（241+コミット・下書き158件）のリリースを「準備作業の前に出す」か「準備込みの大リリースにする」か。推奨は前者 — 準備PRを重ねるほどビッグバンが肥大する一方通行のため、必須ゲート（本番DBバックアップ+復元確認・devでのmigration一括リハ・drift SQL本番確認・_summary.md 作成・版番号決定 v4.2.0/v4.1.8・release:notes --dry）を揃えて先に出し、大整理は以後の小刻みリリースに載せる
- リリース断面は qsheet→techops Phase 1 完了後・Phase 2（URL/Socket.IO切替）前で固定する。liveops 表示レイアウトエディタは PR1（migration 233）のみマージ済みで PR2 が控えており、in-flight フェーズの途中でタグを打たない。断面確定時は他セッションのマージ一時停止をユーザーに依頼
- 本番系の手順（バックアップ・drift SQL・スモークテストA・Release 公開）は Claude セッションから実行不能（サンドボックス）。計画は必ず「Claude がチェックリストを用意→ユーザーが VPS/本番で実施→結果を docs/reviews/ に記録」の分担で書く。Release 公開はユーザーの明示指示のみという不変条件は、CLAUDE.md の旧 dev ブランチ節を削除する PR でも文として必ず残す（消し過ぎ事故に注意）
- ドキュメント大整理（archive 移動・README 減量・CLAUDE.md 圧縮）はリリース後に回す。順序: ①md リンクチェッカー新設 → ②CLAUDE.md 原子的PR（静穏窓・全修正を1本に） → ③archive 移動（git mv のみ・対象が直近2週間変更無しを確認） → ④README 減量（collect-changelog.mjs のマーカー維持か同PRでスクリプト更新+--dry gate） → ⑤ia.md 分割 → ⑥guide/ 執筆（技術層一本化の完了後が確定。逆順は二度手間）
- npm audit fix は tech-debt の「最初のPRで次リリースに同梱」より切り分けを推奨: package-lock.json は qsheet 系並行PRのホットスポット（PR #334 も変更）で、依存一括更新をビッグバンに混ぜると切り分け不能になる。単独短命PRとし、リリース直前に載せるか直後の小リリースに回すかを明示判断。xlsx→exceljs 置換はリリース後の独立PR
- verify:ui 拡張（PAGES 穴埋め・768px・潰れ検査・--shots）は UIUX 個別修正より先に単独PRでマージし、以後の全 UI PR の gate にする。リリース前に3幅スクショ一式を1回取得し qsheet 新画面の証跡とする（保存先はリポジトリ外）
- codex-findings-v4.md（8月35回変更の最大ホットスポット）に触る作業（未レビューPRの掃き出しレビュー記録・棚卸し整理）は、open PR #336 マージ後かつ行追加のみで行い、表の再構成は他セッション停止の静穏時に限る

## 技術負債

技術負債の「帳簿」は極めて健全に管理されている。Codex 指摘の棚卸し（docs/reviews/codex-findings-v4.md）は未確認0件・未解決P1が0件で、残る❌は意図的な見送り3件（全P2）のみ。コード中の実質的な TODO も1件（project-collab の Phase 6 予定）で、廃止アプリ（awards/quiz）の隔離もビルド・配信・ルート登録すべてから外れており完全、クライアント間の重複も shared ラッパーパターンで抑えられている。DB ドリフト監査も migration 206〜209 で解決済みで、legacy フォールバック（resolveLegacyCustomerId 等）も Phase 3-3-9 で既に削除済み。一方で本当の負債は「未リリースの滞留」に集中している: main には customers/vendors 削除など後戻り不能の migration 約27本と changelog 下書き157件が溜まっており、加えて本番依存の既知脆弱性32件（High 14・xlsx は修正版なし）とレビュー0件マージ PR の累積がある。リリース前の必須は①バックアップ＋リハーサル＋スモークテスト体制、②npm audit fix、③未レビュー差分の掃き出しレビューの3点で、それ以外（未使用 export 整理・migration 番号 lint・techops リネーム）はリリース後で足りる。

### [P1/M] 次の本番リリースが「後戻り不能の大型リリース」になっている

本番は v4.1.6 のまま、main には未リリースの破壊的 migration が滞留している: 206_drop_untracked_drift_tables（未追跡23テーブル削除）・208_drop_customers_vendors_tables・209_column_level_drift_cleanup（19列削除）・211_drop_techsheet_schema、ほか 212〜232 の qsheet 系を含む約27本。docs/deploy-pipeline.md に「これ以降は以前のタグへ戻せない」と明記済み。加えて docs/changelog.d/ に未リリースの下書きが157件滞留しており、次リリースは変更量・不可逆性ともに過去最大級になる。

**提案**: リリース前に (a) 消えるテーブルの pg_dump（db-drift-audit.md 記載のコマンド）と直近バックアップの復元テスト、(b) dev環境での migration 一括適用リハーサル、(c) デプロイ直後スモークテスト（phase3-2-plan.md チェックリストA）の実施者・手順の確定、を必須ゲートにする。以後は滞留を減らすため小刻みなリリースに戻す。

### [P1/S] 本番依存に既知脆弱性32件（High 14）— 大半は npm audit fix で解消可

### [P2/M] xlsx 0.18.5 は修正版が存在しない High 脆弱性（要ライブラリ置換）

server の xlsx（SheetJS npm 版 0.18.5）に GHSA-4r6h-8v6p-xvw6（prototype pollution）・GHSA-5pgg-2g8v-p4x9（ReDoS）。npm レジストリでは修正版が出ない。実利用は server/src/shared/utils/excel.ts と server/src/contexts/platform/services/kessan-import.service.ts の2ファイル（＋廃止済み awards の excel-import.service.ts）。アップロードされた Excel を parse する経路なので実際の攻撃面。exceljs は既に server に入っており qsheet 系で実績あり。

**提案**: excel.ts と kessan-import.service.ts を exceljs へ書き換えて xlsx を依存から外す（awards 側は廃止済みなので同時に import を落とすだけ）。次リリースに間に合わなければ「取込は管理者のみ」の運用注意を明記して直後のリリースで対応。
