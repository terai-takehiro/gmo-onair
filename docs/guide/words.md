## 管理番号（GLS番号）

案件1件ごとに付く番号です。画面では「管理番号」と表示します（2026-09-08〜）。
番号の形は `GLS-A012` のようになっていて、「GLS番号」という呼び名も同じものを指します。

- `GLS-A…` は案件（撮影・収録・配信・イベント）、`GLS-B…` はプロジェクト（工事・構築）です。
- 案件を作っただけでは付きません。ステージ「D 仮押さえ」以降なら手で採れ、「A 受注済」に進むと自動で採ります。
- 見積・請求・売上・仕入・回・BOX のフォルダ・進行台本など、ONAiR のほぼ全部のデータがこの番号でつながります。
- 2026年10月以降の新しい番号（`SCS-` / `GSS-` / `GMO-`）は「計上会社」を見てください。

⚠️ 要確認: 10月の再編後に画面の呼び名を「管理番号」のままにするか、設計案にある「案件番号」にするかは決まっていません。

## 案件 ／ プロジェクト

| | 案件 | プロジェクト |
| --- | --- | --- |
| 何か | お客様から受けて、スタジオで実施する仕事（撮影・収録・配信・イベント） | スタジオや設備を作る・更新する「工事・構築」の仕事 |
| 番号 | `GLS-A…` | `GLS-B…` |
| 使うアプリ | 案件管理 | プロジェクト管理（案件管理の隣のタイル） |
| 数え方 | 売上・粗利で数える | 工程の進み具合と未確認事項で数える |

- プロジェクトには**自社構築**（自分たちのスタジオ・設備を作る／更新する）と
  **グループ受託**（グループ本体から依頼を受けて作る）の2種類があります。
- 裏側では案件もプロジェクトも同じ入れ物に入っていて、番号の A／B で分かれています。
  そのため財務管理の集計には、プロジェクトの仕入も入ります。
- 以前の「スタジオ案件」「ビジネス案件」という呼び名は使いません。
- 10月の再編で、プロジェクトは GMOインターネットグループ本体の事業担当へ移り、
  番号も `GMO-…` になる設計です（「計上会社」）。

## ブロックアプリ

ONAiR は1つの巨大なアプリではありません。「案件管理」「機材管理」「日常業務」のように、
役割ごとに分かれた小さなアプリ（ブロックアプリ）を組み合わせたものです。
「GMO ONAiR」はそれら全体をまとめて指す呼び方です。一覧は [ONAiR とは](what-is-onair.md)。

## ミニアプリ

制作技術支援の中にある、番組・イベントごとの小さな道具です
（進行台本・スケジュール表・収録設定・配信設定・レンタル機材検索・計時・視聴者・テロップCG）。
まず番組・イベントを選び、その中でミニアプリを開きます。

## 回

1つの案件の中の、実施の単位です（第1回・7月分 など）。
回ごとにコードが付き、管理番号に枝番を足した形（`GLS-A012-003`）になります。
案件詳細の「回」タブで見られます。

## 凍結 ／ 移行中 ／ 凍結解除中 ／ 廃止

v4（画面の作り直し）の中で、アプリごとの扱いを表す言葉です。正式な定義は
[docs/v4-plan.md](../v4-plan.md) の「用語」の節にあります。

| 言葉 | 意味 | いま該当するアプリ |
| --- | --- | --- |
| 凍結 | 作り直さない。見た目は今のまま、URL は生かす。アプリ一覧・アプリ切替からは外す | なし |
| 移行中 | 後継のミニアプリへ機能を移している途中の移行元。凍結と同じ扱いで、新しい機能は足さない | なし |
| 凍結解除中 | 凍結を解いて、少しずつ新しい見た目に作り直している途中 | 制作技術支援 |
| 廃止 | 機能そのものを止める。プログラムは参照用に残すが、URL を含めどこからも開けない | リアルタイムCG（後継はテロップCG） |

## 検証環境 ／ 本番環境

同じ ONAiR が2つの場所で動いています。

- **検証環境**（`dev.gmo-onair.jp`）: 試す・練習するための場所。壊してよい。
- **本番環境**（`gmo-onair.jp`）: 実際の業務で使う場所。ここのデータが会社の本物。

ログインのしかたはどちらもメールアドレスとパスワードです。詳しくは [本番と検証・壊していい場所](environments.md)。

## ブランチ ／ PR ／ マージ

開発の仕組みを表す言葉です。詳しくは [直しが本番に届くまで](how-changes-ship.md)。

- **ブランチ**: 1つの作業のために作る、作業用の枝分かれ。作業が終わると本体（`main`）に合流させる。
- **PR（プルリクエスト）**: 「この変更を本体に入れてよいか」を確認してもらう申請。
  機械の検査（型チェック・Lint＝書き方の検査・ビルド）と AI のレビュー（Codex）を通り、人が確認してから合流する。
- **マージ**: 承認された PR の変更を本体（`main`）に取り込むこと。マージすると自動で検証環境に出る。

## リリース

本体（`main`）にたまった変更を、あらためて本番環境に出すことです。
GitHub で「Release」を公開したときだけ本番が変わります。版の番号（`v4.6.10` のような形）はこのときに上がります。
いま自分が見ている版は、画面右上の本人メニュー「バージョン履歴」で分かります。

## Issue（イシュー）

書き方は [直してほしいときの頼み方](asking.md)。
