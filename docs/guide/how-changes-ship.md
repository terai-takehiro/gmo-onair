# 直しが本番に届くまで

コードの直しが、いつ・どうやって皆さんの画面に反映されるかを知っておくと、
「直したと聞いたのにまだ変わっていない」ときに、どこを見ればよいか分かります。

## まとめ（先に1枚）

| 段階 | 起きること | 出る場所 | 誰が動かす |
| --- | --- | --- | --- |
| 1. Issue を立てる | 困りごと・要望を記録する | — | 頼む人（[頼み方](asking.md)） |
| 2. ブランチで直す | 作業用の枝分かれでコードを直す | 誰の画面にも出ない | エンジニア（AI を含む） |
| 3. PR を出す | 変更を確認してもらう申請。機械の検査と AI のレビューが付く | 誰の画面にも出ない | エンジニア |
| 4. マージ | 本体（`main`）に取り込む | **検証環境に自動で出る** | 人がボタンを押す → あとは自動 |
| 5. 検証環境で確かめる | 頼んだ人・直した人が実物で見る | `dev.gmo-onair.jp` | 頼んだ人 |
| 6. Release を公開 | 版の番号を上げ、正式な版として出す | **本番に出る** | 人（明示的な判断） |

**マージしただけでは本番は変わりません。** 本番に出す・出さないは、必ず人が判断して行います。
AI（Claude）が自分の判断で本番に出すことはありません。

## 1〜3. 直しは「ブランチ」で行い、「PR」で確認してもらう

- エンジニアがコードを直すときは、まず**ブランチ**（`main` という正の1本から分かれた作業専用のコピー）を作ります。
  直している間は、誰の画面にも影響しません。
- 直しがまとまったら **PR**（プルリクエスト。変更のかたまりを確認してもらう単位）にします。
- PR には、機械の検査（型チェック・Lint＝書き方の検査・ビルド・版の表記の整合）と、
  AI（Codex）のレビューが自動で付きます。検査が通らないとマージできません。
- PR の題名は「種類(アプリ): 何をしたか」の形です（例: `feat(equipment): 機材台帳を v4 の見た目にした`）。
  何が変わったかは、この題名の一覧で追えます。

## 4. マージすると、自動で検証環境に出る

- PR が `main` にマージされると、そのタイミングで自動的に検証環境（`dev.gmo-onair.jp`）に反映されます。
  人が改めて「出す」操作をする必要はありません。プログラムを組み立てて配るのに、少し時間がかかります。
- 検証環境は**確かめるための場所**です。本番（業務が実際に使う環境）とは別物なので、何か問題が起きても業務には影響しません
  （[本番と検証・壊していい場所](environments.md)）。

## 5. 検証環境で確かめる

- 直してもらった人は、検証環境で「頼んだとおりになっているか」を実物で見てください。
- 違っていたら、その PR や Issue にコメントするか、開発担当者に伝えます。ここで直すのが一番安上がりです。

## 6. 本番に出るのは「Release」を公開したときだけ

- 検証環境で問題がないと確認できたら、担当者が版の番号を上げる PR を通し、
  GitHub の Releases で **Release（正式な版。`v4.6.10` のような番号）を公開**します。
  これで初めて本番（`gmo-onair.jp`）に反映されます。
- いま自分が見ている版は、画面右上の本人メニュー「バージョン履歴」で分かります。
  版ごとに何が変わったかも、そこに出ます。
- **戻したいとき**: Release は過去の版が全部残っているので、1つ前の版を出し直せば戻せます。

## 昔の版を検証環境で見る

「あの頃の画面を実物で見たい」ときのために、指定した版を**検証環境だけ**に出す仕組み（Preview）があります。
その間、検証環境には一時的に古い画面が出ます。本番には出せない作りです。
`main` に次のマージがあれば、検証環境は自然に現行へ戻ります。

## 困ったときの確認の順番

1. 見ているのは本番か検証か（アドレスバーの `dev.`）
2. その直しは**マージ済み**か（PR が閉じているか）
3. マージ済みなら、**Release は出たか**（本人メニュー「バージョン履歴」の版の番号）
