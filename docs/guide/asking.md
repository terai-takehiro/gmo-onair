# 直してほしいときの頼み方

「ここ分かりにくいな」「こうなったらいいのに」と思ったときの伝え方です。
言うだけで終わらせず**記録に残す**と、忘れられずに後で直してもらえます。

## 急ぎのとき

**本番で業務が止まっているときは、Issue を立てるより先に Slack で連絡してください。**
記録は後からで構いません。

## Issue（イシュー）とは

GitHub（プログラムを管理しているサービス。エンジニアが作業している場所）にある、
**困りごとや要望を1件ずつ記録しておく場所**です。ここに書いたことが、実際の修正作業の出発点になります。
1つの Issue が1つの作業（ブランチ・PR）になります（[直しが本番に届くまで](how-changes-ship.md)）。

## 頼み方

1. GitHub のこのリポジトリ（`gmo-onair`）を開く
2. 「Issues」タブ → 「New issue」
3. 用意されている型（テンプレート＝あらかじめ決まった書式）から、近いものを選ぶ

型は3つです。名前は GitHub に出ているものと同じです。

| こんなとき | 選ぶ型 | 題名の頭に付くもの |
| --- | --- | --- |
| 動かない・表示がおかしい・保存できない | **不具合の報告** | `[不具合]` |
| 新しい機能が欲しい・既存の機能を作り替えてほしい（v4 の作業もこれ） | **機能の追加・変更** | `[機能]` |
| 現場から上がってきた「こうしてほしい」を、そのまま記録する | **利用者からの依頼** | `[依頼]` |

**白紙のまま作ることはできません。** 必ずどれかの型を選ぶ仕組みになっています。

## 書くとよいこと

型ごとに項目は少しずつ違いますが、次の3つがあれば直せます。

1. **どの画面・どのアプリで**（例: 案件管理の見積タブ。本番か検証かも書く）
2. **何をしたら**（押した順番。「①案件を開く ②見積タブを押す ③PDFを押す」のように）
3. **どうなってほしいか**（不具合なら「本当はどうなるべきか」、要望なら「できるようになってほしいこと」）

- 画面に出た文言やエラーの文章は、自分の言葉に直さず**そのまま貼って**ください。
- スクリーンショットは、書く枠に画像を貼り付けるだけで付きます。
- 「利用者からの依頼」では、頼まれた言葉を**原文のまま**書くのがコツです。
  自分の言葉に直すと、あとで「本当は何を頼まれたのか」が分からなくなります。「こちらの理解」は別の欄に分けて書きます。
- 「機能の追加・変更」には「AI が関わるか」のチェックがあります。
  AI に仕事をさせる・AI の出力を人に見せる機能なら、チェックを付けてください
  （「AI を使い捨てにしない」という会社の方針で、設計のときに確認する項目が増えます）。

## 型の中の「どのアプリ」の選択肢について

型の中の「どのアプリで起きたか」の選択肢は、古い名前のまま残っています。近いものを選んでください。

| 選択肢に出る名前 | いまの名前 |
| --- | --- |
| 案件管理 (/) | 案件管理・プロジェクト管理・財務管理・カレンダー・設定 |
| Qシート (/qsheet/) | 制作技術支援（進行台本ほかのミニアプリ） |
| ライブ運用 (/live/) | 計時・視聴者（制作技術支援の中） |
| リアルタイムCG (/awards/) | 廃止（後継はテロップCG。制作技術支援の中） |
| デイリー (/daily/) | 日常業務 |

⚠️ 要確認: この選択肢（`.github/ISSUE_TEMPLATE/*.yml`）をいまの名前に更新するかどうか。

## そのあとどうなるか

Issue を出すと、エンジニアがブランチを切って直し、PR を経て検証環境に出ます。
検証環境で「頼んだとおりか」を見てもらうのは、頼んだ人の役目です。詳しくは [直しが本番に届くまで](how-changes-ship.md)。

## GitHub を使えない・分からないとき

無理に自分で Issue を立てなくても大丈夫です。開発を担当している人に、上の3つ
（どの画面で・何をしたら・どうなってほしいか）を伝えれば、代わりに記録してもらえます。
