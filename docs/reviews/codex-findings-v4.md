## 読み方

- **P1 / P2 は Codex が付けた重みです。** P1 は「壊れている・データが壊れる・
  権限が抜けている」、P2 は「使えない・読めない・数が合わない」がおおよその目安
- **「状態」は 2026-08-15 に確かめたもの**です。⭕️ = 直っている（別の PR で直った分を含む）／
  ❌ = コードにまだ残っている／❓ = 未確認（読んだだけで、コードは見ていない）
- **❓ を「残っている」と読まないこと。** 後の PR で偶然直ったものが実際にあります
  （`?tab=thread` のリンク・`/gpm/estimates/summary` のルート順・持ち帰りの二重登録）

## いま分かっている優先順位

**1. 時刻（JST）** — ✅ **片づきました**（`server/src/shared/utils/jst.ts`）。
コンテナに `TZ` が無いのに、日本時間のつもりで `Date` のローカル取得を使っていた3か所。
**夜間ジョブが昼に走り、朝9時前のダッシュボードが前日を出して**いました。
⚠️ `TZ=Asia/Tokyo` を置く直し方はしていません — **Alpine は tzdata を持たないので
渡しても黙って UTC のまま**になります（設定したのに効かない、いちばん気づけない形）。
`Intl` は ICU 内蔵の時間帯データを使うので、そちらで明示的に変換しています。

**2. 権限（見えてはいけないものが見える側）** — ✅ **片づきました**（#106）。
`dailyops` だけの人に案件80件が返る／その人が案件・台帳に書ける／BOX のサムネが
持ち主を確かめない／端末を共有すると前の人の案件名が出る、の4件。

**2b. 「押せるのに 403」側** — ✅ **片づきました**（#110）。
`sales` だけの人の請求書 PDF ／ reader に出るタスクの四角 ／ `sales` の一覧へ送るリンク ／
**`dailyops` だけの人のトップページで受信箱が 403 になり、数えていないのに
「お客様を待たせているものはありません」と出ていた**もの。
`HoldListPage` と カレンダー設定は**すでに直っていた**ことを確認しました。

**3. お金** — ✅ **片づきました**（#111 / #112）。二重計上3件（見積→売上の同時変換・
請求番号の採番・書類の引き渡し）と取りこぼし1件（グループ請求が一覧に1行も出ない）は #111。
どれも**確かめてから書くの間に他人が入れる**形だったので、**取引の中で行を押さえて**から書きます。
案件詳細の読み取り側2件（分け合う請求を満額で足す／100件を超える売上・仕入が合計から落ちる）は #112 で、
**合計はサーバーが配分で出す**形にしました（画面が行を足さない）。

**3b. 出した見積を書き換えない** — ✅ **片づきました**（#112）。
「出した版・旧版は直せない」という決めごとが**画面の側にしかなく**、サーバーは
**中身の書き換えも明細の入れ替えも削除も受け付けて**いました（古いタブ・MCP・直接叩きで通る）。
あわせて**承認待ちの見積書が社外フォルダに入る**（置いた時点で送ったのと同じ）のと、
**見積段階の売上に入金・検収を記録できる**のも塞いでいます。

**4. 見積の承認** — ✅ **片づきました**（#107 / #108 / #109）。
決めごと2つ（`can_estimate = false` が読まれていない／限度を**送る人**の役割で見ていた＝
**上司が部下の上限超えを承認せずに送れた**）を効くようにし、**承認する画面**も作りました。
`approval_state = 'pending'` になった見積を承認する導線がクライアントに1つも無く、
**pending になった見積は誰も送れませんでした**（サーバーの `/approve` は正しく動いていた）。
案件と GPM の見積タブに同じ帯と「承認する」を出し（**承認できる人にだけ出す** —
判定はサーバーが `can_approve` で渡す）、⑤ 見積・請求に「承認待ち」の絞り込みを足しています。
⚠️ **GPM には承認の口そのものがありませんでした**ので、あわせて新設しました。

**5. 確定した記録が後から変わる** — ✅ **片づきました**（#113）。
**確定した週報**に後から行が足せた（ニュースの「週報へ送る」・MCP・直接叩き。画面だけが止めていた）／
**AI の再実行が確定した本文を書き換えた**／**終わった棚卸し**をスマホから書き換えられた／
**確かめていない AI の K/P/T が隔週キープの資料に載った**／
**受注にした瞬間に放送種別・媒体が消えた**（`changeStage` が `{}` で発番を呼ぶため）。
⚠️ **塞ぐだけにしないこと** — 確定した週報は戻す口がどこにも無かったので、
**「確定を解く」**をあわせて作りました（無いと「もう1行入れたい」で行き止まりになる）。
⚠️ **`published` だけで判断しないこと** — デイリーニュースは*閲覧型*で
`published` を「確定の操作が要らない種類」の印に使っており、種類で分けずに塞ぐと
**ニュースが1行も書けなくなります**。

**5b. 断り文が画面に届いていなかった** — ✅ **片づきました**（#113・**この作業中に見つけたもの**）。
`AppError` は `(状態, コード, 文)` の順ですが、**日常業務の 6 ファイル・35 か所が逆**でした。
`error.message` にコードが入るので、画面（`notifyApiError`）に出ていたのは
**`VALIDATION_ERROR` の6文字**だけ。**理由も直し方も一度も表示されていません**でした。
型はどちらも `string` なので、**型検査にも lint にも出ません**
（`shared/tests/recordIntegrity.test.ts` が server 全体を数えて止めます）。

**6. AI の指標と費用が信じられない** — ✅ **片づきました**（#114）。
会社方針「AI を使い捨てにしない」の**条件2（修正の差分）と条件3（成果）**が
実際には壊れていました。**直さずに承認した回が1件も記録されず**（受入率は永久に 0%）、
**AI が自分で直した分は人の修正として**数えられ（直すほど修正率が上がる）、
**投入口から作った議事録の直しが投入口の指標に混ざって**いました。
費用側も、**落ちた呼び出し**（軽いモデルのやり直し・議事録の失敗）が使用量に残らず、
**録りながらの下読みは 20 秒のはずが5分まるごと**を送っていました
（＝打合せの音声を丸ごと2回文字にしていた。画面には「費用を抑えるため」と出ている）。
⚠️ **「押せなくする」だけでは足りない** — 写真の縮小が終わる前に押せる問題は、
ボタンを `disabled` にしても**選んだのと同じ瞬間の押下は素通り**します
（実ブラウザで**添付 0 件で送られる**ことを実測）。**送る側が待つ**こと。

**7. プロジェクト管理が「開けるのに使えない」** — ✅ **片づきました**（#115）。
`gpm` だけの人は**依頼元を1件も選べず**（`/customers` は `sales` を要求する）
プロジェクトを作れませんでした。請求タブは**開いた瞬間に 403 で真っ白**、
しかも開けた人にも**月次請求が1つも出ません**でした（`isEstimateMode` を渡していたため）。
受注にしても **GLS-B が採られず、段の履歴も残りません**でした
（採る口は案件側にしかなく `sales` を要求するので、**採る手段が無い**）。

⚠️ **測り方の訂正（#115 で判明）。** 実ブラウザの検査で使っていた開発サーバーの
起動の仕方が**間違っていて、Tailwind が走っていませんでした**（`npx vite <dir>` を
リポジトリの根から実行すると PostCSS の設定が読まれない）。つまり
**v4.0.16〜18 の「横はみ出し 0px」は CSS が当たっていない画面で測ったもの**でした。
`npm run dev -w <アプリ>` で測り直した結果、**どの画面も横はみ出し 0px のまま**で
結論は変わりませんでしたが、当時それを言える根拠はありませんでした。
検査の script には**「`.flex` が本当に flex になっているか」を毎回確かめる行**を入れてあります。

**8. 設定したのに効かない支払期日 ／ 同じ引き合いから2件** — ✅ **片づきました**（#116）。
設定 ⑤ の「支払日が休業日のとき（前の営業日へ／次の営業日へ／寄せない）」は
**どこからも読まれておらず**、日曜のままの期日が入っていました。
⚠️ **さらに `computeDueDate` を呼んでいる場所が1つもありませんでした** —
下見の画面が使うだけで、**保存される行の支払期日はずっと空**です
（つまり締め日も支払日も、設定しても台帳には入っていませんでした）。
案件の二重登録は、**同じ瞬間に2回押すと2回とも通る**形でした
（`disabled` は描き直し1回ぶん遅れる）。**DB の一意索引で止め、
先に出来たほうを返します**（エラーにすると、出来ているのにもう一度作られる）。

**これで ❓ の P1 は残っていません。**（この時点で残っていたのは 69 件・すべて P2）

**9. 黙って切れる・古い結果が出る** — ✅ **片づきました**（#122）。
**切れた側には何も出ません。** 見積・請求の一覧は 300 件で切っているのに
**画面が並んだ行を数え、並んだ行を足して**いたので、**388 件 47,850,000 円 のところ
「300 件 4,136,000 円」**と出ていました（月末に突き合わせるまで気づけません）。
BOX は1回に 100 件しか返さないのに1回しか呼んでおらず、**101 個目からのファイルと
写真は一度も画面に出ていません**でした（置いた人には「上げたのに無い」と見えるので、
**同じファイルがもう一度上がります**）。スマホの案件一覧には**前へ／次へが1つも無く**、
21 件目以降を開けませんでした。打合せの録音は**手元の 50 件の中だけ**を絞っていたので、
51 件目の案件は名前を打っても出てきません。⌘K の窓は、**打ち替えた直後に
古い言葉の結果が並んだまま**で、そこで Enter を押すと関係ないものが開きます
（番号を振る守りは「遅れて届いた結果で上書きしない」ためのもので、
**打ち替えた瞬間に前の結果を消しはしません**）。
❓ のうち **3件はすでに直っていました**（SearchPage の2件と、
打合せの録音の「文字起こしが使えない環境でも録音を始められる」）。
読んだだけの行なので、**1件ずつコードで当たり直して**確かめています。

**10. 数字が嘘になる・記録が別のものに付く** — ✅ **片づきました**（#123）。
**それらしい数字が出る**ので誰も報告しません。やり取りの件数は**どの案件も「20件」**
（引いているのが 20 件まで・実データは 46 件）、「次にやること」にぶら下がる **①②③ は
概要から丸ごと消え**（数も出ないので**やることは1つ**に見える）、**`-10万円` の
マイナスは印として食われ**（符号が逆の金額が出る）、**鉤括弧で始まる文があとの行を
全部飲み込み**、**別の拠点の同じ名前の部屋が1つ消え**、AI の成果は
**`SUM(DISTINCT 金額)`** で**同じ金額の案件を1件に潰して**いました（50万円が3件で 50万円）。
短くできなかった印は、**引いてから失敗するまでに直された本文**に付き、
その本文は**二度と短くされません**でした。

⚠️ **#87（変換後も想定金額が古いまま）は、想定金額を上書きしないことにしました。**
`expected_amount` は**起票のときの見込み**で、AI の成果はそれと実績を比べるための値です。
受注のたびに上書きすると**比べる相手そのものが消えます**。代わりに**数えるほう**を直し、
**確定売上があればそれで数え、見込みで数えた件数を添える**形にしました。

**いま残っている ❓ は 37 件で、すべて P2 です。**
