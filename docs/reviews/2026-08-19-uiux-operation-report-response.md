## 0. 総評

16項目中 **1件は既に解消済み**（営業活動記録のスヌーズ/先送り/完了操作）、**15件は現状も再現する**ことをコードから確認した。特に以下の3つは「表示だけの不具合」ではなく、**別々のクエリ・別々の集計ロジックが同じ言葉を名乗っている**ために起きている構造的な問題であり、優先度が高い。

1. **「見積金額」を名乗る2つの値が別物**: 概要タブの金額は見積が0件だと想定金額 (`expected_amount`) に無言でフォールバックする。ラベルを変えずに中身が入れ替わるため「見積はまだありません」との矛盾に見える。
2. **「機材点数」を名乗る2つの値が別集計**: ダッシュボードは子機材(付属品)を含む全件カウント、台帳一覧は子機材を除いたクライアント側フィルタ後件数。同じ言葉で違う母数を数えている。
3. **タスクの「カラム」と「タスクの有無」を混同**: カンバンは `task_columns` が0件なら中身を見ずに「まだカラムがありません」と表示する。タスクがあってもカラムが無ければ隠れて見える。

これらは表示コンポーネントの修正だけでは直らず、**「何を数えているか」の定義を1箇所にそろえる**必要がある。

## 2. 表示・情報の矛盾

### 2-1. 見積タブとデータ不一致 — **未解決 (要修正) → 対応済み**
- 概要タブの見積額は `project.estimate_amount`（`GET /projects/:id` が `ESTIMATE_AMOUNT_LATERAL` で算出）、見積タブは別エンドポイント `GET /projects/:id/estimates` から取得。計算ルール自体は同じ (束ごとの最新版・却下/差替除外) だが、**見積が0件のとき概要タブは `estimate_amount=0` を `isEstimate=false` として扱い、`expected_amount`（想定金額）に自動フォールバックする** (`OverviewTab.tsx:91-94`)。
- レポートの「¥4,160,000 と表示されるのに見積タブは0件」は、この想定金額へのフォールバックが起きているケースだと推定される。**ラベル「見積」のまま中身が想定金額にすり替わっている**のが根本原因。
- **改善案**: 見積0件時は「見積」ラベルではなく「想定金額（見積未確定）」等、値の出自が分かるラベルに変える。もしくは見積0件時は概要タブでも「見積はまだありません」に統一し、想定金額は別行で表示する。

### 2-2. タスクのカンバン表示が実態と合わない — **未解決 (要修正) → 対応済み**
- `KanbanView.tsx:125` の `noColumns = columns.length === 0` は**タスクの有無を見ずにカラムの有無だけ**で空表示を出す。進捗帯 (`TasksTab.tsx` の `HealthStrip`) はタスク全件を別クエリで数えるため、「0%（0/3）」等の実数とカンバンの空表示が両立してしまう。
- さらにカラムが存在していても `getTasksByColumn` は `column_id` の完全一致でしか振り分けないため (`KanbanView.tsx:55-58`)、未割り当てタスク (`column_id === null`) はどのカラムにも表示されない。リスト表示だけがこれを「未割り当て」グループとして明示する。
- **改善案**: カラムが0件でもタスクが1件以上あれば「未割り当てタスクが○件あります」+「リスト表示で見る」導線を出す。カンバンにも常時「未割り当て」列を用意し、リストと表示件数が一致するようにする。

### 2-3. 機材点数の不一致 — **未解決 (要修正) → 対応済み**
- ダッシュボード `total_items`（`stats.service.ts:27-29`）は `parent_id` 条件なしの `COUNT(*)`＝子機材(付属品)込み・全ステータス込み。
- 台帳一覧の「機材 ◯点」（`ItemsToolbar.tsx:36-38`）は `include_children` 未指定時は `parent_id IS NULL`（子機材除外）で全件取得し、**サーバーのページネーションtotalではなくクライアント側フィルタ後配列の `.length`** を数えている。
- **改善案**: 「機材点数」の定義（子機材を含むか、対象ステータス）を1箇所（サーバーの集計サービス）に集約し、ダッシュボード・台帳の両方がそこを参照する。表示ラベルに「(付属品含む)」等の注記を添えるだけでも矛盾感は緩和できる。

### 2-4. 「押さえている部屋」なのに「場所が未設定」 — **仕様として存在、文言改善の余地あり → 対応済み**
- `OverviewTab.tsx:341-363`: 予約 (`bookings`) が1件もなければ「押さえていません。」。予約はあるが部屋名も外現場メモも空の場合のみ、その行に限り「場所が未設定」（`venueLine()` が `null` を返すケース）。「押さえている部屋はあるが、場所の中身が未入力」という2つの独立した状態を意図的に書き分けている実装。
- **改善案**: 挙動自体は妥当だが、文言が「タイトル＝場所がある前提／行＝場所がない」で矛盾して読める。「押さえている部屋」というセクション見出しを「押さえている予定」に変える、または未設定行に「部屋を設定してください」という誘導リンクを添えると誤解が減る。

### 2-5. カレンダーの「期限が近い仮押さえ」に数ヶ月前の日付 — **未解決 (仕様として意図的) → 対応済み**
- `HoldListPage.tsx:59-65` は `to: until` のみを渡し `from` を渡さないため、過去日付の仮押さえも取得対象。`daysLeft`（`holdLogic.ts:30-38`）は超過日数を負値で返し、コードコメントで「超過した仮押さえが先頭に来る」ことを意図的な仕様としている。
- **改善案**: 実装意図（超過を埋もれさせない）は妥当だが、見出し「期限が近い仮押さえ」が超過分を含意していない。見出しを「仮押さえ（超過・期限順）」に変える、または「期限超過」と「期限が近い」を別セクションに分けて超過分を目立たせる方が実態に即す。

## 3. 回遊性・ナビゲーションの問題

### 3-1. 一覧画面で名称が読めない — **truncate + tooltipは既に実装済み、幅は可変**
- 案件一覧・ダッシュボード「動いている案件」・機材台帳の商品名列はいずれも共通部品 `RowMain`（`shared/src/client/ui/row.tsx:181-188`、`min-w-0 flex-1`）＋ `truncate`（`title`属性でフルテキストのツールチップあり）という設計で、**固定の狭い幅を割り当てているわけではなく、他の固定列を除いた残り全部を使う可変幅**になっている。
- それでもレポートで「サムラ…」のように短く切れて見えるのは、他の固定列（ステータス・金額・担当者等）の数が多い画面幅で残り幅が狭くなるため。
- **改善案**: 案件名・商品名にマウスホバー時のツールチップ表示があること自体をユーザーに気づかせる導線が弱い（`title`属性はブラウザ標準ツールチップのみで発見しづらい）。狭い画面では2行までの折り返し表示に切り替える、または列の優先順位を見直し名称列を最優先で確保する運用にする。

### 3-2. グローバル検索がセクションによって消える — **未解決 (機材管理は全画面で未実装) → 対応済み**
- ヘッダー枠組み (`AppTopbar`/`AppShell`) は `client`・`client-daily`・`client-equipment` の3アプリで共通 (`shared/src/client/shell/`) だが、検索ボックス本体 `GlobalSearch` は `client/` 固有実装であり shared 化されていない。
- `client-equipment/src/components/layout/AppShell.tsx:27-45` は `SharedAppShell` に `searchSlot` を渡していないため、**機材詳細画面だけでなく機材管理アプリの全画面**（ダッシュボード・台帳・ラック図含む）でヘッダー検索が非表示。`client-daily`（日常業務）も同様に未実装。
- 代わりにモバイル下タブ「探す」独自実装 (`SearchPage.tsx`) はあるが、PC向けヘッダー検索とは別コード・別UI。
- **改善案**: `GlobalSearch` を `shared/` へ移し、`client-equipment`/`client-daily` の `AppShell` にも `searchSlot` として差し込む。対象データ種別 (機材・ケーブル等) をアプリごとに切り替え可能にする。

### 3-3. 「Ctrl K」ショートカットが機能しない — **原因を特定 (2種類のバグ) → 対応済み**
- `client/` の `GlobalSearch.tsx:55-64` 自体は `document.addEventListener('keydown', …)` で Ctrl/Cmd+K を正しく拾い `preventDefault()` する実装になっており、単体では機能する。過去の既知バグ (#68 打ち替え直後の誤反応) も `results.q === q` 突合せで解消済み (`docs/reviews/codex-findings-v4.md:656-657`)。
- ただし **2つの実際の不具合**が現存する:
  1. **機材管理アプリには Ctrl+K のリスナー自体が存在しない**（3-2と同一原因）。そのためフォーカスのある入力欄（機材台帳の絞り込み欄など）に "k" がそのまま入力される — レポートの再現条件と完全に一致。
  2. **案件台帳のセル編集中は Ctrl+K が効かない**。`client/src/contexts/sales/pages/projectLedger/CellEditor.tsx:34-39` がキー種別を判定せず無条件で `e.stopPropagation()` するため、`document` レベルの `GlobalSearch` リスナーまでイベントが届かない。
- **改善案**: (1) は3-2の対応で自然に解消する。(2) は `CellEditor.tsx` の `stopPropagation()` を `Enter`/`Escape` の分岐後にのみ呼ぶよう修正すれば、他のキーは通常通り伝播しCtrl+Kも機能する。

### 3-4. 「案件管理」と「プロジェクト管理」の役割が紛らわしい — **未解決 (設計意図はコードにあるがUIに出ていない) → 対応済み**
- 案件管理ダッシュボード (`salesDashboard/`) とプロジェクト管理ダッシュボード (`gpm/pages/dashboard/`) は見た目の構成 (KPI帯＋Panelカード) は似ているが実装・データソースは完全に独立（`GLS-A`＝案件管理／`GLS-B`＝プロジェクト管理という `projects.gls_category` の区分がある）。設計判断は `GpmDashboardPage.tsx:1-17` のコメントと `client/CLAUDE.md` に記載済みだが、**画面上にはこの区分がどこにも説明されていない**。
- **改善案**: 両ダッシュボードのヘッダー付近に「案件管理＝受注前後の営業活動 (GLS-A)」「プロジェクト管理＝制作進行そのもの (GLS-B)」等、一言の説明ラベルまたは初回訪問時のツールチップを追加する。

## 4. UI/UXの問題

### 4-1. 通知が実質機能不全 — **未解決 → 対応済み**
- `shared/src/client-v4/NotificationBell.tsx:122-125` で未読99超は固定で「99+」。通知一覧 (152-181行) は種類別・案件別のグルーピングを一切行わず、`GET /notifications` の `items` をそのままフラットな時系列リストで表示。
- **改善案**: 同一案件・同一種別 (例: 未送付請求書) の通知は「○件」にまとめて折りたたむ。重要度 (支払期限超過など) を優先ソートし、既読済みは自動的に一覧から沈める。

### 4-2. 財務ダッシュボードの符号順 — **未解決 → 対応済み**
- `shared/src/client/ui/money.tsx:62`: `` {isNegative ? `-${currency}` : currency} `` で **マイナス記号→¥記号→数字** の順（`-¥1,234`）。レポートの指摘通りの表示が現行コードに存在する。
- **改善案**: `¥-1,234` ではなく赤字を色と括弧で示す会計表記（`▲¥1,234` または赤字色＋括弧 `(¥1,234)`）に変更し、符号の位置に依存しない誤読対策にする。

### 4-3. 開発者向け文言の露出 — **未解決 (2箇所とも現存) → 対応済み**
- 財務ダッシュボード: 「合計はサーバーが期間全体で数えたもので、内訳の足し算とは一致しません」が `BudgetDashboardPage.tsx:283` に実際に表示されている。
- サイドバー: `nav.ts:104-105` の `note: "v4 の並びをこれから決める画面です。いまのまま使えます。"` が `AppSideMenu.tsx:329` でそのまま描画されている（対象は現在「取引先マスター」1項目のみに縮小済み）。
- **改善案**: 両方ともユーザー向けの文言に書き換える。前者は「合計は台帳と時点がズレる場合があります。正確な内訳は台帳をご確認ください」程度に、後者は開発メモを削除し単に「取引先マスター」のみのラベルにする（1項目まで整理済みなので「そのほか」という括りの意味が既に薄い）。

### 4-4. 案件一覧のタブ集計 — **設計は意図的・妥当。表示の分かりやすさに改善余地 → 対応済み**
- `stages.ts:75-82`: 「すべて」は営業ステージ4種 (仮押さえ〜受注) のみを指し、終了・失注・ネタは含まれない。この設計はコード内コメントで明示されており、`totalAll` もチップの合算ではなく別集計で算出するなど意図的に矛盾なく作られている。
- レポート時点との違いとして、集計ロジック自体に矛盾は見当たらなかった。ただし初見のユーザーには「すべて」が全件を指さないことが伝わりにくい。
- **改善案**: 「すべて」チップに「(進行中)」等の補足を添える、またはツールチップで対象ステージを明示する。

## 5. 運用面

### 5-1. 営業活動記録のスヌーズ・先送り・完了 — **解消済み**
- `client/src/contexts/sales/pages/activityLog/useNextActionActions.ts` に「完了」（`POST /activity-logs/:id/complete-next-action`）と「延期」（明日／1週間、`POST /activity-logs/:id/postpone-next-action`）が実装済みで、`ActivityRows.tsx:63-70` から操作できる。コード内コメントによれば、この作り直しで一覧上から直接操作できるようにしたとのこと。レポート時点では未実装だったため、**この項目は既に解消されている**。
- 残る改善余地: 延期は「明日」「1週間」の2択のみで任意日付選択が無い。運用上不足があれば任意日付ピッカーの追加を検討。

### 5-2. 週報が「未確認」のまま止まる — **未解決 (仕組みが存在しない) → 対応済み（確認ボタン＋督促通知）**
- 週報 (`weekly_activity`) は「確定する (publish)」と同時にしか `reviewed_at` が打刻されず、確定しない限り恒久的に未確認状態になる。一覧 (`WeekRail`) は確認状態に関係なく直近50週分をすべて表示し続ける。
- リマインド・自動エスカレーションの仕組みはスケジューラのジョブ一覧 (`scheduler.service.ts:408-422`) に存在しない（タスク期限・入金督促・機材返却等は既にあるのに、週報だけ無い）。
- 独立した「確認済みにする」操作 (`useReviewReport`) は実装済みだが、日常業務のデイリーニュース報告画面でのみ使われており、週報画面 (`WeeklyDetailPage.tsx` 等) では呼ばれていない。
- **改善案**:
  1. 週報にもデイリーニュースと同じ「確認済みにする」ボタンを追加する（実装済みのAPIを繋ぐだけで済む）。
  2. 未確定のまま一定期間 (例: 2週間) 経過した週報を担当者・上長にリマインドするジョブを `scheduler.service.ts` に追加する。
  3. ホームの「未確認」バッジは最新1件のみが対象になっており、過去の積み残しが可視化されない。積み残し件数を表示するよう改善する。
