# メール自動仕分けの棚卸し（2026-09-06）

> **種類**: 実施済みの記録
> **状態**: 現役の基礎資料。`.claude/skills/mail-intake/`（`SKILL.md`・`references/decision-table.md`）が決定表の根拠として参照する。§6「まだ確かめていないこと」3件（検証環境での実取込・添付 PDF の BOX 格納・書き込み結果）は未確認のまま
> **最終確認**: 2026-09-08（v4.6.10）

Gmail（`terai-takehiro@gmo-globalstudio.com` の受信箱）を **2026-08-06〜2026-09-06 の1か月**
実際に読んで、どういう種類のメールが来ていて、そのうち何が ONAiR に入っていて、
何が入っていないかを数えたもの。

調査は Gmail MCP（`search_threads` / `get_thread` で**本文まで**）と
ONAiR MCP（`list_inquiries` / `list_finance_docs` / `list_inview_attendees` /
`get_ai_feedback_digest`）の両側から突き合わせている。
サンプルは重複排除後 **615通**（GitHub 通知を除く。日付4日ごとの窓×各50スレッドの上限あり）。
件数を「◯件」と書いたものは **Gmail の検索件数（スレッド単位・`in:anywhere`）で実測した値**。

## 結論

1. **入口（Gmail）と出口（ONAiR）の量が桁で合っていない。** 内覧会の予約だけが回っていて
   （`inview_attendees` 85件）、それ以外はほぼ落ちている。
   **`finance_docs` は開設以来 0 件**、`misc_inquiries` は**全期間で 7 件・うち AI 起票 5 件が全部「見送り」**
   （`get_ai_feedback_digest(inquiry_intake)` の見送り率 **100%**）。
2. **落ちている理由は「拾いすぎ」ではなく「拾えていない」。** digest の助言は
   「拾いすぎている」と出るが、母数が5件しかないので**この助言自体が当てにならない**。
   実際には Kairos3 の**資料ダウンロード通知 21件のうち 17件が未処理**で、
   その中に「GMOサムライスタジオの利用を検討しているため」と書いた**明確な見込み客**が含まれていた。
3. **仕分けの単位が「メール1通」になっていて、宛先（メーリングリスト）を使っていない。**
   `sales@` / `info@` / `member@` / `order@` / `account@` / `facility@gmo.jp` / `nasa-contact@gmo.jp` は
   **その時点で用途がほぼ確定する**ので、まず宛先で束ねてから中身を読むべき。

本文は**固定フォーマット**で、`[ラベル]\n値` の繰り返し。抽出できる項目は共通で

`[NEW]` が付いている値は Kairos3 側で**新規**の意味なので、初回接触の判定に使える。
末尾の `※このメールは、登録通知ルール｢…｣による登録通知メールです。` の**ルール名**が
フォーム種別の一番確実な手がかり（問い合わせは `【要対応】問合せフォーム登録`、資料DLは `資料ダウンロード`）。

- お問い合わせ: `お問い合わせ対象の会場` / `お問い合わせ種別`（例「空き状況の確認」）/ `お問い合わせ内容`（自由文・**ここに要件・日程・人数・予算が入る**）/ `このサイトへお越しいただいたきっかけ`

## 4. 「AIを使い捨てにしない」5条件の充足表

対象は**メール取込全体**（Gmail 読み取り → 判定 → ONAiR MCP push）。

| # | 条件 | 判定 | 中身 |
|---|---|---|---|
| 1 | AI出力の記録 | **△** | `record_inquiry` / `record_finance_doc` は `ai_outputs` に引数全文を残す（v4・migration 160）。**`create_activity_log` と `register_inview_attendee` は `recordAiOutput` を呼んでいない**（`onair-current-state.md` の残件5）。**さらに「取り込まなかった」判断がどこにも残らない** — 落としたメールの記録が無いので、取りこぼしを後から数えられない |
| 2 | 人間の修正差分 | **△** | 画面で直すと `ai_corrections` に自動で入る（7日窓）。ただし**母数が5件**しかなく、実測値として使えない |
| 3 | 顧客反応・成果 | **△** | `state`（チケット/案件/ストック/見送り）が成果の代理。**いま全部 dropped なので、指標としては死んでいる** |
| 4 | 改善への還流 | **△** | `get_ai_feedback_digest(inquiry_intake)` はあり、スキルに「取り込む前に1回読む」手順を足す話も書いてある。**が、母数不足で助言が「拾いすぎ」に固定されており、読ませると逆効果** |
| 5 | レビュー頻度と担当 | **✕** | メール取込については未定（digest 全体としては「月1回・営業のマネージャー」だが、取込の見直し担当は決まっていない） |

**穴に対する代替案（できないで止めない）**

- **条件1の穴「落とした判断が残らない」** → 全文を残す必要はない。
  **1日1行の取込ログ**（走査した通数 / 種別ごとの件数 / 取り込んだ件数 / 落とした件数と代表件名10本）を
  `ops_reports` の `kind='mail_intake'` に置く。`kind` に CHECK 制約が無いので migration 不要。
  これだけで**取りこぼし率が測れるようになる**。
- **条件2の母数不足** → 差分を待たずに、**Gmail のラベルを弱い正解ラベルとして使う**。
  `studio-intake-done` / `inview-reg-done` が付いていないのに人間が返信しているスレッドは
  「AI が取りこぼした」の代理指標になる。
- **条件3が dropped 一色** → 「見送り」と「ストック」の意味が現場に伝わっていない疑いが強い。
  仕分け画面の文言確認を先にやる。指標としては当面
  **「取り込んだ件のうち、人間がその後メールで返信したもの」**を成果の代理に使う。
- **条件4の逆向きループ** → digest の助言は**母数が20件を下回る間は出さない**（または
  「母数不足のため判断しない」と返す）ようにする。いまの実装は5件で「拾いすぎ」と断言してしまう。
- **条件5** → 取込ログ（上記）を**週1回・営業のマネージャー**が見る。
  見送り率ではなく**取りこぼし率**を見る。

**リスク（必ず踏むもの）**: 「見送り率」を精度の指標として読むと、
**拾わなくなるほど数字が良くなる**。いまの `inquiry_intake` はまさにその状態で、
見送り率100%＝「拾いすぎ」という助言が出ている。
**分母を「受信した業務メール」側に置き換えない限り、この指標は改善の役に立たない。**

## 6. 試験実行（2026-09-06・読み取りのみ）

PR #595 / #596 をマージしたあと、**ルーティンの検索式をそのまま実際の受信箱に当てて**、
拾いすぎ／拾えなさすぎを測った。⚠️ **ONAiR への書き込みは1件も行っていない**
（この会話に繋がっている GMO ONAiR の MCP コネクタは**本番 `gmo-onair.jp` を指している**ため。
`list_users` が実在の社員を返し、検証環境のシードは `admin@onair.local` /
`sato@globalstudio.example.com` なので区別できる）。**検証環境で実際に取り込むには、
`dev.gmo-onair.jp/api/v1/mcp` を指すコネクタが要る。**

### 分かったこと

| # | 何が起きるか | 直したもの |
|---|---|---|
| 1 | **枠が通知に食い潰される。** ルーティンの検索式そのままで3日窓に **201スレッド**。新しい順40件のうち **`notifications@github.com` が33件・`dmarc-report@` が2件（87.5%）**。GitHub は開発中1日25通以上出るので、**30通/回の枠は毎回 GitHub の通知だけで尽きる**（決定表 #1 は「拾ってから捨てる」なので、ラベルでは間に合わない — 印を付けても翌日また同じだけ届く） | 検索式に `-from:` を4つ追加（**201 → 54**）。決定表に #0 として「ここに来たら検索式が壊れている」を明記 |
