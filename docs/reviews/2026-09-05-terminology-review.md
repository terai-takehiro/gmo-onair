## 1. 結論

### 1-1. ご指摘は当たっている。ただし主犯は別にいる

「噛み砕きすぎ」（以下 **B**）は実在し、約 **40件** 見つかった。
ただし全画面を数えたうえで言うと、**実害の大きさでは B は3番目**で、順位はこうなる。

| 順位 | 症状 | 件数の目安 | なぜ効くか |
|---|---|---|---|
| **1位** | **C: 同じものを別の名前で呼んでいる** | **約 60 概念**（表記は2〜4通り） | 画面を移るたびに「これは同じもの？」と考える。**覚えたことが次の画面で使えない** |
| **2位** | **D: 噛み砕いた語が別の語とぶつかった／内部の言葉が漏れた** | 約 35 件 | 誤解して操作する。誤誘導が起きる |
| 3位 | **B: 名前の場所に説明文を置いた** | 約 40 件 | 長くて読み飛ばす・口頭で言えない・検索できない |

**「分かりにくい」の体感の正体は、たぶん B ではなく C です。**
たとえば `reader / editor / manager` の3段は、いま画面上に**3系統**あります。

| 出どころ | reader | editor | manager |
|---|---|---|---|
| `shared/src/client/states/NoPermissionPanel.tsx:25-27`（権限が無い画面） | 見るだけ | **書ける** | **任せる** |
| `client/src/contexts/platform/pages/members/moduleLabels.ts:74-77`（設定＞権限） | 見るだけ | **直せる** | **管理** |
| `docs/wording.md:96`（決めごと） | 見るだけ | 書ける | 任せる |
| `client/src/contexts/platform/AuthContext.tsx:29-31`（死んだ定数） | 閲覧 | 編集 | 管理 |

同じ人が同じ日に「あなたは**書ける**権限が要ります」と言われ、設定画面では「**直せる**」を選ぶ。
これは平易化の失敗ではなく、**平易化を全画面に当てきっていない**ことの失敗です。

### 1-2. 外部SaaSの答え合わせ

Salesforce / Slack / Outlook / Google カレンダー / kintone / Asana / freee / マネーフォワードの
日本語UIを調べた結果、**用語を残すか開くかの線は「難しさ」では引かれていませんでした。**

| 種類 | 各社の扱い | 実例 |
|---|---|---|
| **概念・構造物** | **カタカナ／専門語のまま残す** | Salesforce「**フェーズ**」「**確度**」「**パイプライン**」「リード」、Slack「チャンネル」「スレッド」、Asana「セクション」 |
| **人・日付・状態** | **和語に開く** | Salesforce「取引先責任者」「完了予定日」「活動」、Outlook「出席者」「予定表」、kintone「未処理／処理中／完了」 |
| **単独で意味が立たない語** | **語を足して開く** | Outlook `Rules` → 「**仕分け**ルール」、Slack `Huddle` → 「ハドル**ミーティング**」、Salesforce `Contact` → 「取引先**責任者**」 |
| **社外・帳簿・法令に出る語** | **絶対に残す** | マネーフォワードは「仕訳」「補助科目」を維持 |

**ONAiR はこの線をちょうど逆に引いています。**
概念（按分・パイプライン・ステージ）を開き、状態と動詞（確定・押さえる・任せる）は放置している。
だから「専門語は残っているのに、覚えるべき名前が長くて覚えられない」という体感になります。

なお「専門用語を残すほうが正しい場合がある」ことには、UX研究の裏付けもあります
（NN/g *Use Specialized Language for Specialized Audiences*、*Writing Digital Copy for Domain Experts*:
専門家に基本語を説明し直すと「自分向けの文章ではない」と読まれる。
*Use Old Words When Writing for Findability*: 造語は**そもそも検索されない**）。

### 1-3. いちばん大事な1行

> **名前は短く固定する。説明は名前の下に置く。**

B判定 40件のうち **32件はこれだけで解ける**（ラベルを短くし、いまラベルに入っている説明文を
副題・ヒント・ツールチップに落とすだけ。文言そのものは既に書けている）。

## 2. 用語を決めるときの判断基準（提案）

`docs/wording.md` の「5つのルール」は良い規範ですが、**「開く／残す」の基準が無い**ため、
現場では「とにかく開く」に倒れています。次の3条件を追加することを提案します。

### ルール6: 開くかどうかは「画面の外で通用するか」で決める

| 条件 | 判定 | ONAiR での該当 |
|---|---|---|
| **社外・帳簿・請求・契約・法令に出てくる** | **残す** | 按分・検収・販管費・限界利益・売上総利益・税区分・適格事業者・役務提供完了日・GLS番号 |
| **業界標準語で、他社ツール・書籍・転職先でも同じ語** | **残す** | ステージ・パイプライン・確度・ガント・カンバン・ランダウン・プロンプター・香盤・尺・稿・押し／巻き・TAKE／PVW・ラック・U位置 |
| **ONAiR の中でしか意味を持たない機能名・状態・操作** | **開く** | 未仕分け・今日さばくもの・見るだけ／書ける・仮押さえ |
| **単独では何のことか分からない** | **語を足す**（開くのではなく） | 「ルール」→「貸出のルール」、「レイヤー」→「出すもの」 |

### ルール7: ラベルは12文字まで。それを超えたら副題に落とす

現状の違反例（いずれもラベル本体）:
- 「費用を分け合うグループ」（11文字・左メニュー）
- 「アーカイブする（一覧から隠す。消えません）」（21文字・ボタンのツールチップ）
- 「売上・請求への登録を取り消して見積もりに戻す」（22文字・ボタン）
- 「先行タスク（これが終わってから着手する）」（19文字・入力欄のラベル）
- 「あとから足された機材を取り込む」（15文字・ボタン）
- 「まだ持ち出さない（出庫の予定として登録する）」（21文字・トグル）

### ルール8: 動詞は1組に固定する

いま画面上に**和語系と標準語系の2系統**が並走しています（全アプリ実測）。

| 操作 | 和語系 | 標準語系 | 判断 |
|---|---|---|---|
| 追加 | 足す（13） | 追加（31） | どちらかに決める |
| 編集 | 直す（16） | 編集（11） | 〃 |
| 削除 | 消す（2 / sales は21） | 削除（11） | 〃 |
| 中断 | やめる（63） | キャンセル（27） | **外部SaaSは「キャンセル」で固定**（Apple HIG・SmartHR）。ただし社内で「やめる」が定着しているなら「やめる」でよい。**両方あるのが最悪** |
| 表示 | 出す（14） | 表示（27） | どちらかに決める |
| 失敗の文 | 〜できませんでした（45） | 〜に失敗しました（11） | 「〜できませんでした」＋次の一手 |

**分岐は「v4 で作り直した画面か否か」とほぼ一致します。** つまり作業の切れ目がそのまま
語彙の切れ目になっており、利用者から見ると理由なく言葉が変わります。

### P4: アプリ名（全体設計に効くので別枠）

命名の流儀が**4つ混在**しています。

| 流儀 | 該当 | 評価 |

| ① 対象＋管理 | 案件管理・機材管理・財務管理・プロジェクト管理 | 予測できる。**これを基準形にすべき** |

| アプリ | 判定 | 所見 |
|---|---|---|
| 案件管理 / 財務管理 / 機材管理 / 設定 | **A** | 名前と中身が一致。基準形 |
| **プロジェクト管理** | **D** | 「案件管理」と日本語として同義。新しい人はどちらを開くか判断できない（区別 GLS-A/B は画面に出ない）。→ 対象を名前に（例「社内プロジェクト」「グループ受託」） |
| **制作技術支援** | **D** | 部署名。中身は7つのミニアプリなのに、説明「台本づくりと本番進行 (Qシート)」は**うち1つしか説明しておらず**、かつ「Qシートは内部識別子のみ」という自分の決めごとに反する |

| リアルタイムCG | C | 後継が techops 内で「テロップCG」。同じ能力に2つの名前が同時に存在 |

## 4. 文型の統一案（全アプリ共通）

外部SaaS調査と、既にリポジトリ内にある良い実装（`shared/.../ErrorPanel.tsx` の `humanizeError()`）を
合わせた型です。**これは既にあるものを全アプリに広げるだけです。**

### ボタン
```
実行系  : 動詞を1組に固定（足す／直す／消す／保存する／取り消す）
中断    : 「やめる」に一本化（いま やめる63 / キャンセル27 で並走）
進行中  : 「動詞＋中…」（三点リーダは …）
```
※ Apple HIG・SmartHR Design System は「キャンセル」で固定を推奨。社内定着を優先するなら
「やめる」でよいが、**両方あるのが最悪**という点だけは動かない。

### エラー（正は `ErrorPanel`。原因1文＋次の一手1文）
```
〈対象〉を〈動詞〉できませんでした。〈次の一手〉。
✕ 共有URLの発行に失敗しました
○ 共有URLを作れませんでした。もう一度お試しください。
```
techops / live には「◯◯に失敗しました」1行が**約30か所**残っている。

### 空状態（2型だけにする）
```
型A まだ0件 : まだ〈対象〉がありません。〈〜すると、ここに出ます〉。[ 〈対象〉を足す ]
型B 絞込0件 : 条件に合う〈対象〉はありません。〈条件を変えてお試しください〉。
```
`shared/.../EmptyState.tsx:19` の既定値「データがありません」は**廃止し `title` を必須にする**
（渡し忘れると `wording.md` が名指しで禁止した文が出る）。

### 権限（正は `NoPermissionPanel`）
```
必要なのは〈アプリ名〉の「〈レベル〉」です。
```
techops / live の「管理者権限」「編集権限」「管理レベル」をこの型に寄せるだけで、
**誤誘導7か所が同時に消える**。今回いちばん費用対効果が高い1本。

`pcOnlyScreens.ts` が「配信卓・OBS に固定して使う運用画面」と宣言しているとおり、
**制作技術者が本番中に見る画面**です。ここで語を開くと ① 現場の口頭指示と画面がずれ、
② 区別が消えて事故る（TAKE と PVW を両方「出す」にはできない）。

## 6. 併せて分かった構造的な問題

### 6-1. `docs/wording.md` の決めごとと実装が乖離している

決めたのに直っていない／逆になっているもの:

| `wording.md` の決定 | 実装の現状 |
|---|---|
| AI起票/AI取込/AI登録 → **AI作成に統一** | **8通りが現存** |

| 按分グループ → 費用を分け合う案件のまとまり | 「按分グループ」が14か所で現存（＝**言い換えが中途半端に効いて2語になった**） |

## 7. 進め方の提案

用語の一括置換は**全画面に効く**ので、まとめて1本の大きな PR にすると検証できません。
次の順で、独立して出せる単位に切ることを提案します。

| 段 | 内容 | 効き方 |
|---|---|---|
| **1** | **権限3段の統一**（4系統 → 1系統）＋ `NoPermissionPanel` の型に寄せる | 誤誘導7か所が消える。`shared` 1ファイル＋各アプリの数か所で済む |
| **2** | **P0 の誤り10件**（矛盾する脚注・壊れた文・別項目の名前・陳腐化したマニュアル2本） | 実害の除去。互いに独立していてレビューしやすい |
| **3** | **P1 の禁止語**＋`check-ui-tokens.mjs` の baseline を減らす（新規追加を止める） | 再発防止。**ここを先にやらないと以降が漏れる** |
| **4** | **文型の統一**（空状態2型・エラー1型・三点リーダ・動詞1組） | 機械的に当てられる。`EmptyState` の既定値廃止を含む |
| **5** | **P2 のラベル短縮**（ラベル→副題への移動 32件） | ご指摘の本体。文言は既に書けているので移すだけ |
| **6** | **P3 の揺れ統一**（用語対照表を1枚作り、未改修画面に当てる） | 件数最大。表さえ作れば分割して進められる |
| **7** | **アプリ名の再設計**（特に「制作支援」は公開前に必須） | 合意形成が要るので最後 |
| **8** | `docs/wording.md` に**ルール6〜8（開く／残すの基準・12文字・動詞1組）を追記**し、言い換え表を実装に合わせて更新 | 決めごとと実装の乖離を止める |

**段1〜4だけでも「分かりにくい」の体感はかなり変わるはずです。**
ご指摘の B（噛み砕きすぎ）は段5ですが、実は段1〜3のほうが先に効きます。
