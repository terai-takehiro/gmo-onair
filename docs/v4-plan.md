# GMO ONAiR v4.0 開発プラン

## 大前提 — モックが v4 の基準（2026-08-07 決定・他のすべてに優先する）

**`docs/design/v4/mockups/` のモックが v4 の正です。** 実装・過去の決めごと・用語ルール・
検査スクリプトのいずれかがモックと食い違ったら、**モックに合わせるのが既定**です。

> v3 までは増築の連続で、分かりにくいところや機能していない機能が残りました。
> **v4 はそれを体系的に整理し直すための版**です。モックはその整理の結果なので、
> 「いまの実装がこうだから」「前にこう決めたから」はモックを曲げる理由になりません。

### この原則から出る運用

| 状況 | どうするか |
| --- | --- |
| 実装がモックと違う | **モックに合わせる**。理由が「既存がそうだから」なら議論の余地なし |
| 過去のルール（用語・色・情報設計）がモックと衝突 | **ルールのほうを直す**（`docs/wording.md`・`scripts/check-ui-tokens.mjs` を書き換える） |
| モックの項目に対応する DB 列が無い | **列を足す**。画面から落とすのは最後の手段 |
| モックの機能に対応するサーバー実装が無い | **作る**。「押しても何も起きない」を避けるために出さない、で止めない |
| モックどおりにすると**実害**が出る | **そこだけ指摘して止める**（下記） |

### 「実害」として止めてよいのは次の4種類だけ

1. **人・物・お金が実際に間違う** — 違う部屋のカードを渡す、会計の番号が二重になる、本番の外部サービスに実物ができる
2. **既存データが壊れる・消える** — 移行できない列の削除、上書き保存で履歴が消える
3. **他の画面の数字が黙って変わる** — 集計の前提を変えると読んでいる側が全部ずれる（`revenues` の前例）
4. **凍結4アプリに影響が出る** — 見た目・URL を1バイトも変えない約束

**上記に当たらない「そう決めたから」「そのほうが親切だと思ったから」は理由になりません。**
判断が分かれたものは `docs/v4-mock-deviations.md` に**残さず、モックに合わせて消す**こと。

## Part 0 — Git のかたち（ご質問への回答）

### 「最終的に master ブランチに統合」は不要です

`master` は**古い名前**です。2020年に GitHub と Git コミュニティが既定のブランチ名を `main` に変えました。
いま新しく作られるリポジトリはすべて `main` です。

そして **このリポジトリは既に `main` 一本の運用になっています**（`docs/branching.md`）。
ご希望の「一般的な形」はすでに達成されているので、`master` は作りません。

```
                          ┌── PR（検査が通らないとマージできない）
                          │
 feature/xxx  ●───●───●───┤
             ╱            ▼
main ───────●─────────────●──────────●──────────────●────────►
                          │                        │
                          ▼                        ● タグ v4.0.0 を Release 公開
              ┌─────────────────────┐               │
              │ 検証 dev.gmo-onair.jp│               ▼
              │ （main にマージで自動）│      ┌──────────────┐
              └─────────────────────┘      │ 本番 gmo-onair.jp │
                                           └──────────────┘
```

**いちばん大事な点: `main` は本番ではありません。** 本番は「最後に Release を公開したタグ」が指すコードです。
だから **作りかけの v4 を `main` に入れても本番のお客様には何も起きません**。
これが「全部そろえて v4.0.0 を一度に」を安全に選べる理由です。

### 「アプリ・機能単位でブランチを切る」— やり方

ご希望どおりにできます。ただし**ブランチは短命**にします。放置された `claude/*` ブランチが40本溜まって
どれが生きているか誰にも分からなくなったのが、いまの運用を作り直した直接のきっかけです。

| 表したいこと | 使うもの | 寿命 |
| --- | --- | --- |
| アプリ全体のまとまり | **Milestone** ＋ 親 Issue | 数週間〜数か月 |
| アプリの分類 | **ラベル** `area:equipment` など | ずっと |
| 1つの作業（例: 機材台帳の一覧を v4 に） | **ブランチ ＋ PR** | 数日 |

```
feature/201-v4-shell-topbar          ← 共通の土台
feature/214-v4-equipment-ledger      ← 機材管理 / 機材台帳
feature/215-v4-equipment-rack        ← 機材管理 / ラック図
fix/220-v4-money-alignment           ← 金額表記の直し
```

> **なぜ「長生きする v4 ブランチ」を作らないのか**
> 数か月ぶんの変更を1本に溜めると、最後のマージで「何十ファイルもの衝突」と「一度も検証していない巨大な差分」が
> 同時に来ます。共同編集では他の人の作業も全部そこに集まるため、事故の原因を切り分けられません。
> 一般的な現代の作法（GitHub Flow / trunk-based development）は
> **小さく `main` に入れ続けて、出す時期だけタグで決める**やり方です。

## Part 2 — 「打ち返し」と「トークン」を極限まで減らす仕組み

### 診断: 打ち返しの原因はデプロイの粒度ではありません

「デプロイしてからバグが見つかり、数回やり直す」の原因を追いました。**手元で確かめる道が塞がっています。**

| 打ち返しが起きる場所 | いまの状態 | 対策 |
| --- | --- | --- |
| 手元でDBを立てて動かす | `npm run verify:up` が **npm script から消えている**（`scripts/dev-verify/up.sh` はある） | Phase 0-4 で復活（**4秒**で立つ） |
| 触ったアプリだけビルドする | `scripts/build-changed.mjs` が**放置**（全部だと2分） | Phase 0-4 で復活 |
| 見た目の崩れ（桁ずれ・はみ出し） | `verify-ui.mjs`（実ブラウザで10項目を実測）が**放置** | Phase 1 の G4 で復活 |
| 計算の間違い（金額の丸めなど） | **テストが1本もない** | Phase 1 の G5 で土台の計算だけ |
| ブランチ単位で検証環境に出す | **Preview ワークフローで既にできる**（気づかれていない） | 今すぐ使える |

**順番を変えるのが一番効きます。**

```
いま  : main にマージ → 検証環境 → 見てもらう → バグ → 直す → 再マージ …
これから: 手元で通す → Preview でブランチだけ検証環境に出す → 見てもらう → OK なら main にマージ
```

後者なら直す作業が**ブランチの中**で終わります。`main` が汚れず、1往復のコストも
「push→CI待ち→デプロイ待ち→報告→ログ読み」から「手元で数十秒」に縮みます。

### デプロイの分割はしません（理由）

- **ビルドの差分化はすでに効いています。** `Dockerfile` は7アプリ別のステージに分かれており、
  変わっていないアプリのビルドはスキップされます。
- 残るコストは `shared/` を触ったときの全アプリ再ビルドで、これはアプリ別イメージに分割しても同じです。
- アプリ別イメージ（7イメージ＋nginx のアプリ別ルーティング＋7本のデプロイ経路）にすると
  インフラの複雑さが7倍になる一方、得られるのは1〜2分が数十秒になる程度です。**割に合いません。**
- **代わりに、v4 対象の3アプリだけをビルド対象にします**（下記 B-3）。これで実質的に「機能単位」になります。

### トークンを極限まで抑える構造（効果の大きい順）

#### A. 毎セッションの固定費を消す ← 桁が違う

| # | やること | 効果 |
| --- | --- | --- |
| **A-1** | **`CLAUDE.md` の変更履歴68万文字を `docs/version-history.md` に一本化** | `CLAUDE.md` は全体70.7万文字のうち **96%が変更履歴**で、**毎セッションの最初に自動で読み込まれます**（30〜50万トークン相当）。同じ内容が既に `docs/` にあるので情報は失われません。**これが最大の1手** |
| **A-2** | **アプリごとに `CLAUDE.md` を置く** | root には「共通ルール＋どこを読むかの索引」だけ（数千文字）。`client/CLAUDE.md`・`client-daily/CLAUDE.md`・`client-equipment/CLAUDE.md`・`shared/CLAUDE.md` に固有の決めごとを置き、**作業するディレクトリの分だけ読み込まれる**形にします |

#### B. 1回の作業で読む量を減らす（ファイル構造）

| # | やること | 効果 |
| --- | --- | --- |
| **B-3** | **凍結4アプリを開発コマンドの既定から外す**（`dev` / `typecheck` / `build` / `lint` を3アプリに。凍結分は `:frozen` 付きの別コマンドへ退避） | **34,209行が視界から消える。** ビルド・型チェック・CI 時間も約6割に |

#### C. 往復を減らす

## Part 3 — 「どの機能にどういう修正を加えたか」を残す

**いまの設定でほぼ達成できています。** `main` は **Squash merge が強制**されているので、
**1 Issue = 1ブランチ = 1 PR = `main` 上の1コミット**になります。決めるのは **PR タイトルの型だけ**です。

```
種類(アプリ): 何をしたか

feat(equipment): 機材台帳を v4 の見た目にした
fix(finance):    金額の桁がずれていたのを直した
chore(shared):   設計トークンを v4 の値に差し替えた
docs:            ブランチ運用の説明を実際の運用に合わせた
```

- **種類**: `feat` 足した ／ `fix` 直した ／ `chore` 設定・雑務 ／ `docs` 文書 ／ `refactor` 作り替え（動きは同じ）
- **アプリ**: `projects` `finance` `schedule` `settings` `gpm` `equipment` `daily` `shell` `shared`

| 知りたいこと | 打つもの |
| --- | --- |
| v3.2.2 から v4.0.0 までの全変更 | `git log --oneline v3.2.2..v4.0.0` |
| 機材管理に加えた修正だけ | `git log --oneline --grep "(equipment)"` |
| ある画面がいつどの PR で変わったか | `git log --oneline -- <ファイル>` |
| リリースノート | GitHub が PR タイトルとラベルから自動生成 |

**新しい仕組みは要りません。**

## Phase 1 — 共通の土台（shared/）

対象画面すべてに効くので、**ここを固めないと後戻りが全画面分になります。**

### 大事な前提: ゼロからではありません

前回の刷新（v2.9.251〜v3.1.5）は v3.2.0 で**画面だけロールバック**されましたが、
コードは `origin/release/v3` に残っています。調べたところ、
**v4 のモックが要求している規律を実現する部品と、それを機械で強制する検査が、すでに作られていました。**

| `origin/release/v3` にあるもの（`main` には無い） | v4 のどの要求に対応するか |
| --- | --- |
| `ui/money.tsx`（`Money` / `MoneyCell`） | 「**￥を左端・数字を右端に分ける**」— まさにこの実装 |
| **`ui/tableBadge.tsx`（`TableBadge` ＋ 7段の固定幅）** | 「**バッジ・チップは固定幅の枠に入れる**」— まさにこの実装 |
| `ui/numbers.tsx`（`StatValue` / `Num` / `ManYen` / `PageTitle`） | KPI 数値と見出しの大きさを画面ごとにバラつかせない |
| `states/`（EmptyState / ErrorPanel / NoPermissionPanel / NotFoundPanel / Skeleton） | 空・エラー・権限なし・読み込み中の統一 |
| `ui/confirm.tsx`（`confirmAction`）／`notify.ts`＋`notifications/` | 「確認は条件を出してから」「トーストではなく消えないお知らせ帯」 |
| `base.css` | 高さ・字詰め（`palt`/`kern`）・印刷解除を1か所に集約 |

### 前回失敗した理由と、今回の絶対規則

前回は「**枠の作り替え**」と「**情報設計の変更**」を**同じ作業でやりました**。
情報設計が却下されたとき、**一緒に枠まで捨てられた**のがロールバックの正体です。

→ **今回は逆にします。まず今のメニュー項目・並び・ラベルをそのまま維持して枠だけ入れ替えます。**

## モックと既存基準の衝突（すべて決着済み）

調査中に、**モックの指定と既存の基準が正面から衝突する点**が見つかりました。全て処理方針が決まっています。

### ① 薄い文字色 `#9aa1ab` — **読ませる文字には使わない**（決定）

モックが「テキスト 薄」に指定している灰色は、**白背景でコントラスト 2.61:1**。
国際基準（WCAG AA）の本文 4.5:1 も、文字以外の要素の 3:1 も満たしません。
さらに**このリポジトリの既存の検査コードに「`#8b929c` は 3.08:1 しかなく AA を満たさないので使用禁止」と明記**されており、
`#9aa1ab` はそれよりさらに薄い色です。つまりモックのまま実装すると、自分たちの禁止ルールに違反します。

**方針**:
- `#9aa1ab` は `--fg-disabled` として登録し、**入力欄のヒント文字・押せない状態・アイコンの塗り**だけに使う
- **読ませる文字（表の補助情報・注記など）は一段濃い `#5d6470` に上げる**
- 検査の判定値（`verify-ui.mjs` の FAINT 閾値）は**下げない**
- モックと比べて補助文字がわずかに濃くなります（読みやすさを優先）

```bash
npm run verify:ui      # Playwright で実測
```
`verify:ui` が実際に見ている10項目（**v4 の規律とほぼ一致しているので、そのまま使えます**）:
横はみ出し 0px ／ JSエラー 0件 ／ 地の色が共通 ／ **書体が共通（LINE Seed JP）** ／ **字詰め（palt）** ／
シェルが画面いっぱい ／ 薄すぎる文字 0件 ／ ボタンの高さが決まった段のみ ／
**金額は¥と数字が別要素** ／ 見出しの大きさが1つ

v4 で足す検査（G3・G4）:
- **バッジの左端が列ごとに縦一直線か**（実ブラウザで座標を測る）
- **金額の右端が ±0.5px で揃っているか**
- **期間が1つの文字列になっていないか**（`〜` の手打ちが72か所）
- **LINE Seed JP に無い太さ（500/600等）が残っていないか**（957か所が対象）
- **スマホ375pxでタップ領域44px以上・下タブ3つ・主アクションが下端固定か**

これらは**静的な文字列検査では測れない**（座標が要る）ため、実ブラウザで測る `verify-ui` が本命です。

### 自動テストについて（いまゼロなので方針を決めます）
テストが1つもありません。73画面すべてに書くのは費用が見合わないので、**土台の計算だけ**に絞ります
（Phase 1 の G5・6ファイル・約40項目・2秒未満）。

| 対象 | なぜここだけ |
| --- | --- |
| **トークンの契約**（モックの色コードとコードの値が一致／設定が参照する色が全部定義済み） | いま未定義の色を参照しても**エラーにならず黙って色が付かない**。実際に「コメントの色と実際の色が違う」事故が起きている |
| 金額の丸め（`Money` / `manYen`） | 万円の丸めが**4通りに実装されており負の数で結果が違う** |
| **メニューの権限フィルタ** | 壊れると**利用者からメニュー項目が黙って消える**。レビューでは絶対に見つからない壊れ方 |
| アプリ判定・バッジの文字数判定 | 現在地表示とバッジ幅の根拠 |

**歯止め**: 純関数以外のテストは書きません（見た目は `verify:ui` が実ブラウザで測るほうが確実）。
テスト文化ゼロに73画面分のテストを入れると、3か月で誰も直さなくなって消されます。

## Phase 0-1 の実行方法 — ブランチ整理を「GitHub の画面から」流す

Phase 0-1（放置ブランチ41本の整理＋タグ11本）は `scripts/github/cleanup-legacy-branches.sh` を流すだけですが、
**Claude Code のセッションからは流せません。** git プロキシがタグ作成とブランチ削除を組織ポリシーとして
拒否します（`error: RPC failed; HTTP 403`）。`git push --dry-run` は通ってしまうので dry-run では気づけず、
実際に流したときリモートは1バイトも変わりませんでした（タグ0本・ブランチ45本のまま＝壊れていません）。

「GitHub の画面でできないか」を調べた結果:

| やること | GitHub の画面で | 理由 |
| --- | --- | --- |
| ブランチ41本の削除 | **できる**（ただし一括削除が無く41回クリック） | Branches ページのゴミ箱アイコン |
| タグ11本を打つ | **できない（やると本番が出る）** | 画面でタグを作る入口は Releases だけ。`deploy.yml` は `release: types: [published]` で発火するので、**公開した瞬間そのタグの中身が本番に出る**。`v3.1.5`（本番未投入）と `archive/*` 7本（古い作業ブランチ）を本番に出すことになる。下書きのままではタグが作られないので目的も果たせない |

→ **Actions タブから実行する** `.github/workflows/cleanup-branches.yml` を用意しました。
画面だけで完結し、41回クリックも不要で、タグは push するが Release は作らないので**本番は動きません**
（`deploy.yml` はタグの push では発火しない）。

```
Actions → Cleanup branches → Run workflow
  mode = dry-run                        ← 何が消えるかを出すだけ（リモートは無変更）
  mode = execute + confirm = cleanup    ← 実行
```

`confirm` に `cleanup` と入力しないと止まります（41本の削除は取り消しにくいため）。
結果は Actions の画面に日本語のまとめとして出ます。

ワークフロー側で押さえた3点（どれも欠けると黙って失敗する）:

1. **`fetch-depth: 0` ＋ 全ブランチの refspec を明示** — スクリプトは `origin/main` `origin/dev`
   `origin/release/v3` と `claude/*` 40本の先端 SHA を照合する。浅い clone では判定できない
2. **`git remote set-head origin <既定ブランチ>`** — 「`dev` が既定ブランチだと削除できない」という
   安全確認が `refs/remotes/origin/HEAD` を見るが、`actions/checkout` はこれを張らない。
   無いと確認が黙って飛ばされ、削除できないブランチを消そうとして落ちる
3. **`git config user.name` / `user.email`** — `git tag -a`（注釈つきタグ）は打つ人の名前とメールを
   要求する。Actions は既定で設定しないため、無いとタグ作成の時点で落ちる

> **ワークフローは既定ブランチ（`main`）にある分しか手動実行できません。**
> この仕組みを含む PR が `main` にマージされてから、Actions タブに `Cleanup branches` が現れます。
> `docs/ops/github-repo-settings.md` の移行手順はもともと「1. この変更を `main` にマージ →
> 3. ブランチ整理」の並びなので、段取りは変わりません。
