# どの仕事にどのモデルを使うか

**決め方の実体は [`server/src/shared/services/ai-model.ts`](../server/src/shared/services/ai-model.ts) です。**
この文書はその考え方と、いま何がどうなっているかの一覧です。
値を直すときはコード側を直してください（**この文書を先に直しても何も変わりません**）。

## 段は2つだけ

| 段 | 何をやらせるか |
| --- | --- |
| **light** | 形を整える・短い文から項目を拾う（**間違えても人がその場で気づける**） |
| **heavy** | 取引先との合意を記録する・写真や PDF を読む・長い文をまとめる |

**判断の基準は「間違いに気づけるか」です。費用ではありません。**

気づけない間違い（議事録の決定事項が捏造される等）は、何円安くなっても割に合いません。
逆に、画面上で読めばすぐ分かる崩れは軽いモデルで十分です。

> **段を3つ以上に増やさないこと。** 増やすと、機能を足すたびに「どれを選ぶか」を
> 毎回考えることになります。2つなら「気づけるか / 気づけないか」の1問で決まります。

## いまの割り当て

| 仕事 | 既定 | heavy に上がる条件 | なぜその段か |
| --- | --- | --- | --- |
| **投入口の解析**<br>`intake` | light | 添付あり／400字超／7行超 | 大半は「山田さんに明日18時までに請求書を送るよう頼んだ」程度の1行。**確認画面に出て人が押す**ので、外していればその場で直せる |
| **やり取りの整形**<br>`activity` | light | 4,000字超 | やることは**形を整えるだけ**で、崩れていれば読んだ人が気づく。**原文は1バイトも触らない**ので「打った文をみる」でいつでも突き合わせられる |
| **議事録の構造化**<br>`minutes` | **heavy** | 常に | **取引先との合意の記録**。決定事項に引用を必須にしてあり、補われると「言った / 言わない」の材料になる。読む人は文字起こし全文と突き合わせないので**気づけない** |
| **KPT の下書き**<br>`kpt` | **heavy** | 常に | 材料は やり取り＋議事録＋遅れたタスク を束ねた長い文。**長い文から要点を抜くのは軽いモデルがいちばん苦手**。出来上がりは隔週キープの資料に出る |
| **文字起こし**<br>（Whisper） | — | — | モデルは1つだけ（`whisper-1`）。段の概念が無い |

### 軽いモデルで落ちたら、上位モデルで1回だけやり直す

投入口とやり取りの整形の両方に入れてあります。モデル名が使えない環境で**黙って失敗**すると、

- 投入口 …「行き先を決めてくれなくなった」（規則ベースに縮退し、全部タスクに倒れる）
- やり取り …「整わない記録がある」（`format_error` が立って待ち行列から外れる）

という、**理由の分からない劣化**になるためです。

⚠️ **やり直すのは落ちたときだけです。** 中身が気に入らないときはやり直しません —
「もっともらしいが違う」は例外にならないので、検知できません。
そこは**人が「整え直す」を押す**のが正しい直し方です（`redoFormat`）。

## いま使っているモデル

| 段 | OpenAI | Anthropic |
| --- | --- | --- |
| heavy | `gpt-5.6-terra` | `claude-opus-5` |
| light | `gpt-5.6-luna` | `claude-haiku-4-5-20251001` |

**正は [`BUILTIN_MODELS`](../server/src/shared/services/ai-model.ts) です。** この表は写しなので、
食い違っていたらコード側が正しいと思ってください。

### 新しい世代に上げるとき

1. **先に環境変数で検証環境に当てて、実際に呼ぶ**
   （`AI_MODEL_HEAVY_DEV` / `AI_MODEL_LIGHT_DEV` → `docker compose up -d app_dev`）
2. **軽いほうと重いほうを両方通す。** 軽いほうは短い記録で自然に通りますが、
   **重いほうは長い記録か議事録でしか呼ばれません** — 確かめずに本番へ入れると、
   **議事録と KPT だけが動かない**という気づきにくい形になります
   （手っ取り早く試すには `AI_MODEL_LIGHT_DEV` に一時的に heavy のモデル名を入れる）
3. `ai_usage` に新しいモデル名が出て、`activity_logs.format_error` が 0 件なら通っている
4. そのあと本番の環境変数 → 最後にこのコードの既定を書き換える

⚠️ **構造化出力（JSON スキーマ）に対応していない世代・名前があります。** 対応していないと、
軽いほうは上位モデルへ逃げ、上位も落ちれば `format_error` が立って**待ち行列から外れます**。
「整わない記録が増える」という**理由の分かりにくい形**で出るので、必ず 2 と 3 をやってください。

⚠️ **上げたら `AI_PRICING_JSON` の鍵も足すこと。** モデル名が変わると古い鍵は当たらなくなり、
**その行は合計に足されず静かに安く見えます**。古いモデルで動いたぶんの記録は残るので、
**古い鍵も消さずに残す**のが正解です。

## 環境変数

**優先順位: 機能ごとの名指し → 段ごとの上書き → 組み込みの既定**

| 変数 | 効く範囲 |
| --- | --- |
| `AI_MODEL_HEAVY` / `AI_MODEL_LIGHT` | **機能をまたいで**効く。`AI_MODEL_LIGHT=off` で軽いモデルを一切使わない |
| `INTAKE_AI_MODEL` / `ACTIVITY_AI_MODEL` / `MINUTES_AI_MODEL` / `KPT_AI_MODEL` | その機能だけ。**段より先に効く**（入れると長い入力でも上がらない） |
| `INTAKE_AI_MODEL_LIGHT` | 投入口の軽いほうだけ |
| `MINUTES_STT_MODEL` | 文字起こし |

⚠️ **`docker-compose.yml` に書かないと `.env` に入れても届きません。**
`npm run lint`（`check-env-passthrough.mjs`）が照合します。

## 落ちてきたと感じたら

**まず数字を見てください。** 勘で上位モデルに戻すと、費用だけ増えて効果が分かりません。

1. **設定 → システムの情報 →「AI の使用量」** — 種類 × モデルの件数と金額
2. **`ai_corrections`** — 人がどれだけ直したか。やり取りの整形なら
   **「整え直す」= `reject`** が増えていれば、それが精度が落ちた印
3. 比べるときは **`ai_outputs.prompt_version` で分ける** — プロンプトを変えた版と
   混ぜると、モデルのせいかプロンプトのせいか分からなくなる

戻すのは環境変数1つです（`ACTIVITY_AI_MODEL=gpt-5.6-terra` など）。**コードを直す必要はありません。**

## 増やすとき

新しい AI 機能を足すときは、**`AiJob` に1つ足して `POLICY` に段を書く**だけです。
機能ごとの環境変数は**増やさないでください** — 増やすほど「なぜこのモデルなのか」を
追うのに読む場所が増えます。

判断に迷ったら **heavy に倒してください。** 読み落として依頼が消えるほうが、数円より高くつきます。
