**移行センター（設定＞「10月の切替」）に改番の対象一覧を追加した**（`docs/reorg-2026-10-plan.md` §4.8「改番の手順と移行センター」の画面側・P1残作業）。サーバー側（直前のコミット）が実装済みだった `GET /org-transition/renumber-candidates`・改番の確認2段階API（`renumber-preview`/`renumber`）を呼ぶ側を作った。①「会社と切替」画面に対象一覧のカード（新設 `RenumberCandidatesPanel.tsx`）を追加。列は現在の番号・実施日・お客様・グループ内外・導出された計上会社（案件一覧・詳細・台帳と同じ `ENTITY_BADGE_LABEL`/`ENTITY_BADGE_TONE` を流用）・止める理由（発行済み・入金済みの売上があれば「請求書発行済み（請求キーは変わりません）」の注記）。客先がグループ内外の自社行になり得る案件（`self_customer_hint`）は警告色の注記を目立たせる（自動では書き換えない）。②行ごとの「改番」ボタン→確認ダイアログ（新設 `RenumberDialog.tsx`）で新番号をプレビュー→理由必須入力→確定、の2段階（サーバーの理由必須チェックを先回りしてボタンを無効化）。成功したら対象一覧をinvalidateするだけで改番済みの行が自然に消える（`listRenumberCandidates` が未改番の案件だけを対象にする作りのため、専用の削除処理は書いていない）。③進捗の「残り件数」は対象一覧の `.length` をそのまま出し、別の集計APIは作らない（設計の原則どおり）。④`TransitionPanel.tsx` の「完了にする」ボタンは、対象一覧の残り件数が1件以上ある間は無効化し理由を添える（サーバーの400 `RENUMBER_REMAINING` を先回りする。件数が未取得・取得失敗のときはブロックせずサーバー側の最終ガードに任せる）。⑤`ReorgPage.tsx` は `renumber-candidates` を1回だけ読み、対象一覧・進捗・doneゲートの3箇所で使い回す。新規コンポーネント3枚（`RenumberCandidatesPanel.tsx`/`RenumberRow.tsx`/`RenumberDialog.tsx`）はいずれも130行以内。検証: `npx tsc -b client`・`npm run lint` のうち `check-mobile-declared`/`check-file-size`/`check-links`・eslint（対象ディレクトリ）、検証用Postgresに実サーバーを起動してのHTTPレベル確認（`state` を `off→preparing→cutover` へ進め、GJV/GSS/GMOの3ターゲット・`self_customer_hint`ありを含む案件を作って対象一覧に出ることを確認、改番3件（理由なし400・成功・プレビュー整合）で行が消えていくこと、残り1件のまま `done` で400 `RENUMBER_REMAINING` になることを確認——確認後はテストデータ（案件3件・取引先2件）を削除し `state`/`cutover_date` を元に戻した）。
