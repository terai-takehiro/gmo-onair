**計時・視聴者（liveops）で、計測中の番組を削除すると計測ロックが永久に解放されなくなる不具合と、タイマー状態APIのキー名の割れを直した**（多エージェント監査 `docs/reviews/2026-08-24-logic-audit.md` 由来）。
①計測中（`measuring=TRUE`）の番組を `DELETE /liveops/programs/:id` で削除すると、`measure.service.ts` の `stopMeasurement()` を一切呼ばずにソフトデリート（`deleted_at` を立てる）していた。組織全体で「同時に計測できるのは1案件だけ」というロック（`startMeasurement()` の `NOT EXISTS` 判定・部分ユニーク索引）はどちらも `deleted_at` を見ないため、`measuring=TRUE` のまま削除された行がロックとして残り続け、以後どの案件でも計測開始が常に409で失敗するようになっていた。画面側にはこの詰まりを解消する導線が無く、詰まると管理者がDBを直接触るしかなかった。`programs.routes.ts` の DELETE ハンドラで、`deleted_at` を立てる前に必ず `stopMeasurement(id, 'system', ...)` を呼ぶよう直した（`stopMeasurement()` 自体は `AND measuring = TRUE` で自己ガードしているため、計測中でない番組の削除でも無条件に呼んで問題ない）。
②`GET /liveops/timers/:id` が返す残り時間のキー名が、タイマーが停止中（`remainingMs`）か稼働中（`remaining_ms`）かで割れており、この応答を素直に読むクライアントは片方の状態でしか値を取れなかった。Socket.IO 側の `getClientState()`（`socket.ts`）は常に `remainingMs` で統一しているため、このREST応答だけ形が違っていた。`timers.routes.ts` の `computeClientState()` を両分岐とも `remainingMs` に揃えた。
検証: `npx tsc -b server`・`npm run test`（1461件）・`npm run lint` を確認済み。実DB・実ブラウザでの動作確認はこのセッションから行っていない。
