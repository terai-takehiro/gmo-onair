**総勘定元帳の決算取込で、失注等の自動整理により案件が削除済みだと投入全体が失敗していたのを直した**（利用者からのご指摘。エラー `duplicate key value violates unique constraint "projects_code_key"`）。
`projects.code`・`gls_number` は削除済み行(`deleted_at`)を除外しない素の UNIQUE 制約のため、GLS番号を持つ案件が失注・放置ネタの自動整理（`project-purge.service.ts`）で論理削除された後、その番号を含む取引が総勘定元帳にあると、決算取込の `ensureProject` は削除済み案件を「存在しない」と誤判定して新規作成を試み、DB の一意制約違反で取込全体（`sga`/`revenues`/`purchases` すべて）が失敗していた（同型の不具合は過去に `episodes.episode_code` でも発生し migration 275 で対応済み）。GLS番号は `project_numbers` で旧番号も永久に引ける永続的な識別子であり、削除済みの番号を別案件へ使い回す方向ではなく、決算実績が見つかった時点で「本来消すべきではなかった」案件として復活させる方が `project-purge.service.ts` 自身の「動いたお金がある案件は残す」という方針とも整合するため、新規作成の直前に削除済みの同一 `code`/`gls_number` を探し、見つかれば `deleted_at` を戻して復活させるようにした。復活件数はレポートの `masters.revivedProjects` と取り込み結果の表示、`warnings` に出す。CLI 版（`server/scripts/import-kessan-dev.mjs`）にも同じロジックを反映し、あわせて事前照合フェーズでキャッシュされた「未登録」判定を `ensureProject` がそのまま信じてしまい `--create-masters` を指定しても新規作成に進めない別のキャッシュ共有バグも直した。検証: `npm run typecheck`。検証用 Postgres（`npm run verify:up`）上で「GLS番号を持つ案件を作成→論理削除（自動整理を模擬）→同じGLS番号を含む総勘定元帳CSVを決算取込」を実施し、修正前は報告と同一のエラーで失敗することを確認したうえで、修正後はエラーなく取り込め、案件が正しく復活する（`deleted_at` が `NULL` に戻る）ことを確認した。
