**ウィークリー活動報告に「AI下書きを作る」ボタンを足した。** 従来は MCP ツール（`get_weekly_activity_stats` → `submit_ops_report`）を AI エージェントが自発的に叩く前提で、実際に週明けにそれを起動するトリガー（定期実行）がどこにも無かった（ドキュメントの「週明けの定期実行」は絵に描いた餅だった）。画面から即時に生成できるようにし、GMO ONAiR 上の情報（`getWeeklyStats`＝新規案件・営業活動・パイプライン・売上・今週来週のイベント・来週期限のアクション）をサーバーが集計 → OpenAI/Anthropic（`weekly_report` ジョブ・常時 heavy、`ai-model.ts`）が文章化 → `ops_reports.body` に保存する経路を新設した（`POST /dailyops/reports/:id/draft-ai`）。会社方針「AIを使い捨てにしない」の5条件を満たす設計にした: ①出力全文を `ai_outputs`(kind=`weekly_report_draft`) に記録 ②本文を人が直せる編集入口（`PUT /dailyops/reports/:id`。これが無いと差分が永久に「無修正」にしかならない）を新設し、**確定時**にサーバーが AI 下書きと確定本文を自動比較して `ai_corrections` に記録 ③成果は既存の `get_ai_feedback_digest`（無修正確定率・よく直されるフィールド）をそのまま流用（新規テーブルなし） ④次の下書きに前回までの傾向（advice）を載せる ⑤レビューは既存の月1回運用に相乗り。あわせて MCP の `submit_ops_report`（AI エージェント経由の投稿）にも同じ `ai_outputs` 記録を足し、ボタン経由・MCP 経由のどちらの下書きも同じ集計対象にした（`model` 引数を任意追加・`mcp:` 接頭辞で区別）。AI未設定環境ではボタン自体を出さない（`ai_available` フラグ）。検証: `server`/`client`/`client-daily` の型チェック、`shared` の Vitest 2,225 件、`npm run lint`（0 errors）全通過。マイグレーションなし（既存の `ai_outputs`/`ai_corrections`/`ai_usage`・`ops_reports.payload` を再利用）。実ブラウザでの確認は未実施。
