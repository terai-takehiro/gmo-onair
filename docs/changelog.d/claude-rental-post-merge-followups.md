PR #304 マージ後のデプロイで実クロールが正常に動作していることを確認したが、ユーザーから「dev反映した時点でまだダミーの機材がします（実際ダミーでした）」との報告を受けた。デプロイログで `SKIP_RENTAL_SEED=true のためスキップ` を確認できたため、新たにダミーが投入されているのではなく、**その対処（v4.1.8）より前にデプロイ済みの検証環境に残っていた初期投入ダミー8件がそのまま表示され続けている**ことが原因と判明した（`rental_scraper_dev` の実クロールはSQLiteの取得結果にある `(company, item_id)` しか触らないため、ダミーのIDと偶然一致しない限り自然には上書きされない）。

これまでREADMEに手動SQLの後片付け手順を書くだけだったが、マイグレーション `229_qsheet_rental_cleanup_seed.sql` を追加し、次のデプロイで自動的に片付くようにした。`company + item_id + name` の3列が `seed-rental.ts` のダミー値と完全一致する行だけを削除する設計（実クロールが同じIDを先に取り込んで `name` が書き換わっていれば一致せず消えない）。実 Postgres（`verify:up`）で「ダミーと完全一致する行は消える／同じIDでも実クロールで名前が変わった行は残る」の両方を確認済み。
レンタル機材検索に「今すぐ取得」ボタンを追加した。これまではクロールが検証環境の自動実行（毎日5時 or デプロイ直後の1回）を待つしかなく、動作確認のたびに時間を置く必要があった。`rental_scraper_dev`（Python の常駐プロセス）に HTTP サーバーは持たせず、Postgres の新テーブル `qsheet_rental_sync_requests` をキューにする方式にした：画面のボタン→`POST /qsheet/rental/sync-trigger`が'pending'行を1件INSERT→`scheduler.py`が20秒ごとのポーリングでそれを見つけてクロールを実行→'done'/'error'で締める。同時多重リクエストは409、直近30分以内の再トリガーは429で断る（対象2社サイトへの連打を防ぐ）。画面は取得状況欄（前回追加）に「今すぐ取得」ボタンと進行状況（取得中…／失敗）を表示するようにした。実Postgres（`verify:up`）でトリガー→claim→done、already-running（409）、cooldown（429）、error経路のすべてを確認済み。単体テストも追加（`test_sync_requests.py`）。

あわせて、会社名「東京オフラインセンター」をバッジ・チップ等の固定幅UIで文字数が長すぎるとのご指摘を受け「TOC」に短縮した（ご指示）。`company`列はDBの実データ値（qsheet_rental_items/qsheet_rental_reservationsの主キーの一部）なので、コードの定数を変えるだけでは既存行が古い名称のまま取り残されるため、マイグレーションで一括リネームした（実Postgresで確認済み・レスター側のデータは無影響）。
