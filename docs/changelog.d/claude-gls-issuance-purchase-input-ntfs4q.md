**GLS発番と仕入・売上入力の絞り込みが噛み合っていなかった矛盾を直した。**
①「GLS発番がどこでできるのか分からない」「GLS未発番だと仕入が入力できない」という
ご指摘から実装を調べ直したところ、v3時代の設計とv4で追加した設計が同居していた。
②手動でのGLS発番（`POST /projects/:id/issue-gls`）はコード上「口頭決定（B）以降で呼ぶ」
と明記されていたのに、実装にはその制限が無く、問合せ段階（E）の案件からでも新しい
GLS番号を焼けてしまい、v4の「受注が固まるまで番号を焼かない（欠番を増やさない）」
という前提を無効化できる抜け道になっていた。サーバー側にステージのガードを足し、
画面（GLS発番ダイアログの「新しい番組」選択肢）も口頭決定より手前では選べないように
した（「いまある案件に足す」はこの制限を受けない）。
③仕入・精算PDF取込レビュー・予算詳細・書類引き渡しの案件プルダウンは
`gls_number IS NOT NULL` で絞り込んでいたため、受注（`a_won`）に上がっても
案件分類未設定などの理由でGLS番号だけ振られなかった案件には実務を一切記録できない
詰みがあった。**受注確定の判定は `gls_number` の有無ではなく `stage` が正**という
考え方に統一し、新設した `GET /projects/won-projects`（`stage IN ('a_won','s_completed')`）
に絞り込み先を差し替えた。「GLS番号そのものへ紐づける」操作（回の追加・付け替え・
費用を分け合うグループ）は番号が無いと成立しないので `gls-projects` のまま変えていない。
④売上入力だけは絞り込みが無くヨミ段階の案件にも売上を計上できる非対称があったため、
他画面に合わせて受注確定済みだけに揃えた。
⑤あわせて「GLS発番がどこでできるのか分からない」という声を踏まえ、案件詳細（概要
タブ）の「GLS 番号」欄・案件編集の「GLS 発番」ボタン・仕入や売上など実務入力の
案件プルダウンに、発番できる条件（受注＝A受注済になると自動発番／急ぐときは
口頭決定＝B以降なら先に発番できる）を簡潔に案内する文を足した。
検証: `npm run typecheck` / `npm run lint` / `npm run test` OK。
