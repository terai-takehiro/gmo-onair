**管理権限モデルを単純化した。** ユーザーから「管理権限がアプリ単位で分かりにくい、
シンプルにしたい」との指示を受け、現状の権限モデル（アプリ内部12区画・「型」と
個人ごとの例外編集の2階建て・272箇所に分散した判定）を、ブロックアプリ単位の7区画
（`sales`が旧`budget`/`gpm`/`studio`/`partner_schedule`を吸収）＋「型」だけの1階建てに
統合した。「権限とメンバーの管理」は `system_admin` だけに絞り、区画としての `admin`
は廃止した。①ユーザーから「原則チームメンバーはフルアクセス、一部だけ特定アプリに
絞った臨時アクセスもある」という実態を聞き、「型を押されているか＝正規メンバーか
臨時アクセスか」の既存データの形をそのまま移行判定に使えることが分かったため、
当初懸念していた「実データを見ないと危険（凍結4アプリの個人設定が消える）」という
制約が外れ、計画（`docs/reviews/permission-model-simplification-plan.md`）に加えて
コード実装まで完了させた。②サーバー側の272+α箇所の権限チェック・MCPの権限ゲート・
クライアント側のルートガード/UI（`RoleDialog`は7区画表示に、個人ごとの例外編集
`UserPermissionsDialog`は削除）を新しい区画に合わせて更新。③移行マイグレーション
（migration 210）で、旧5つの組み込み型を押されていた人は「フルアクセス」型へ、
個人設定オンリーの人（凍結4アプリの個人設定を含む）は実効権限を1文字も変えずに
captures する型を自動生成して割り当てる方式にした。ローカルの検証用Postgresで
移行前の状態を人工的に再現して migration を実行し、全パターン（旧型を押されていた人／
個人設定オンリーの人／既存カスタム型を押されていた人／権限が無い人）で意図通りに
動くことを確認した。検証: `npm run typecheck`（server/client）/ `npm run lint` /
`npm run test`（1141件）OK。⚠️ 実際の検証/本番DBへは未反映（このセッションはネット
ワークポリシー上アクセスできない）。dev への反映とその後の観測は
`docs/reviews/permission-model-simplification-plan.md` の Phase 3 を参照。
