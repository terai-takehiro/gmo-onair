**議事録・やり取りのAIまとめが、きわめて短いテキストにしかならず議事録の意味をなしていなかったのを直した**（利用者からのご指摘）。①原因はプロンプトとスキーマの両方に「短く書け」だけが書かれ、**材料の長さに追従する指示が1つも無かった**こと — 議事録は `summary` が「3〜5行で」の固定（1時間の打合せでも3行）、やり取りは「## 短く書くこと」の節と件数の上限（`turns` 6件・`facts` 4件・`quote` 2文）だけがあり、**長い打合せ・長いメールほど落ちる情報が増える**形だった。さらに `activity-struct.ts` の検査側の上限（`facts` 6件・`lead` 400字）も同じ方向に効いていて、超えたぶんは静かに捨てられていた（捨てた事実はどこにも出ないので、画面を見ても「短い」としか分からない）。②直し方は「長く書け」ではなく**2段の制御**にした — (a) 分量の目安を**材料の文字数から計算**して毎回プロンプトに渡す（`server/src/shared/services/ai-coverage.ts`。議事録は文字起こしの約1割・やり取りは原文の約1/4、床と天井つき）、(b) 出てきたまとめを**測り、下限を下回ったら1回だけ拾い直させる**（指示は「落とした論点を拾え」であって「長く書け」ではない。長さを直接求めると水増しで満たされ、この製品がいちばん避けたい「言っていないことが書かれた記録」になる）。拾い直しても足りなければ長いほうを採って先に進む（網羅が足りないことを理由に記録そのものを失わせない）。③あわせて議事録の `summary` を**話題ごとに1行（行頭 `■`）**と決め（話題を1つも落とさない・決定事項と持ち帰りの件数上限を外す）、やり取りは件数の上限を実態に合わせて広げ（`turns` 12件・`facts` 8件・`statuses` 6件）、検査側の上限も**プロンプトが求める件数のひと回り外側**に置き直した（柵であって「この長さに収めろ」ではない、と明記）。`max_output_tokens`／`max_tokens` も固定値をやめて材料の長さから決め、途中で切られた議事録が出ないようにした。長い材料では推論の `effort` を `medium` に上げる。④**会社方針「AIを使い捨てにしない」の条件2と4を塞いだ**: 人の直しを `fix`（書き換え）と `enrich`（書き足し）に分ける判定を入れ（`classifyTextCorrection`・構造は `activityStructLength` の増加で見る）、書き足しが書き換えより多いときは「まとめが短すぎる」という助言を `get_ai_feedback_digest` が次のプロンプトに返すようにした。着手前は全部 `fix` だったため、**今回のご指摘を集計からは言い当てられなかった**。網羅量の実測（材料の字数・まとめの字数・下限・やり直したか）は `ai_outputs.payload_snapshot` に残す（条件1）。検証: `npm run typecheck`（client/daily/equipment/server）・`npm run test`（shared 2,488件＋server のレビュー試験 94件）・新規 `shared/tests/aiCoverage.test.ts` 19件（短い材料では測らないこと＝水増しを強制しないことを含む）。プロンプト版は `minutes-v2` / `activity-v4` に上げたので、改善効果は版ごとの無修正採用率で比較できる。⑤**上流（メール取込）も直した**: `create_activity_log`（MCP）の `description` は`.describe('活動内容の詳細')` としか書いておらず、取込スキルも「…お問い合わせ内容を整形…」としか指示していなかったため、**取込側の AI が要約したものを、サーバーの整形器がさらに要約する**二重圧縮になっていた。`description` は**要約せず本文をそのまま渡す**（署名・引用返信・定型フッターだけ外す。整形はサーバーの仕事）とツールのスキーマと `.claude/skills/mail-intake/` の両方に明記し、`update_activity_log` の `description` にも「原文を縮めて上書きしないこと」を足した — **元の本文に書かれていないことは、どんな整形器でも取り戻せない**ため。
