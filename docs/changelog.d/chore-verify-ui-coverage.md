**`verify:ui` の穴を4つまとめて塞いだ**（画面の検査スクリプトのみ・アプリのコード変更なし）。①v4 で作り直し済みなのに1画面も検査に載っていなかったカレンダー4画面（予定・部屋の空き・仮押さえ・設定）と、顧客一覧（`/sales/companies?role=customer`）・探す（`/search`）・設定5画面（拠点・お金・休日・通知・システム）・機材の検索を PAGES に足した（顧客360 と内覧会の日別画面は、シードに固定の顧客 id・内覧会予約が無く URL を組み立てられないため見送り、理由をスクリプト内に明記した）。②3つ目の画面幅として 768px（タブレット）を足した — まずはレイアウトの検査（横はみ出し・到達不能な隠れ・シェルの高さ）だけを当て、整列の検査は結果を一度レビューしてから段階的に有効にする。③「潰れ検知」を足した — 文字の入った要素が数px幅に潰れて1文字ずつ縦に折り返される崩れは横はみ出しの検査（`document.scrollWidth`）に現れないため、`clientWidth < 24px` かつ中身が幅に入っていない要素を数える。いまは報告のみで落とさない（既存の積み残しを潰し終えたら 0件必須に格上げする）。④`--shots` モードを足した — 検査の代わりに全ページを 375/768/1280 の3幅で fullPage スクリーンショットに撮り、リポジトリの外（既定 `~/verify-ui-shots/<日付>/`・`--shots-dir` で変更可）に保存する。検証: `node --check` / `npm run lint` に加え、検証用 Postgres（`verify:up`＋フルシード）＋ビルド済み client/client-equipment ＋実 Chromium で15ページ×3幅の検査と `--shots` の実走を行い、潰れ検知の報告（2ページ・実在の崩れ）と 768px のレイアウト検査全通過を確認した。カレンダー3画面で既存の崩れ（薄すぎる文字・ボタンの段・バッジの右端）が新たに6件見つかったが、これは検査の穴が塞がった成果そのもので、直しは別PRで行う。
