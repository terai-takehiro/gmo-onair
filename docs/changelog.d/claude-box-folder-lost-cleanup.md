**失注・見送りになった案件の BOX フォルダが現役の場所に残り続けるのをやめた**（ユーザー報告「失注や見送りのなった案件について BOX に残り続けてしまうので、失注、見送りの時点で BOX フォルダを削除していただきたい」）。**中身が1つも無ければ本当に削除し、中身があれば `99_失注・見送り` へ引っ越す**形にした（migration 248）。⚠️ **無条件の削除にしなかったのは、調べたら消してはいけないものが入っていたため**: ①**見積書・請求書・検収書の PDF は BOX にしか無い**（アプリは発行のたびに生成して流すだけで保存しておらず、出した原本は `01_見積・提案` と `03_請求` だけ。失注案件でも「何をいくらで出したか」の唯一の記録で、失注分析の根拠。請求書・検収書は電子帳簿保存法の保存対象）②**失注は取り消せるステージで、しかも機械が付ける**（90日放置の自動見送り・Excel取込・MCP）ので、取り消せる状態を根拠に取り消せない削除をしてはいけない ③**`box_url_internal`/`box_url_external` は画面から書き換えられるただの文字列**で、そこから取り出したIDを無検査で消すと別の案件や親フォルダを消せる ④**本番DBのバックアップ（`00_DB_Backup/`）が社内親フォルダの直下にある**。安全弁を純関数にして 21 件のテストで固定した: 触ってよいのは「親フォルダ・取込フォルダのIDでない」「実際の親がその案件の親である」「名前が【社内】/【社外】で始まる」の3つを全部満たすものだけで、**一覧が取れない・深すぎる・多すぎるはすべて『空ではない』に倒す**（BOX が数秒詰まっただけで書類が消えないように）。削除は `recursive` を付けないので、数え間違いがあっても中身があれば BOX 側が断る二重の守りになる。「空」は木全体で見る（作った直後は空のサブフォルダを数枚持つため、直下だけ見ると1件も消えない）。案件を失注から戻すと元に戻る（引っ越したものは親へ戻し、消したもの＝空だったものは同じ形の空フォルダを作り直す）。発火はステージが動く全経路（案件詳細・GPM・一括更新・**90日放置の自動見送り**）。完了（`s_completed`）は対象外（納品物が入っており現役で参照する）。**既存の失注案件は migration では遡らず**（本番の BOX で数百フォルダが人の知らないうちに一斉に動くため。245 で活動記録を遡って閉じたのとは別の判断で、あちらはDBの中だけで完結する可逆な操作だった）、案件一覧の「終了」帯から**過去分をまとめて処分するボタン**を足した（ユーザー報告「一括処理するボタンが欲しい／過去失注分をまとめて処分する」）。1リクエストで全部やるとフォルダ1件につきBOXを数回叩くため数百件で必ずタイムアウトし、途中まで動いたのか1件も動いていないのか誰にも分からなくなるので、**20件ずつ続けて呼び進み具合（N / M 件）を出す**形にし、途中で止められるようにした。⚠️ **終わり方を「残り0件」にしていない** — 安全弁で見送った行は「次に試せば片づくかもしれない」ので印を付けず対象に残るため、残り0件を待つと同じ行を永久に叩き続ける。**1件も進まなかったら止める**のが正しい終わり方で、これをテストで固定した。触らなかった件数と理由は画面に出す（消えていないことに人は気づけない）。0件なら帯ごと出さない。検証: `npm run typecheck:all` 緑、`npm run test` 1701件緑（新規21件）、`npm run lint` 緑、migration 248 を検証DBに実流し。
