# レギュラー案件（回が蓄積するパターン）のロジック

案件管理で「レギュラー番組」を扱うための決めごと。**この文書がレギュラーの正**。

> なぜ独立した文書にしたか: レギュラーの仕様は旧モック `mockups/v4-mockup-main.dc.html:3121-3240`
> にしか無く、そのファイルは `mockups/README.md:5-12` で「**古いほうを見ると、マージ済みの作業を
> 巻き戻します**」と書かれている。新しい正のモック `v4-live-sales.dc.html` はタブが7つで
> 回（エピソード）が無かったため、2026-08 にタブごと外された
> （`docs/reviews/client-v4-build-log.md:1185-1200`）。
> **「絵が無いから外した」という判断だけが残り、業務要件が宙に浮いたのが「結局できていない」の正体。**
> 絵ではなくロジックを先に固定するために、モックから独立させる。

## 1. 何をレギュラーと呼ぶか

**判定は `projects.recurrence = 'regular'` ただ1つ。** `gls_category` での代用をやめる。

レギュラー ＝ **1つの案件（＝番組・シリーズ）の下に回が積み上がり、契約・単価・請求の
取り決めが案件側に1度だけ置かれるもの**。単発は「案件 = 1回」。

### レギュラーではないもの（★混同禁止）

定例イベント（パートナーズ・カンファレンス／決算説明会／定時株主総会）は、
実データ上**毎回が独立した案件で独立した GLS 番号と請求を持つ**。

```
パートナーズ・カンファレンス  GLS026 → GLS039 → GLS060 → GLS065 → GLS068 → GLS097 → GLS098 → GLS-A009 …（10件）
定時株主総会 2026-03         GLS148〜GLS155 の9社ぶん（金額はほぼ全部 2,416,331 で同一）
```

これらを回にすると **GLS 番号が回コードに降格し、会社ごとの請求先が持てなくなる**。
よって定例イベントは**レギュラーにしない**。必要なのは別の機能（「前回から複製」と
「系列でまとめて見る」）であって、本文書の対象外とする。 → §9

## 2. 階層 — 収録日は「テーブルを作らない」

```
案件（番組）  GLS-A007「インテリジェンス」        ← 契約・単価・請求サイクルはここに1度だけ
  └ 収録日（セッション） 2026-06-18（木）         ← ★実体を持たない。導出する
      ├ 回 #1  GLS-A007-001  公開 6/25
      └ 回 #2  GLS-A007-002  公開 7/02          ← 2本撮り
```

⚠️ **収録日（セッション）に新テーブルを作らない。`episodes.recording_date` が同じ回を
束ねて表示するだけ**（`GROUP BY recording_date`）。

理由: 旧モックは3階層で描かれているが、実体を作ると「回を別の収録日へ移す」「収録日だけ
消す」「回0件の収録日」といった状態を全部作り込むことになる。一方で**収録日が持つべき固有の
情報は `studio_bookings` が既に持っており**（スタジオ・時間帯・機材）、回とは
`studio_bookings.episode_id` で既に繋がっている。**同じ事実に2つ目の置き場を作らない。**

実データがこの形を裏付けている: `GLS161「ｲﾝﾃﾘｼﾞｪﾝｽ #1-2」` の `#1-2` は
「1回の収録で第1回と第2回を撮った」跡＝**収録日:回 = 1:N**。同じ番組の
`GLS-A007` は 1:1。**同一シリーズ内で 1:1 と 1:N が混ざる**ので、束ね方は
固定の階層ではなく日付での導出が正しい。

## 3. 案件（シリーズ）が持つ4つの取り決め

回を作るたびに聞かれては困る値。**案件に1度だけ**置く。（旧モック `v4-mockup-main.dc.html:7447-7452`）

| 取り決め | 例 | 使いみち |
|---|---|---|
| 収録の頻度 | 隔週木曜・基本2本撮り | 回の一括生成の既定値 |
| 固定セット | 用賀 SKY STUDIO・3カメラ | スタジオ予約の既定値 |
| 回の単価 | ￥84,000 | 回を作ったときの売上見込み |
| 請求サイクル | 月末締め / 収録日ごと / 契約一括 | 請求のまとめ方（§6） |

⚠️ **単価は「今の単価」であって履歴ではない。** 改定したら過去の回の金額は動かさない
（既に請求済みの金額が遡って変わるのは事故）。改定は新しく作る回にだけ効く。

## 4. 回の状態は書かない。導出する

`episodes.status` は `109_episodes_title_status.sql` で足された TEXT だが、
**CHECK も enum も無く、誰も書いていない**（`EpisodesPanel.tsx:26` に自白コメントあり）。

**状態はその回のタスクの完了状況から導出する。** 旧モックの決めごと
「各回の状態は工程の進み方で自動で決まります」（`v4-mockup-main.dc.html:3136`）を正とする。

```
未着手  … その回のタスクが1件も完了していない
進行中  … 1件以上完了、ただし全部は終わっていない
完了    … その回のタスクが全部完了
```

⚠️ **`episodes.status` に書き戻さない。** 2つ目の真実を作ると必ず食い違う。
将来 Kanban 6状態（準備中→収録準備完了→収録済→編集中→確認待ち→納品済）が要るなら、
**標準工程テンプレートの工程名がそのまま状態になる**ので、状態列ではなく工程を足す。

## 5. ステージと「終わった」の判定 ★実害の直し

### いま起きること

`completeElapsedWonProjects` は `stage='a_won' AND event_end < 今日` で完了へ繰り上げる。
レギュラーの `event_end` に第1回の日付が入っていると、**2回目を迎える前に完了扱いになり、
BOX フォルダごと `98_終了案件` へ片づけられる**。
逆に `event_end` を空にすると `NULLIF(...) IS NOT NULL` に弾かれ、永久に `a_won` に残る。

### 決めごと

1. **`recurrence='regular'` の案件は `event_end` では完了させない。** 日次ジョブの対象から外す。
2. レギュラーが完了になる条件は **「残っている回が無い」**:
   - 回が1件以上あり、かつ
   - 未完了（§4の「完了」に達していない）の回が0件で、かつ
   - いちばん遅い `broadcast_date`（無ければ `recording_date`）が今日より前
3. **回が0件のレギュラーは絶対に完了させない。** まだ始まっていないのか終わったのかを
   区別する材料がこちらに無い（v4.5.14 で「日付が1つも無い案件は対象外」としたのと同じ理由）。
4. **`event_end` の意味を変えない。** レギュラーの `event_end` は「今クールの最終収録日」であって
   案件の終わりではない。この列に別の意味を持たせず、判定に使うのをやめるだけにする。

### 受注時（`a_won`）にやること

GLS を採るのに加えて、**レギュラーなら第1回を1件だけ自動で作る**。
- 日付は `event_start`（無ければ空）
- 以降の回は人が §7 の一括生成で足す

⚠️ **まとめて全回を作らない。** 何回やるか決まっていない時点で24件作ると、
失注や本数変更のときに消す作業が発生する。**1件だけ作って「回はここに積む」と分かる状態にする。**

## 6. 請求 — 原子は回、まとめ方は3つ

金額は回に付く（`revenues.episode_id`。既存の仕組み）。**請求書のまとめ方だけが選択肢。**

| サイクル | まとめ方 |
|---|---|
| **月末締め**（既定） | その月に「完了」に達した回を1枚に集める |
| 収録日ごと | 同じ `recording_date` の回を1枚に集める |
| 契約一括 | 案件に1枚。回には金額を持たせない |

請求キーは既存ルールのまま `{episode_code}-{税枝番}`（`billing-key.service.ts:6-11`）。

⚠️ **月末締めで「その月に完了した回」を集めるとき、締めたあとに回の状態が戻ると
請求済みの回が請求対象から消える。** 請求書を発行した時点で回と請求書の対応を
`invoice_group_episodes` に固定し、**あとから状態が動いても対応は動かさない**。

⚠️ **`invoice-groups.routes.ts:164` は SQLite の `GROUP_CONCAT` を使っており、
PostgreSQL では必ず 500 になる**（`string_agg` が正）。クライアントから呼ばれていないので
誰も気づいていない。月まとめ請求を作るなら**ここを直すのが最初の一歩**。

## 7. 回の作り方 — 「毎週水曜・2本撮り・全12回」で作る

いまの `POST /:projectId/episodes/batch` は**件数を渡すだけ**で、日付もタイトルも入らない
（`EpisodesPanel.tsx:74`）。作ったあと1件ずつ `PUT` で日付を入れる運用になっている。

**入力を「頻度 × 期間 × 1日あたりの本数」に変える:**

```
開始日      2026-09-10（木）
繰り返し    毎週 / 隔週 / 毎月第N◯曜 / なし（日付を手で並べる）  ← 例では「隔週」
1日あたり   2本撮り
回数        全12回  または  終了日まで
```

生成されるもの:
- 指定した回数ぶんの回。`recording_date` は指定の曜日で埋まり、同じ日に2件ずつ
- `broadcast_date` は「収録日 + N日」の既定（オフセットは案件の取り決め）
- 単価が設定されていれば売上見込みも同時に作る（現行 `batch` の `revenue_budget_per_episode` の挙動を踏襲）

⚠️ **既にある回とぶつかる日付は作らない。** 同じ `recording_date` の回が既に
指定本数ぶんあれば飛ばし、**何件作って何件飛ばしたかを実行前に画面へ出す**
（お金の行が増えるので、押したあとで分かるのは事故）。

⚠️ **`episode_number` の採番をアトミックにしてから作る。** いまは read-then-write
（`sequence.service.ts:71-77`）で、`UNIQUE (project_id, episode_number)` も無い。
12件を一気に作ると番号が重複しうる。GLS 採番（`sequence.service.ts:36-42`）と同じ
`ON CONFLICT ... RETURNING` の形に揃える。

⚠️ **`/episodes/month`（GLS-B の月次ユニット）と混ぜない。** あちらは
`episode_number` に `2607` のような YYMM を入れるため、同じ案件で話数運用と混ざると
`MAX(episode_number)+1` が 2608 を返して話数に戻れなくなる。
**レギュラー（GLS-A）では `/month` を呼ばない。**

## 8. GLS 番号 — 変えない

| | 形 | 出どころ |
|---|---|---|
| 案件（番組） | `GLS-A007` | 案件に1本。既存のまま |
| 回 | `GLS-A007-001` | `generateEpisodeCode`（`sequence.service.ts:66-68`）。既存のまま |

年度・クールをまたいでも**回番号はリセットしない**（案件内の通し）。
リセットすると `episode_code` の UNIQUE が壊れる。クールを分けたいなら
**案件を分ける**（＝新しい GLS を採る）のが正しい。

## 9. 対象外（別途）

- **定例イベントの「前回から複製」**: パートナーズ・カンファレンス／決算説明会／株主総会。
  独立案件のまま、前回の見積・売上・仕入・タスクをコピーして新しい案件を作る機能。
  実データでは金額が毎回同一の系列が多く（キックオフMTG 220,800/86,400 が3回とも同額）、
  効果が大きいが、レギュラーとは別の仕組み。
- **費用を分け合うグループ**: 上場8社株主総会（GLS015-022 が全部同額）のような
  1イベントを会社数で按分する形。既存の配分機能の話。
- **顧客の名寄せ**: 「GMOサムライコンテンツスタジオ」と「〜株式会社」が別レコードで、
  同じ番組の案件が別顧客にぶら下がっている。レギュラーとは独立した問題。

## 10. 作る順番

お金と自動処理に触るものを先に、画面を後に。

| # | やること | なぜ先か |
|---|---|---|
| 1 | 日次ジョブから `regular` を外す（§5-1） | **いま実害が出ている。** 放置すると次の朝に案件が完了へ落ちて BOX が片づく |
| 2 | `UNIQUE (project_id, episode_number)` と採番のアトミック化（§7） | 一括生成の土台。あとから直すと既に壊れたデータの修復が要る |
| 3 | 回UIの出し分けを `gls_category` から `recurrence` へ（§1） | 1行の変更。これで「regular を選ぶ意味」が生まれる |
| 4 | 受注時に第1回を1件作る（§5） | regular にした案件が空のままにならない |
| 5 | 回の一括生成を「頻度×期間×本数」に（§7） | ここまでで日々の運用が回る |
| 6 | 案件の4つの取り決め（§3） | 単価と請求サイクルの置き場 |
| 7 | `GROUP_CONCAT` → `string_agg`（§6）と月まとめ請求 | 請求は取り決めが決まってから |
| 8 | レギュラー用の標準工程テンプレート3ブロック | 状態の導出（§4）が工程に依存するため最後 |

⚠️ **1〜4 は既存の穴埋めで、モックの絵が無くても進められる。** 5以降が画面の話。
