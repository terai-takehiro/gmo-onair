## 0. 何を作るか

プロジェクト管理（`/gpm`）の「体制」タブにある**チームと線の組織図**
（`client/src/contexts/gpm/pages/projectDetail/MembersTab.tsx`・migration 169）を、
運営マニュアルのキャンバスに置ける**自由ブロック「体制図」**として作り直す。

利用者の言葉は「プロジェクト管理で作れる組織図を、運営マニュアルの機能としてコピーしたい」。

---

## 1. 結論（先に答え）

1. **自由ブロック**（`free.type: 'orgchart'`）にする。**差し込みブロックにしない**（§2）
2. 中身はマニュアルが持つ（`free.content`）。階層・チーム・人を**キャンバスの上で直接**編集する（表ブロックと同じ作法）
3. **置いた直後は空**（名前の無い階層が1つだけ）。テンプレートは持たない（§10-1・2026-09-13 の判断）
4. **立場の区分（自社／発注者／PM会社／業者）は持たない。** 所属は自由入力の文字で、
   枠線はどのチームも同じ（§10-2・2026-09-13 の判断）
5. 一から打ち直さないために**取り込み**を1つ用意する
   （案件のメンバー ／ 同じ案件のプロジェクト管理の体制）。取り込んだあとは**マニュアル側の独立したデータ**
6. **表も migration も増やさない。** 新しい API は取り込み用の `GET …/org-seed` 1本だけ

---

## 2. なぜ差し込みにしないか（実測4点）

| # | 実測 | 差し込みにすると |
| --- | --- | --- |
| ① | マニュアルは案件にも番組にも紐づく（`CHECK (num_nonnulls(project_id, program_id) = 1)`） | **番組のマニュアルには案件が無い** → 差し込み元が存在しない |
| ② | 階層・チーム・バッジを持つ表は `gpm_members` だけ（`tier`/`group_label`/`badge`・migration 169）。編集画面はプロジェクト管理（GLS-B ＝ 新 `GMO-`）にしかなく、制作案件（新 `SCS-`/`GSS-`）はその一覧に出ない | 制作案件のマニュアルでは**永久に空**。入力する画面がどこにも無い |
| ③ | `project_members`（migration 130）は `role`/`member_name`/`is_external`/`sort_order` だけで、**階層もチームも持たない** | 1列の並びにしかならず組織図にならない。それは既存の `project.team` そのもの |
| ④ | 紙に刷るのは**その日の現場の体制**（当日だけの役割・外部スタッフが入る） | 案件メンバー一覧と一致しない。元が変わるたびに紙と食い違う |

**「案件のメンバーをそのまま出す」は既存の `project.team`（体制・連絡先）が担う。**
体制図はそれとは別の道具で、**マニュアルの中で完結させる**。

## 3. データの形

```ts
/** 自由ブロック「体制図」の中身（shared/src/opsmanual/types.ts に足す） */
export interface ManualOrgChartContent {
  tiers: ManualOrgTier[];
  /** 階層のあいだに縦罫を引くか（既定 true） */
  connectors?: boolean;
  /** キャンバスに出す項目。密度を下げるため既定は役割だけ */
  show?: { role?: boolean; org?: boolean; phone?: boolean; email?: boolean };
}

export interface ManualOrgTier {
  id: string;           // genId('tier')
  label: string;        // 階層の名前（自由入力。置いた直後は空）
  boxes: ManualOrgBox[];
}

export interface ManualOrgBox {
  id: string;           // genId('box')
  label: string;        // チーム名（「技術」「中継」など）
  org?: string;         // 所属（自由入力・任意。チームの見出しに小さく出る）
  people: ManualOrgPerson[];   // 空でよい（人が決まっていないチームを紙に出せる）
}

export interface ManualOrgPerson {
  id: string;           // genId('psn')
  name: string;
  role?: string; org?: string; phone?: string; email?: string;
  badge?: string;       // 決裁 / 進行 / 議事録 など
}
```

**立場（`side`）の列は持たない。** GPM は `side IN ('internal','client','pm','vendor')` の
CHECK を持ち、枠の色をそれで決めている（migration 161）。制作現場には当てはまらない区分が混ざる
（「PM会社」は建築・構築案件の言葉）ため、**区分をやめて所属の文字だけを持つ**
（2026-09-13 の判断・§10-2）。取り込みで入ってくる `side` は**日本語の文字に落として**
所属欄へ入れる（値は捨てない・§5-4）。

### 3-1. GPM と違って「チーム」を明示的に持つ

migration 169 は「**チームを別テーブルにしない**」と決めた。理由は「チームは名前が同じ人の集まりでしかなく、
チームそのものに持たせる値がない。表を分けると人を消したときに空のチームが残る」。
**DB の行が人単位だから正しい判断**で、マニュアルでは前提が変わる。

- マニュアルの中身は JSON なので**入れ子で持てる**（別テーブルの話にならない）
- 現場のマニュアルでは**人が決まっていない空のチーム**（「音声 ── 調整中」）を紙に出したい。
  GPM の持ち方では空のチームは表現できない

### 3-2. 階層は3階層固定にしない

GPM は `tier IN ('top','lead','unit')` の CHECK を持つ（決裁層・推進層・実務層）。
これは**発注者と PM 会社がいる構築案件**の見方で、制作現場の体制は案件ごとに切り方が違う。
**階層はマニュアルごとに増減・改名できる**し、既定のテンプレートも持たない（§10-1）。

## 4. 紙の決めごと（production-manual.md §6-6「インクを使わない」）

- チームは**枠線だけ**。塗らない
- **枠線はどのチームも同じ**（0.25mm の細い実線）。立場による線種の描き分けはしない（§10-2）。
  どこの会社かは**チームの見出しの所属の文字**で読む
- バッジ（決裁・進行）は**枠線の小さな角丸**。塗らない
- 階層のつながりは**縦の細罫 0.25mm**
- ⚠️ **SVG で座標を計算して線を引かない。** `MembersTab.tsx` 冒頭が実測で書き残したとおり
  「チームの高さは中の人数で変わる」ので、画面幅が変わるたびに線がずれる。キャンバスでも同じ
  （ブロックの幅は利用者が変える）。**上下のつながりだけを縦罫で示し、横の並びは「同じ階層にある」ことで表す**
- 既定サイズ **180 × 90 mm**（A4横の左2/3ほど）

## 5. 画面

### 5-1. 置く（自由ブロックのカタログ）

文字 ／ 図形 ／ 画像 ／ 表 ／ QR に **体制図** を足して6つ。

**置いた直後**は、名前の無い階層が1つと「＋ チーム」だけ（空の状態から始める・§10-1）。

### 5-2. キャンバスの上で編集（表ブロックと同じ作法）

- **選択中だけ**入力欄になる。`onPointerDown` をブロック内で止める
  （`TableBlockContent.tsx` と同じ。止めないと `ManualBlockView` の「つかんで動かす」が起きる）
- チームの中に「＋ 人」、階層の右に「＋ チーム」、各行に「−」
- 階層の名前・チーム名・所属・氏名・役割はすべて**その場で打つ**
- **ダイアログは出さない。** GPM の `MemberDialog`（211行）は転記しない
  — キャンバスが隠れると「刷ったときにどう見えるか」が分からなくなる

### 5-3. 右パネル「体制図」

| 区画 | 中身 |
| --- | --- |
| 階層 | 追加・名前・上下の入れ替え・削除（最後の1階層は消せない） |
| 出す項目 | 役割 ／ 所属 ／ 電話 ／ メール のチェック（既定は役割だけ） |
| 線 | 階層のつながりの縦罫（入／切） |
| 取り込み | 「案件のメンバーから」「プロジェクト管理の体制から」 |

立場の凡例は**置かない**（区分そのものを持たないため・§10-2）。

### 5-4. 取り込みの決めごと

- **1回かぎりの流し込み。** 取り込んだあとはマニュアルのデータで、元を直しても追わない
  （差し込みブロックの「元が変わりました」は**出ない**。自由ブロックだから）
- 流し込み先は**いま選んでいる階層**。同じ名前の人は足さない（**マニュアル全体**で見る。階層をまたいで二重に入らない）
- **紙にも画面にも出ていない項目は持ち込まない。** 「紙に出す項目」で電話・メールを切っている状態で取り込むと、
  その2つは**入れない**（入れた自覚も、見る手段も、消す手段も無いまま保存されるのを避ける）。
  役割・所属は §5-4 の対応表そのものなので持ち込む

| 差し込み元 | 体制図のどこへ |
| --- | --- |
| `project_members.member_name` | 人の名前 |
| `project_members.role` | 人の役割 |
| `users.phone`（社内ユーザーだけ） | 人の電話（`project.resolver.ts` の `project.team` と同じ規律） |
| `project_members.is_external` | **使わない**（外部の方の会社名を持つ列が無いため。所属は手で打つ） |
| `gpm_members.tier` | 階層（`top`/`lead`/`unit` → 決裁層／推進層／実務層 の**文字**にして階層の名前に） |
| `gpm_members.group_label` | チーム名 |
| `gpm_members.side` | **チームの所属の文字**（`internal`→自社・`client`→発注者・`pm`→PM会社・`vendor`→業者）。区分としては持たず、文字として残す |
| `gpm_members.org` / `role` / `email` / `badge` | 人の所属・役割・メール・バッジ |

### 5-5. API

| メソッド | 道 | 権限 |
| --- | --- | --- |
| GET | `/techops/manuals/:id/org-seed` | **qsheet editor** ＋ マニュアルが `canAccessManual` を通っていること。**`gpm_members` の脚だけ追加で `sales` reader**（無ければその部分を空で返す・403 にしない） |

⚠️ **当初は「qsheet reader だけ」と書いていたが、実装時のレビューで穴だと分かったので上のとおりに直した。**
`manual-resolvers/` の共通ポリシー（冊子を見られる人になら差し込んだ情報は見える）はこの口には当てはまらない:
①resolve はマニュアルに実在するブロックしか読まないが、`org-seed` は**ブロックが1つも無くても全件返る**
②`gpm_members`（担当者のメール）を読む既存の口は `sales` reader を要求している（`server/src/contexts/gpm/index.ts`）
③取り込んだ結果を保存するには editor が要るので、reader に返す意味がそもそも無い

保存は既存の `PUT /techops/manuals/:id/pages/:pageId`（ブロックの中身として一緒に保存される）。
`org-seed` はマニュアルの `project_id` から `project_members` と `gpm_members` を読んで候補を返すだけ
（`program_id` のマニュアルでは両方とも空で返す ＝ 取り込みボタンを出さない）。

## 6. 確定・スマホ・PDF

- **確定（`fix`）**: 自由ブロックなので**そのまま凍る**（`frozen` は差し込みブロック専用の仕組み）
- **スマホ閲覧（⑥）**: チームが横に入らないので**1列に積む**。階層の見出しがそのまま順序になる
  （`MembersTab.tsx` と同じ考え方）。**これだけ未了**（§8 の⑤に実測とともに書いた）
- **PDF**: キャンバスの React ツリーをそのまま描く（`manualPrintExport.ts`）。体制図も他のブロックと同じ

## 8. 作る順

| 階層 | 中身 |
| --- | --- |
| ① | 型（`types.ts` の union に1行）＋ 置くカタログに1つ ＋ 空の体制図を置ける |
| ② | キャンバスの描画（枠線・縦罫）とキャンバス上の編集（階層・チーム・人の追加削除・その場入力） |
| ③ | 右パネル（階層・出す項目・線） |
| ④ | 取り込み（`/org-seed` 1本） |
| ⑤ | インクの目安 ✅ ／ 出す前の検査 ✅ ／ **スマホ1列 ── 未了**（下記） |

**⑤の「スマホ1列」だけ未了**（2026-09-13 時点）。スマホ閲覧（⑥）は `ManualPrintDocument` を
そのまま縮小して見せる作りで、ブロックを積み直す受け皿が無い。体制図だけのために分岐を足すと
「編集＝閲覧＝紙」の保証が崩れるため、v1 は紙と同じ縮小表示のままにした（§6）。

**実測**: 375px 幅では縮小率が約 0.31 になり、体制図の本文 10px は実効およそ 3.1px ＝ 読めない。
つまり**いまのスマホ閲覧では体制図は事実上読めない**。直すときは体制図だけに分岐を足すのではなく、
スマホ閲覧そのものに「1列に積む」道を作る（§6）。

## 9. v1 でやらないこと

- **チームをドラッグして並べ替える** — 階層と並び順のボタンで足りる。キャンバスのブロック移動と取り合う
- **マニュアルから案件・プロジェクト管理へ書き戻す** — **一方通行**。現場の体制を案件の正にしない
- **線を手で引く** — つながりは階層の縦罫だけ。自由な線が要るときは既存の図形ブロック（線・矢印）で引ける
- **写真つきの顔写真入り体制図** — 紙の決めごと（§4・写真は原則載せない）

## 10. 決まったこと（2026-09-13・利用者の判断）

### 10-1. 階層のテンプレートは持たない ── 空の1階層から始める

**既定の階層の名前（「統括／各パート／外部・応援」か「決裁層／推進層／実務層」か）を用意するか**
を訊いたところ、**どちらも用意せず空から**と決まった。案件ごとに呼び方が違うため、
テンプレートがあるとかえって直す手間になる。

- 置いた直後は**名前の無い階層が1つ**と「＋ チーム」だけ
- 階層の名前は自由入力。階層は増減・並べ替えできる
- （同じ案件で使い回したくなったら、マニュアルごと**テンプレート**にする既存の仕組みが使える・
  production-manual.md 階層E）

### 10-2. 立場の区分は持たない ── 所属は自由入力

**チームの「立場」（自社・発注者・PM会社・業者）を制作向けに言い換えるか増やすか**を訊いたところ、
**区分そのものをやめて自由入力**と決まった。

- チームは**所属の文字**（任意）を持つだけ。「自社」「東都TV」「東洋中継サービス」など好きに打つ
- **枠線はどのチームも同じ。** 立場による線種・色の描き分けはしない
- ⚠️ その代わり、**ひと目で「社内／社外」が分かる手がかりはキャンバスから無くなる**
  （利用者が承知のうえでの判断）。見分けたいときはチーム名・所属の文字で書き分ける
