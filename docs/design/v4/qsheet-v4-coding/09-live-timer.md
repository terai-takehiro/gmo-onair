# 計時・視聴者（計時LIVE の統合）— ミニアプリとしての実装設計

> **2026-08-21 作成。** 計時LIVE（`client-live/`・ベースパス `/live/`）を制作資料に取り込み、
> **Qシート／スケジュール表／収録・配信設定と並ぶミニアプリ**にするための設計です。
>
> **モックアップ**: https://claude.ai/code/artifact/aa1b9c08-ffb4-4cb1-8ce9-c6aba576734a
> （運用画面・表示画面・タイマー管理・スマホの4枚）
>
> ⚠️ **機能は1つも落としません。** 利用者の指示は「現在の計時LIVEの機能はいいが、
> UI/UX がネイティブ風になっていないのと、導線を制作資料の思想に合わせ直したい」です。
> **変えるのは導線と見た目**で、タイマーの意味論と公開URLは現行のままです。
> ⚠️ **1点だけ挙動を変えます**: 視聴者の取得をサーバー側に移します（利用者の判断・§5）。

## 0. 決めたこと

1. **セッション一覧（`/live/`）をやめる。** 入口は**案件のミニアプリ一覧**に一本化する。
   いまの「セッション」は案件と二重に存在しており、GLS 紐付けが任意なのもそのため。
2. **`liveops_programs` は残す。** 視聴者取得の設定（YouTube URL・Jstream LPID・Zoom・Teams）を
   持つ実体として意味があるので、**案件から 1:1 で自動的に用意する**形に変える。
3. **公開URL `/live/display/:timerId` は 1 文字も変えない。** 会場モニター・OBS のブラウザソース・
   配布済みのURLがそこで成立している。**無認証のまま**にする。
4. **タイマーの意味論を変えない。** カウントダウンのみ・0 を過ぎたら `+MM:SS`・
   サーバーが正で 100ms ごとに配信・リセットは尺ごと 0 に戻す・±調整は計時中も効く。
5. **画面が無かった2つを出す。** 黄色に変わるしきい値（DB は 60 秒固定）と、
   運用画面がどのタイマーを出すか（いまは常に 1 本目）。
6. 権限区画は **`liveops` のまま**にする（migration 210 で7区画に統合済みのため増やさない）。
7. ⚠️ **視聴者の取得をサーバー側に移す**（利用者の明示の判断・2026-08-21）。
   いまは運用画面を開いている間しか取りに行かないため、**本番中に閉じると表示画面の数字が止まります**。
   これを塞ぎます。→ **§5 が新しい設計の本体**。
8. **計測は組織共通の鍵1本で回す**（同・2026-08-21）。人の鍵にはフォールバックしない。
   未設定なら**計測を開始させない**。→ §5-4
9. **自動停止は開始日の 23:59（JST）が既定**。24時間を超える番組は**終了時刻を手で入れて**延ばす
   （同・2026-08-21）。→ §5-2-1
10. **同時に回すのは 1 案件**（同・2026-08-21）。集計は「開始」を押してから「停止」を押すまでで、
    押し忘れは 23:59 の自動停止で止める。**1案件が回っていれば運用上は足りる**という判断。→ §5-2

## 2. 置き場所と導線

### 2-1. ミニアプリとして並べる

```
案件 60周年 記念式典（GLS-A012）
├── スケジュール表
├── Qシート（香盤表）
├── 収録設定 ／ 配信設定
└── 計時・視聴者          ◀ ここ
```

⚠️ **`shared/src/production/miniapps.ts`（[`01-app-structure.md`](01-app-structure.md)）に
1件足すこと。**

**名前**: 画面上は「**計時・視聴者**」にします。「計時LIVE」はアプリ名でしたが、
制作資料の中のミニアプリになるので、何をするものかで呼びます
（⚠️ `docs/wording.md` に追記が要ります）。

### 2-2. セッションと案件の関係

いまは `liveops_programs`（セッション）が主体で、`project_id` は**任意**でした。
統合後は**案件が主体**になります。

- **案件のミニアプリを初めて開いたとき、その案件の `liveops_programs` を1件自動で作る**
  （名前は案件名から。`project_id` を入れる）
- 既存の行はそのまま使う（`project_id` が入っているものは案件から引ける）
- **`project_id` が無い既存セッション**は、案件に紐づかない資料単体（`doc_no`）として扱うか、
  移行時に人が案件を選ぶ。→ §7-1 で確認

⚠️ **`liveops_programs` を消さない。** 表示画面が `program_id` で視聴者の記録を引いており、
タイマーとも紐づいています。消すと配布済みの表示URLが壊れます。

### 2-3. URL

| いま | これから | 理由 |
| --- | --- | --- |
| `/live/` （セッション一覧） | **`/live/`（案件の文脈で運用画面）** | 一覧をやめるため |
| `/live/program/:programId` | `/live/`＋`?project=` | 案件から入るので programId を URL に出さない |
| `/live/program/:programId/timers` | `/live/timers` | 同上 |
| `/live/program/:programId/settings` | `/live/sources` | 「番組設定」は視聴者の取得元設定なので名前を変える |
| `/live/settings` | **そのまま** | 全社共通のキー設定 |

⚠️ 旧URL（`/live/program/:id`）は**リダイレクトを残す**こと。ブックマークされています。

## 3. 画面

### 3-1. 運用画面（PC）

左に**タイマー**、右に**視聴者**。モックのとおり。

- タイマーは大きな数字＋フェーズ色＋下端の進捗バー。**「設定 MM:SS」と点滅ドット**を残す
- プリセットは計時中に淡くして、その理由を1行で書く
- **リセットの意味を注記に書く**（「設定した尺ごと 0 に戻ります。プリセットには戻りません」）
- 視聴者は取得対象のチップ（ON=塗り／OFF=取り消し線／未設定=淡色）→ YouTube の内訳 →
  Jstream・Zoom・Teams・合計 → 推移 → ログ
- **計測はサーバーが回している**ので、この画面を閉じても止まりません（§5）。
  代わりに「**誰がいつ計測を始めたか**」と「**いつ自動で止まるか**」を帯に出します

### 3-2. 表示画面（公開URL）

**この画面が本番の出力です。** 歯車の7つの切替で3レイアウトが実際に変わります。

- 既定は黒・タイマーのみ。歯車から視聴者を足すと 6:4 分割、タイマーを消すと視聴者のみ
- 赤フェーズ: 文字の点滅・グロー・背後の放射グラデーションの脈動
- **白ベース**で全体反転
- 切替は**この端末にだけ**残す旨を書く

### 3-3. タイマー管理

- タイマーは案件に**何本でも**（本番尺・休憩・リハ）
- タイマーごとに**表示画面のURL**（コピー／開く）
- **黄色に変わるしきい値**をタイマーごとに選ぶ ← 新
- **運用画面に出すタイマー**を選ぶ ← 新
- 「URLの作り直しはできない。外したいときはタイマーごと消す」と明記

### 3-4. スマホ

**会場で手元から操作する**のが主目的。表示は見るだけ。

- 大きな数字 → 開始/停止（幅広）＋リセット → ±調整（46px）→ プリセット → 視聴者（見るだけ）
- 計時中のリセットは**下から出るシートで確認**
- 「表示画面のURLをコピー」を置く（現場で人に渡す）
- 取得の開始/停止と設定変更は PC に案内する

## 4. データモデル

**既存テーブルをそのまま使います。** ここに書くのは導線のための2つだけで、
**サーバー側計測のための列とテーブルは [§5-4](#5-4-誰の鍵で回すか) / [§5-5](#5-5-失敗が誰にも見えなくなる問題) にあります**（そちらのほうが大きい）。

```sql
-- 運用画面に出すタイマーを案件ごとに1本決める
ALTER TABLE liveops_programs
  ADD COLUMN main_timer_id TEXT REFERENCES liveops_timers(id) ON DELETE SET NULL;

-- 案件から1:1で引けるようにする（既存は NULL 可のまま）
CREATE UNIQUE INDEX liveops_programs_project_key
  ON liveops_programs (project_id)
  WHERE project_id IS NOT NULL AND deleted_at IS NULL;
```

- `warning_threshold_sec` は**既にある**ので DDL は不要。API と画面を足すだけ
- `liveops_snapshots` / `liveops_settings` / `liveops_teams_subscriptions` は**変更なし**
- ⚠️ **`liveops_snapshots` を変えないことが重要**です。表示画面はこの表を読んでいるので、
  書き手がブラウザからサーバーに変わっても**表示画面は1行も直さずに済みます**

⚠️ **一意インデックスを張る前に、`project_id` が重複している既存行が無いか確認すること。**
いまは1案件に複数セッションを作れてしまうため、重複していたら移行時に統合が要ります。

## 5. 視聴者の取得をサーバー側へ（この統合でいちばん大きい変更）

> **利用者の判断（2026-08-21）**: 「計時LIVEはサーバー側に移してください。」

### 5-1. なぜ移すのか

いまは**運用画面を開いているブラウザが取りに行っています**（`useViewer.ts` の
`setInterval`）。そのため:

- **本番中に運用画面を閉じると、取得が止まります**
- 取得が止まると `liveops_snapshots` に記録が増えないので、
  **表示画面（会場モニター・OBS）の数字が最後の記録のまま固まります**
- 現場では「見ていないなら閉じてよい」と考えるのが自然なので、**踏みやすい**

サーバーが回せば、**誰も画面を開いていなくても数字が動き続けます**。

### 5-2. 何を回すか — 「計測」という単位を作る

⚠️ **全案件を常時回すことはできません。** YouTube Data API v3 の既定の割り当ては
**1日 10,000 ユニット**で、`videos.list` は 1 回 1 ユニットです。取得間隔 10 秒だと
**1案件で 1日あたり約 8,640 回**＝ほぼ割り当て全部を使い切ります。
**2案件を同時に常時回すと超過します。**

**利用者の判断（2026-08-21）**:

> 「YouTube含めた視聴者数の集計は開始ボタンを押してから集計を開始し、終了を押したら終わるのが基本。
> ただし押し忘れによるAPI浪費を回避するため、その日の23:59に自動停止。（例外設定された場合は除く）
> そのうえで1案件まわっていれば基本問題ありません。」

つまり **「計測」を明示的に始めて終える単位**にし、**同時に回すのは 1 案件**にします。
割り当ての件（§5-7 b）は**これで閉じます** — 引き上げを待たずに実装してよい、ということです。

| | 決め |
| --- | --- |
| 始める | 運用画面（またはスマホ）の**「計測を開始」**。誰が押したかを記録する |
| 終える | **「計測を停止」**、または**自動停止の時刻**に達したとき |
| 自動停止 | **原則は開始日の 23:59（JST）**。24時間を超える番組もあるので、**終了時刻を手で入れれば延ばせる**（→ §5-2-1） |
| 同時に回せる数 | **1 案件**（既定）。超えたら開始を断り、**いま回っている案件と、誰がいつ始めたか**を見せる |
| 間隔 | 既存の `liveops_settings.polling_interval_sec`（5〜300秒・既定 10）をそのまま使う |

**「計測中」はみんなに見える状態**になります（いまは押した本人のブラウザだけ）。

#### 5-2-1. 自動停止の決め（利用者の判断・2026-08-21）

> 「24時間以上配信する番組もなくはないので、原則は開始日23:59まで、
> イレギュラーは終了時間を入力するような感じがいい。」

| | 決め |
| --- | --- |
| **既定** | **開始した日の 23:59:59（JST）**。何も指定しなければこれ（`measure_until_kind = 'default'`） |
| **イレギュラー** | 開始のときに**終了の日時を手で入れる**（`measure_until_kind = 'manual'`）。**24時間を超えてもよい** |
| 途中で延ばす | 計測中でも `measure_until` を変えられる（画面の帯から） |
| 上限 | **設けない。** ただし **7日を超える指定は確認を挟む**（打ち間違いを止めるため。止めはしない） |

⚠️ **「開始から N 時間」にしない。** 朝から仕込んで夜に本番、という日は
**開始が早いほど早く切れて**しまい、本番中に止まります。日付で切るほうが現場の感覚に合います。

⚠️ **タイムゾーンは JST 固定**（`Asia/Tokyo`）。`toISOString()` を使うと1日ずれます
（`flow-template.service.ts` に同じ形の実バグが残っている・[`02-schedule.md`](02-schedule.md) 参照）。
**日付の境目はサーバーで JST として計算すること。**

⚠️ **日をまたぐ計測は割り当てを2日ぶん使います。** YouTube の割り当ては
**太平洋時間の 0:00 にリセット**されるので、JST の日付とはずれます。
24時間超の計測をするときは、**リセットをまたぐぶん実質的には回りますが、その日は他の案件を計測できません**
（→ §5-7 b）。

**画面**: 開始のボタンの隣に「**今日の 23:59 まで**」と出し、
その横に「**終了時刻を指定する**」を置く（既定を選ばせない・イレギュラーだけ手を動かす形）。

### 5-3. 動かし方（既存の作法に合わせる）

**すでに同じ形のものがあります** — Teams のサブスク更新
（`liveops/index.ts` の `initLiveopsServices()` → `restoreSubscriptions()` →
`startSubscriptionRenewal()`）。**これに倣います。**

```
サーバー起動
  └ initLiveopsServices()
      ├ restoreSubscriptions()        （既存・Teams）
      ├ startSubscriptionRenewal()    （既存・Teams）
      └ restoreMeasurements()         ◀ 新規
          ├ measuring = true の行を読む
          ├ auto_stop_at を過ぎているものは stopped にして起こさない
          └ 残りに setInterval を張る
```

- **1案件につき 1 つの `setInterval`**（`Map<programId, NodeJS.Timeout>`）。
  開始で張り、停止・自動停止・エラー打ち切りで `clearInterval`
- **取得の中身は既存の proxy をそのまま使う**（`proxy.routes.ts` の
  YouTube / Jstream / Zoom の呼び出しをサービス関数に切り出して共用する）。
  **新しい API クライアントは書かない**
- **Teams は既に push（Graph の通知）でサーバー側**なので、そのまま
- 1 回の取得が終わったら、**いまと同じ形で `liveops_snapshots` に 1 行入れる**
  （表示画面はこれを読んでいるので、**表示画面側は 1 行も変えなくてよい**）

⚠️ **多重起動に注意。** 本番と検証は別コンテナなので衝突しませんが、
将来サーバーを 2 つに増やすと**同じ案件を 2 重に取りに行って割り当てが倍**になります。
`liveops_programs` の行に**取得中のインスタンス印**を持たせ、
`UPDATE … WHERE measuring = false` の戻り行数で取り合う形にしておくこと。

### 5-4. 誰の鍵で回すか — **組織共通の鍵を1本置く**

> **利用者の判断（2026-08-21）**: 「誰の鍵で回すか — 組織共通の鍵を1本置く。」

いまは**画面を開いている人の鍵**を使い、無ければ**組織内の他人の鍵にフォールバック**します
（`resolve-key.ts`）。サーバーには「いまの人」がいないうえ、この作りには問題があります。

| いまの作り | 何が困るか |
| --- | --- |
| `liveops_settings` は **PK が `user_id`**（1人1行） | サーバー側計測に「その人」がいない |
| 無ければ**他人の鍵に落ちる** | **誰の割り当てを使っているのか誰にも分からない**。画面は「他ユーザーのキーを共有利用中」と出すだけ |
| 退職・異動でその人の行が消えると | **本番の最中に計測が止まる**（原因も分かりにくい） |

**組織共通の鍵を1本持ちます。**

```sql
-- 組織で1本だけ。id に CHECK を付けて2行目を作れなくする
CREATE TABLE liveops_org_settings (
  id                      BOOLEAN PRIMARY KEY DEFAULT true CHECK (id),
  youtube_api_key_enc     TEXT,
  jstream_token_enc       TEXT,
  zoom_account_id_enc     TEXT,
  zoom_client_id_enc      TEXT,
  zoom_client_secret_enc  TEXT,
  teams_tenant_id_enc     TEXT,
  teams_client_id_enc     TEXT,
  teams_client_secret_enc TEXT,
  updated_by              TEXT REFERENCES users(id),
  updated_at              TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

- 暗号化は既存と同じ **AES-256-GCM**（`liveops/crypto.ts`）。列名も `liveops_settings` に揃える
- **編集できるのは `liveops:manager`** だけ。設定画面に「組織共通の鍵」の節を作る
- **サーバー側計測はこの鍵だけを使う。** 人の鍵にはフォールバック**しない**
  （落ちるときは「組織共通の鍵が未設定です」と**はっきり止まる**ほうがよい。
  黙って誰かの割り当てを食う今の形が事故のもと）
- 鍵が未設定なら**計測を開始させない**（画面に「設定 → 組織共通の鍵」への導線を出す）

**`liveops_programs` に足す列**（`measure_started_by` は**記録用**であって、鍵の選択には使いません）:

```sql
ALTER TABLE liveops_programs
  ADD COLUMN measuring          BOOLEAN NOT NULL DEFAULT false,
  ADD COLUMN measure_started_at TIMESTAMPTZ,
  ADD COLUMN measure_started_by TEXT REFERENCES users(id),   -- 誰が始めたかの記録だけ
  ADD COLUMN measure_until      TIMESTAMPTZ,                 -- 自動停止の時刻（§5-2）
  ADD COLUMN measure_until_kind TEXT NOT NULL DEFAULT 'default'
                                CHECK (measure_until_kind IN ('default','manual')),
  ADD COLUMN measure_platforms  JSONB NOT NULL DEFAULT '["youtube","jstream","zoom","teams"]'::jsonb,
  ADD COLUMN measure_last_ok_at TIMESTAMPTZ,
  ADD COLUMN measure_fail_count INTEGER NOT NULL DEFAULT 0,
  ADD COLUMN measure_owner      TEXT;                        -- 取り合い用のインスタンス印
```

- **`measure_platforms` が「何を取りに行くか」の正**。いまは端末の
  `localStorage['lv_dash_platforms_{programId}']` にありますが、
  **サーバーが読めないので DB に移します**
- ⚠️ **表示の ON/OFF は端末のままでよい**（表示画面の 7 つの切替）。
  **取りに行くか**と**出すか**は別物です。混ぜないこと
- 鍵が失効した場合は、**失敗を数えて 5 回続いたら計測を止め**、
  理由をログに残す（黙って回し続けて割り当てを消費しない）

#### 個人ごとの鍵はどうするか

**残します。ただし用途を分けます。**

| | 使うところ |
| --- | --- |
| **組織共通の鍵**（新） | **サーバー側計測**（これだけ） |
| 個人ごとの鍵（既存 `liveops_settings`） | 設定画面の**接続テスト**。「自分の鍵で試す」用 |

⚠️ **「他ユーザーのキーを共有利用中」の表示は、いまの意味のままでは誤解を生みます。**
組織共通の鍵ができた後は、**計測はその鍵で回っている**のに、設定画面だけ
「他ユーザーのキーを共有利用中」と出ると読み手が取り違えます。
**この文言は接続テストの文脈に限定するか、書き換えること**
（`1-4` の棚卸しでは「そのまま（消すと事故る）」としていましたが、
**この判断により文言の見直しが要ります**）。

⚠️ **移行**: 組織共通の鍵は**自動で入れません**（誰の鍵を昇格させるか機械には決められない）。
移行時に `liveops:manager` が設定画面で1回入れる運用にし、
**入るまでは計測を開始できない**（既存の画面からの取得は今までどおり動きます）。

### 5-5. 失敗が誰にも見えなくなる問題

いまのログは**画面の中のメモリだけ**（100 件・閉じると消える）でした。
サーバーが回すと、**失敗しても誰も見ていません**。そこで記録します。

```sql
CREATE TABLE liveops_poll_log (
  id          BIGSERIAL PRIMARY KEY,
  program_id  TEXT NOT NULL REFERENCES liveops_programs(id) ON DELETE CASCADE,
  at          TIMESTAMPTZ NOT NULL DEFAULT now(),
  platform    TEXT NOT NULL,          -- youtube | jstream | zoom | teams | system
  level       TEXT NOT NULL,          -- ok | error | info
  count       INTEGER,                -- 取れた数（ok のとき）
  message     TEXT                    -- 失敗の理由（API が返した文言）
);
CREATE INDEX liveops_poll_log_prog ON liveops_poll_log (program_id, at DESC);
```

- 運用画面のログ欄は**この表を読む**（見た目は今のまま・色分けも同じ）
- ⚠️ **際限なく貯めない。** 計測が終わったら**その案件の直近 500 行だけ残して消す**か、
  日次で 30 日より古い行を消す。`ok` の行は数が多いので、
  **`ok` は 10 回に 1 回だけ書く**のでも足ります（失敗は毎回書く）
- **成功が続いている間の「最終更新」は `measure_last_ok_at`** を見ればよいので、
  ログを毎回書く必要はありません

#### b. YouTube の割り当て（決着・2026-08-21）

**利用者の判断で閉じました。** 「1案件まわっていれば基本問題ありません」。
組織共通の鍵1本（§5-4）に消費が集まっても、**同時 1 案件なら既定の割り当てに収まります**。

| | |
| --- | --- |
| 既定の割り当て | **1日 10,000 ユニット**（`videos.list` は 1 回 1 ユニット） |
| 取得間隔 10 秒だと | **1案件あたり 1日 約 8,640 回**（10,000 の約 86%） |
| したがって | **同時に回せるのは 1 案件**。2案件目の開始は**断る**（エラーではなく「いま回っている案件」を見せる） |
| 割り当ての引き上げ | **不要**。引き上げ申請を待たずに実装してよい |

⚠️ **8,640 は 10,000 の 86% です。余白は 1,360 ユニットしかありません。**
つまり **1案件を丸1日回すと、その日は他に何もできない**ということです。実装で必ず守ること:

1. **計測していない番組は 1 回も呼ばない。** 運用画面を開いただけ・一覧を出しただけで
   `videos.list` を呼ばないこと（いまのブラウザ側の実装は開いている間ずっと呼びます）。
2. **同時 1 案件を DB で担保する。** 「画面で断る」だけでは多重起動で抜けます
   （→ §5-3 の `measure_owner` による取り合いの解決と同じ仕組みで、**開始時に本数を数えて弾く**）。
3. **失敗しても間隔を詰めない。** 失敗 5 回で打ち切り（§5-5）はそのまま。
   再試行で間隔が縮むと割り当てを一気に食います。
4. **消費数を数えて画面に出す。** `quotaUser` では割り当てを分けられないので、
   **こちらで呼んだ回数を数えます**（`liveops_poll_log` の行数がそのまま消費数になります）。
   運用画面に「**今日の消費 8,412 / 10,000**」と出す。
5. **日をまたぐ計測は 2 日ぶんを使います。** リセットは**太平洋時間の 0:00**（JST の 16:00〜17:00）で、
   JST の日付とはずれます。23:59 までの既定でも、**JST 16:00 で 1 回リセットが入る**ということです。
   24時間超の手入力（§5-2-1）をしたときは、**リセットをまたぐので実質的には回りますが**、
   その日の他の計測はできません。

**同時 1 案件で足りなくなったとき**（設計としては用意しておく・いまは作らない）:

- 取得間隔を**案件ごとに**変えられるようにする（既定 10 秒 → 本番以外は 60 秒 等）
- YouTube だけ間隔を長くする（Jstream・Zoom は割り当ての制約が違う）
- 割り当ての引き上げを申請する（Google の審査があるので即日では増えません）
