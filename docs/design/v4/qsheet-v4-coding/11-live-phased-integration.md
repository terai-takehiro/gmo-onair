## 2. フェーズ1: 軽量統合（バンドル分離のまま）

**詳細設計は [`10-live-lite-integration.md`](10-live-lite-integration.md) が正。** ここでは
「フェーズ」としての要点だけを要約する。

### 2-1. スコープ

- `MiniAppDef` に `kind: 'external'` を新設し、`MINI_APPS` に計時・視聴者を1件登録する
  （`MiniAppKey: 'liveops'`）。`crossBundle: true` を持たせ、**別バンドルへの本物のページ遷移**
  であることを型で明示する（`<Link>` の誤用を型で塞ぐ・10 §1）
- `JourneyPage` の `MiniAppTiles` に、**`scope === 'project'` のときだけ**タイルを追加する
  （`scope === 'program'` では出さない・理由は §4-4 と共通、10 §4-4）
- ヘッダーの `MiniAppSwitcher`（`RecordingPage` / `StreamingPage` の2画面）に計時・視聴者を追加する。
  **他の画面（進行台本・スケジュール表）へは広げない**（今回のスコープ外・10 §2-4）
- Owner（案件）→ `liveops_programs` の解決は、**新設する API ルート1本**
  （`POST /api/v1/liveops/programs/resolve-by-project/:projectId`）で「取得または作成」を
  アトミックに行う。**DB migration は不要**（既存の一意インデックス `liveops_programs_project_key`
  ＝ migration 221・実装済みに乗るだけ・10 §4）
- `client-live` 側に橋渡し用の新規画面（`/live/open?project=:id`）を1つ置き、
  そこで「取得または作成」を呼んでから実プログラムの画面へリダイレクトする
  （qsheet 側は静的な URL テンプレートを組み立てるだけで済む・10 §4-3）
- 改称は**表示名（`label`）だけ**。ディレクトリ名・ベースパス・`permissionModule`・
  DB テーブル名・Socket 名前空間・`localStorage` キーといった内部識別子は一切変えない
  （10 §3-2 の対応表を `client-live/CLAUDE.md` に残す）
- `scope === 'program'`（qsheet 自身のマニュアル番組）への対応は**この段階では解決しない**
  （§4-4 で改めて扱う。抜け道として `/live/` からのスタンドアロン作成が残る）

### 2-2. 「白い一瞬」の扱い（正直に書く）

バンドルが別（`client-qsheet` は `/qsheet/`、`client-live` は `/live/`）なので、
**切替はブラウザの本物のページ遷移であり、React ツリーが破棄・再構築される。**
同一オリジンなので DNS/TLS のコストは無く、Cookie/JWT もそのまま使えるため再ログインは
挟まらないが、**HTML/JS の取得と初回描画の間の空白は消せない**。

| 手段 | 効果 | 限界 |
| --- | --- | --- |
| 同一オリジン | 接続コストがそもそも発生しない | 取得自体は必要 |
| `prefetch` | ホバー時に事前取得しておける | 空白そのものは消えない |
| Speculation Rules（`prerender`） | Chromium系では体感を SPA 内遷移に近づけられる | Safari/Firefox は非対応。**副作用のある処理（「取得または作成」の POST）をホバーだけで実行しないよう対策が要る**（10 §2-3） |

**フェーズ1ではこの空白を完全には消せないことを前提として受け入れる。** これが
「体感の悪さが実際にどれだけ問題になるか」を運用で測る対象になる（§4-2 の判断材料）。

## 3. フェーズ1がフェーズ2の前提を崩さないことの確認

**フェーズ1で作るものは、フェーズ2で作り直さず土台として使う。** 型・URL・DB の3観点で確認する。

| 観点 | フェーズ1が作るもの | フェーズ2でどうなるか | 後戻りが要るか |
| --- | --- | --- | --- |
| **型** | `MiniAppKey: 'liveops'`、`kind: 'external'`、`MiniAppExternalDef`（`crossBundle` / `path` / `supportedOwnerKinds`） | `kind` を `'external'` から、同一バンドル内の遷移を表す種別（`'document'` 相当。§4-1 で詳述）へ**差し替える**。`MiniAppKey: 'liveops'` は**変えずにそのまま使う**（「あとから変えない安定キー」の原則どおり） | **いいえ。** キー自体は流用でき、差し替わるのは `kind` の値と付随フィールドだけ |
| **URL** | `/live/open?project=:id`（橋渡し専用）、`resolve-by-project` ルート | `/live/open` は橋渡し役目を終えたら**削除してよい**（09本体の URL 再設計・自動プロビジョニングが同じ役割を運用画面自身の初回オープンで肩代わりするため）。**表示画面 `/live/display/:timerId` にはどちらのフェーズも一切触れない** | `/live/open` 自体は消えるが、**それ以外の URL（表示画面・案件のミニアプリ導線）には影響しない**。消える1画面のためだけの後戻りで、設計判断の巻き戻しではない |
| **DB** | migration ゼロ。既存の一意インデックス（migration 221・`liveops_programs_project_key`）に乗るだけ | フェーズ2で `main_timer_id` 等の列を足すとしても、**同じ一意インデックスの上に積むだけ**（09 impl §3-2 の DDL 案がまさにこの形） | **いいえ。** フェーズ1はスキーマに触れていないので、フェーズ2側が何を足しても矛盾しない |
| **権限区画** | `liveops` のまま。触らない | フェーズ2で `qsheet` に寄せるかどうかは未決（§6） | フェーズ1はここに手を付けないため、**どちらの結論になっても後戻りコストはフェーズ1側には発生しない** |

**結論**: フェーズ1は「フェーズ2をやらないなら要らない大工事」を一切含んでいない。
唯一使い捨てになるのは橋渡し画面 `/live/open` 一枚（当初から橋渡し専用と明記した部品）であり、
**設計判断（型のキー・DB制約・表示画面の不可侵）はどれもフェーズ2にそのまま持ち越せる。**

## 4. フェーズ2: バンドル統合（本体）

### 4-1. スコープ（概要）

- `client-live` の運用4画面（ダッシュボード・タイマー管理・番組設定・設定。**表示画面は除く**）を
  `client-qsheet` バンドルの中へ実際に移し、React Router 内の `<Link>` 遷移にする
  （切替時の全画面リロードを解消する＝この文書の元の依頼事項）
- **表示画面（`/live/display/:timerId`）だけは `client-live` バンドルに残す**か、
  少なくとも**無認証・URL固定という契約は寸分も変えない形で**独立させ続ける。
  運用画面の作り直しと表示画面の作り直しは**別の PR に切り離す**（09 impl §8-4 と同じ判断）
- 09 §2-3 の URL 再設計（`/live/program/:id` → 案件文脈の URL）を実施し、旧URLへは
  リダイレクトを残す
- 09 §2-2 のとおり、案件のハブ画面を初めて開いたときに `liveops_programs` を自動で用意する
  （フェーズ1の `resolve-by-project` ロジックを運用画面側の初回オープン処理に統合する）
- セッション一覧（`SessionHomePage`）を廃止する
- `MiniAppKey: 'liveops'` の `kind` を `'external'` から、同一バンドル内の遷移を表す種別へ
  差し替える。ただし**そのまま `kind: 'document'` に当てはめられるかは要検討**——
  `MiniAppDocumentDef` は `docPrefix` / `docNoSeq`（資料番号の採番）を前提にしており、
  計時・視聴者には「資料番号」という概念が無い。**フェーズ2着手時に型をどう拡張するかは
  改めて設計が要る**（`kind: 'panel'` に寄せる案・新しい `kind` を作る案のどちらもあり得る）
- 権限区画（`liveops` のまま残すか `qsheet` に寄せるか）の方針を決める（§6）

### 4-2. フェーズ2着手の判断条件

#### 旧 impl doc §12-11 の推奨は、もう満たされている

09 impl §12-11 は PR7 のスコープを絞った理由の1つとして
「制作技術支援自身もまだ v4 共通シェルへの載せ替えを終えていない」ことを挙げ、
「制作資料自身の共通シェル載せ替えと合わせて別段で行うことを推奨する」としていた。

**事前調査④で確認したとおり、これはもう成立しない。** `client-qsheet/CLAUDE.md` に
「共通シェル（`shared/src/client/shell/`）への載せ替え」が完了済みと明記されており、
git 履歴にも該当コミット（`7187a8c` / `49c0028`）がある。

**したがって、旧文書が挙げていた着手を止める理由は解消済みである。**

#### それでも、今すぐフェーズ2に進むべきではない理由

旧条件が1つ外れたことは、**着手してよい必要条件が1つ揃っただけ**であり、
十分条件ではない。以下の理由が新たに（あるいは引き続き）残っている。

| # | 理由 | 詳細 |
| --- | --- | --- |
| 1 | **フェーズ1が未リリース・未実測** | フェーズ1は「別バンドルへの遷移がどれだけ問題になるか」を実際の利用で測る機会でもある。§2-2 の緩和策（prefetch／Speculation Rules）でどこまで体感が改善するかを見ないまま、いきなり「バンドルを1つにする」という大工事に進むのは、**問題の大きさを確かめる前に最も高いコストの解決策を選ぶ**ことになる。まずフェーズ1を出し、最低1回の通常リリースを挟んで運用で観測してから判断する（決めたこと §0-9） |
| 2 | **`scope === 'program'`（マニュアル番組）対応の設計そのものが、09本体にも存在しない** | 10 §6-2 が指摘したとおり、`liveops_programs.project_id` は `projects` テーブルしか指せず、qsheet 自身の「番組」＝ `qsheet_programs`（migration 227・別テーブル・別ID型）との対応は、09本体の設計にも書かれていない。**フェーズ2に進んでも、この非対称は自動的には埋まらない。** バンドルを1つにする効果（一体感）は「案件配下でしか使えない」という制約がある限り部分的にしか活きない。着手前に、この空白を埋めるか・埋めずに割り切るかの方針を先に決める必要がある |
| 3 | **変更範囲が広がるほど、表示画面を壊す事故の機会が増える** | フェーズ2は運用4画面を作り直す大工事で、`App.tsx` の `DisplayRouter` 分岐を含むファイル群に手が入る範囲がフェーズ1より大きく広がる。09 impl §8-3 の契約テストは残るが、テストは「気づける」仕組みであって「事故を減らす」仕組みではない。**フェーズ1はこのファイル群に一切触れないため、このリスクをゼロに保てる**。フェーズ2に進むなら、この事故機会の増加を利用者に説明した上での判断が要る |
| 4 | **権限区画の方針が未決** | `liveops` のまま残すか `qsheet` に寄せるかで、統合後のミニアプリ一覧・権限画面の一貫性が変わる（§6）。バンドルを1つにする判断とセットで決めるべき論点であり、着手前に利用者確認が必要 |
| 5 | **改称をフェーズ1で先に済ませておく効果が失われる** | フェーズ1で改称（表示名だけ）を独立した小さいPRとして先に出しておけば、フェーズ2は「名前を追う作業」を本体工事に混ぜずに済む。フェーズ1を経ずにいきなりフェーズ2に進むと、改称がバンドル統合の巨大な差分に埋もれ、レビューの切り分けが難しくなる |

**結論**: 旧 impl doc §12-11 の推奨条件は満たされたが、**それは「着手してよい」への必要条件が
1つ揃っただけ**であり、上記1〜5、特に**1（フェーズ1の実測）と2（`scope === 'program'` 設計の空白）**
が新たな障害として残っている。**この文書の時点ではフェーズ2に進むべきではない。**
フェーズ1をリリースし、運用観測を経てから、この §4-2 を判断材料に着手可否を改めて決める。

### 4-4. フェーズ2の完了判定基準

- 計時・視聴者への遷移が React Router 内の `<Link>` になり、**ページ全体の読み直しが起きない**
  （体感で確認・Safari/Firefox を含む）
- `/live/*` のうち運用系 URL がミニアプリの URL 体系に一本化され、旧URLはリダイレクトで生きている
- **`/live/display/:timerId` の契約5つが1文字も変わっていない**（09 impl §8-1 の契約テストが
  変更なく通り続ける。これが唯一「絶対に緩めてはいけない」基準）
- セッション一覧が廃止され、案件を初めて開いたときに `liveops_programs` が自動で用意される
- `scope === 'program'` への対応方針（対応する／しないをこの時点で明示的に選び切る）が
  コードに反映されている（未決のまま放置しない）
- 権限区画の扱いが決着し、反映されている
- フェーズ1で作った `/live/open` 橋渡し画面・`resolve-by-project` の重複呼び出し経路が
  整理されている（二重に「取得または作成」を持たない）
