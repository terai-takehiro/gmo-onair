## 0. 結論

**「機能が無い」のではなく、サーバーにある機能が画面に配線されていない。**
REST と MCP には 表・列・項目・共有・ひな形・Excel・ブレイクダウンが一通り揃っている
（§1 の表）のに、画面は**作った直後に何もできない**:

```
新しく作る → 列が 0 本 → 「項目を追加」が disabled（SchedulePage.tsx:207）
          → 列を作る UI が無い → ひな形適用か AI 生成を通す以外に手が無い
```

さらに 表の設定（題・日付・拠点・状態・備考）・共有・削除・列の管理 が**画面のどこにも無い**。
共有を設定できないので、**作成者以外は管理者でない限り一生見られない**（`access.ts:38-50`）。
「MCP しかできない」という体感はここから来ている。

したがって第2版は次の順で進める。

| 段 | ねらい | サーバー作業 |
| --- | --- | --- |
| **A まず使える** | 袋小路を塞ぐ。列の管理・表の設定・共有・削除・スマホからの追加・ひな形設定への導線 | **案件メンバーの自動共有 1 本だけ**（§3-2）。ほかは既存 REST の配線のみ |
| **B 日々の運用が楽になる** | ドラッグで押し・巻き、確定の見え方、既存台本との結び直し、連日、絞り込み、印刷 | 複製 1 本＋AI 事後差分 1 本（どちらも小） |
| **C 考えてから** | 利用者の判断が要るもの（§6）。判断が出るまで着手しない | — |

**画面は 2 枚（一覧・表）のまま増やさない。** 設定・列・共有は表の上に重ねるシートに置く。

## 2. 決めごと（シンプルを守るための線）

1. **画面は増やさない。** 一覧・表の 2 ページ。設定／列／共有は表の上のシート、項目は既存のダイアログ
2. **サーバーは判定しない**（[`01-app-structure.md`](01-app-structure.md) §4-2 を維持）。状態（下書き／確定／保管）は人が付ける札。「遅れている」「変更済み」の自動判定・％バーは作らない
3. **既存 REST を使い切ってから足す。** 段Aのサーバー変更は 案件メンバーの自動共有（§3-2）だけ。段Bの新設は 複製 と AI 事後差分 の 2 本だけ
4. **第1版の「やらない」を維持**（[`02-schedule.md`](02-schedule.md) §11）: 公開URL・PDF 生成・尺の自動書き戻し・ひな形変更の追随ボタン・重なりの DB 禁止・進み具合ラベル
5. **shared に新しい部品を足さない。** 右サイドドロワーは無いので `client-v4/sheet.tsx` の `Sheet`（PC=中央・スマホ=下端）で組む
6. **削るもの（20 人規模に不要）**: リアルタイム同時編集（Yjs）・項目ごとのコメント・添付・承認ワークフロー・変更履歴の閲覧・任意色ピッカー・区分の自由追加・繰り返し予定・通知・スマホのドラッグ・個人別「自分の 1 日」ビュー（§6 の判断まで）・予約との自動突き合わせ

#### 3-1. スタジオ予約から列を自動で立てない理由

`studio_bookings` は `hold_rank`・`possible_duplicate` を持つ「仮押さえを含む予約」で、その日の進行そのものではない。
自動で列が立つと仮押さえの部屋まで表に出て、消す手間が増える。一方 `studio_booking_rooms.room_id` と
`qsheet_schedule_columns.room_id` は同じ `studio_rooms` を指すので、**コピー型なら FK もずれも出ない**。
ひな形適用と同じ「下見→選択→コピー」の作法（02 §5-1）に揃える。案件の回（`episodes`）からは日付・拠点の**先埋めだけ**。

#### 3-2. 案件メンバーの自動共有（2026-09-06 決定）の作り

**共有テーブルに写さず、判定のときに案件メンバーを見る**（動的判定）。

- `canAccessSchedule`（`server/src/contexts/qsheet/access.ts`）と `listSchedules` の可視条件
  （`schedule.service.ts` の `created_by = $uid OR EXISTS(shares)`）に、次の 2 条件を **OR で足す**:
  1. `EXISTS (SELECT 1 FROM project_members pm WHERE pm.project_id = s.project_id AND pm.user_id = $uid AND pm.deleted_at IS NULL)`
  2. `EXISTS (SELECT 1 FROM projects p WHERE p.id = s.project_id AND p.assigned_to = $uid)`（主担当。`project_members` に自分を入れていない案件のため）
- 写さない理由: メンバーの追加・削除に追随する。マイグレーション不要。`qsheet_schedule_shares` は「案件メンバー以外に見せたい人」（社外の技術・受付など、案件にメンバーとして載せない人）専用になる
- **番組（`qsheet_programs`）はメンバーを持たない**ので、番組の表は従来どおり 作成者＋明示共有＋管理者
- 外部メンバー（`project_members.user_id IS NULL`・`is_external`）はログインできないので影響なし
- **台本（`qsheet_documents`）は変えない。** 台本は「その番組を作る人」、当日進行表は「その日動く全員」に配るという区別（02 §2-4）の通りで、非対称は意図したもの。`canAccessDoc` には触らない
- 画面: 設定シートの「共有」節の先頭に「案件 GLS-xxxx のメンバー N 人には自動で見えます」と事実だけ 1 行出し、その下に明示共有のチップを置く。一覧の「共有 N 人」は明示共有の数のまま（案件メンバーを数えると案件側の変更で数字が動く）
- 逆引き（`GET /documents/:docId/schedule-items`）と AI 提案（`canAccessProposal`）は `canAccessSchedule` 経由なので自動で揃う。MCP の `gate.ts` も同じ関数を通っているか実装時に確認する（codex 棚卸し #395 が未確認のまま）

#### 3-3. 「1 日 1 枚・イベントごとにまとめる」（2026-09-06 決定）の作り

- データは変えない。`qsheet_schedules` の 1 行＝1 日のまま。束ねる鍵は `project_id`／`program_id`（どちらも無い表は「案件・番組なし」の束）
- 一覧（§4-2 (a)）は 束＝イベント（GLS 番号・題）、その中の行＝日付順の表。`?project=`・`?program=` で来たときは束が 1 つになるだけで同じ画面
- 表のヘッダーに「同じイベントの他の日」を日付チップで出す（`GET /schedules?project_id=`／`program_id=` を一覧と同じキャッシュで読む）。前日／翌日の矢印は付けない（飛び日のイベントで意味がずれる）
- 複製（B5）は「同じイベントの別の日として写す」に限定する。写すのは 列・項目・表示時間帯・拠点。共有は写さない（自動共有で足りる）

#### 3-4. PR1 で足した小さな読み取り API と、見出しの「…」

- **`GET /techops/studio-rooms`**（`server/src/contexts/qsheet/routes/schedule-rooms.routes.ts`）: 拠点ごとの部屋（id・名前・種別・色）。
  `/studios/locations` は `requirePermission('sales')` の下にあり、制作技術支援だけを使う技術・運営のアカウントには 403 になるため、
  qsheet の権限で同じ `studio_rooms` を読むだけの口を足した。書き込みは無い
- **見出しの「…」は依存を増やさず自前で作った**（`components/schedule/MoreMenu.tsx`）。このアプリと shared にドロップダウンの部品が無く、
  Radix の dropdown-menu も依存に入っていない。外側クリック・Esc で閉じる・項目 44px
- **列の削除は `confirmAction`**（`window.confirm` をやめた）。`SchedulePage.tsx` にあった「ConfirmHost 未設置」のコメントは古く、
  共通シェルが器を持っている
- 実ブラウザ確認（PC 1280 / 375px・Playwright）: 空状態→会場 2 部屋から列作成→「…」→列を足す（支度・MC）→鉛筆→左へ→項目を置いて
  列を削除（確認文に項目数）まで通し、横はみ出し 0px・JS エラー 0 件・スマホの主ボタンが下端（48px）に出ることを確認した

### 段C「考えてから」— §6 の判断が出るまで着手しない

担当を `users` に繋ぐ（`assignee_user_id`）／表→ひな形の逆流／ひな形の分類軸（拠点×式典・配信・公開収録）。

### 4-3. 操作の詳細

- **ドラッグ（段B）**: PC は移動＋下端リサイズだけ。`client/src/contexts/production/pages/calendar/useGridDrag.ts` の決めごとを踏襲（動くまで保存しない・Esc で取りやめ）。5 分スナップは**画面側だけ**、API は 1 分単位（02 付録）。保存は `bulkUpdateItems` に `expected_updated_at` を付ける
- **キーボード**: Esc=閉じる／取りやめ、Enter=保存、選択中の項目に Delete で確認へ
- **409**: 既存の `conflictedIds` をそのまま使う。ドラッグ由来の 409 は元位置に戻し、赤枠＋「最新を読み込む」
- **ポーリング停止**: 項目シート開放中（既存）に加え、ドラッグ中・設定シート開放中も止める。列の変更後は即時 refetch
- **削除の確認**: `confirmAction({ tone: 'danger' })` に一本化。復元 API が無いのでトースト式の undo は選ばない。
  ⚠️ `SchedulePage.tsx:129` の「client-techops は ConfirmHost 未設置」は**古い** — 共通シェル `shared/src/client/shell/AppShell.tsx:218` が `<ConfirmHost />` を持つので `window.confirm` はそのまま置き換えられる

### 4-4. 状態（下書き／確定／保管）の見せ方 — 1 案

状態は**人が付ける札**。ロックしない・サーバーは判定しない。
- **確定**にすると (1) 見出し右にバッジ「確定」 (2) 一覧の同じ位置に同じ幅で出る (3) 編集は従来どおり可能。項目シートの保存ボタン脇に「確定後の変更として保存」と 1 行出すだけ（保存は止めない）
- **保管**は一覧の既定絞り込みから外れる（「保管」を選べば見える）
- 「変更済み」の自動判定は持たない

## 5. AI「枠を作る」とフィードバックループ（会社方針の確認）

すでに閉じている部分: ①生成を `recordAiOutput` で記録（`ai/generation-common.ts`）②取り込み時の人の修正を `sanitizeApplied`

**穴**: 取り込んだ**後**にグリッド上で直した分（当日の押し・巻きを含む）が差分に残らない＝成果指標が無い。
**最小の追加（段B・B10）**: 表を「確定」にした時点で AI 由来の項目（`applied_ids.items`）と現在値を比べ、
