## 決めたこと（結論先出し）

1. **AI 機能は4つに割る。** `event_plan_draft`（当日の枠の叩き台）／`script_outline_draft`（ロールと尺の並び）／`script_line_draft`（セリフ）／`production_chat`（壁打ち）。**性質が違うものを1つの kind にまとめない** — 混ぜると無修正採用率が意味を失う（既存の `activity_format` と `next_action_short` を分けた判断と同じ）。
2. **AI の出力を `qsheet_documents.data` へ直接書かない。** 提案は専用テーブル `qsheet_ai_proposals` に置き、画面でプレビューし、**人が「取り込む」を押したときにクライアントが Yjs 経由（`applyDataUpdate`）で流し込む**。サーバーが JSONB を直接書いても collab の `persist` が3秒後に上書きするため、これは好みではなく**構造上の要請**（§3-1）。
3. **これが条件2（確定前スナップショット）をそのまま満たす。** 取り込んだ内容と、そのとき採番された `section_id` / `row_id` を提案側に記録する。差分は**確定時に、AI が作った行だけを id で突合して**取る。人が後から足した行を AI の誤りに数えない（§3-3）。
4. **ベクトル検索は入れない。** 本番 Postgres は `postgres:16-alpine` で `CREATE EXTENSION` を打つ migration が1本も無く、pgvector を入れるにはイメージ差し替えが要る。加えて**欲しいのは自然文の類似ではなく構造の類似**（案件種別・配信/収録・会場・尺・ロール構成）で、これは全部カラムか JSONB から数えられる。索引テーブル `qsheet_doc_index` ＋ 重み付きスコアで足りる（§2-2）。**後から embedding 列を足せる形**にはしておく。
5. **「一撃」は連鎖で作る。** 枠 → 骨格 → セリフを1つのボタンで順に走らせる導線を持つが、**段ごとに人が止められる**し、段ごとに別の kind で記録する。連鎖しても統計は混ざらない（§2-6）。
6. **AI に埋めさせるブロック型は第1版で `scenario` のみ**（骨格は行ラベルと尺、セリフは本文）。`audio_mic` / `stage_diagram` / `led_xr` / `slide` は**参照 id や座標を持つ型なので AI に書かせない** — 存在しない `sceneId` や `templateIndex` を作られるとデータが壊れる（§2-4）。11型は1つも減らさない、が **AI が触る型は絞る**。
7. **AI に HTML を書かせない。** `scenario` の本文は現行実装がプレーンテキストで書き、読み出しで `replace(/<[^>]*>/g,'')` してタグを落とす。HTML を出させても表示時に消えるうえ XSS の口になる。構造化スキーマ（`zod/v4`）で `{ name, text }` を返させる（§2-5）。
8. **成果（条件3）の主指標は「尺の精度」。** ただし**本番の実尺は現在どこにも保存されていない**（`RundownPage.tsx:135` の `useState` だけ）。これを保存する `qsheet_cue_actuals` を本設計に含める。**AI 機能の副産物ではなく、次回の尺見積もりに単独で効く**（§5-3）。
9. **条件4は `get_ai_feedback_digest` に kind を足すだけでは足りない。** 式典と配信で尺の傾向が逆になるため全社平均の助言は使えない。**`segment`（案件種別 × 拠点）で切れるようにする**＋人が承認したナレッジ表 `qsheet_ai_knowledge` ＋ 過去の確定済み骨格の few-shot、の3段構え（§6）。
10. **条件5のレビューは営業マネージャーではない。** 制作管理のマネージャー（`qsheet` 区画の `manager`）が**月1回**、`ops_reports.kind='ai_review_production'` で見る（§5-5）。
11. **壁打ちはストリーミングしない。** サーバーに `text/event-stream` が1本も無く、SSE 基盤の新設は AI 機能の都合だけでは決められない。第1版は POST 1往復（§4-3）。
12. **AI が落ちても業務は止まらない。** 提案は別テーブル、記録は全部 best-effort、無人バッチ（確定の締め・実尺の集計）に AI 呼び出しを1つも置かない（§8）。

## 1. AI 機能の切り分け

### 1-1. 4つに割る

| # | 機能 | `ai_outputs.kind` | 入力の主体 | 出力 | 書き込み先 |
| --- | --- | --- | --- | --- | --- |
| ① | **イベント設計**（当日の枠の叩き台） | `event_plan_draft` | 案件・会場・本番時刻・ひな形・過去の類似日 | 列と項目の一覧 | `qsheet_schedule_columns` / `qsheet_schedule_items` |
| ② | **台本の骨格**（ロールと尺の並び） | `script_outline_draft` | 枠（`start_min`/`end_min`）・案件・過去の類似台本の骨格 | `sections[]`（ロール名・尺・行ラベル） | `qsheet_documents.data.sections` |
| ③ | **セリフ**（プロンプター原稿） | `script_line_draft` | 骨格・話者・同じ案件/顧客の過去のセリフ | 行 id ごとの `{ name, text }` | `data.sections[].rows[].cells[scenarioBlockId]` |
| ④ | **壁打ち**（対話） | `production_chat` | スレッドの履歴・紐づいた案件/台本の要約 | 発言1つ ＋ 任意の「提案の種」 | どこにも書かない（採用時に①②③へ渡す） |

**kind の命名**: 既存の規則（snake_case・単数・「対象＋動作の名詞」、`〜_draft` = 下書きを出す）に合わせています。
④だけ `_draft` を付けないのは、**下書きではなく対話の1ターン**だからです。

**なぜ4つに割るか。** ②と③を1つの kind にすると「ロール名がよく直される」と「セリフがよく直される」が
同じ分母に入り、`top_corrected_field_types` が読めなくなります。既存が `activity_format` と
`next_action_short` を分けたのと同じ理由です（`ai-feedback.service.ts` の設計意図）。

### 1-2. 第2版に送るもの（第1版でやらないと決めたもの）

| 見送り | kind（将来） | 理由 |
| --- | --- | --- |
| 映像/テロップ/オーディオ列の下書き | `script_block_fill` | セリフと混ぜると統計が汚れるので別 kind が要る。まず②③の傾向が貯まってから |
| マイク香盤の割当 | — | `masters.micChannels` と物理チャンネルに依存。間違えると本番で音が出ない。**AI に触らせない**（§2-4） |
| 立ち位置図 | — | `templateIndex` が配列 index 参照で、AI が数字を作ると別のテンプレートが刺さる（`01`/データモデル調査の要注意点1） |
| 議事録からの自動起票 | 既存 `minutes_draft` | 既にある。制作資料側で二重に作らない |

### 1-3. 定数の置き場所（文字列を書き写さない）

既存の作法（`MINUTES_KIND` を `ai-feedback.service.ts` が import している形）に合わせ、
**サービス側に1か所だけ定義**します。写すと kind を変えた日に集計だけ黙って 0 件になります。

```ts
// server/src/contexts/qsheet/services/ai/kinds.ts
export const EVENT_PLAN_KIND     = 'event_plan_draft';
export const SCRIPT_OUTLINE_KIND = 'script_outline_draft';
export const SCRIPT_LINE_KIND    = 'script_line_draft';
export const PRODUCTION_CHAT_KIND = 'production_chat';

/** プロンプトを変えたら必ず上げる。改善効果の比較単位になる */
export const EVENT_PLAN_PROMPT_VERSION     = 'event-plan-v1';
export const EVENT_PLAN_PROMPT_VERSION_FB  = 'event-plan-v1+fb';
export const SCRIPT_OUTLINE_PROMPT_VERSION    = 'script-outline-v1';
export const SCRIPT_OUTLINE_PROMPT_VERSION_FB = 'script-outline-v1+fb';
export const SCRIPT_LINE_PROMPT_VERSION    = 'script-line-v1';
export const SCRIPT_LINE_PROMPT_VERSION_FB = 'script-line-v1+fb';
export const PRODUCTION_CHAT_PROMPT_VERSION    = 'prod-chat-v1';
export const PRODUCTION_CHAT_PROMPT_VERSION_FB = 'prod-chat-v1+fb';
```

`+fb`（フィードバックを載せた版）を**必ず別の文字列**にするのは既存5か所と同じ作法です。
混ぜると「載せた効果があったのか」を後から数字で言えなくなります。

## 2. 「一撃である程度いく」ための工夫

ここが利用者の名指しの要求です。効くのは **プロンプトの巧拙ではなく、渡す材料の量と質**なので、
材料の集め方に紙面を割きます。

### 2-1. 何を渡すか（材料の全量）

| 束 | 中身 | 出どころ | ①枠 | ②骨格 | ③セリフ | ④壁打ち |
| --- | --- | --- | :-: | :-: | :-: | :-: |
| 案件 | `name` / `project_type` / `broadcast_type` / `media_platform` / `event_start` / `event_end` / `tags` / `notes` | `projects` | ○ | ○ | ○ | ○ |
| 顧客 | `companies.name`（社名のみ。取引条件は渡さない） | `companies` | ○ | ○ | ○ | ○ |
| 回 | `episode_number` / `episode_code` / `recording_date` / `broadcast_date` / `notes` | `episodes` | ○ | ○ | ○ | ○ |
| 会場 | 拠点の略称・部屋名・列構成 | `studio_locations` / `studio_rooms` / `qsheet_schedule_columns` | ○ | ○ | — | ○ |
| 枠 | 当日の `kind` / `start_min` / `end_min` / `title` / `assignee` | `qsheet_schedule_items` | ○ | ○ | — | ○ |

| **過去の類似** | 上位3件の**骨格だけ**（§2-2・§2-3） | `qsheet_doc_index` → `qsheet_documents.data` | ○ | ○ | ○ | ○ |
| **過去のセリフ** | **同じ案件 or 同じ顧客**の確定済み台本から、同じ話者の発言を最大10行 | 同上（守秘の制約は §2-7） | — | — | ○ | — |

| **実尺の傾向** | 「この型のロールは予定より平均 N 秒押す」 | `qsheet_cue_actuals`（§5-3） | — | ○ | — | ○ |

⚠️ **渡さないもの**: 見積・原価・仕入・支払条件。台本を作るのに要らず、`payload_snapshot` に
金額が焼き込まれると、教師データの閲覧権限を財務並みに上げる必要が出ます。

### 2-2. 過去の Qシートをどう探すか（ベクトル検索を入れるか）

**判断: 第1版はベクトル検索を入れない。メタデータ ＋ 構造スコアで探す。**

**根拠**（推測ではなく実装と方針から）:

1. **拡張が入っていない。** `docker-compose.yml:11` は `postgres:16-alpine`、migration 全走査で
   `CREATE EXTENSION` が **0 件**。pgvector を使うにはイメージを `pgvector/pgvector:pg16` へ差し替え、
   本番 DB を作り直す必要があります。02-schedule.md は `btree_gist` について
   **「拡張を1機能のために本番 DB へ入れる判断は重い」**として避けており、**同じ判断に揃えます**。
2. **欲しいのが自然文の類似ではない。** 「似た台本」の実態は
   *式典 / 配信 / 公開収録のどれか*・*会場*・*尺*・*ロールの並び*・*出演人数* で、
   これは全部カラムか JSONB から**数えられる**構造の一致です。埋め込みは
   「メタデータで絞れないほど多様」なときに効きますが、ここは逆に**構造が支配的**です。
3. **費用と失敗点が増える。** 埋め込みは文書が変わるたびに API 呼び出しが要り、
   `AI_PRICING_JSON` に鍵を足し忘れると静かに安く見える既知の地雷を1つ増やします。
4. **母数が不明。** そもそも確定済み Qシートが何件あるか実測できていません（§13-1）。
   数千件までなら索引テーブルの全件スキャン＋Node 側スコアリングで数十 ms です。

**入れるとしたらどこか**（将来のために形だけ空けておく）:

- `qsheet_doc_index` に `embedding` 列を**後から** `ALTER TABLE` で足せる形にする（今は作らない）。
- 効いてくるのは「**自由記述の企画メモから似た回を探す**」ときで、これは④壁打ちの機能拡張。
  そのときに改めて母数と効果を測って判断する。
- 判断の材料: `qsheet_doc_index` の件数が **3,000 を超え**、かつ
  §2-3 のスコア上位3件が「似ていない」と人に言われる率が高いとき。

### 2-3. 索引テーブル `qsheet_doc_index` と類似スコア

`qsheet_documents.data` を毎回舐めると、JSONB の展開が検索のたびに走ります。
**要約を縦持ちした索引**を1本持ちます。


**いつ作り直すか（ここが設計の勘所）**

`collab.persist` は 3000ms ごとに走ります。**そこに索引の作り直しをぶら下げてはいけません**
（編集中ずっと JSONB を舐め直すことになる）。

- **確定したとき**（§3-3 の `settle`）に1回だけ作る。見本にしたいのは確定済みだけなので、これで足ります。
- 取りこぼしは**日次バッチ**（AI を呼ばない純粋な Node 処理）で拾う:
  `source_updated_at < qsheet_documents.updated_at` の行を作り直す。
- 手で作り直す口: `POST /qsheet/ai/index/rebuild`（`system_admin` のみ）。

⚠️ **ソフトデリートを必ず見ること（検査 地雷#6）。**
`qsheet_documents.deleted_at` は **TEXT のソフトデリート**（`012_qsheet_schema.sql:25`）なので、
上の `ON DELETE CASCADE` は**永久に発火しません**。索引は「確定したとき1回だけ」作る設計なので、
**確定後に消された台本が永久に見本（few-shot）と `find_similar_qsheets` に残ります。**

- 索引の**読み出しに必ず**
  `JOIN qsheet_documents d ON d.id = i.document_id AND d.deleted_at IS NULL` を入れる
  （02 §3-3 が `qsheet_document_id` の join で同じ手当てをしているので作法が揃います）。
- `DELETE /documents/:id`（ソフトデリート）で `qsheet_doc_index` の行を削るか
  `is_reference = false` を立てる。日次バッチにも同じ条件を入れる。

**類似スコア（Node 側で計算する）**

SQL は絞り込み（`is_reference` かつ `document_id <> 自分`）だけにして、
点は Node で付けます。SQL に埋めると読めなくなり、重みを直すたびに migration が要ります。

| 条件 | 点 |
| --- | --- |
| **同じ案件の過去回**（`project_id` 一致） | **+6** — 連続もののときこれが最強 |
| 同じ顧客（`customer_id` 一致） | +3 |
| `project_type` 一致 | +3 |
| `broadcast_type` 一致 | +2 |
| `media_platform` 一致 | +1 |
| `location_id` 一致 | +2 |
| 合計尺が ±20% 以内 | +3 |
| 行数が ±50% 以内 | +1 |
| ロール名の Jaccard 係数 × 4 | 0〜+4 |
| ブロック型の集合が一致 | +1 |
| `settled_at` が 18 か月より古い | **−2**（型が変わっている可能性） |

上位3件を返します。**同点なら新しい方**。0 点の行は返しません（「似ていないもの」を見本にすると害）。

⚠️ **`TEXT[]` のバインドに注意。** DB 層は `?` プレースホルダですが、
**SQL に jsonb の `?` 存在演算子は書けません**（プレースホルダと誤認されて syntax error。
`ai-feedback.service.ts` が実際に踏んだ既知の地雷）。配列の判定は `= ANY($n)` か Node 側で行います。

### 2-4. 出力の形（11ブロック型のどれを埋めるか）

**11種類は1つも減らしません。減らすのは「AI が書く型」だけです。**

| ブロック型 | ① 枠 | ② 骨格 | ③ セリフ | 理由 |
| --- | :-: | :-: | :-: | --- |
| `scenario` | — | **ラベルのみ** | **本文＋話者** | AI が書けるのはここだけ |
| `video` / `telop` / `audio` | — | — | — | 第2版（`script_block_fill`）。素材名は実在の ID なので幻覚が致命的 |
| `audio_mic` | — | — | — | `masters.micChannels` と物理 ch に依存。**間違えると本番で音が出ない** |
| `led_xr` | — | — | — | `sceneId` が `data.ledScenes[]` への参照。**存在しない id を作られると壊れる** |
| `stage_diagram` | — | — | — | `templateIndex` が**配列 index 参照**。数字を作られると別のテンプレートが刺さる |
| `slide` | — | — | — | そもそも**書き込み経路が実装に無い**（読みだけの幽霊型） |
| `lighting` / `remarks` / `item` | — | — | — | 汎用 `{value}` セル。書けるが、第1版では出さない（増やすほど直す量が増える） |

**②骨格が出すもの**（`sections[]` の形）:

```
ロール名（label）／ 尺（duration・秒）／ その中の行（rows）
   行ごとに: 行ラベル（CueRow.label）・尺・scenario の話者名（name）だけ
```
**本文（`html`）は空**にします。骨格の段階で本文まで書くと、人が骨格を直す前に大量の文章が生まれ、
「骨格が悪かったのか文章が悪かったのか」が分からなくなります（②と③を分けた理由そのもの）。

**③セリフが出すもの**: **既にある行 id に対してのみ** `{ row_id, name, text }` を返します。
**行を増やしも減らしもしません。** 増やすと ②の骨格が人の手で確定した形を AI が崩し、
条件2の突合（§3-3）が壊れます。行が足りないと AI が判断したら、
`text` ではなく `advice: string[]` に「ここで1行足したほうがよい」と書いて**人に判断させます**。

**①枠が出すもの**: `qsheet_schedule_items` の候補（`column_id` は既存列に当てるか、新規列の提案）。
**時刻はその日の 00:00 JST からの分（`INTEGER`）**で返させます（02-schedule.md §7 の型に揃える）。
`"HH:MM"` 文字列を返させて後で変換すると、日跨ぎ（`25:30 = 1530`）で必ず崩れます。

### 2-5. AI に HTML を書かせない

**ONAiR の既存判断であり、この設計でも守ります。**

- 実装上、`scenario` の本文は**プレーンテキストで書き込まれ**、読み出しで
  `replace(/<[^>]*>/g,'')` してタグを落としています（`CueRow.tsx:412` / `PrompterPage.tsx:37`）。
  HTML を出させても**表示時に消える**ので、生成する意味が最初からありません。
- プロンプターは大きな文字で全画面表示するため、書式は画面側の責務です。
- LLM 出力をそのまま DOM に入れる経路を作らないことが、XSS の口を1つ減らします。

**代わりに構造で返させます。** 強調したい語は `emphasis: string[]`（本文中の語をそのまま列挙）で返し、
画面が本文からその語を探して強調する。**マークアップを本文に混ぜない。**

⚠️ **「LLM に渡すスキーマ」と「normalize 後の内部型」を分けます（検査 地雷#3）。**
初版はこの2つを1つの `zod` スキーマで書いていましたが、**そのままでは
`zodTextFormat` の時点で落ちます。** 既存5サービス（`intake-ai` / `activity-ai` /
`minutes-ai` / `kpt-ai` / `next-action-short`）は `openai/helpers/zod` の
`zodTextFormat` ＋ `client.responses.parse()` を使い、
**`.optional()` / `.nullable()` / `.default()` を1つも使わず**、
全部必須フィールド＋「無ければ空文字」という `describe` で表現しています
（`intake-ai.service.ts:174-228`。OpenAI の strict structured outputs が optional/default を拒否するため）。

```ts
// server/src/contexts/qsheet/ai/schemas.ts  ← **LLM スキーマ専用**（検査で新設）
// zod/v4。既存の作法（import * as z from 'zod/v4'）に合わせる。
// **.optional() / .nullable() / .default() を使わない。全部必須・無ければ空文字 or 0。**
const ScriptLineSchema = z.object({
  row_id:    z.string().describe('提案対象の行 id。無い id を作らない'),
  name:      z.string().describe('話者。masters.persons のどれか。分からなければ空文字'),
  text:      z.string().describe('プレーンテキスト。改行は \\n。HTML タグ禁止'),
  emphasis:  z.array(z.string()).describe('本文中の強調したい語。無ければ空配列'),
  is_q_word: z.boolean().describe('Qワード（赤 Q→）なら true'),
});
```

**§11 のコードブロックは `normalize` 後の内部型**（`speaker: string | null` など）で、
**LLM スキーマではありません。** `normalize` が空文字 → `null` に落とします。

`normalizeScriptLines()`（純関数・ネットワークに触らない）で:
- `text` に `<` を含む行は**タグを剥がす**（落とすのではなく剥がす。文章自体は使える）
- `row_id` が提案対象に無い行は**捨てる**（幻覚した行 id で書き込ませない）
- `name` が `masters.persons` に無ければ**空にする**（勝手に人物を作らない）
- `emphasis` のうち `text` に含まれない語は捨てる

⚠️ **捨てたものを必ず記録する（検査 AIループ#F8）。**
初版の `normalize` は「捨てる」だけでしたが、**捨てているのは人が触る前の純粋な AI の誤りで、
いちばん自動で取れる教師データ**です。どこにも残らないのは条件2の穴です。

```ts
// normalize は「落とした要素」も返す。recordAiOutput の直後に:
recordCorrections(outputId, dropped.map(d => ({
  fieldPath: `normalize.${d.reason}.${d.path}`,   // 例 normalize.bad_reference.rows[3]
  before: d.value, after: null, type: 'reject',
})));
```

`normalize.` 接頭辞を付けると digest の `top_corrected_field_types` で区別でき、
「`normalize.bad_reference.rows[]` が 28 件」と出れば**プロンプトを直す先が一発で分かります。**
①の「合計が枠を超える骨格を落とす」も同じ扱いにします。

⚠️ **`emphasis` は第1版のスキーマから落とします（検査 整合#17）。**
`entries[0]` は `{ name, html, isQWord, image, highlight }` で **`emphasis` を置く場所が無く**、
「画面が本文からその語を探して強調する」実装もありません
（プロンプターは `replace(/<[^>]*>/g,'')` で平文にするだけ）。
**生成させて検証して捨てるだけの欄**になります。強調が要るなら、
`isQWord` と同じく**セルの構造として先に決めて**から足してください。

`shared/tests/` に vitest を1本置きます（`nextActionShort.test.ts` が手本）。

### 2-6. 「まとめて作る」— 連鎖と、途中で止まれること

利用者の「一撃である程度いく」に応えるため、**1つのボタンで ①→②→③ を順に走らせる**導線を持ちます。

```
[この日をまとめて作る]
  ① 枠の叩き台        → プレビュー（列と項目のガント）  … 取り込む / 直す / やめる
  ② 本番の枠から骨格   → プレビュー（ロールと尺の一覧）  … 取り込む / 直す / やめる
  ③ 骨格からセリフ     → プレビュー（行ごとの原稿）      … 取り込む / 直す / やめる
```

**設計上の約束**:

- **段ごとに別の提案レコードを作り、別の kind で記録する。** 連鎖しても統計は混ざりません。
- **前の段の「取り込んだ後の内容」を次の段の入力にする。** 提案のままではなく、人が直した後を渡す。
  こうすると人の修正がその場で次の段に効き、**連鎖するほど当たる**。
- **どの段でも止められる。** ②で止めても①は残ります。ロールバックしません。
- **③は既定で「全行」ではなく「本番ロールだけ」**にします。全部を一度に出すと、
  人が全文を読む気力を失って雑に取り込み、**条件2の差分が「無修正」で埋まって嘘になる**（既知の計測バグ）。
  「もっと出す」を押したときだけ範囲を広げます。

### 2-7. 過去の台本を見本にしてよいか（守秘）

**顧客をまたいで文言を流用しない**、が原則です。

| 材料 | 使ってよい範囲 |
| --- | --- |
| **骨格**（ロール名・尺・行数） | **全社**。番組の型は当社のノウハウで、顧客固有の情報ではない |
| **セリフ本文** | **同じ案件 または 同じ顧客のみ**。他社の台本の言い回しを別の顧客に流し込まない |
| 出演者名（`masters.persons`） | **同じ案件のみ**。他案件の出演者名は出さない |

`qsheet_doc_index.is_reference` を人が落とせるようにします（既定 `TRUE`）。
「この台本は見本にしないでほしい」と言われたとき、**その1行を落とすだけで全 AI 機能から外れる**
状態にしておきます。落とした事実は監査のため `updated_by` / `updated_at` を持ちます。

⚠️ **アクセス権との関係。** Qシートは「作成者本人／共有先／`system_admin`」しか見えず、
**権限なしは 404**（`access.ts`）。few-shot に他人の非共有台本の**本文**を混ぜると、
**AI 経由で非共有の中身が読める裏口**になります。したがって:

- **本文は、要求者がその文書に `canAccessDoc` で通る場合に限り**渡す。通らないものは混ぜない。
- ⚠️ **骨格の見える範囲の既定を「可視のもの＋同一顧客」に倒しました**（検査 AIループ#F18・地雷#5）。

初版は「骨格（ロール名・尺）は全社共有として扱う」を**既定**にしていましたが、
**05-mcp.md §4-5 は同じスコア関数を呼びながら「見える範囲で絞ってから返す」と書いており、
実装は片方の意味しか持てません。** どちらに寄せても、もう片方が黙って壊れます
（MCP が全社を見せる＝`access.ts` の存在秘匿の破れ／画面の AI が見本ゼロで一撃が当たらない）。

さらに、**ロール名には「◯◯社 新製品発表会」のような顧客が特定できる自由文が普通に入ります。**
「骨格は顧客固有の情報ではない」はそこそこ強い仮定です。

**決め: 引数で明示的に分け、既定は狭いほうにする。**

```ts
findSimilarDocs(opts: {
  viewerId: string;
  scope: 'visible' | 'org_outline';   // **既定は 'visible'**
}): Promise<SimilarVisible[] | SimilarOutlineOnly[]>;
```

- `org_outline` の戻り値型は **`{ label, durationSec, rowCount }[]` と点数だけ**にし、
  `title` / `projectName` / `customerName` / 本文を**型として持たせない**（漏れを型で止める）。
- **MCP（05 §4-5）は `scope:'visible'` のみ許可。**
- 全社解禁（`org_outline` を既定にする）は §14-4 の回答が出てから、
  `qsheet_doc_index.is_reference` とは**別の運用フラグ**で開ける。

## 3. 提案テーブルと「取り込み」（条件2の要）

### 3-1. なぜ AI の出力を `data` へ直接書かないのか（構造上の理由）

`collab.persist` が 3000ms ごとに **Y state から `data` JSONB を丸ごと書き戻します**
（`collab.ts:62-73`）。したがってサーバーが `UPDATE qsheet_documents SET data = ...` を打っても、
**その台本を誰かが開いていれば最大3秒で消えます**。これは 02-schedule.md が
スケジュール表を `data` に相乗りさせなかった理由と**まったく同じ**です。

さらに、仮に書けたとしても:

- **人の編集と AI の出力が同じ場所に混ざり、条件2の差分が永久に取れなくなります。**
  「上書き保存で下書きを消すと修正差分が取れない」という既知の地雷そのものです。
- Yjs の `applyDataUpdate` を通さない書き込みは、`ensureStableIds` の順序保証の外に出ます。
  これを崩すと行が指数的に増える実績があります（3→769→100万行）。

**したがって**:

```
AI → qsheet_ai_proposals（提案。data には触らない）
          ↓ 人がプレビューで取捨選択
     クライアントが applyDataUpdate 経由で data へ流し込む
          ↓ 同時に
     POST /proposals/:id/apply  ← 「何を取り込んだか」と「採番された id」をサーバーに戻す
```

**書き込みはクライアントがやる。サーバーは記録するだけ。** 珍しい形ですが、
Yjs が `data` の所有者である以上これしかありません。

### 3-2. DDL

```sql

  --   こちらは「画面に出す提案」として読むので用途が違う（教師データの正は ai_outputs 側）

                CHECK (state IN ('open', 'applied', 'discarded', 'failed')),
  error_message TEXT,
  /* ★検査（AIループ#F5・F16／整合#12）で 05 の ALTER からこちらへ移した3列。
     04 が提案テーブルの正なので、04 単独で実装すると期限処理ごと落ちていた */
  -- 人が見送った理由（discard の reason）／'expired'（放置）。**人が残す唯一の「なぜ」**
  discard_reason TEXT,
  -- open のまま放置された提案を落とす期限（既定 14日）。
  -- ⚠️ §3-3 の timeout（取り込み済みの差分を締める期限）とは**別物。同じ定数にしない**
  expires_at    TIMESTAMPTZ,
  -- MCP 由来を見分ける（05 §8）。既定 'server' なので 04 が先でも後でも壊れない
  source        TEXT NOT NULL DEFAULT 'server' CHECK (source IN ('server','mcp')),
  -- ▼ 取り込み（条件2の起点）
  applied_at    TIMESTAMPTZ,
  applied_by    TEXT REFERENCES users(id),
  /* 取り込んだ内容そのもの。**人がプレビューで消した分を除いた形**。
     proposal との差（＝プレビュー上の取捨）も、ここと proposal を比べれば取れる */
  applied_payload JSONB,
  /* 取り込みで採番された id。**AI が作った要素だけを後で見分ける鍵**（§3-3）
     { "sections": ["sec_x"], "rows": ["row_a","row_b"], "items": ["itm_1"] } */
  applied_ids   JSONB,
  -- ▼ 確定（差分を取る瞬間）
  settled_at    TIMESTAMPTZ,
  settled_reason TEXT CHECK (settled_reason IN ('on_air', 'broadcast_date_passed', 'timeout', 'manual')),
  /* ★検査（AIループ#F2）で追加。2段締め。
     early = applied_at+7日（AI 起因の修正として数える。field_path 無加工）
     final = 本番翌日（field_path に 'late.' を付ける。本番直前の動きは別の読み） */
  settle_stage  TEXT CHECK (settle_stage IN ('early', 'final')),
  settled_final_at TIMESTAMPTZ,
  created_by    TEXT REFERENCES users(id),
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  CHECK (schedule_id IS NOT NULL OR document_id IS NOT NULL)
);

CREATE INDEX IF NOT EXISTS idx_qsheet_ai_prop_doc
  ON qsheet_ai_proposals(document_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_qsheet_ai_prop_sch
  ON qsheet_ai_proposals(schedule_id, created_at DESC);
-- 締めバッチが拾う対象（§3-3）。**数える SQL と拾う SQL でこの条件を共有する**
CREATE INDEX IF NOT EXISTS idx_qsheet_ai_prop_pending_settle
  ON qsheet_ai_proposals(applied_at)
  WHERE state = 'applied' AND settled_at IS NULL;
```

### 3-3. いつ差分を取るか（**ここが設計の核心**）

**「確定」に相当する操作が Qシートには無い**、というのが実装を読んで分かった一番厄介な事実です。

- `qsheet_documents.status` は CHECK 付きで存在しますが、**`rehearsal` / `on_air` に上げる UI が
  クライアントに1つも無い**（grep 0 件）。PUT は不正値を `'draft'` に落とすので、
  実運用では**全部 `draft` のまま**です。**これを確定の合図に使えません。**
- 上書き保存（というより Yjs の常時同期）なので、「保存した＝確定した」も使えません。

⚠️ **初版は「最も早いもの」と書いており、文書内で自己矛盾していました（検査 AIループ#F2）。**
「最も早いもの」なら、**本番が8日以上先の台本では `timeout`(7日) が必ず勝ちます。**
つまり §5-2a が「**本番日を軸にするのがこの領域の正解**」と書いた規則は、
本番の1〜2週間前に骨格を作るという普通の業務では**一度も発火せず、
測りたいと言っている「当日の直し」を 100% 取りこぼします。**

**決定（作り直し）: 2段で締める。`timeout` は「本番日が特定できないとき」の保険に降格。**

| 段 | `settle_stage` | いつ | 何を数えるか |
| --- | --- | --- | --- |
| 1段目 | `early` | `applied_at` から **7日**（`CORRECTION_WINDOW_DAYS`） | **AI 起因の修正**。`field_path` は無加工。**digest の無修正採用率の分母はここだけ** |
| 2段目 | `final` | 本番の翌日 03:00 JST | **本番直前にどれだけ動いたか**。`field_path` に **`late.` 接頭辞**を付けて積む |

`settled_reason` は 2 段目の理由を持ちます:

| `settled_reason` | 条件 |
| --- | --- |
| `on_air` | その台本で**本番トランスポートが動いた**（`qsheet_cue_actuals` にその文書の行が入った）日の**翌日 03:00 JST** |
| `broadcast_date_passed` | `qsheet_documents.broadcast_date`（または `qsheet_schedules.service_date`）の**翌日 03:00 JST** |
| `timeout` | **本番日が特定できないときだけ**（`broadcast_date IS NULL AND schedule.service_date IS NULL`）。`applied_at` から 30 日で打ち切り |
| `manual` | 「今すぐ締める」を人が押した（デバッグと、日程が飛んだときの手動締め） |

**これで「AI の誤り」と「正常な業務更新」を混ぜずに両方測れます。**
ONAiR の案件は数か月更新され続けるので、素の7日窓だけでは当日の直しが取れず、
本番日だけにすると数か月ぶんの通常の練り直しが AI の誤りに混ざります。

**なぜ翌日か。** 本番当日の直前まで台本は直り続けます。当日の 18:00 に締めると、
**19:00 の本番前の差し替えが「無修正」に落ちて数字が嘘になります。**

**放置された提案も必ず数える（検査 AIループ#F5）**

`getFeedbackDigest` の分母は `EXISTS (SELECT 1 FROM ai_corrections WHERE output_id = o.id)` です。
つまり **`ai_corrections` に1行も無い出力は、集計上「存在しなかったこと」になります。**
締めバッチが拾うのは `state='applied' AND settled_at IS NULL` だけなので、
**`state='open'` のまま放置された提案は永久に誰も拾いません。**
結果、「10回生成して1回だけ使った」場合、無修正採用率は**その1回だけで計算され、非常に高く出ます。**
これは `onair-current-state.md` が実測で直した「よく開かれる行ほど精度が高く見える」の別形です。

- 締めバッチに1本足す: `state='open' AND expires_at < NOW()` →
  `state='discarded'` / `discard_reason='expired'` /
  `recordCorrections(outputId, [{ fieldPath:'(全体)', type:'reject', note:'未使用のまま期限切れ' }])`。
- digest に **`generated / applied / discarded / expired` の生成ベースの4数**を足す
  （`ai_outcomes` には焼かない）。
- ⚠️ **「一撃で当たったか」の主指標は無修正採用率ではなく `applied / generated`（取り込み率）です。**
  初版にはこの数字がどこにもありませんでした。

**差分の取り方（`settleProposal(proposalId)`。AI を1回も呼ばない純粋な処理）**:

1. `applied_payload`（＝取り込んだ内容そのもの）を **before** にする。
   ⚠️ **`proposal` ではなく `applied_payload`。** 人がプレビューで消した行を「AI が間違えた」と
   数えないため（消した行は取り込み時に `reject` として別途1回だけ記録する）。
   ⚠️ **「保存直前の行」を before にしない。** 既存実装が実測で踏んだ地雷そのもの。
2. **after** は現在の `qsheet_documents.data`（collab 中でも最大3秒古いだけ。締めは翌日なので十分)。
3. **before と after を同じ表現に正規化してから**突合する（⚠️ 検査 AIループ#F6）。
   `applied_payload` は **「クライアントが `applyDataUpdate` で実際に書いた形」＝`data` と同じ表現**で
   記録します（§3-4）。`ScriptOutlineProposal`（`duration_sec: number`）は**プロンプトの出力型**で、
   台本の内部表現ではありません。役割を分けること。
   **理由**: `diffByKey` の比較は `isNumericLike(bv) && isNumericLike(av)` のときだけ数値比較で、
   それ以外は `String(bv) === String(av)` です。`90` と `"1:30"` は不一致になるので、
   **人が1文字も触っていない行が全部 `fix` になります。**
   話者名（`speaker` vs `entries[0].name`）、行ラベル、本文（`entries[0].html`）も同じ経路でずれます。
   両者を `toComparable(row)` に通してから渡すこと。
4. `applied_ids.rows` に載っている **row_id だけ**を突合する。
   - **人が後から足した行は対象外**（AI の誤りではない）。
   - 配列は
     **`diffByKey(before, after, 'row_id', ['label','duration','name','html'], 'rows')`** で業務キー突合。
     - ⚠️ **`text` という欄は実装に存在しません**（検査 整合#5）。セルは
       `row.cells[<scenarioBlockId>].entries[0] = { name, html, isQWord, image, highlight }` で、
       本文は **`html` に平文**が入ります。02 §6-4 と 05 §5 は正しく `html` と書いており、
       **04 だけが違っていました。**
     - ⚠️ **第5引数 `'rows'` を省略しないこと。** 既定は `'items'` で、
       見積（`estimate_draft`）と同じ鍵空間になります。
     - index 突合は 1 行挿入で全行が「修正された」ことになるため禁止（既存の作法）。
   - **消えた行 = `reject`／空→値 = `enrich`／値→別値 = `fix`／文章の言い換え = `rephrase`**。
     ⚠️ `rephrase` と `fix` の機械判定を **±20% の文字数差から正規化編集距離に変えます**
     （検査 AIループ#F13）。±20% だと**同じ長さの全面書き換え**（＝中身が違う）を
     `rephrase` と誤判定し、§5-3c が「ナレッジを直すかプロンプトを直すか」の判断材料に
     使っているので、**改善の方向を間違えさせます。**
     - `similarity >= 0.6 → rephrase`、それ未満は `fix`。純関数で
       `shared/src/qsheetAi/normalize.ts` に置き、vitest で固定する。
     - `ai_corrections.note` に `sim=0.62` を機械的に入れておく（後から閾値を引き直せる）。
     - **`correction_type` は人が上書きできるようにする**（スキルの明文の要求）:
       `PUT /qsheet/ai/corrections/:id { correction_type, note }`（`manager` 以上）。
       月次レビューで読むときに直せれば十分で、日常の操作にはしない。
5. **差分が 0 件でも `[{ field_path: '(全体)', correction_type: 'none' }]` を必ず1行残す。**
   これが正解ラベルで、無いと無修正採用率の分母が壊れます。
   直した場合も、直さなかった項目を `none` で埋めて分母を作ります。
6. `hasCorrections(outputId)` で二重計上を防ぐ。**1段目（`early`）は1提案につき1回きり。**
   2段目（`final`）は `late.` 接頭辞付きなので鍵空間が重ならず、別に1回積めます。
7. 締めたら `settle_stage` / `settled_at`（`final` なら `settled_reason` も）を立て、
   `qsheet_doc_index` を作り直す（§2-3）。

⚠️ **初版の手順6「`if (userId === config.mcpActorId) return;`」は削除しました（検査 整合#9）。**
あれは**更新イベントごとに走る既存パターン**（`activity-log.service.ts` 等）から写した1行ですが、
`settleProposal` は翌日のバッチで `applied_payload` と現在の `data` を突合するだけで、
**`userId` がスコープに存在しません。** このままでは実装できないか、無害に無視されて
条件2の防御が1つ消えます。正しくは:

> **Yjs の origin では書き手を区別できないので、AI が書いた分は `applied_ids` の id 集合でしか見分けない。**

（05 §3-1 は静的 API キーを拒否する根拠の1つにこの行を挙げていましたが、
**存在しない防御を根拠にしていた**ので、そちらの根拠リストからも落としました。
結論の OAuth 専用は他の3つで十分立ちます。）

**「これは違う」ボタン**: プレビューや編集画面から、AI が出した特定の行に
「これは違う」を押せるようにします。
⚠️ **この経路で `findLatestAiOutput` を使わないこと（検査 地雷#7）。**
`findLatestAiOutput(targetTable, targetId, kind, withinDays)` は
`(target_table, target_id, kind)` の**最新1件**を返しますが、1つの台本に
`script_line_draft` の提案は何度も生まれます（「もう少し短くして」の作り直しが普通、と
05 §7 自身が書いている）。3つ前の提案の行に押すと、**最新の別提案の成績が汚れます。**
→ 画面が持っている `proposal_id`（または行 id → `applied_ids` の逆引き）から
`ai_output_id` を直接引き、そこに `reject` を積む。§3-2 で
`targetTable='qsheet_ai_proposals'` / `targetId=proposal.id` に統一したので、
**窓なし検索そのものが不要になります。**

⚠️ **`ai_outputs.target_table` / `target_id` を統一しました（検査 AIループ#F7）。**
初版は ④だけ `targetTable:'qsheet_ai_messages'` と明記し、①②③は無記述、
一方 05 §4-7 は `targetTable:'qsheet_documents'` / `targetId: document_id` と書いており、
**食い違っていました。** `document_id` を target にすると、同じ台本に対する複数の提案が
同じ target になり、突合の起点が壊れます。

- **①②③は `targetTable='qsheet_ai_proposals'` / `targetId=proposal.id`。**
- ④は `targetTable='qsheet_ai_messages'` / `targetId=message.id`（変更なし）。
- 業務レコードへの参照は `qsheet_ai_proposals.document_id` / `schedule_id` で辿る。

### 3-4. 取り込み API がやること（改ざん防止）

`POST /qsheet/ai/proposals/:id/apply` の body は**クライアントが作る**ので、
**そのまま `applied_payload` に入れてはいけません。**

⚠️ **初版は「提案に無いものは黙って落とす」だけで、いちばん濃い修正差分を捨てていました
（検査 AIループ#F4）。** 動機（人が書いた名文を AI の出力として教師データに入れない）は
正しいのですが、対処が逆効果です。人がプレビューで台詞を書き直してから取り込むと、
その書き換えは `dropped_count`（数だけ）に潰れ、**何が悪かったのかが1バイトも分かりません。**
しかも「取り込む前に直した」台本が **`fix` になるのか無修正採用になるのかが
§3-4 と §3-3 で決まっておらず、実装者がコインを投げる**状態でした。

**決め（`apply` の1関数で完結します）**:

```ts
// POST /proposals/:id/apply の内部
for (const el of body.applied_payload の要素) {
  const orig = proposal の同じ key の要素;
  if (!orig) {
    // 人が自分で足したもの。AI に帰属させない → applied_ids からも外す
  } else if (等しい) {
    applied_payload にそのまま入れる;
  } else {
    // ★ 人がプレビューで直した
    applied_payload に「人が直した後の値」を入れる;   // ← after 側の基準を揃える（F6）
    recordCorrections(outputId, [{
      fieldPath: `preview.rows[${row_id}].${f}`,      // ← 「取り込む前に直された」
      before: orig[f], after: el[f], type: 'fix',
    }]);
  }
}
```

- **`preview.` 接頭辞**を付けるのは、digest の `top_corrected_field_types` が
  `[...]` を潰す仕様（`regexp_replace`）でそのまま生き残り、
  **「取り込む前に直された」と「取り込んだ後に直された」を人が読み分けられる**からです。
- `applied_payload` には**人が直した後の値**を入れます。これで §3-3 の before/after の基準が揃い、
  「取り込んで一切触らなかった台本が `fix` になる」も起きません。
- `context.dropped_count`（提案に無い要素の件数）は残してよいが、**それだけでは何も分かりません**
  （スキルの「確認フラグを差分と呼ぶな」と同じ形）。
- 400 にはしない（人が編集してから取り込むのは正常な操作で、弾くと運用が止まる）。

## 4. 壁打ち（対話）

### 4-1. 何のための機能か

「ある程度を AI で作成して最後は人間が整える」の**手前**、
つまり **何を作るかがまだ決まっていない**段階の道具です。
①②③が「材料が揃ってから叩き台を出す」のに対し、④は**材料を作るための対話**です。

したがって④の出口は**文章ではなく「①②③のどれかを起動できる状態」**です。
`[この案から骨格を作る]` が押せることをもって、④は成功したと数えます（§5-2）。

### 4-3. 対話の回し方

- **1往復 = 1 POST。** ストリーミングしません（サーバーに SSE が1本も無く、
  基盤の新設は AI 機能の都合だけで決められない。§13-3）。画面は「考えています…」を出します。
- **履歴の渡し方**: 直近 **20 往復**（40 メッセージ）まで。それを超えたら
  **古い側を要約せずに落とす**。要約すると「AI が要約を間違えた」が新しい失敗要因になり、
  しかも記録に残りません。落としたことは画面に出します（「ここより前は渡していません」）。
- **記録**: `assistant` の発言ごとに `recordAiOutput({ kind: 'production_chat', targetTable: 'qsheet_ai_messages', targetId: <message.id>, payload: { 入力の全文（渡した履歴と材料）＋ 出力の全文 } })`。
  ⚠️ **メッセージ行を作る前に出力を記録する場合は `targetId: null` で入れ、
  行ができたら `UPDATE ai_outputs SET target_id = ?`**（既存 `activity-log.service.ts:205,285` の作法）。
  埋め忘れると `findLatestAiOutput` が引けず条件2が閉じません。
- **費用の上限**: 1スレッドの往復数に上限を置きます（既定 40 往復・`system_admin` が設定で変更）。
  上限に当たったら「新しいスレッドを作ってください」で止める。**黙って要約に切り替えない。**
- **権限**: スレッドは `created_by` 本人のみ。共有機能は第1版で作りません（§13-5）。
  `document_id` / `schedule_id` を紐づけるときは `canAccessDoc` / `canAccessSchedule` を通し、
  通らなければ **404**（`access.ts` の作法）。

### 4-4. 画面

- 置き場所: **編集画面とスケジュール表の右サイドパネル**（PC）／**ボトムシート**（スマホ）。
  別ページにすると「台本を見ながら相談する」ができません。
- 入力欄は **`BufferedTextarea`**。素の `<textarea>` に replace すると
  IME の実バグ（「さくら」→「ささくさくらさくら」）を持ち込みます。**ここは必ず守る。**
- 発言ごとに 👍 / ✏️（言い直して） / ❌ の3つ。押した瞬間に `feedback` を PUT。
  **理由欄は任意**（必須にすると入力されず、テーブルが空になる）。
- assistant の発言に `suggestion` があれば `[この案で骨格を作る]` を出す。
  押すと ②を起動し、生まれた提案 id を `spawned_proposal_id` に書き戻す。

### 5-2. 条件2 — どこで差分を取るか

**a) ①②③（提案型）**: §3-3 の `settleProposal`。要点の再掲:

- **before は `applied_payload`**（取り込んだ内容そのもの）。`proposal` でも「保存直前の行」でもない。
- **突合は `applied_ids` に載った id だけ**。人が足した行を AI の誤りに数えない。
- **差分 0 件でも `none` を1行**。
- **締めは1提案1回きり**（`hasCorrections` で守る）。
- **時間窓**は「本番の翌日」または7日。ONAiR は案件が数か月更新され続けるので、
  素の7日窓だけだと当日の直しを取りこぼします。**本番日を軸にするのがこの領域の正解**です。

**b) ④壁打ち — ✕ と、その代替**

対話は「人が直して確定する」ものではないので、**自動 diff が原理的に取れません。✕ です。**

代替（3つ重ねる）:

| 代替 | どう `ai_corrections` に落とすか |
| --- | --- |
| 👍 **good** | `{ field_path: '(発言)', correction_type: 'none' }` … 無修正採用に相当 |
| ✏️ **rephrase**（言い直させた） | `{ field_path: '(発言)', correction_type: 'rephrase', note: 任意 }` |
| ❌ **reject**（的外れ） | `{ field_path: '(発言)', correction_type: 'reject', note: 任意 }` |
| **起票率**（`spawned_proposal_id` が付いた率） | `ai_corrections` ではなく digest の `chat` 分岐で導出（§6-1） |

⚠️ **フィードバックが付いていない発言を `none` に数えないこと。** 押されなかった＝良かった、ではありません
（大半は押されない）。分母は**「3値のどれかが付いた発言」だけ**にします。
ここを甘くすると、④の無修正採用率が「押す人がどれだけ几帳面か」を測る数字になります。

⚠️ **押し直し（👍→❌）で `feedback` と `ai_corrections` が食い違います（検査 AIループ#F19）。**
`qsheet_ai_messages.feedback` は**上書き**、`ai_corrections` は**追記**なので、
そのままだと2つの真実ができます。しかも `hasCorrections` を使うと**2回目が黙って捨てられます。**

→ **`feedback` 列を正**とし、更新時は
`DELETE FROM ai_corrections WHERE output_id = ? AND field_path = '(発言)'` してから
**1行だけ INSERT** する。**④は `hasCorrections` を使わない。**

### 5-3. 条件3 — この領域固有の成果指標

**a) 尺の精度（主指標）— ただし前提が欠けている**

「AI が作った骨格が本番でどれだけ押し引きされたか」が、この領域で最も意味のある成果です。
**しかし本番の実尺はどこにも保存されていません**（`RundownPage.tsx:135` の `useState` だけ・確認済み）。
**このままでは ✕ です。**

**代替（本設計に含める）: `qsheet_cue_actuals` を新設する。**

```sql
CREATE TABLE IF NOT EXISTS qsheet_cue_actuals (
  id             TEXT PRIMARY KEY,
  document_id    TEXT NOT NULL REFERENCES qsheet_documents(id) ON DELETE CASCADE,
  /* 本番1回 = 1 run。リハ・本番・撮り直しを分ける。
     クライアントが cue:reset / 最初の play で genId('run') し、socket で全端末に配る */
  run_id         TEXT NOT NULL,
  run_started_at TIMESTAMPTZ NOT NULL,
  /* **行 id で持つ。globalIndex では持たない** — 行を1つ挿すと全部ずれる。
     ⚠️ ただし CM/VTR/ロール一括のキューは row_id を持たない（下の ⚠️）。
     **section_id は必ず入れる。** */
  section_id     TEXT NOT NULL,
  row_id         TEXT,
  /* ★検査（AIループ#F15・地雷#8）で追加。その run でその行に何回目に入ったか（1 始まり）。
     cue:jump で戻ってやり直したときに、最初の（多くは失敗した）尺で上書きされないため */
  pass_no        INTEGER NOT NULL DEFAULT 1,
  cue_index      INTEGER,            -- 記録時点の通し番号（参考。突合には使わない）
  planned_sec    INTEGER,            -- そのとき画面が出していた予定尺
  actual_sec     INTEGER NOT NULL,   -- 実尺
  recorded_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  recorded_by    TEXT REFERENCES users(id)
);

/* 同じキューの二重送信を無害にする（NEXT を2端末が同時に押しても1行）。
   ★ row_id が NULL のキュー（CM/VTR/ロール一括）は section_id で一意にする */
CREATE UNIQUE INDEX IF NOT EXISTS uq_qsheet_cue_actuals_run_row
  ON qsheet_cue_actuals(run_id, row_id, pass_no) WHERE row_id IS NOT NULL;
CREATE UNIQUE INDEX IF NOT EXISTS uq_qsheet_cue_actuals_run_section
  ON qsheet_cue_actuals(run_id, section_id, pass_no) WHERE row_id IS NULL;
CREATE INDEX IF NOT EXISTS idx_qsheet_cue_actuals_doc
  ON qsheet_cue_actuals(document_id, run_started_at DESC);
```

⚠️ **`row_id` だけで持つと、設計が避けたはずの「1行挿すと全部ずれる」がそのまま起きます
（検査 AIループ#H5）。** `RundownPage.tsx:218-240` の `flatCues` は CM/VTR/ロール一括のキューに
**`cm-<sectionIdx>` / `vtr-<sectionIdx>` / `sec-<sectionIdx>` という配列 index 由来の合成 id** を
作ります。これを `row_id` に入れると、ロールを1本足しただけで別のキューと同じ id になります。

→ **CM/VTR/ロール一括は `row_id = NULL, section_id = sec_…` で持つ。**
あわせて **`flatCues` が `section.id` を運ぶよう直す**（現状 `sectionIdx` しか持っていない）。
これは [`07-onair-roles.md`](07-onair-roles.md) §3 の実装要件です。

⚠️ **書き手を「進行（OnAir）の1台」に固定します（検査 AIループ#H4・F14）。**
初版は「`cue:next` / `cue:jump` を**発火した端末だけ**が POST する」としていましたが、
**実装では進行（OnAir）はローカルで `next()` を呼び `cue:update` しか emit しません**
（`OnAirPage.tsx:270-305` のキーボード操作、`:358` の emit）。
`cue:next` / `cue:jump` を emit しているのは **`RundownPage` だけ**です。つまり:

- **進行卓が普通に本番を回すと `cue:next` は誰も発火せず、実尺は空になります。**
- 実際に測っているのは `RundownPage.tsx:129-145`（`cue:sync` 由来の cue 変化から `actualDurations` を計算）で、
  **ランダウンを開いていない本番では測定自体が存在しません。**

→ **cue が切り替わったとき、進行（OnAir）が planned/actual を算出して POST する。**
ランダウンからの操作も `cue:*` を OnAir が受けてから記録するので、**二重送信も構造的に起きません。**
`pass_no` は OnAir がその run 内でその行に入った回数として送り、
サーバーは `ON CONFLICT DO NOTHING`（同じ pass の二重送信だけを無害にする）。
集計は既定で **`MAX(pass_no)` の行**（＝最後に通った版）を使います。

⚠️ **`run_id` を配る socket 契約が必要です。** 現行の
`server/src/contexts/qsheet/socket.ts:145-167` は **`cue:reset` に payload が無く、
`run_id` を配る口がありません。** 契約の追加は
[`07-onair-roles.md`](07-onair-roles.md) §3 に書きました（`cue:reset` に
`{ runId, runStartedAt }` を載せ、後から入った端末には `cue:sync` で同じものを配る）。

⚠️ **本番中の書き込みが計時をブロックしないこと。** fire-and-forget（`await` しない）、
失敗しても画面に何も出さない、`maxRetries: 0`。**計時の正しさ > 記録の完全さ** です。

**この表は AI の副産物ではありません。** 「この型のロールは予定より平均 N 秒押す」は
次回の尺見積もりにそのまま効くので、**AI 機能を作らなくても価値があります**。
逆に言えば、**この表が入るまで ②の条件3 は ✕ のまま**です（§14-6 で確認）。

指標の出し方（`getFeedbackDigest('script_outline_draft')` の `outline` 分岐で導出。
`ai_outcomes` に焼かない）:

⚠️ **初版の式は「AI の尺」ではなく「人が直したあとの尺」を測っていました（検査 AIループ#F3）。**
`planned_sec` は DDL のコメントどおり**「そのとき画面が出していた予定尺」＝本番当日に
人が直し終わった値**です。行を `applied_ids.rows` に絞っても、**絞られるのは行であって値の版ではありません。**
したがってこの数字は「**ディレクターの尺見積もりの精度**」であり、
**AI が酷い尺を出しても人が全部直せば良く出ます** — 改善判断が逆向きになります。

**決め: `settleProposal` の時点で `applied_payload` から AI の初期値を取り出し、3つ計算して全部返す**
（新規カラムは不要）:

```
ai_duration_mape    = median(|actual_sec - applied_payload の duration| / applied_payload の duration)
                        ← **AI の精度（主指標）**
human_duration_mape = median(|actual_sec - planned_sec| / planned_sec)
                        ← 人の最終見積もりの精度（参考。初版が主指標にしていたもの）
plan_drift_sec      = median(planned_sec - applied_payload の duration)
                        ← **人が AI の尺をどちらへ何秒動かしたか**
```

`plan_drift_sec` は **§6-3 のナレッジの自動ルール案に直結します**
（「挨拶系のロールは AI の初期値より中央値 −90 秒に動かされる」）。
§6-3 の例文が想定していたのはまさにこれで、**`fix` の件数からでは秒数が出ません。**

⚠️ **実尺の取得率を必ず並べること（検査 AIループ#F14）。**
ランダウンを使わない現場の本番は `qsheet_cue_actuals` に1行も入らないので、
`duration_mape` の分母が「几帳面なチームの本番」に偏ります（自己選択バイアス）。

```
runs_measured / broadcasts_total     ← broadcasts_total = その期間に broadcast_date が過ぎた台本の数
```

を月次レポートと `FeedbackDigest.outline` に**必ず並べ**、取得率が5割を切っている間は
`advice` に「実尺の記録がある本番が少ないため、尺の傾向は断定できません」を出す
（既存の「10件未満は断定しない」作法と同じ）。

**b) ①枠の成果 — △**

枠が実際どう動いたかの記録がありません（進行表は「予定」だけ）。
代替: **確定時の枠と、取り込み時の枠の差**（開始が何分ずれたか・項目が何本消えたか）。
これは条件2の差分と同じデータなので、成果としては弱い（人が直したこと自体は測れるが、
当日その通りに動いたかは分からない）。**△ と書きます。**

将来: `qsheet_cue_actuals.run_started_at` と `qsheet_schedule_items.start_min` を突き合わせれば
「本番が予定より何分遅れて始まったか」が出ます。**これは実尺表が入った後の第2版**。

**c) ③セリフの成果 — △**

文章の良し悪しを外から評価する仕組みは社内に存在しません。
代替の3つ:

1. **行の生存率**: 取り込んだ行のうち、確定時に **`reject` でも `fix` でもない**行
   （＝ `none` と `rephrase`）の割合。
   ⚠️ 初版は「`text` が残っている割合」でしたが、**全文書き換えでも「生存」**になっていました
   （検査 AIループ#F21）。上の定義なら、F13 の類似度が入った時点で自動的に意味が通ります。
2. **改稿の深さ**: `rephrase`（±20% 以内）と `fix`（それ以外）の比。
   `rephrase` が多い＝方向は合っているが言い回しが合わない → **ナレッジ（文体）の出番**。
   `fix` が多い＝中身が違う → **プロンプトか材料の出番**。この2つを分けられることに意味があります。
3. **プロンプターで実際に読まれたか**: `qsheet_cue_actuals` にその行の記録があれば、
   **その台詞は本番で使われた**と言えます。捨てられた行と区別できます。

**d) ④壁打ちの成果 — ✕ と代替**

対話の成果は測れません。代替:

- **起票率** = `spawned_proposal_id` が付いた assistant 発言 / 全 assistant 発言
- **起票の質** = そこから生まれた提案の無修正採用率（②③の数字を④に紐づけて読む）
- **👍率** = 3値が付いた発言のうち `good` の割合

**「壁打ちが役に立ったか」の直接の証拠は最後まで手に入りません。** ✕ のまま残します。

### 5-4. 顧客反応（条件3の後半）— 4機能とも ✕

台本や進行表に顧客の反応は付きません。**新しいアンケート基盤は作りません**（`patterns.md` の定石）。

代替（弱い proxy であることを明記して使う）:

| proxy | 出どころ | 弱さ |
| --- | --- | --- |
| **同じ案件の次の回が作られたか** | `episodes` が増えたか | 継続は AI とほぼ無関係 |
| **同じ顧客のリピート** | `projects` に同じ `customer_id` の新規が立ったか | 同上 |
| **案件の `stage`** | `a_won` / `e_lost` | **台本は受注の後に作るので、因果が逆。使えない** |

**結論: 顧客反応は測らない、と正面から書きます。** 測れないものを測れるふりをして
数字を出すほうが害が大きい（既存の `minutes.tracked_rate` に
「これを『AI が正しかった率』と読まないこと」という注意書きが付いているのと同じ発想）。

代わりに §5-5 のレビューで、**制作管理のマネージャーが定性的に見る**ことで埋めます。

### 5-5. 条件5 — レビュー頻度と担当

**既存（月1回・営業のマネージャー）とは担当が違います。**

| 項目 | 決め |
| --- | --- |
| **担当** | **`ops_reports.assignee_user_id` で1人を指名する。**⚠️ 初版の「`user_permissions.module='qsheet'` かつ `access_level='manager'`」は、**migration 210 の後では「フルアクセス型の全員」にマッチし、担当を特定できません**（検査 地雷#12）。通知は下の 2 のとおり qsheet manager 全員へ出し、**責任者は1人を名前で決める**（誰かは §14-10） |

| **承認の反映** | 承認したナレッジだけ `qsheet_ai_knowledge.status='active'` になり、次の生成から効く。**自動昇格させない**（誤ったルールが固定化する） |

⚠️ **既存の課題を繰り返さないこと。** `onair-current-state.md` の「残っていること #1」に
「頻度と担当は決まったが**仕組みへの落とし込みが未**」とあります。
**この設計では月次の `ops_reports` 行を作る処理を実装スコープに含めます**（下書きの自動生成まで。
公開は人が押す）。ここを「決めただけ」で終えると、また ✕ が1つ増えます。

⚠️ **初版は「何が起動するのか」を書いていませんでした（検査 AIループ#F9）。**
問題意識だけあって仕組みが無いのは、まさに繰り返してはいけない失敗の形です。
ONAiR には既に `server/src/contexts/platform/services/scheduler.service.ts` に
`scheduled_job_runs(job_key, run_date)` ベースの定時実行と、週報公開時の通知
（`link` / `refType:'ops_report'` / `refId`）の前例があるので、**そこに載せると
1行も新しい仕組みが要りません。** 次の3つを実装スコープに入れます:

1. `scheduler.service.ts` に **`job_key='ai_review_production_draft'`** を足し、
   **毎月1日 03:20 JST**（既存の 3:10 とずらす）に先月分の digest を集めて
   `ops_reports(kind='ai_review_production', period_key='YYYY-MM', status='draft')` を作る。
   `uq_ops_reports_kind_period` が二重作成を DB 側で止めます。
2. 作ったら**週報と同じ通知経路**で `qsheet` の manager 全員に出す
   （**担当を個人名だけで通知しない** — 休職・異動で止まる）。責任者は `assignee_user_id`。
3. **`ops_reports.reviewed_at` を条件5の計測に使う。**
   2か月連続で `reviewed_at IS NULL` なら `getFeedbackDigest` の `advice` 先頭に
   「先月・先々月の AI レビューが未実施です」を出す
   （**AI 自身が読む場所に出すのがいちばん確実**）。

⚠️ **月次レポートの `payload` に個票（`recent_examples`）を入れないこと**（下の §5-6）。

---

### 5-6. ⚠️ 台詞の本文が共有APIキーで読めてしまう穴を塞ぐ（検査 AIループ#F1・P0）

**この設計をそのまま実装すると、台本の台詞が全社の誰からでも読める経路が新しくできます。**

- `get_ai_feedback_digest` は **read ツールなのでゲートが無く**
  （`gate.ts:14` の既知の穴。`enforceToolPermissions` は `isOAuth===false` で即 return）、
  `kind` は **enum ではなく素の `z.string()`**。
- 返り値の `recent_examples` は `before_value` / `after_value` を**そのまま**返します
  （`ai-feedback.service.ts` の examples クエリ）。
- `script_line_draft` の差分は before/after が**台詞の本文そのもの**です。

05-mcp.md は §3-1 で「台本は 404 で存在秘匿だから静的キーを拒否する」と丁寧に設計していますが、
**その同じ台詞が既存の無ゲート read ツールから読めては意味がありません。**
同じ問題が `ops_reports` にもあります（`kind='ai_review_production'` の器の読み取りは
`requirePermission('dailyops','reader')`。**制作の台本の断片が日常業務アプリの権限で読める**）。

**決め（3つとも実装する）**:

1. `server/src/contexts/mcp/tools/aifeedback.tools.ts` の **`kind` を `z.enum([...])` に変え**、
   qsheet 系4 kind は **OAuth actor かつ `qsheet` manager 以上でないと弾く**。
   403 にすると既存バッチの挙動が変わるので、**`recent_examples` を落として集計値だけ返す degrade** にする。
   ⚠️ `kind` 引数は**必須にしない**（`z.enum([...]).optional()`）。
   既存の `kind` は `z.string().optional()` で、Git 管理外のメール取込スキルが最短1時間おきに
   叩いています。**必須引数を1つ足すと次の実行から全部落ちます**（05 §11 の禁止事項そのもの）。
2. `settleProposal` が `ai_corrections` に積む `script_line_draft` の
   `before_value` / `after_value` は、**本文そのものではなく
   `{ len, head: 先頭20字, hash }`** にする。
   **全文の正は `ai_outputs.payload_snapshot`（MCP から読めない）に既にあるので、教師データは失われません。**
3. 月次レポート（§5-5）の `payload` に個票を入れない。**集計値と `field_path` だけ**にする。
   個票が要るなら `ops_reports` に相乗りせず、**`qsheet` 権限の別ルート**を作る。

## 6. 「履歴を学習して精度を上げる」の具体設計

**digest をプロンプトに載せるだけでは弱い**、という指摘はその通りです。3段重ねます。

### 6-1. 第1段: digest（自動・毎回・全機能）

生成の**プロンプトを組む前に**読みます（既存6機能と同じ作法）。

```ts
let advice: string[] = [];
try {
  advice = (await getFeedbackDigest(SCRIPT_OUTLINE_KIND, 90, segmentKey)).advice ?? [];
} catch { /* 取れなくても生成は続ける */ }
// 先頭 6〜8 件をプロンプトへ
```

**`get_ai_feedback_digest` に kind を足すだけでは足りません。** 理由:

> 式典（`project_type='ceremony'`）は前半が押して後半で巻く。
> 配信（`streaming`）は逆に序盤が巻く。**全社平均の助言は両方に嘘をつきます。**

**したがって `segment` を足します。**

- `getFeedbackDigest(kind, windowDays, opts?)` に第3引数を足す。
  ⚠️ **第3引数は `segmentKey` の文字列ではなく `{ segmentKey?: string; source?: 'server'|'mcp' }`
  のオブジェクトにします**（検査 AIループ#F12）。05 §10-3 が「`source` 別に切りたいが 04 の
  `segment` 待ち」と書いており、**別々に足すと digest を2回いじることになる**ためです。
  05 の「当面は C（混ざったまま）」は**採りません** — 混ざった期間のデータは後から切り分けられません。
- `segmentKey` は `type:<project_type>|loc:<location_id>` の形の文字列。
- 保存場所は **`ai_outputs.payload_snapshot.context.segment_key`**。
  **`ai_*` 3表のスキーマは変えません**（既存の方針）。ただし**索引だけ1本足します**:

```sql
-- ai_outputs へのスキーマ変更ではなく、式インデックスの追加のみ
CREATE INDEX IF NOT EXISTS idx_ai_outputs_segment
  ON ai_outputs ((payload_snapshot->'context'->>'segment_key'))
  WHERE payload_snapshot->'context'->>'segment_key' IS NOT NULL;
```

⚠️ **SQL で jsonb の `?` 存在演算子を書かないこと**（プレースホルダと誤認されて syntax error。
既知の地雷）。上のように `->> ... IS NOT NULL` で書きます。

⚠️ **segment で切ると母数が減ります。** 既存の作法（3件未満は比較しない・10件未満は
「断定できない」と添える）に従い、**segment の母数が 10 未満なら全社の digest に落とす**。
落としたことを `advice` の1行目に書く（「この型の実績が少ないため全体の傾向を使っています」）。

digest に足す分岐（`FeedbackDigest` の任意プロパティ ＋ `buildAdvice` の文面もセットで）:

```ts
/** 骨格の成績 (kind=script_outline_draft のときのみ)。ai_outcomes には焼かない */
outline?: {
  settled: number;              // 締めた提案の数
  rows_applied: number;         // 取り込まれた行の総数
  rows_survived: number;        // 確定時に残っていた行
  survival_rate: number | null;
  /** 尺の精度。qsheet_cue_actuals がある行だけ（無ければ null） */
  duration_mape: number | null;     // median(|actual-planned|/planned)
  duration_bias_sec: number | null; // median(actual-planned)。正=押し
  runs_measured: number;
};
/** セリフの成績 (kind=script_line_draft のときのみ) */
line?: {
  lines_applied: number;
  lines_survived: number;
  rephrased: number;   // 言い回しだけ直された
  fixed: number;       // 中身を変えられた
  rejected: number;
};
/** 壁打ちの成績 (kind=production_chat のときのみ) */
chat?: {
  assistant_messages: number;
  rated: number;            // 3値のどれかが付いた数 = 分母
  good: number;
  spawned: number;          // 提案を起こした発言
  spawn_rate: number | null;
};
```

### 6-2. 第2段: few-shot（自動・毎回）— **過去の確定済み Qシートを見本に入れる**

digest は「傾向の文」ですが、few-shot は「**現物**」です。効き方が違います。

**②骨格の場合**（プロンプトに入れる形）:

```
## 過去の似た回（見本 / 3件まで）

### 見本1 — 類似度 17 点（同じ案件の第4回・2026-05-12・用賀 WORLD STUDIO・合計 68分）
| ロール | 尺 | 行数 |
|---|---|---|
| 開場・影アナ | 5:00 | 2 |
| オープニング映像 | 1:30 | 1 |
| 主催者挨拶 | 6:00 | 3 |
...
（本文は入れない。ロール名・尺・行数だけ）

### 見本2 — 類似度 11 点（同じ顧客・別案件・…）
```

- **本文（セリフ）は入れません。** トークンが跳ね、守秘の面も難しくなり、
  そして**骨格を作るのに本文は要りません**。
- **3件まで**。増やすと「見本の平均」に寄り、その案件固有の事情が消えます。
- **類似度の点を明示して渡す**。AI に「どれをどれだけ信じるか」を判断させます。

**③セリフの場合**: 同じ案件 or 同じ顧客の確定済み台本から、
**同じ話者の発言を最大10行**（§2-7 の守秘制約つき）。これが文体の学習になります。

```
## この番組での「司会」の話し方（過去の確定稿から）
- 「それでは、ただいまより……を開会いたします」
- 「続きまして、…より一言ご挨拶を申し上げます」
```

**①枠の場合**: 同じ拠点・同じ `project_type` の過去の進行表を、
`kind` と `start_min`/`end_min` の一覧で1〜2件。

### 6-3. 第3段: ナレッジ（人が承認したときだけ効く）

digest は「よく直された」という**統計**、few-shot は**現物**、ナレッジは**明示的なルール**です。
3つは代替関係ではありません。

```sql
CREATE TABLE IF NOT EXISTS qsheet_ai_knowledge (
  id          TEXT PRIMARY KEY,
  /* どの機能に効かせるか。NULL = 全部 */
  kind        TEXT,
  /* どの型に効かせるか。NULL = 全部。§6-1 と同じ形の文字列 */
  segment_key TEXT,
  /* ルール文。プロンプトにそのまま行として載る */
  body        TEXT NOT NULL,
  /* なぜこのルールがあるか（レビューで読む） */
  rationale   TEXT,
  /* draft = 提案されただけ / active = 人が承認して効いている / retired = 効かせるのをやめた
     **draft は絶対にプロンプトへ載せない**（誤ったルールの固定化を防ぐ） */
  status      TEXT NOT NULL DEFAULT 'draft'
              CHECK (status IN ('draft', 'active', 'retired')),
  /* どこから来たか。auto = 集計から機械的に提案 / human = 人が直接書いた */
  origin      TEXT NOT NULL DEFAULT 'human' CHECK (origin IN ('auto', 'human')),
  /* auto のとき、根拠になった集計（件数・割合・例）を残す */
  evidence    JSONB,
  sort_order  INTEGER NOT NULL DEFAULT 0,
  approved_by TEXT REFERENCES users(id),
  approved_at TIMESTAMPTZ,
  created_by  TEXT REFERENCES users(id),
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_qsheet_ai_knowledge_active
  ON qsheet_ai_knowledge(kind, segment_key, sort_order) WHERE status = 'active';
```

**育て方**:

1. 月次レビュー（§5-5）の下書き生成時に、`top_corrected_field_types` の上位から
   **`origin='auto'` / `status='draft'` のルール案**を機械的に作る。
   例: 「`sections[].duration` の 62% が短縮修正されている（中央値 −90 秒）」
   → 「**尺は控えめに置く。特に挨拶系のロールは過去実績の中央値を超えない**」
2. マネージャーが承認したものだけ `active` になる。
3. `active` のルールは**全機能のプロンプトに毎回載る**（`kind`/`segment_key` で絞って）。
4. 効かなくなったルールは `retired` にする。**削除しない**（なぜ外したかを後から読めるように）。

⚠️ **`draft` を載せない**のが最重要です。自動昇格させると、
たまたま2件続いた偏りが恒久ルールになり、以後ずっと同じ方向に外し続けます。

### 6-4. 3段の関係（まとめ）

| 段 | 更新の速さ | 人の関与 | 効き方 |
| --- | --- | --- | --- |
| digest | **次の生成から即** | 不要 | 弱いが広く効く。リリースを待たない |
| few-shot | 確定するたび | 不要（`is_reference` を落とすときだけ） | **一番効く**。現物の型がそのまま伝わる |
| ナレッジ | 月1回 | **承認が必須** | 強く効く。だから承認が要る |

### 6-5. 「改善したか」を測れるようにする（検査 AIループ#F10・F11・F12）

**初版のままでは「ナレッジを5本承認したら良くなったのか」を構造的に言えません。**
`by_model` は `model` × `prompt_version` の組でしか切れないのに、
3段のうち2段（digest の advice 文・ナレッジ）は**毎月中身が変わるのに
`prompt_version` は `script-outline-v1+fb` のまま**だからです。
ナレッジ承認は §5-5 の月次レビューの主要な決定事項なのに、その効果検証ができません。

**a) `prompt_version` にナレッジの版を入れる**

```ts
// server/src/contexts/qsheet/ai/kinds.ts に純関数を1つ置く
export const promptVersionOf = (base: string, knowledgeRev: number, adviceCount: number) =>
  `${base}+k${knowledgeRev}${adviceCount > 0 ? '+fb' : ''}`;   // 例 script-outline-v1+k7+fb
```

`knowledgeRev` は件数ではなく**承認のたびに増える単調なリビジョン**にします
（`qsheet_ai_knowledge` に `rev INTEGER` を持たせ、`status` を変えるたびに `MAX(rev)+1` を採る）。
`by_model` の行は割れますが、**割れないと比較そのものが成立しません。**

**b) 生成に使った材料を復元できるようにする**

初版の `context`（§10-1）は `advice_count` / `knowledge_count` / `references[{document_id, score}]` で、
**全部カウントと参照だけ**です。few-shot の現物は `qsheet_documents.data` を指しますが、
**その `data` は Yjs が3秒ごとに上書きし続ける**ので、1か月後に同じ見本を再現できません。
「なぜこの出力になったか」を後から読めないのは、教師データとして半分死んでいます。

→ **`ai_outputs.payload_snapshot` に入力側も全文で入れます**（切り詰めないのが既存の方針）:

```json
{ "output": { ... },
  "input": {
    "advice":    ["...", "..."],                                  // 実際に載せた文そのもの
    "knowledge": [{ "id": "...", "rev": 7, "body": "..." }],
    "fewshot":   [{ "document_id": "...", "score": 17, "outline": [ ... ] }],  // 渡した現物
    "materials": { "…§2-1 の束…": "…" },
    "segment_key": "type:ceremony|loc:yoga" } }
```

`qsheet_ai_proposals.context` は**画面表示用の要約**のままでよい
（教師データの正は `ai_outputs` 側、という役割分離は既に採っている考え方）。

**c) MCP から来た自己申告の `model` を混ぜない**

05 §4-7 は `model` / `prompt_version` を**任意の文字列引数**にしています。呼ぶのは外部の Claude で、
検証はできません。`by_model` は改善の唯一の比較軸なので、
**検証できない値とサーバーが自分で入れた値を同じ列に混ぜてはいけません。**
→ MCP から来た値は **`model` に `mcp:` を前置して保存**する（`mcp:claude-opus-4`）。
digest はそのままでよく、**`mcp:` で始まる行は「自己申告」と読めます。**

**d) 記録が黙って切れていないかを見る（F17）**

`ai_output_id` は FK 無し・記録は best-effort（§8-1）なので、失敗すると条件1〜2が黙って切れます。
→ **`ai_output_id IS NULL AND state <> 'failed'` の件数を月次レポートに1行出す。**
0 でないことを見る人がいる状態にします。

**e) 生成回数の上限（F20）**

初版は④（40往復）にしか上限がありません。①②③の「まとめて作る」は heavy×3 で、
乱打すると**費用と F5 の分母汚染が同時に起きます。**
→ **1文書あたり `state='open'` の提案は5件まで**（超えたら古いものを自動 `expired`）、
**直近1時間の生成回数にも上限**。どちらも `qsheet_ai_proposals` を数えるだけで新テーブル不要。

## 7. モデル選択（`light` / `heavy`）

`shared/services/ai-model.ts` に `AiJob` を4つ足し、`POLICY` に段を書きます。
**判断基準は「間違いに気づけるか」であって費用ではありません**（`docs/ai-models.md`）。

```ts
export type AiJob =
  | 'intake' | 'activity' | 'minutes' | 'kpt'          // 既存
  | 'event_plan' | 'script_outline' | 'script_line' | 'production_chat';  // 追加
```

| 機能 | 段 | 根拠（「間違いに気づけるか」） |
| --- | --- | --- |
| ① `event_plan` | **heavy（常時）** | 時刻の計算違いは当日を壊す。**枠の重なりは画面で気づけるが、移動時間や転換の抜けは気づけない**。抜けは「無いこと」なので目視で見つからない |
| ② `script_outline` | **heavy（常時）** | 尺の配分は**足し算が合っていても現実と合わない**ことがあり、本番まで分からない。押し引きは最も気づきにくい誤り |
| ③ `script_line` | **light（既定）／ 4,000 字超で heavy** | セリフは**読めば良し悪しが分かる**。間違いに気づける典型。長文は文脈保持が必要なので heavy に上げる（`activity` の閾値に揃える） |
| ④ `production_chat` | **light（既定）** | **次のターンで直せる**のが対話。ただし `suggestion` を伴う（＝生成に踏み込む）ターンは heavy に上げる |

```ts
// ⚠️ 実際のフィールド名は { base, lightMaxChars }（ai-model.ts:200）。
//    初版が書いていた heavyOver は**存在しません**（検査で判明）。
const POLICY: Record<AiJob, { base: AiTier; lightMaxChars?: number }> = {
  // …既存…
  event_plan:      { base: 'heavy' },
  script_outline:  { base: 'heavy' },
  script_line:     { base: 'light', lightMaxChars: 4_000 },
  production_chat: { base: 'light' },   // suggestion を出すターンは force: 'heavy'
};
```

⚠️ **機能ごとの環境変数は新設しませんが、`JOB_ENV` には4行足さないと型が通りません。**
`JOB_ENV: Record<AiJob, EnvName[]>` なので、`AiJob` を4つ足すと
**`JOB_ENV` にも4行（`event_plan: []` 等の空配列）が必要**です（検査で判明。
初版の「新設しません」だけを読んでコンパイルが通らないのを避けるため明記）。
段ごとの `AI_MODEL_HEAVY` / `AI_MODEL_LIGHT` と組み込み既定で足ります。
`env` は必ず `process.env.X` の literal で読むこと
（`scripts/check-env-passthrough.mjs` が literal を数えて渡し漏れを検出するため）。

**`ai_usage.kind` に4つ足す**（`ai_outputs.kind` とは**別体系**なので混同しないこと）:

```ts
export type AiUsageKind =
  | 'intake' | 'minutes' | 'activity' | 'activity_short' | 'kpt' | 'stt' | 'stt_preview'
  | 'event_plan' | 'script_outline' | 'script_line' | 'production_chat';
```

**画面ラベル `KIND_LABEL`（`client/src/contexts/platform/pages/settings/AiUsageCard.tsx:54`）も
同時に直す。** 片方だけ直すと使用量画面に生の英語が出ます。

⚠️ **`AI_PRICING_JSON` に新モデルの鍵を足し忘れると、その行が合計に入らず静かに安く見えます。
古い鍵も消さないこと**（既知の地雷）。

## 8. 失敗のさせ方（AI が落ちても業務が止まらない）

### 8-1. 原則

| 原則 | 具体 |
| --- | --- |
| **`data` に触らない** | AI が落ちても台本は無傷。提案テーブルに `state='failed'` が1行残るだけ |
| **記録は best-effort** | `recordAiOutput` / `recordCorrections` / `recordAiUsage` は全部 try/catch で warn に落とす。**記録の失敗で業務を止めない**（既存の作法） |
| **無人バッチに AI を置かない** | 締め（`settleProposal`）・実尺の集計・索引の作り直し・月次レポートの下書きは**全部 AI を呼ばない純粋な処理**。夜間バッチが LLM のタイムアウトで詰まる経路を作らない |
| **人が待つ経路は `maxRetries: 0`** | `new OpenAI({ timeout, maxRetries: 0 })`。1 だと上限時間が倍になる（既知） |
| **light → heavy の1回だけリトライ** | ③④のみ。**例外が出たときだけ**やり直す。**内容が気に入らないときはやり直さない**（人が「作り直す」を押す） |
| **部分成功を許す** | `normalize` が壊れた section / 行だけ落として残りを返す。**ゼロか全部かにしない**。ただし**全部落ちたら失敗**にする（空の提案を「成功」と見せない） |
| **失敗した呼び出しも課金される** | `recordAiUsage({ ok: false, errorMessage })` を必ず残す（既存 `minutes.service.ts:194-201` と同じ） |

### 8-2. 本番中（OnAir / Rundown）の扱い

**本番中は AI を1回も呼びません。** 提案の生成ボタンは
`qsheet_cue_actuals` にその日の run が立っている間、**画面から消します**。
理由: 本番中に「考えています…」で数十秒待たされる操作を1つも作りたくない。

実尺の記録（§5-3a）だけは本番中に走りますが、これは**単純な INSERT で AI を呼びません**。
fire-and-forget、失敗しても画面に何も出しません。

### 8-3. 待ち行列は作らない（既存の作法に従う）

**ジョブ表を作りません。** 状態は `qsheet_ai_proposals` の2列で表します
（migration 187/188/190 と同じ形）:

- `state='applied' AND settled_at IS NULL` … 締め待ち
- `state='failed' AND error_message IS NOT NULL` … 失敗
- `state='open'` … 人の判断待ち

**数える SQL と拾う SQL は同じ定数（`PENDING_SETTLE_SQL`）を共有**します。
書き戻しの UPDATE には **`WHERE ... AND settled_at IS NULL`** を付けて、
同時実行と二重締めを構造で防ぎます。

⚠️ **実装で必ず守ること（既知の地雷）**

- **`applyProposal.ts` は `applyDataUpdate` の3手順（`backfillIds` → `yDocToData` → `ensureStableIds(updater(prev))`）を絶対に崩さない。** 崩すと行が指数的に増える（実測 3→769→100万行）。
- ⚠️ **`updater` は必ず `prev` の関数にする。定数スナップショットを返さない**（検査 地雷#1）。
  `applyDataUpdate(ydoc, () => 合成済みデータ)` と書くと、プレビュー中に他人（**または自分の別タブ**）が
  足した行が削除分岐に落ちて**黙って消えます**。提案の取り込みは
  `applyDataUpdate(ydoc, prev => applyProposalOps(prev, proposal))` の形にすること。
  03-excel.md §8-1 が同じ規約を持ちます。
- **提案の要素に `key` を持たせ、取り込み時に `genId()` へ置き換える。** AI に id を作らせない。
- **尺は必ず `shared/src/schedule/time.ts` の `fmtDur(sec)` / `parseDur(str)` を通す。**
  提案の型は `duration_sec: number`、書き込み先は `"1:30"` 形式の**文字列**です。
  どちらの書式に揃えるかは 03 §12-3 の確認事項と一緒に決めること
  （既定は「入っている文字列をそのまま・新規は `M:SS`」）。**差分は文字列同士ではなく
  `parseDur` した秒で比べる**（検査 整合#5）。
- **壁打ちの入力は `BufferedTextarea`。** 素の `<textarea>` に replace すると IME が壊れる。
  ⚠️ **`onCommit` を送信ハンドラに繋がないこと**（検査 地雷#21）。`useBufferedValue` は
  「打鍵が止まって 500ms」で `onCommit` を呼ぶので、繋ぐと**入力途中で勝手に送信されます。**
  `onCommit` は**下書きの保持だけ**。送信は明示のボタン。Enter 送信を付けるなら
  `onCompositionEnd` を見て**変換確定と区別する**こと。
- **`data` を書くのはクライアントだけ。** サーバー側に**既存文書の**
  `UPDATE qsheet_documents SET data` を1行も書かない。
  ⚠️ **新規 INSERT は例外**です（Yjs のルームがまだ無いので安全。02 §6-2「枠から台本を作る」が
  これに当たる）。初版の「1行も書かない」という書き方だと、実装者はどちらかを必ず破ります（検査 整合#11）。

## 13. 未確定の判断と、そう判断した根拠（迷ったところ）

### 13-1. ベクトル検索を入れないこと（§2-2）

**根拠は §2-2 に書いたとおりですが、決め手が1つ足りていません: 確定済み Qシートの実件数です。**
本番 DB を数えていません（このセッションから本番へアクセスできない）。

- **3,000 件未満なら**、索引テーブルの全件スキャン ＋ Node 側スコアリングで数十 ms。迷いなくこれで足ります。
- **数万件になったら**、`is_reference` と `project_type` の部分索引で絞ってからスコアリングすれば
  なお足りますが、「メタデータで絞れない探し方」（自由記述からの検索）が欲しくなる時期でもあります。

**迷ったところ**: 「一撃で当てる」ためには見本の質が全てなので、
**ベクトル検索を入れないぶん、類似スコアの重み（§2-3）が当たっているかが命**になります。
重みは私が置いた推測値で、根拠のある数字ではありません。**運用開始後に
「この見本は似ていない」を人が押せるようにして、重みを直す材料を貯めるべき**です
（`SimilarDoc` に「似ていない」ボタンを足す ＝ 第2版）。

### 13-2. 確定の合図を「本番の翌日」にしたこと（§3-3）

`qsheet_documents.status` が実質使われていない（`rehearsal`/`on_air` に上げる UI が無い）ため、
本番日を軸にしました。**しかし**:

- **`broadcast_date` が空の台本が実際どれくらいあるか分かりません。** 空なら `timeout`（7日）に落ちますが、
  7日は「案件が数か月更新され続ける」ONAiR には短すぎる可能性があります。
- **代案として「`status` に UI を足す」も検討しました**（「この台本で本番に入る」ボタン）。
  こちらのほうが意図が明確ですが、**押し忘れると永久に締まりません**。
  時間ベースは押し忘れがない代わりに、意図が曖昧です。
- **判断: 時間ベースを主、ボタンを従**にしました。ボタンは足してもよいが、
  **無くても回る**設計にしてあります。→ §14-5

### 13-3. 壁打ちをストリーミングしないこと（§4-3）

サーバーに SSE が1本も無く、Nginx の設定（バッファリング）も確認していません。
**「AI 機能の都合だけで基盤を決められない」**（Excel の `exceljs` 移行を 02-schedule.md が
同じ理由で見送ったのと同じ）ので、第1版は1往復にします。

**迷ったところ**: 壁打ちは体感が全てで、10 秒黙って待たされる UI は使われなくなります。
`light` 段のモデルを使う（§7）ことで待ち時間を短くしていますが、
**それで足りるかは実測しないと分かりません**。足りなければ SSE を別途検討します。

### 13-4. `qsheet_cue_actuals` をこの設計に含めたこと（§5-3a）

**厳密には AI 機能ではありません。** 「AI 機能の設計書に、本番の計時の設計が入っている」のは
筋が悪いとも言えます。

**それでも含めたのは、これが無いと ②の条件3 が ✕ のままだからです。**
「尺の精度」は利用者が例として挙げた指標そのもので、代替がありません。

**迷ったところ**: 実装の順序として、**先に実尺表だけ入れて数か月データを貯めてから
AI 機能を作る**ほうが、初回から digest が効いて立ち上がりが速いかもしれません。→ §14-6

### 13-5. 壁打ちスレッドを共有しないこと（§4-3）

第1版は `created_by` 本人のみ。**チームで1本のスレッドを囲んで相談する**ほうが実務に合う可能性は
高いと思っていますが、共有すると:

- 誰の 👍 なのかが混ざる（`feedback_by` は持っていますが、集計の分母が曖昧になる）
- スレッドに紐づく案件のアクセス権と、スレッド自体のアクセス権の二重管理になる

**判断: まず本人のみで出し、要望が出たら `qsheet_document_shares` と同じ形で足す**。
（既存の共有テーブルと同型なので後付けのコストは小さい）→ §14-8

### 13-6. `slide` / `lighting` / `remarks` / `item` を AI に書かせないこと（§2-4）

`remarks` と `item` は汎用 `{value}` セルなので**技術的には書けます**。
書かせなかったのは、**出す量を増やすと人が読む量が増え、雑に取り込まれて
条件2の差分が「無修正」で埋まる**ことを恐れたためです。

**迷ったところ**: 実務では「小道具」が最初から埋まっていることの価値が高いかもしれません。
→ §14-3

## 14. 利用者に確認すべきこと

1. **4つの切り分けでよいか。**（①当日の枠 ②骨格 ③セリフ ④壁打ち）
   実務でもっと手前、たとえば「**企画書そのものの下書き**」が欲しくはないですか。
   要るなら5つ目の kind（`event_concept_draft`）になります。（§1）
2. **「まとめて作る」は ①→②→③ の順でよいか。** 段ごとに止まる作りにしていますが、
   「全部作ってから見たい」なら止め方を変えます。**どこで一番止まりたいですか。**（§2-6）
3. **AI に埋めさせるのは `シナリオ` だけでよいか。**
   第1版は「ロール名・尺・話者・セリフ」だけです。**最初から `映像` `テロップ` `小道具` が
   埋まっていてほしいですか。** 埋めるほど便利になりますが、**読んで直す量も増えます。**（§2-4・§13-6）
4. **他社の台本を見本にしてよいか。**
   設計では「**骨格（ロール名・尺）は全社共有／セリフ本文は同じ案件か同じ顧客のみ**」にしています。
   骨格も顧客ごとに閉じるべきですか。（§2-7）
5. **「本番が終わった」をどう判定するか。**
   設計では「**本番日の翌日 03:00**」または「**本番のトランスポートが動いた日の翌日**」です。
   「**この台本で本番に入る**」ボタンを足して、押した時点を確定にしますか。
   （押し忘れると永久に締まらないので、時間ベースと併用する前提です）（§3-3・§13-2）
6. **実尺の記録を先に入れますか。**
   「AI が置いた尺がどれだけ押したか」は**現在まったく記録されていません**。
   これを先に数か月動かしてから AI 機能を作ると、**初回から実績が効いた尺**が出せます。
   AI と同時に出すか、先に実尺だけ出すか、どちらがよいですか。（§5-3a・§13-4）
7. **本番中に AI のボタンを消してよいか。**
   設計では消します（本番中に数十秒待つ操作を作らないため）。
   **本番中に「差し替えのセリフをすぐ出して」が要りますか。**（§8-2）
8. **壁打ちはチームで共有しますか。** 第1版は本人のみです。（§4-3・§13-5）
9. **壁打ちの上限（1スレッド 40 往復）は妥当ですか。**
   上限に当たったら「新しいスレッドを」で止めます。（§4-3）
10. **月次レビューの担当は「制作管理のマネージャー」でよいか。** 具体的にどなたですか。
    営業のマネージャー（既存の AI レビュー担当）とは別にしています。（§5-5）
11. **月1回で足りますか。** イベントの本数が月に数本なら月1回、
    十数本以上あるなら**隔週**のほうが早く効きます。（§5-5）
12. **「顧客反応は測らない」でよいか。**
    台本に顧客の反応は付かないため、**測れないと正面から書きました**。
    もし「顧客が台本を見て何と言ったか」を残す場所があるなら教えてください。（§5-4）
13. **セリフの「良し悪し」は誰が決めますか。**
    設計では「人が直したか」でしか測っていません。
    **本番前に誰かが赤入れする工程**があるなら、そこが最良の教師データです。（§5-3c）
14. **見本を「これは似ていない」と却下する操作は要りますか。**
    類似スコアの重み（§2-3）は私が置いた推測値で、**直す材料が無い状態**です。（§13-1）
15. **「AI が作った」ことを画面に出しますか。**
    設計では提案のプレビューにしか出しません（取り込んだ後は人の台本として扱う）。
    本番の台本に AI バッジが残っているべきですか。

**ここから下は検査（2026-08-21）で足した確認事項です。**

16. ⚠️ **月次レビューの責任者を1人、名前で決めてください。**
    「`qsheet` の manager」は migration 210 の後では**フルアクセス型の全員**を指すので、
    権限からは特定できません（§5-5・02 §9-2）。
17. **台詞の差分を「本文のまま」記録してよいか。**
    設計では **`{ len, head: 先頭20字, hash }`** に落とします（全文の正は `ai_outputs` 側に残る）。
    そうしないと、無ゲートの `get_ai_feedback_digest` から**台詞が全社で読めます**（§5-6）。
18. **締めのタイミング（2段）でよいか。** 1段目＝取り込みから7日（AI 起因の修正）、
    2段目＝本番の翌日（本番直前にどれだけ動いたか）。1段目だけにすると当日の直しが取れず、
    2段目だけにすると数か月ぶんの通常の練り直しが AI の誤りに混ざります（§3-3）。
