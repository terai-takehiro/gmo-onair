## 2. `MiniAppDef` / `MiniAppKind` の型変更

### 2-1. 型の拡張（軽量統合案 §1 を採用）

```ts
// shared/src/production/miniapps.ts（変更イメージ）

export type MiniAppKind = 'document' | 'panel' | 'external';

interface MiniAppBase {
  key: MiniAppKey;
  label: string;
  listLabel?: string;
  enabled: boolean;
  /**
   * 権限区画。省略時はハブ自身の区画（'qsheet'）と同じとみなす。
   * qsheetとは別区画のミニアプリ（計時・視聴者）だけ明示する。
   */
  permissionModule?: string;
}

export interface MiniAppExternalDef extends MiniAppBase {
  kind: 'external';
  /** true 固定。「同一バンドル内の遷移ではない」ことを型で保証し、<Link> の誤用を防ぐ */
  crossBundle: true;
  /** 遷移先 URL のひな形。:ownerId を置換する。別バンドルの絶対パスであること */
  path: string;
  /** このミニアプリが受け付けられる owner の種類。今回は 'project' のみ（§3-5） */
  supportedOwnerKinds: readonly ('project')[];
}

export type MiniAppDef = MiniAppDocumentDef | MiniAppPanelDef | MiniAppExternalDef;
```

登録エントリ:

```ts
{
  kind: 'external',
  key: 'liveops',
  label: '計時・視聴者',
  crossBundle: true,
  path: '/live/open?project=:ownerId',
  supportedOwnerKinds: ['project'],
  permissionModule: 'liveops',
  enabled: false, // PR-A では false のまま登録、PR-B で true に反転（§5）
}
```

- `MiniAppKey` に `'liveops'` を追加する。`apps.ts` の `AppKey` にも同名の `'liveops'` があるが
  **型としては別物**（別ファイル・別 union）。あえて同じ文字列を選ぶのは、
  「このミニアプリはトップレベルアプリ `liveops` と1:1対応する」ことをコード上も読み取れるようにするため
- ⚠️ **`server/src/shared/production/miniapps.ts`（`check-collab-parity.mjs` が検査する複製）にも
  同じ変更を同じ形で入れること**

### 2-2. `permissionModule` を足す理由（完全統合案の知見をフェーズ1へ前倒し）

既存5件のミニアプリ（進行台本・スケジュール表・収録設定・配信設定・レンタル機材検索）はすべて
`qsheet` 権限の配下（ハブ自体が `requirePermission('qsheet')`）だが、計時・視聴者だけ
**別区画 `liveops`**（migration 210 で確認済み・別区画）。**放置すると「`qsheet` の権限だけを
持つ人にタイルが見え、押すと403になる」という新しい穴ができる**（完全統合案 §3-2 が指摘）。

- `MiniAppTiles` / `MiniAppSwitcher` は、**タイルを描く前に `permissionModule` を見て、
  その区画の権限が無ければタイル自体を出さない**
- サーバー側の owner 解決エンドポイント（§3-4）も `requirePermission('liveops')` で守る
  （**qsheet の権限では通さない**。タイル非表示と対になる最終防御）
- 「見えるのに押せない」という体験を作らないための**二重防御**。これはフェーズ1・フェーズ2
  どちらでも変わらない設計原則とする

### 2-3. 既存ヘルパーへの影響

| ヘルパー | `kind: 'external'` を足すと |
| --- | --- |
| `docPathOf` | 変更不要（`external` は元から弾かれる） |
| `panelPathOf` | 変更不要 |
| `miniAppOfPath` | ⚠️ **`kind === 'external'` は候補から除外すること。** `/live/*` という pathname が qsheet 側ルーターに渡ってくることは構造上ない（別バンドルなので qsheet の JS がそもそも動いていない） |
| `enabledMiniApps` | 呼び出し側は `kind === 'panel'` を除外しているのと同じ書き方で `kind === 'external'` も除外する（新規作成の概念が無いため） |
| 新設: `externalPathOf(key, ownerId)` | `panelPathOf` と同じ形（`:ownerId` を置換するだけの純関数）。**I/O は持たせない**（「取得または作成」は遷移先ページ側でやる。§3-4） |

### 2-4. `<Link>` 誤用を防ぐ部品

```ts
function ExternalMiniAppLink(props: {
  def: MiniAppExternalDef;
  ownerId: string;
  children: React.ReactNode;
}) {
  // <a href={...}> だけを返す。<Link> を書く余地を無くす。
  // permissionModule のチェックに落ちたら null を返す（タイル自体を描かない・§2-2）。
}
```

`<Link>` と `<a>` はどちらも見た目が同じリンクに見えるため、レビューだけでは
`kind: 'external'` に `<Link to>` を使う誤りに気づきにくい。**型で塞ぐ。**

## 3. フェーズ1: 軽量統合（バンドル分離のまま・今すぐ実行）

### 3-1. スコープ

```
案件 60周年 記念式典（GLS-A012）
├── スケジュール表
├── Qシート（進行台本）
├── 収録設定 ／ 配信設定
└── 計時・視聴者          ◀ ここ（scope==='project' のハブにだけ・liveops権限保持者にだけ出る）
```

- `JourneyPage` の `MiniAppTiles` に、**`scope === 'project'` かつ `liveops` 権限があるときだけ**
  タイルを追加する
- ヘッダーの `MiniAppSwitcher`（`RecordingPage`/`StreamingPage` の2画面のみ）に計時・視聴者を追加する。
  **進行台本・スケジュール表の画面へは広げない**（今回のスコープ外）
- 遷移は**ブラウザの本物のページ遷移**（`<a>` 経由）。React ツリーは破棄され再構築される
  （§3-6 で「白い一瞬」を扱う）

### 3-2. バンドルは分離したまま

`client-live`（`base: '/live/'`）と `client-qsheet`（`base: '/qsheet/'`）は**別の Vite バンドル**。
この文書のフェーズ1では**この事実を前提として受け入れ**、別バンドルのまま軽く繋ぐ。
バンドルを1つにする作業はフェーズ2（§4）に送る。

### 3-3. 二重防御（§2-2 の実地適用）

| 層 | 何をするか |
| --- | --- |
| クライアント（タイル・スイッチャー） | `permissionModule: 'liveops'` を見て、権限が無ければ描画しない |
| サーバー（owner 解決エンドポイント） | `requirePermission('liveops')`。**`qsheet` の権限では通さない** |

### 3-4. Owner 解決（DBスキーマ変更なし）

09 の完全統合設計（旧 §4）は `main_timer_id` 列・案件との一意インデックスを新設する前提だったが、
**その一意インデックスは PR1〜4 で既に実装済み**:

```sql
-- migration 221（実装済み・この文書では触らない）
CREATE UNIQUE INDEX liveops_programs_project_key
  ON liveops_programs (project_id)
  WHERE project_id IS NOT NULL AND deleted_at IS NULL;
```

「1案件につき `liveops_programs` は最大1件」という制約は**既にDBが担保している**。
フェーズ1に必要なのは、この制約に乗っかって「取得または作成」をアトミックに行う経路だけ。
**新しい列も新しいテーブルも要らない。**

```
POST /api/v1/liveops/programs/resolve-by-project/:projectId
requirePermission('liveops')
```

- `SELECT ... WHERE project_id = $1` → 無ければ
  `INSERT ... ON CONFLICT (project_id) WHERE project_id IS NOT NULL AND deleted_at IS NULL
  DO NOTHING RETURNING id` → それでも取れなければ（同時実行で誰かが先に作った）もう一度 `SELECT`
- 既存の一意インデックスがあるので、**2人が同時に押しても行は2件できない**

**呼び出し元は `client-live` 側に置く橋渡しページ**（qsheet 側で事前fetchする案より、
静的URLで prefetch/prerender と相性が良い）:

```
/live/open?project=:projectId  （OpenByProjectPage.tsx・新設）
  → マウント後に resolve-by-project を呼ぶ
  → programId が確定したら /live/program/:id へクライアント側リダイレクト
```

⚠️ **Speculation Rules（`prerender`）を使う場合の落とし穴**: `prerender` は対象ページを
実際に読み込んで JS を実行する。`/live/open` が**マウントと同時に**「取得または作成」の POST を
叩く実装だと、**ホバーしただけで `liveops_programs` の行が作られてしまう**。
`document.prerendering`（Page Lifecycle API）を見て、プリレンダー中は API 呼び出しを保留し、
`prerenderingchange` イベントで実際に activate されてから初めて呼ぶこと。対応しないなら
`prerender` は使わず `prefetch`（副作用の無い静的アセットの前倒し取得だけ）に留める。

### 3-5. `scope === 'program'` は解決しない（受容する制約）

`liveops_programs.project_id` は `projects` テーブルだけを指す。qsheet 自身の「番組（マニュアル）」
= `qsheet_programs`（migration 227）は**別テーブル・別ID型（TEXT と UUID）で、外部キー関係が無い**
（事前調査④で確認済み）。DBスキーマを変えないというフェーズ1の前提では、この経路は作れない。

- `MiniAppExternalDef.supportedOwnerKinds = ['project']` なので、
  `scope === 'program'` のハブには計時・視聴者のタイル自体を出さない
- **完全統合案にもこの解決策は無かった**（09完全刷新案 §5-2 も `project` のみ対応としている）。
  この非対称は**フェーズ1固有の妥協ではなく、現状すべての案に共通する未解決の空白**として正直に扱う
- 抜け道として、`client-live` の `/live/`（セッション一覧）からの「スタンドアロン作成」が
  引き続き残っている旨を案内する

### 3-6. 「白い一瞬」の扱い（正直に書く）

同一オリジン（`/live/` も `/qsheet/` も同じホスト・同じサーバー）なので、DNS/TLS の追加コストは無く、
Cookie/JWT もそのまま使えるため再ログインは挟まらない。**しかし HTML/JS の取得と初回描画の間の
空白は完全には消せない。**

| 手段 | 効果 | 限界 |
| --- | --- | --- |
| 同一オリジン | 接続コストがそもそも発生しない | 取得自体は必要 |
| `prefetch` | ホバー時に事前取得しておける | 空白そのものは消えない |
| Speculation Rules（`prerender`） | Chromium系では体感を SPA 内遷移に近づけられる | **Safari・Firefoxは非対応**。副作用対策（§3-4）が必須 |

⚠️ **Safari/Firefox では 1〜2 秒の空白が残ることを、利用者に事前に伝える。** これは
バンドルを1つにしない限り解決しない構造的な制約であり、**フェーズ2に進むかどうかを判断する
材料そのもの**になる（§4-1）。

## 4. フェーズ2: バンドル統合（着手条件を満たすまで実施しない）

### 4-1. 着手条件（この文書で新しく定義する）

⚠️ **旧 impl §12-11 が挙げていた見送り理由の1つ（「制作技術支援自身が共通シェル未移行」）は、
もう解消済みである。** ただし、**これは着手してよい必要条件が1つ揃っただけで、十分条件ではない。**
以下の3条件を**すべて**満たしたときに、着手可否をユーザーへ諮る。

| # | 条件 | 判定方法 |
| --- | --- | --- |
| ① | **フェーズ1が本番公開されている** | GitHub Release で該当バージョンが公開され、本番デプロイが成功していること |
| ② | **フェーズ1公開後、最低1回の通常リリースを挟む観測期間を経て、下記の指標が実際に計測されていること** | 下表 |
| ③ | **②の観測結果を材料に、フェーズ2着手をユーザーが明示的に指示すること** | AIの判断だけでは着手しない（本番デプロイの原則「ユーザーの明示的指示なしに本番に触れない」と同じ考え方をフェーズ2着手判断にも適用する） |

**②で計測する指標（具体的に）:**

| 指標 | 何のために計測するか |
| --- | --- |
| 「白い一瞬」に関する問い合わせ・不満の件数 | §3-6 の体感の悪さが実際にどれだけ問題になっているかの直接指標 |
| ブラウザ内訳（Safari/Firefox の実際の利用比率） | Speculation Rules が効かない層がどれだけいるかを確認する |
| 旧URL（`/live/program/:id` 等）へのアクセス数の推移 | ミニアプリ経由への移行がどれだけ定着しているか |

これらが揃わないまま「時間が経ったから」で着手しないこと。**指標が芳しくなければ、
フェーズ2に進まずフェーズ1のまま運用を続けるという判断もありうる**（フェーズ1で完結させてよい）。

### 4-3. 修正点 b: 「一発切替」PRを2本に分割する
