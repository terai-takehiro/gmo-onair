# プロジェクト管理（GPM）— データの持ち方の決め（Phase 5）

> ⚠️ **決め①（`projects` に相乗りさせない）は [`gpm-merge.md`](gpm-merge.md) で差し替えました。**
> 決め①は「**GPM のプロジェクトは案件ではない**」を前提にしていますが、
> 業務側の定義は **案件管理 = GLS-A ／ プロジェクト管理 = GLS-B** で、
> **GPM のプロジェクトは GLS-B 案件そのもの**でした。前提が消えたので、
> `gpm_projects` は `projects` に畳みます。**決め②〜⑤はそのまま生きています。**
>
> `docs/v4-plan.md` の Phase 5 は「最初の作業は**この4点の設計を1本のドキュメントに落とすこと**
> （コードを書く前に）」と決めています。これがその文書です。
> **実測した数字を根拠に書いてあります。** 推測で決めた箇所はありません。

## そもそも何が違うのか

案件管理（`projects`）は **GLS 番号を採って、売って、請求する**ための入れ物です。
プロジェクト管理（GPM）は **「用賀スタジオ 第2副調整室 構築」のような構築案件を、
工程表で管理する**ためのものです。モックは自社構築とグループ受託の2種類を持ちます。

似ていますが、**数え方が違います**。案件は売上・粗利で数え、プロジェクトは工程の進みと
未確認事項で数えます。

---

## 決め① プロジェクトは `projects` に相乗りさせない → `gpm_projects` を新設

### 根拠（実測）

```
server/src で `FROM projects` を書いている箇所            94
そのうち stage / gls_category / gls_number で絞っていない  75  (80%)
MCP・集計・ダッシュボード・決算取込・週報から来ているもの  38
```

**75 か所が「projects にある行はすべて案件だ」という前提で書かれています。**
ここに構築プロジェクトを混ぜると、案件一覧・財務の集計・決算取込・検索・
MCP の `list_projects`・週報が**全部それを拾います**。
`gls_category` に 'C' を足すような案では、75 か所すべてに除外条件を足すことになり、
1 か所忘れると**エラーにならずに数字が狂います**。

これは migration 138 で「見積を `revenues` に相乗りさせない」と決めたときと同じ形です
（あのときは `revenues` を読む 53 か所のうち 41 か所が `status` を見ていませんでした）。
**同じ判断をします。**

### 決めたこと

`gpm_projects` を新設し、既存 `projects` への**任意のリンク**（`project_id`）を持たせます。
グループ受託で GLS を採るケースは、案件を作ってからそこに紐づけます。
自社構築は `project_id` が NULL のままです。

## 決め② 工程（フェーズ）は `gpm_phases`。配下のタスクは既存 `project_tasks` を使う

### 根拠

`project_tasks`（migration 137 ほか）は親子・開始/終了日・`progress`・`is_milestone`・
`work_state`（未着手 / 進行中 / 相手待ち）を持ち、`task_dependencies` でガントの依存線も引けます。
**タスクとして足りないものはありません。**

一方 migration 137 の冒頭に「6つの書き手がそれぞれ直接 SQL で読み書きしている」と
明記されています（案件管理のタスク一覧・カンバン・ガント・MCP `list_tasks`・依頼フロー・週報）。
**フェーズ行を `project_tasks` に混ぜると、その6つ全部にフェーズが出ます。**

### 決めたこと

- **フェーズは `gpm_phases`**（別テーブル）
- **フェーズ配下のタスクは `project_tasks` に `gpm_phase_id` を1列足して紐づける**
  — タスクの実装・MCP・依頼フローを二重に持たない
- **進捗 % は列に持たない。** フェーズ配下タスクの完了率から**導出**します。
  列に持つと「同じ数字を2か所で数えない」に反し、必ず食い違います

## 決め③ 標準工程テンプレートは新設（既存 `task_column_templates` は使わない）

`task_column_templates`（migration 087/088）は**かんばんの列の定義**で、
日数・担当ロール・タスクの雛形を持ちません。モックのテンプレート（`GP_TPLS`）は
フェーズごとに `days` / `role` を持ち、その下にタスクの雛形（`days` / `role` / `must`）を持ちます。
**別物なので新しく作ります。**

- `gpm_templates` … テンプレート本体
- `gpm_template_phases` … フェーズの雛形（label / days / role / 並び）
- `gpm_template_tasks` … タスクの雛形（label / days / role / 必須か / 並び）

**展開は「写す」。** 展開後にテンプレートを直しても、動いているプロジェクトには影響しません
（モックも同じ注記を持っています）。直したら影響が波及するほうが事故になります。

## 決め④ 未確認事項は `gpm_open_items`。議事録の持ち帰りとは**結ぶ**

`project_minutes`（migration 141）は既に `open_items` を JSONB で持っています。
ただしそれは**その議事録の中の持ち帰り**で、プロジェクトをまたいで
「いま何件止まっているか」を引けません（モックのダッシュボードはそれを数えます）。

- `gpm_open_items` を新設（誰に・いつから・何が止まっているか・期限）
- 議事録から送ったときは `source_minutes_id` で結ぶ。
  **同じものを2か所に書かない** — 議事録側の JSONB は議事録の記録のまま残します

## 権限モジュール

`shared/src/client/apps.ts` は既に `permissionModule: 'gpm'` と宣言していますが、
**権限を付けられる一覧（`UserListPage.tsx` の `PERM_MODULES` と
`auth.routes.ts` の `MODULES`）に入っていません**。つまりいまは誰にも付与できず、
`system_admin` だけが通ります。

**ルートを守るより先に、この2か所に `gpm` を足します。**
逆順でやると `system_admin` 以外の全員が 403 になり、画面から権限を付けることもできません。

## 決め⑤ ⑥ 見積・請求は**この回では作らない**（画面を作ってから決めたこと）

画面6枚（① ダッシュボード ／ ② 一覧 ／ ③ 詳細 ／ ④ 新規作成 ／
⑤ やること ／ ⑦ 標準工程テンプレート）を作った時点で、
**⑥ 見積・請求だけは作らずに止めました。** 理由を残します。

### 根拠（実測）

```
estimates.project_id                NOT NULL REFERENCES projects(id)   （migration 138）
estimates に「提出先」に相当する列   0
server/src で estimates を読み書きしている箇所                        12
estimates を読んでいる画面                                             4
  client/src/contexts/sales/pages/projectDetail/EstimateTab.tsx
  client/src/contexts/sales/pages/BillingListPage.tsx
  client/src/contexts/sales/pages/ProjectFormPage.tsx
  client/src/contexts/platform/pages/salesDashboard/KpiStrip.tsx
```

### 何が足りないか（2つある）

1. **GPM のプロジェクトは `estimates` の行を持てません。**
   `estimates.project_id` は `NOT NULL` で `projects(id)` を指します。
   `gpm_projects` は `projects` への**任意のリンク**しか持たない（決め①）ので、
   自社構築（`project_id IS NULL`）には見積を1枚も作れません。
   作れるようにするには `project_id` を NULL 許容にするか
   `gpm_project_id` を足すことになり、**どちらも既存の見積の作りを変えます**。

2. **モックの「提出先」（自社 / 依頼元 / PM会社）を入れる列がありません。**
   `GP_EST` は `to` / `toName` を持ちますが、`estimates` にも `revenues` にも
   相当する列はありません（grep で 0 件）。案件の見積は
   **お客様に出すもの1種類**しかないので、そもそも概念が違います。

### 足すと何に影響するか

`estimates` は**サーバー 12 か所・画面 4 か所**から読まれています。列を足すと、

- **案件詳細の見積タブ**（`EstimateTab.tsx`）… 版の作成・送付・受注変換
- **見積・請求の一覧**（`BillingListPage.tsx`）… 返事待ちの件数と合計金額
- **案件管理ダッシュボードの KPI**（`salesDashboard/KpiStrip.tsx`）…「見積の返事待ち」

が同時に「提出先とは何か」を持つことになります。案件側には提出先という
概念が無いので、**既存の見積すべてに既定値を入れる決め**も要ります。
これは画面の作り直しではなく**見積のデータ設計の変更**です。

### だからこうした

- **⑥ の画面は作らない。** ルートもメニュー項目も置かない
  （押しても何も起きない項目を出さない）
- **数字も出さない。** ① ダッシュボードのモックにある KPI
  「個別見積 未提出」「検収待ち」は**枠ごと出さず**、
  出していない理由を画面に書いた（`pages/dashboard/KpiStrip.tsx` の `NotCounted`）。
  ② 一覧にも金額の列を置かず、同じ理由を1行で書いた
- **`apps.ts` の `comingSoon` は外さない。** 7画面が揃ってから開ける決めなので、
  6画面では導線を開けない

### 次にやるなら（設計から始める）

1. 見積を**どちらに持たせるか**を決める
   （`estimates` を GPM でも使えるようにする ／ `gpm_estimates` を別に作る）。
   決め①・決め④と同じ判断軸 = **既存の読み手が何か所あり、
   そのうち何か所が絞り込んでいないか**を先に数える
2. 「提出先」を列にするか、`gpm_members`（社外を含む体制）への参照にするか
3. 既存 `estimates` に入れる既定値と、案件側の画面での見せ方
