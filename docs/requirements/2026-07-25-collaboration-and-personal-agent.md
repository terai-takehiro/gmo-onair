# GMO ONAiR 改革要件 — 共同作業 / 個人秘書 / タスクと依頼の可視化

作成 2026-07-25 ／ 起点バージョン v2.9.239 ／ ステータス **要件定義（実装未着手）**

ユーザー提示の 4 テーマを、現在の実装を読んだ上で要件に落としたもの。
実装はまだしない。**この文書で合意 → フェーズごとに着手**の順で進める。

## 0. 結論（先に）

| テーマ | 一言 | 効き方 | 難易度 |
|---|---|---|---|
| **A. AI 文言の簡潔化** | 文言だけ。DB もロジックも触らない | 小さいが即日効く | 低 |
| **B. GLS-B の共同作業化** | Qシートの同時編集エンジンをそのまま転用できる | 中 | 中 |
| **C. 個人秘書エージェント** | データは既に揃っている。足りないのは「個人軸の集約」と「通知」 | 中 | 中 |
| **D. 個人タスクと依頼の可視化** | **今回一番効く。かつ今一番できていない** | 大 | 中〜高 |

**D が最優先。** 理由は感覚論ではなく構造的なもので、
`project_tasks.project_id` が **NOT NULL** のため、
**案件に紐づかない個人タスクと、人から人への依頼が、そもそも DB に存在できない**。
「口頭で伝えて、期限も分からず、忘れられる」の原因はここ。器がないので記録しようがない。

**着手順の推奨は A → D → B → C。**
C（秘書）を先にやっても、見せるネタ（= D のタスクと依頼）がまだ無いので薄くなる。

**AI 側の下地は既にできている。** v2.9.238/239 で `ai_outputs` / `ai_corrections` /
`ai_outcomes` と `get_ai_feedback_digest` が入ったので、今回作る AI 機能は
**新テーブルを足さずに相乗りするだけ**で必須 5 条件の 1〜4 を満たせる。
残る穴は条件 5（レビューを誰がいつやるか）だけ。→ 第 5 章。

## 2. テーマ A — AI 表示テキストの簡潔化

### 課題

現状の文言は「実装の内部事情」がそのまま画面に出ている。実例：

| 場所 | 現在の文言 | 何がダメか |
|---|---|---|
| 案件編集・AI 起票バナー | この案件は AI（問い合わせメール取込等）により起票されました。指示: 寺井 | 「等」が曖昧。何をすればいいかが書いてない |
| 見積下書きバナー | 作成: 3時間前 ／ 指示: 寺井 ／ 実行: 共用キー | **「実行: 共用キー」は内部の認証方式**。読む人に関係ない |
| 見積下書きバナー | 確定するまで想定金額には反映されません。 | 二重否定に近く、読み替えが必要 |
| ホーム・AI 活動フィード | AI (MCP 経由) がこの1週間に実行した書き込みの履歴です。 | **「MCP」は社内用語ですらない。技術用語** |
| 受信箱 | AI起票 3 件をまとめて確認済みにしますか？\n(内容を確認してから実行してください) | 括弧の注意書きが説明的すぎる |

### 方針（この 5 ルールを全 AI 文言に適用する）

1. **1 文 = 1 情報。** 2 つ言いたいときは 2 文に割る
2. **技術用語を画面に出さない。** MCP / 監査ログ / actor / 共用キー / payload → 使用禁止
3. **「何が起きたか」より「あなたが次に何をするか」を先に書く**
4. **内部の詳細はツールチップか折りたたみに移す。** 消すのではなく主線から外す
5. **中学 3 年生が読んで詰まらない語彙。** 熟語を並べず、動詞で書く

### 書き換え例

| 現在 | 変更後 |
|---|---|
| この案件は AI（問い合わせメール取込等）により起票されました。指示: 寺井 | AI がメールから作った案件です。内容が合っているか見てください。 |
| 作成: 3時間前 ／ 指示: 寺井 ／ 実行: 共用キー | 3時間前に AI が作成（寺井さんの指示） |
| 確定するまで想定金額には反映されません。 | 「確定する」を押すと想定金額に入ります。 |
| AI (MCP 経由) がこの1週間に実行した書き込みの履歴です。 | AI がこの 1 週間にやったことです。 |
| AI起票 3 件をまとめて確認済みにしますか？(内容を確認してから実行してください) | 3 件を確認済みにします。内容は見ましたか？ |

### 対象ファイル

`ProjectFormPage.tsx` / `HomePage.tsx`（AI 活動フィード・AI 起票インボックス・営業ボード）/
`InboxPage.tsx` / `AiActivityPage.tsx` / `lib/aiFeed.ts`（ツール名 → 日本語ラベル 17 種）/
`ActivityLogPage.tsx` / `CustomerDetailPage.tsx` / `ProjectListPage.tsx` /
タスク 3 コンポーネントの AI バッジ / `manual/content.tsx`

### 完了条件

- 上記ファイルの AI 関連文言すべてが 5 ルールを満たす
- 「MCP」「監査ログ」「actor」「共用キー」が画面テキストから 0 件になる（grep で確認）
- 内部詳細はツールチップに移して、消さない（調査時に必要なため）
- **DB とロジックは変更しない**

## 3. テーマ B — GLS-B 案件の共同作業プラットフォーム化

### ゴール

GLS-B（ビジネス案件）を「1 人が入力する台帳」から
「複数人が同時に触れて、AI が横で手伝う作業場」にする。

### 要件

**B1. 案件の同時編集**
- 案件編集ページを Qシートと同じ Yjs 方式にする
- **新規開発ではなく転用**：`shared/src/collab/yjsDoc.ts` の変換層と
  `collab.ts` の部屋管理をそのまま使い、対象を `qsheet_documents` から `projects` に広げる
- 後勝ち上書き（今は 2 人が開くと片方の保存が黙って消える）を解消する
- 段階を切る：まず**タスク・メモ・チェックリスト**から。金額欄は監査の都合があるので後回し

**B2. プレゼンス（誰がいるか）**
- 案件を開いている人のアバターをヘッダーに出す（Qシートに実装済みのものを流用）
- 誰がどの欄を編集中かを枠で示す

**B3. コメントとメンション**
- 案件・タスク単位にコメントを付けられる
- `@名前` でメンション → **その人のタスク一覧に「未読の指名」として出る**（テーマ D と直結）
- 新テーブル 1 つ（`project_comments`）

**B4. 変更履歴**
- 誰が・いつ・何を変えたかを案件単位で見られる
- Yjs を入れると更新が細かく流れるので、**5 分単位にまとめて 1 行**にする

**B5. AI エージェント（案件に貼り付く）**
| エージェント | やること | 起動 |
|---|---|---|
| 進行チェック | 期限超過・次アクション未設定・担当未割当を洗い出す | 日次 |
| 議事録 → タスク | 議事録を読んでタスク案を作る（→ テーマ D5） | 都度 |
| 見積下書き | 既存 `set_project_simulation` を継続 | 都度 |
| ふりかえり | 終了案件の粗利と工程遅延から次回の改善案を出す | 案件終了時 |

すべて**下書きで出して人が確定する**方式にする。勝手に確定させない。

### 使える既存資産

Yjs 基盤（qsheet）／ `project_members` ／ `task_dependencies` ／ ガント編集 ／
`meeting_minutes`（migration 129）／ `ai_outputs`（下書きの記録先）

## 4. テーマ C — 個人秘書エージェント

### ゴール

トップページを「会社全体の数字」から
**「今日のあなた」**に変える。目指すのは超優秀な秘書チーム。

### 現状の問題

ホームは 8 セクションあるが、ほぼ全部が**全社共有の情報**（受信箱・スケジュール・
今月の指標・営業ボード・AI 活動・直近案件）。**「自分だけの並び」がない。**

### 要件

**C1. 個人ホーム**
- 最上部を「あなたの今日」に置き換える
  1. 今日の予定（会議・現場・移動）← `personal_events` + `studio_bookings` + Google/Outlook 同期
  2. 今日やること（期限が今日・超過分）← テーマ D
  3. あなたへの依頼（未承諾・未読メンション）← テーマ D
  4. 待たせているお客様 ← 既存の受信箱 API を個人で絞る
- 全社の数字は下に置く（消さない）

**C2. 朝のブリーフ**
- 出社時に 1 画面で「今日の勝ち筋」を出す
- 中身：予定 / 今日の 3 件 / 期限が危ないもの / 今日決めるべきこと
- **既存の `ops_reports` を流用する**（`kind` に CHECK 制約がないので `kind='personal_daily'`
  を足すだけ。migration 不要）

**C3. 秘書エージェント群**
| 名前 | 役割 |
|---|---|
| 予定係 | 予定の衝突・移動時間不足・準備漏れを指摘 |
| 催促係 | 自分が出した依頼の期限前に「先方に催促しますか」を出す |
| 段取り係 | 今日やることを重要度・緊急度で並べ替えて 3 件に絞る |
| 記録係 | 会議のあと「決まったこと・宿題」を下書きにする |
| ふりかえり係 | 週末に「今週やったこと・来週の勝負」をまとめる |

これらは**個別の実装ではなく、同じ MCP ツール群 + スキルの組み合わせ**として作る。
エージェントごとにコードを増やすと接点が増えて収束しないため。

**C4. 通知**
- 現状アプリに通知経路がない（テーブルも Slack 配線もサーバーに存在しない）
- 方針：**まず既存方針を踏襲**（Claude が MCP で読んで Slack に投げる）＝追加実装ゼロ
- そのうえで薄い**アプリ内通知**（ベル + 未読カウント）を足す。メール通知は当面やらない

### プライバシー（重要）

個人予定はセンシティブ。**既存の設計を崩さない**：
`personal_events` は本人のみ（system_admin でも他人の分は見えない）、
共有は `personal_event_shares` で明示的に。秘書エージェントも**本人の分しか読まない**。

## 5. テーマ D — 個人タスクと依頼の可視化（最重要）

### 課題

チームの実態：
- 個人が抱えているタスクが、チームから見えない
- 口頭で頼んだ依頼が、どこにも残らない
- 期限が曖昧なまま、忘れられる

原因は運用ではなく**データモデル**。

| 表現したいこと | 今できるか |
|---|---|
| 案件に紐づかない個人タスク | **✕**（`project_id` が NOT NULL） |
| 「A さんが B さんに頼んだ」 | **✕**（依頼者カラムがない） |
| 重要度 × 緊急度 | **✕**（カラムがない） |
| 「7/25 18:00 まで」 | **✕**（`due_date` は日付のみ） |
| 自分のタスクだけ見る | **✕**（画面がない） |
| 依頼を受けた／断った | **✕**（状態がない） |

### D1. データモデル（方針の提案）

**`project_tasks` を拡張し、`project_id` を NULL 可にする**。新テーブルを作らない。

理由：
- 既存のかんばん / リスト / ガント / 依存 / MCP 7 ツールが**そのまま使える**
- 「個人タスクを案件に昇格」「案件タスクを個人に切り出す」が同じテーブルの更新で済む
- 別テーブルにすると一覧・MCP・権限が 2 系統になり、統合ビューが常に UNION になる

追加するカラム：

| カラム | 型 | 意味 |
|---|---|---|
| `project_id` | **NULL 可に変更** | NULL = 個人タスク |
| `requester_id` | users FK | **依頼した人**（NULL = 自分で作った） |
| `requested_at` | timestamp | 依頼日時 |
| `due_at` | timestamp | **時刻まで入る期限**（既存 `due_date` は残して併存） |
| `importance` | text | high / low |
| `urgency` | text | high / low |
| `delegation_status` | text | requested / accepted / declined / done |
| `accepted_at` | timestamp | 承諾日時 |
| `source` | text | verbal / meeting / mail / slack / ai / self |
| `source_ref` | text | 議事録の日付・メールの message_id など |
| `visibility` | text | team（既定）/ private |

**権限**：`project_id` が NULL のタスクは案件権限で判定できないので、
**本人 + 依頼者 + （明示共有先）のみ**が見える。`visibility='private'` は本人のみ。

### D2. 重要度・緊急度マトリクス

GMO ToDo リストの考え方を踏襲し、4 象限で並べる。

| | 緊急 高 | 緊急 低 |
|---|---|---|
| **重要 高** | ① すぐやる | ② 計画してやる |
| **重要 低** | ③ 任せる・すぐ片づける | ④ やらない |

- 一覧のデフォルト並び順を **① → ② → ③ → ④**、同象限内は期限の近い順にする
- ② が空っぽの人は「目の前の火消しだけしている」ので、そこを画面で示す
- 4 象限ビュー（2×2 のボード）を用意する

**未決**：GMO ToDo リストの実際の粒度が 2 段階（高／低）か 3 段階かを確認する（→ 第 8 章）。

### D3. 依頼（人 → 人）

- 「依頼する」ボタン：相手・内容・**期限（日時）**・重要度・緊急度 を入れて送る
- 受け手側に「あなたへの依頼」として出る → **承諾 / 相談 / 辞退**を選ぶ
- 依頼した側は「出した依頼」の一覧で進捗を見られる
- **期限を空にできない。** 「何日何時何分まで」を必須にする（GMO イズムの期限の考え方）
- 相手が承諾しないまま期限が近づいたら、依頼者に催促を出す

### D4. 議事録・チャット → タスク自動起票（AI）

- 入力：既存 `meeting_minutes`（決定事項 + 論点を持っている）、または貼り付けたテキスト
- 出力：**タスク案の下書き**（内容・担当・期限・重要度・緊急度・根拠の引用）
- 人が「採用 / 直す / 捨てる」を選んでから登録される。**勝手に本登録しない**
- 新 MCP ツール（案）
  | ツール | 役割 |
  |---|---|
  | `draft_tasks_from_text` | 議事録やチャットからタスク案を作る（下書き） |
  | `create_delegation` | 依頼を作る（相手・期限・重要度・緊急度） |
  | `list_my_tasks` | 自分のタスクを 4 象限で返す |
  | `list_my_delegations` | 自分が出した / 受けた依頼 |
  | `accept_delegation` | 承諾・辞退 |
  | `get_personal_brief` | 朝のブリーフ用（予定 + 今日の 3 件 + 危ないもの） |

### D5. GMO ToDo リストとの連携

**未確認事項が多いので、段階を分ける。**

| 段階 | 内容 | 前提 |
|---|---|---|
| 1 | ONAiR 内で完結（連携なし） | なし |
| 2 | ONAiR → GMO ToDo に**書き出し**（片方向） | ToDo 側の書き込み API |
| 3 | 双方向同期（`external_task_id` で突合・冪等） | 同上 + 競合の解決規則 |

段階 1 だけでも「口頭依頼が消える」問題は解ける。連携は後追いでも損失ゼロ。

**GMO ToDo リスト MCP は現在このセッションに接続されていない**ため、
ツール名・データ構造・書き込み可否は未確認。→ 第 8 章。

### D6. 画面

| 画面 | 内容 |
|---|---|
| マイタスク | 4 象限ボード + リスト。案件タスクと個人タスクを**混ぜて**表示 |
| 依頼 | 「受けた依頼」「出した依頼」の 2 タブ。未承諾・期限超過を上に |
| チームタスク | メンバー別の負荷（件数・期限超過数）。private は件数だけ出して中身は隠す |
| ホーム | 上記のサマリー（→ テーマ C1） |

## 6. AI 必須 5 条件の充足表

CLAUDE.md の絶対原則にもとづく確認。対象は今回作る AI 機能
（B5 案件エージェント / C3 秘書エージェント / D4 議事録 → タスク）。

| # | 条件 | 判定 | 根拠と、足りない分の埋め方 |
|---|---|---|---|
| 1 | AI の出力を記録・保存 | **○** | `ai_outputs.payload_snapshot` に切り詰めなしの全文。タスク案・ブリーフ・依頼案は `kind` を分けて同じテーブルに入れる。**新テーブル不要** |
| 2 | 人間の修正を差分で残す | **△** | 仕組みは `ai_corrections` + `diffByKey` で完成済み。**タスク案の登録経路に差し込む実装が必要**。タスクは配列なので index ではなく**タスクの業務キー（内容 + 担当）で突合**する（index だと 1 件挿入で以降全部が「変更」になる）。捨てられた案は `reject`、そのまま採用は **`none`（正解ラベル。これが無いと無修正採用率の分母が壊れる）** |
| 3 | 成果指標を紐づける | **△** | タスクは**成果が既存データから引ける**（期限内完了率・完了までの日数・放置日数）。`ai_outputs.target_id = project_tasks.id` で読み取り時に導出する。**バッチを作らない**（v2.9.239 と同じ方針）。秘書ブリーフの「役に立ったか」は proxy を使う → 下記 |
| 4 | AI 改善に戻す経路 | **○** | `get_ai_feedback_digest` に `kind` を足すだけ。「タスク案を作る前に必ずダイジェストを読む」をツール説明に契約として書く |
| 5 | レビュー頻度と担当 | **✕** | **今回で決める必要がある。** → 下記 |

### 条件 3 の埋め方（経路が作りにくいもの）

| 測りたいこと | 直接は取れない | 代わりに使う |
|---|---|---|
| タスク案の質 | — | **無修正採用率**（`none` ÷ レビュー済み）。既存の集計がそのまま使える |
| ブリーフが役に立ったか | 満足度を聞く運用は続かない | **開いた / 開かなかった**、および**ブリーフに出したタスクがその日に完了したか** |
| 依頼の粒度が適切か | — | **辞退率**と**期限延長回数** |
| 議事録抽出の漏れ | 漏れは記録に残らない | 人が**後から手で追加したタスク**を「AI が拾えなかった候補」として数える |

### 条件 5 の提案（これで合意したい）

| 何を | 誰が | 頻度 | どう反映するか |
|---|---|---|---|
| タスク案の修正傾向 | 案件の主担当 | 週 1 | `ops_reports` に `kind='ai_review'` で記録（**CHECK 制約がないので migration 不要**） |
| 全体の無修正採用率 | 寺井 | 隔週（既存キープ会議に相乗り） | 下がっていればプロンプト / スキルを直す |
| ナレッジ昇格 | 寺井 | 月 1 | 承認したものだけ AI が読むナレッジに入れる |

### リスク（必ず踏むもの）

**正常な業務更新を「AI の誤り」として数えてしまう。**
タスクの期限が 1 ヶ月後に延びたのは、AI が間違えたのではなく状況が変わっただけ。
対策：**AI 出力からの時間窓（7 日以内）で修正候補を絞る** + 種別は人が上書きできるようにする。
ここを甘くすると修正率が無意味な数字になり、改善したかどうか判断できなくなる。

もう 1 つ。**同時編集（B1）を入れると `ai_corrections` が壊れやすい。**
Yjs は文字単位で更新が流れるので、1 文字直すごとに「修正」が積まれる。
対策：差分は**保存確定時のスナップショット比較**で取り、Yjs の更新ストリームからは取らない。
