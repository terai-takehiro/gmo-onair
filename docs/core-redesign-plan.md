## 1. 診断 — なぜ「意味不明」で「ゴミが溜まる」のか（コードで確定した事実）

### 1-1. 「お待たせ中」は状態ではなく、4つの別ドメインの寄せ集め

- `GET /dashboard/inbox` が毎回4本の SQL を集めて作る**導出ビュー**であり、保存された状態は無い。
  中身は ①AI起票ネタ（stage=neta・未確認） ②期限超過の次回アクション ③未仕分けの問い合わせ
  ④未処理の見積・請求書類 — **性質も消し方も別々の4種**を「お待たせ中」という言葉だけで束ねている。
- 同じペイロードから3つの違う件数を導出（total / タイル用の2分割 / レール用の2種）。
  カード脚注「残りN件」は上限つき items から、バッジは上限なし counts から計算 → **同一カード内で食い違う**。
- カード上に完了・不要・スヌーズ等の**アクションが1つも無い**（純粋なナビゲーション）。
  期限超過は活動記録画面でしか消せず、AI起票ネタは「確認 or ステージ移動」しか出口が無い。
- `reply_due`（「相手を待たせている目安」のために作った唯一の列・migration 170）は**どこからも使われていない**。

### 1-2. 「案件自動整理」という機能は存在しない

「自動整理」と呼べる処理はリポジトリに無く、代わりに4つの断片が分散している:

1. `a_won`→`s_completed` の繰り上げ — **cron ではなく `GET /dashboard/check-completed` が生 UPDATE**。
   誰もダッシュボードを開かない日は動かず、`event_end` の無い受注案件は永久に `a_won`、履歴も残らない。
2. 受付（ネタ）から消える条件 = 「stage が neta から動いたか」**だけ**。不要判定は一切していない。
3. 人がステージを動かしたら AI 確認印（`ai_reviewed_at`）を自動付与。
4. `e_lost` にしたときだけ「不採用」を事後記録。

**不要判定ができない構造的理由**は「不要」を表すデータが無いこと。`e_lost` が
「競合に負けた失注」と「そもそも案件ではなかった見送り」を兼ね、ネタ画面で読み替えているだけ。
停滞（7日・3か所ハードコード）は並び順とバッジにしか効かず、何も片づけない。
アーカイブ概念も無く、古いネタの出口は「e_lost にする」か「物理削除」の二択。

### 1-3. タスクは1テーブルに6つの人格・期限列が2本

- `project_tasks` 1本に、案件タスク・個人タスク・依頼・GPM工程・投入口起票・チケットが同居。
  **期限列が `due_date`（DATE）と `due_at`（TIMESTAMP）の2本**あり、書き手8者・読み手6者が別々の列を使う。
  - 投入口・依頼・GPM・チケット由来のタスクはカンバンで「期限なし」・ガントに出ない・
    **期限前通知（tk_due）が絶対に飛ばない**（due_date しか見ないため）。
  - マイタスクで期限を直してもカンバンに反映されない（別の列に書くため）。
- 標準工程テンプレ（最大26タスク/案件）と議事録持ち帰りは**意図して担当者を設定しない**ため、
  マイタスク・チーム負荷・AI の全てから不可視。最大量の生成源が誰にもカウントされない。
- **依頼（delegation）は作成・承諾・辞退・再割当のどこにも通知が無い**。受け手がバッジを偶然見るだけ。
- `visibility='private'` の強制は1か所のみで、**全案件タスク一覧と GPM 一覧は private タスクの全文を
  sales 権限者全員に返す**。
- work_state（相手待ち）は案件タスク画面だけ、重要度×緊急度は個人タスク画面だけ。互いに読めない。

### 1-4. カレンダーとタスクが接続していない

Google/Outlook/ICS 同期・書き戻しまで完備しているのに、**タスク・期限はどのカレンダーにも出ない**
（統合カレンダーは予約・パートナー・個人予定の3層のみ。週間予定・.ics も同様）。
「何月何日何時何分まで」を軸にした設計なのに、期限を予定の隣で見る手段が無い。

### 1-5. AI連携は「起こしっぱなし」で閉ループに穴

- AI表面は13以上あるが、**AI起票ネタに「不要（作られるべきでなかった）」ボタンが無い**
  （却下が学習データに一度も入らない）。制作技術支援側は discard+14日自動失効で解決済みのパターンを
  営業側が持っていない。
- メール取込2種（inquiry/finance_doc）は**無修正時に「正解ラベル」を書かないバグ**で
  無修正採用率が構造的に常に 0。
- デイリーニュースの5段階評価はループ未接続、ナレッジ承認UIなし、営業側の月次AIレビュー未実装、
  **「AIが今日何をしたか」を見る画面が存在しない**（v4 で削除・代替なし）。

## 2. 設計原則 — 他社ツール13本の収斂点から採るもの

1. **「次の一手」を唯一の健全性シグナルにする**（Pipedrive/Close/Copper/Mazrica/kintone）。
   「次に誰が・いつ・何をするか」の日付1つが案件の生死を表す。期日が未来なら静か、
   過ぎたら浮上、無ければ危険。
2. **「待ち」はステータスではなく「未来日付＋期限切れ時の自動再浮上」**（スヌーズ。Close/Zendesk）。
   独立の待ち状態は (a)誰待ちか (b)いつまでか (c)抜ける条件 の3点で必ず破綻する — 現行の症状そのもの。
   無期限の待ちを作れなくする。
3. **停滞は視覚的腐敗で見せる。自動では消さない**（Pipedrive の赤・HubSpot のグレー）。
   しきい値はステージごとに変える（ネタは長め、口頭決定は短め）。
4. **自動整理は「二段階・可逆・生存宣言があれば触らない」**（Linear が完成形）。
   機械に判定できるのは「不要か」ではなく**「生きている証拠が無いか」だけ**。
   証拠が無ければ 警告 → 猶予 → 自動クローズ（理由付き・通知・1クリックで復活）。
   アーカイブはクローズ済みのみ。削除は永久に人間だけ。
5. **クローズを安くする**。失注理由は定義済みドロップダウン1クリック・可逆。
   「見送り（案件化せず）」を「失注」と別の理由に分ける — ゴミが溜まる根本は
   クローズが重い/失注扱いが心理的に不当なこと。
6. **ステージは「顧客側で起きた事実」で切り、内部の温度感（待ち・保留）は別軸に**（board の2軸分離）。
7. **「探す」のではなく「届く」**。期限が来たもの・スヌーズ明け・腐敗し始めたものだけが並ぶ
   個人 Inbox を日常の入口にする（Close）。数十件規模・数名のチームならこれで完結する。

採用しないと決めたもの: AI による次回アクション自動提案（規模に過剰・まず日付運用を定着させる）、
無差別な時間ベース自動アーカイブ（完了/失注済み以外への適用は誤爆する）、停滞の独立ステータス化
（保存すると必ず実態とずれる — 現行の轍）。

## 3. あるべき姿（全体の骨格）

### 3-1. 案件 — 状態は「ステージ（事実）× 次の一手（日付）」の2軸だけ

- **ステージ**は現行7値のまま（外部の事実で切れており数も適正）。「お待たせ中」的な状態は追加しない。
- **健全性は保存せず、表示のたびに1か所のロジックで導出する**:

| 表示 | 条件 | 意味 |
|---|---|---|
| スヌーズ中 | `snooze_until` が未来 | 意図して寝かせている。静かにする（停滞にも整理候補にも出さない） |
| 🔴 期限超過 | 次の一手（次回アクション/タスク）の期日が過去 | 最優先で浮上 |
| 🟠 停滞 | 次の一手が**無く**、最後の動きがステージ別しきい値超過 | 「放置◯日」を数字で見せる |
| ⚪ 健全 | 次の一手の期日が未来 | 静かにしておく |

- **生きている証拠（生存宣言）** = 未来のスヌーズ / 未来の次回アクション / 期日が未来の未完了タスク /
  未来の実施日。これが1つでもあれば自動整理は**絶対に触らない**。
- ステージ別しきい値（初期値）: ネタ 30日 / 仮押さえ 14日 / 見積提案 14日 / 口頭決定 7日 /
  受注済は対象外（制作の遅れはタスク側で管理）。定義は**サーバー1か所**。
- **スヌーズ** = `projects.snooze_until`（日付必須・無期限は作れない）。期日が来たら自動で失効し
  普通の判定に戻る（再浮上）。どのステージからでも掛けられる。

### 3-2. 自動整理 — 機械は候補出しとエスカレーション、決定は人の1クリック

三段構え（すべて可逆・すべて通知あり・削除は絶対にしない）:

1. **候補通知（60日）**: ネタのうち生存証拠が無く60日動いていないものを、日次ジョブが
   起票者へ「整理候補」として通知する。
2. **自動見送り（90日）**: さらに30日誰も触らなければ、ジョブが `e_lost`
   （理由 =「自動整理（長期放置）」）へ**履歴付きで**動かし、通知する。
   ステージ帯からいつでも戻せる。**自動クローズの対象はネタだけ**
   （仮押さえ以降は人が動かした案件なので機械は閉じない — 誤爆防止）。
3. **受注→完了の繰り上げ**: `event_end` を過ぎた受注案件は同じ日次ジョブが
   `changeStage` 経由（履歴付き）で `s_completed` にする。GET 依存をやめる。

**見送りと失注を分ける**: 失注理由マスタに「見送り（案件化せず）」「自動整理（長期放置）」を追加。
ネタを閉じるのは失注ではなく見送り（1クリック）。失注分析でノイズにならない。

### 3-3. 受信箱 — 「お待たせ中」の廃止

ホームのタブを「お待たせ中」から**「受信箱」**へ改める。中身の口（4種）は変えないが:

- **種類ごとの節に分けて出す**（AI起票ネタ / 期限超過 / 問い合わせ / 書類）。
  4種を混ぜた1本のリストにしない — 種類ごとに取るべき行動が違うため。
- **全行にその場のアクション**を置く: AI起票ネタは「案件にする」「不要」、
  期限超過は「済んだ」。開くだけの行を無くす。
- **件数の整合**: 脚注の「残りN件」は counts（実数）から計算する。
- **AI起票ネタの「不要」** = 1クリックで `e_lost`＋理由「見送り（案件化せず）」。
  既存の `recordIntakeDecision('dropped')` 経路に乗るため、**却下がそのまま AI の教師データになる**。

### 3-4. タスク — 期限は1本・状態は共通・依頼には通知

- **期限は `due_at` に一本化**。読み手は全員 `COALESCE(due_at, due_date + 18:00)`、
  書き手は全員 `due_at` を書く（`due_date` は互換のため残すが新規書き込みを止める）。
  これで「どの画面で作っても、どの画面でも同じ期限が見え、通知も飛ぶ」。
- **期限前通知（tk_due）**は COALESCE で判定し、リンク先を `/daily/tasks` にする
  （dailyops のみの担当者が 403 に飛ばされない）。
- **依頼に通知**: 作成（受け手へ）・承諾/辞退/相談（依頼主へ）・再割当（新しい受け手へ）。
- **private タスクの漏れを塞ぐ**: 全案件タスク一覧・GPM 一覧も担当者/作成者以外には出さない。
- **担当なしタスクの見える化**: 標準工程・議事録由来の「担当なし」を一覧で明示する
  （Phase 2 で割当 UI を強化）。

### 3-5. カレンダー連携 — 期限を予定の隣に

- 統合カレンダーに**「タスクの期限」レイヤー**（自分の未完了タスク）を追加。
- ダッシュボードの週間予定にも自分の期限タスクを併載。
- Phase 2: 個人カレンダー（Google/Outlook/ICS）への期限書き戻し。

### 3-6. AI連携 — 「AIが起こし、人が1クリックで裁き、裁きが学習に戻る」を全機能の標準形に

- AI が起こしたものには必ず**採用/修正/不要の3出口**を置く（受信箱の「不要」で営業側の穴を塞ぐ）。
- メール取込2種の**無修正時に正解ラベル（type:'none'）を書かないバグを修正**
  （無修正採用率が永久に0になっていた）。
- Phase 2 で: AI活動ページ（digest の人間向け画面）・営業側の月次AIレビュー・
  ナレッジ承認UI・デイリーニュース評価のループ接続・prompt_version の全 kind 展開。

### 3-7. 用語・定義の一本化

- ステージのラベルは `shared/src/constants/statuses.ts` を**唯一の正**とし、
  client の型・一覧バッジ・MCP がそこへ揃う（現状4系統に分裂）。
- 停滞しきい値・生存証拠・健全性の定義はサーバーの1モジュール（`project-health.ts`）だけが持つ。

## 6. 決めごと（wording）

- 「お待たせ中」という名称は**廃止**し「受信箱」とする（モックからの逸脱として
  `docs/v4-mock-deviations.md` に記録する）。
- 「見送り」= 案件にならなかった（失注ではない）。「失注」= 案件だったが取れなかった。
- 「スヌーズ」= 再開日付きで意図して寝かせること。無期限の保留・待ちは存在しない。
- 「整理候補」= 生存証拠が無いまま60日経ったネタ。「自動見送り」= 90日で機械が閉じたもの（可逆）。
