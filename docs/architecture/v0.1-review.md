## 2. 構造上の課題

### 2.1 ドメイン境界が未分離
- 全17テーブルが1つのスキーマファイルに同居
- サービス層が薄い（pagination、sequence、billing-keyの3つのみ）
- ルートハンドラ内にビジネスロジックが直接記述されている
- 例: opportunities.routes.ts 内でプロジェクト作成、エピソード作成、売上作成を一括実行

### 2.2 データモデルの設計課題
- `opportunity_simulations`（見積）と `revenues`（実績）が完全に分断
  - 予算vs実績の比較ができない
- エピソードに作業ステータスがない（日付のみで進捗管理）
- 機材・スタジオ資産の概念が不在
- 香盤表やマニュアルのデータモデルが不在

### 2.3 スケーラビリティの懸念
- sql.js（インメモリSQLite）は本番運用に非対応
- 全テーブル直接JOINのクエリパターン
- マイグレーションが単一ファイル（増分管理不可）

### 2.4 未実装の業務要件
- 営業活動のレビュー・評価
- スタジオ資産（機材）管理
- イベント運用マニュアルの雛形管理・案件別生成
- 香盤表（当日スケジュール）
- 外部システム連携（Qシート、テロップ）
- 権限管理（ロールはあるが実際の制御が不十分）
- 通知・アラート機能
- ファイル管理（ロゴ、資料、契約書等）

## 3. 良かった設計判断（v1.0に引き継ぐべき）

1. **モノレポ構成**（client/server/shared）— 型の共有が効率的
2. **shared パッケージ**のenum定義 — ラベル・色・確率をenumと一緒に管理
3. **ソフトデリート**パターン — データ保全に有効
4. **監査フィールド**（created_by, updated_by）— 追跡可能性
5. **シーケンス管理テーブル** — 番号体系の一元管理
6. **Feature-basedディレクトリ構成**（クライアント側）
