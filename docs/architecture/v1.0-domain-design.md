# GMO ONAiR v1.0 システム再設計 - ドメイン設計

> ゼロベースでの再設計方針。v0.1の良い部分は引き継ぎつつ、会社基盤システムとして再構築する。

## 1. 設計思想

**Modular Monolith + Domain-Driven Design**

- 4つの境界づけられたコンテキスト（Bounded Context）でドメインを分離
- 各コンテキストは独自のサービス層を持ち、他コンテキストとはサービス経由で連携
- DBは共有するが、テーブルアクセスはコンテキスト内に閉じる
- 将来的にコンテキスト単位でのマイクロサービス化も可能な設計

## 3. コンテキスト間の連携フロー

```
                    ┌──────────┐
                    │  営業     │
                    │  Sales   │
                    └────┬─────┘
                         │
              受注確定イベント
              (見積金額 → 予算として引き継ぎ)
                         │
                    ┌────▼─────┐         ┌──────────┐
                    │  制作     │────────→│  資産     │
                    │Production│ 機材予約  │  Asset   │
                    └────┬─────┘         └────┬─────┘
                         │                    │
              納品完了イベント            スタジオ空き情報
              (実績コスト確定)           (営業への提案用)
                         │                    │
                    ┌────▼─────┐              │
                    │  財務     │◄─────────────┘
                    │ Finance  │  減価償却費
                    └──────────┘
```

### 主要なドメインイベント

| イベント | 発行元 | 消費先 | 処理内容 |
|---------|--------|--------|---------|
| `opportunity.won` | Sales | Production, Finance | 案件作成、予算設定 |
| `opportunity.lost` | Sales | (ログのみ) | 失注理由記録 |
| `episode.status_changed` | Production | Finance | 売上計上トリガー |
| `episode.completed` | Production | Finance | 実績コスト確定 |
| `equipment.reserved` | Production | Asset | 機材割当 |
| `equipment.returned` | Production | Asset | 機材返却 |
| `invoice.sent` | Finance | (通知) | 請求書送付通知 |
| `invoice.paid` | Finance | Sales | 入金確認 → 営業実績反映 |
| `studio.availability_changed` | Asset | Sales | 提案可能日更新 |

## 4. 各コンテキスト詳細

### 4.1 営業コンテキスト (Sales)

**責務:** 受注活動の全ライフサイクルとその評価

**集約（Aggregate）:**

```
Opportunity（ヨミ）[集約ルート]
├── OpportunityDate（候補日程）
├── Simulation（見積シミュレーション）
│   └── SimulationItem（見積明細）
└── ActivityLog（営業活動記録）  ← NEW

Customer（顧客）[集約ルート]
└── ContactHistory（接触履歴）  ← NEW

SalesReview（営業評価）[集約ルート]  ← NEW
└── ReviewMetric（評価指標）
```

**v0.1からの変更点:**
- `ActivityLog` 追加: 営業活動（電話、訪問、メール等）の記録
- `ContactHistory` 追加: 顧客との接触履歴
- `SalesReview` 追加: 期間別の営業評価（受注率、平均単価、リードタイム等）
- ヨミの失注時に `lost_reason`（失注理由カテゴリ）を必須化
- ファネル分析用のビュー（各ステージのコンバージョン率、滞留日数）

### 4.2 制作コンテキスト (Production)

**責務:** 受注後の案件実行、制作進行、当日運用

**集約（Aggregate）:**

```
Project（案件）[集約ルート]
├── ProjectGroup（案件グループ）
├── Episode（話数/回）
│   ├── EpisodeStatus（制作ステータス）  ← NEW: Kanban
│   └── EpisodeCost（話数別コスト見込）
├── RunSheet（香盤表）  ← NEW
│   └── RunSheetItem（香盤表項目）
├── OperationManual（運用マニュアル）  ← NEW
│   └── ManualSection（セクション）
└── ExternalLink（外部連携）  ← NEW
    ├── QSheetLink（Qシート連携情報）
    └── TelopLink（テロップ連携情報）

ManualTemplate（マニュアル雛形）[集約ルート]  ← NEW
└── TemplateSection（雛形セクション）
```

**v0.1からの変更点:**
- エピソードにKanbanステータス追加:
  `準備中 → 収録準備完了 → 収録済 → 編集中 → 確認待ち → 納品済`
- `RunSheet`（香盤表）: タイムライン型の当日スケジュール管理
- `OperationManual`: 雛形ベースで案件ごとにカスタマイズ可能なマニュアル
- `ExternalLink`: Qシート・テロップシステムとの連携ポイント
- `ManualTemplate`: 運用マニュアルの雛形マスタ

### 4.3 財務コンテキスト (Finance)

**責務:** 売上・仕入・経費の計上と、予算対実績の管理

**集約（Aggregate）:**

```
Budget（予算）[集約ルート]  ← NEW
├── BudgetRevenue（売上予算明細）
└── BudgetCost（コスト予算明細）

Revenue（売上）[集約ルート]
└── RevenueItem（売上明細）

Purchase（仕入）[集約ルート]
├── PurchaseAllocation（按分）
└── PurchaseEpisodeAllocation（話数按分）

Invoice（請求）[集約ルート]
├── InvoiceItem（請求明細）
└── Payment（入金記録）  ← NEW

SgaExpense（販管費）[集約ルート]

ProfitLoss（損益計算）[読み取り専用集約]
├── MonthlyPL（月次PL）
└── ProjectPL（案件別PL）
```

**v0.1からの変更点:**
- `Budget` 追加: ヨミのシミュレーション金額を予算として取り込み
  - 予算vs実績の突合が可能に
- `Payment` 追加: 入金管理（請求→入金の追跡）
- `ProfitLoss`: 月次/案件別PLの計算ロジックを専用集約として整理
- 予実差異分析のビュー追加

### 4.4 資産管理コンテキスト (Asset)

**責務:** スタジオ・機材の管理と案件への割当

**集約（Aggregate）:**

```
Studio（スタジオ）[集約ルート]  ← NEW
├── StudioSchedule（予約スケジュール）
└── StudioSpec（スタジオ仕様）

Equipment（機材）[集約ルート]  ← NEW
├── EquipmentHistory（履歴: 購入/修理/廃棄）
├── EquipmentReservation（案件への割当予約）
└── MaintenanceSchedule（メンテナンス予定）

EquipmentCategory（機材カテゴリ）[集約ルート]  ← NEW
```

**主要機能:**
- 機材台帳: 型番、購入日、購入金額、耐用年数、状態管理
- スタジオ予約: カレンダーベースの空き管理
- 案件への機材割当: 制作コンテキストからの予約要求に応答
- メンテナンス管理: 定期点検スケジュール
- 減価償却計算: 財務コンテキストへの費用連携

### 4.5 共通基盤 (Platform)

**責務:** 全コンテキスト共通の横断的関心事

```
Auth（認証・認可）
├── User（ユーザー）
├── Role（ロール）
└── Permission（権限）

Notification（通知）  ← NEW
├── NotificationTemplate（通知テンプレート）
└── NotificationLog（通知履歴）

FileStorage（ファイル管理）  ← NEW
├── FileMetadata（ファイル情報）
└── FileVersion（バージョン管理）

AuditLog（監査ログ）  ← NEW
└── AuditEntry（操作履歴エントリ）
```

## 5. v0.1 からの引き継ぎ判定

| v0.1 の要素 | 判定 | 理由 |
|------------|------|------|
| モノレポ構成 (client/server/shared) | **引き継ぐ** | 型共有が効率的 |
| shared の enum 定義方式 | **引き継ぐ** | ラベル・色・確率の一元管理が良い |
| ソフトデリート | **引き継ぐ** | データ保全に必須 |
| 監査フィールド (created_by等) | **引き継ぐ** | ただしAuditLogに集約 |
| シーケンス管理テーブル | **引き継ぐ** | 番号体系の一元管理 |
| Feature-basedディレクトリ | **引き継ぐ** | コンテキスト単位に再編成 |
| sql.js (インメモリSQLite) | **変更検討** | 開発用は維持、本番はPostgreSQL等 |
| 単一マイグレーションファイル | **変更** | 増分マイグレーションに移行 |
| ルート内ビジネスロジック | **変更** | サービス層に移動 |
| モック認証 | **変更** | JWT or セッション認証に移行 |
| React + Vite + TailwindCSS | **引き継ぐ** | フロント技術スタックは良い |
| Zustand + React Query | **引き継ぐ** | 状態管理パターンは適切 |
